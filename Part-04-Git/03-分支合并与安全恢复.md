# 03 分支、合并与安全恢复

Git 的恢复能力很强，但前提是先判断问题发生在哪一层：工作区、暂存区、正在进行的合并、本地尚未共享的提交，还是已经共享的远程历史。不同层次需要不同工具；把所有问题都交给强制重置，往往会把原本可精确修复的小问题变成真正的数据丢失。

继续使用练习仓库，并先确认现场：

```bash
cd ~/terminal-practice/git-workflow-demo
git status
git branch --show-current
git log --oneline --decorate --graph --all -10
```

预期当前分支为 `feature/subtraction`，已有减法功能和 `.gitignore` 提交，工作区干净。状态不同时先查清已有变化，不要带着来源不明的修改进入合并和恢复练习。

## 1. 用分支和一次可控冲突理解合并

查看分支并切回主分支：

```bash
git branch
git switch main
git log --oneline --decorate --graph --all -10
```

`main` 仍停在原来的基础提交，`feature/subtraction` 指向更后的提交。分支只是指向提交的可移动名称，不会复制整个仓库。将功能分支合入主分支：

```bash
git merge feature/subtraction
git log --oneline --decorate --graph --all -10
```

若 `main` 没有独立提交，Git 可能 fast-forward，直接把主分支指针向前移动。确认功能已经进入主分支后，可使用小写 `-d` 删除已合并分支：

```bash
git branch -d feature/subtraction
```

接着制造一次可控冲突。先在主分支修改并提交 `calculator.py`：

```bash
cat > calculator.py <<'PY'
def add(left, right):
    """Return the sum of two numbers."""
    return left + right


def subtract(left, right):
    return left - right
PY

git add calculator.py
git commit -m "docs: document add operation"
```

从父提交建立另一分支并修改同一位置：

```bash
git switch -c feature/type-hints HEAD~1

cat > calculator.py <<'PY'
def add(left: int, right: int) -> int:
    return left + right


def subtract(left, right):
    return left - right
PY

git add calculator.py
git commit -m "refactor: add type hints to add operation"
```

切回主分支合并：

```bash
git switch main
git merge feature/type-hints
git status
```

冲突文件会出现 `<<<<<<<`、`=======` 和 `>>>>>>>` 标记。它们不是要保留的代码，而是 Git 展示两条历史给出的不同答案。若希望同时保留类型标注和文档字符串，将文件整理为最终语义：

```bash
cat > calculator.py <<'PY'
def add(left: int, right: int) -> int:
    """Return the sum of two numbers."""
    return left + right


def subtract(left, right):
    return left - right
PY

rg -n '<<<<<<<|=======|>>>>>>>' .
python3 -m unittest -v
git add calculator.py
git commit -m "merge: combine documentation and type hints"
```

若冲突范围过大、合并方向错误或需要先讨论，应在确认当前处于 merge 状态后使用：

```bash
git merge --abort
```

它表达的是“取消当前合并”，比用强制重置处理普通冲突更精确。当前练习已经完成合并，不需要再执行 abort。

## 2. 工作区和暂存区要分别恢复

先制造并暂存一处本地实验：

```bash
printf '%s\n' '' '# Local experiment' >> calculator.py
git add calculator.py
git status
git diff --cached -- calculator.py
```

若只是不想让它进入下一次提交，但希望保留文件内容：

```bash
git restore --staged calculator.py
git status
git diff -- calculator.py
```

修改仍在工作区，只是退出暂存区。若确认这段未暂存修改完全不要，先读 diff，再恢复文件：

```bash
git diff -- calculator.py
git restore calculator.py
```

`git restore calculator.py` 会丢弃该文件当前未暂存内容，因此不能在没看差异时随手执行。一个文件同时含有重要修改和错误修改时，应手工编辑或使用交互恢复：

```bash
git restore -p calculator.py
```

这两类操作必须分清：`restore --staged` 改变暂存区但保留工作区，普通 `restore` 会覆盖工作区内容。

## 3. 提交级撤销取决于是否已经共享

已经推送并被别人基于其开发的提交，不应直接从历史中删除。先查看目标提交，再创建反向提交：

```bash
git log --oneline -5
git show COMMIT_SHA
git revert COMMIT_SHA
```

`revert` 保留错误提交，并新增一个抵消它的提交，审查者可以看到发生了什么以及如何撤销。撤销合并提交需要指定主线父提交，不能照搬普通示例；共享分支上的复杂合并撤销应先由维护者确认方案。

若最后一次提交尚未推送，只是提交信息写错或漏了一个紧密相关的小文件，可以修正并暂存后执行：

```bash
git commit --amend
```

amend 会产生新的提交哈希。提交已经共享后再 amend，通常意味着还要改写远程历史，因此不能把它当作普通编辑按钮。很多情况下新增一个小修复提交更容易审查，是否整理历史应服从团队规则和分支共享状态。

## 4. 未跟踪文件与引用救援是另一类问题

普通 restore 无法保护未跟踪文件。`git clean` 会处理这类文件，因此只应先预览：

```bash
git status --short
git clean -n
```

未跟踪内容可能是尚未提交的源码、数据、实验结果、认证配置或个人笔记。Agent 不应自动执行实际 clean，本书也不把它作为日常清理模板；需要处理时优先逐个确认，或把重要内容移到项目外备份目录。

如果误切换、误 reset 或分支指针移动，`git reflog` 可以记录本地 HEAD 和分支近期如何变化：

```bash
git reflog --date=local -20
```

找到原提交后，先创建救援分支：

```bash
git branch rescue/accidental-move COMMIT_SHA
git show rescue/accidental-move
```

给提交重新建立有名字的引用后，再慢慢调查。Reflog 通常只存在本地且会过期，也无法恢复从未进入 Git 的文件，因此发现问题后应尽快建立救援引用。

## 5. 强制重置和强制推送不是默认恢复手段

强制重置可能同时移动分支、改变暂存区并覆盖工作区；强制推送会改写远程分支历史。它们在特定维护场景中有用途，但影响范围远大于 restore、revert 和 merge abort。多人共享分支上，即使使用带 lease 的形式，也仍属于历史重写。

需要考虑高风险历史操作时，先保存现场：

```bash
git status
git log --oneline --decorate --graph --all -20
git reflog --date=local -20
git remote -v
```

然后确认分支是否共享、远程当前指向哪里、哪些提交会失去引用、是否已有备份分支，以及团队是否允许。不要让 AI CLI 根据一句“恢复到之前状态”自行选择 reset、clean 或 force push。

## 6. 按问题所在层次选择工具

```text
只是暂存错了，修改要保留
→ git restore --staged 文件

未暂存修改明确不要
→ 先 git diff，再 git restore 文件

合并进行中但不想继续
→ git merge --abort

共享提交需要撤销
→ git revert 提交

最后一次本地提交尚未共享且需要修正
→ 谨慎评估 git commit --amend

分支或 HEAD 指针误移动
→ git reflog，再建立 rescue 分支

未跟踪文件准备清理
→ 只先 git clean -n，逐项确认
```

恢复的首要原则不是“找最强命令”，而是先保存现场、识别层次，再选择影响范围最小且可解释的操作。
