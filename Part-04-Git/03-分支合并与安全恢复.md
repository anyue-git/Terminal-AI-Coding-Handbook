# 03 分支、合并与安全恢复

Git 的恢复能力很强，但前提是先判断问题发生在哪一层：工作区、暂存区、尚未共享的本地提交，还是已经共享的远程历史。不同层次需要不同处理方式。把所有问题都交给 `reset --hard`，通常会让一个可以精确修复的小问题变成真正的数据丢失。

继续使用练习仓库：

```bash
cd ~/terminal-practice/git-workflow-demo
git status
git branch --show-current
git log --oneline --decorate --graph -10
```

预期当前分支是 `feature/subtraction`，并且已经有减法功能与 `.gitignore` 两个提交。工作区应当干净；如果不是，先判断现有修改属于什么任务，再继续分支练习。

## 1. 分支用于隔离任务

查看本地分支：

```bash
git branch
```

星号表示当前分支。切回主分支：

```bash
git switch main
```

查看文件和历史：

```bash
git log --oneline --decorate --graph --all -10
```

你会看到 `main` 仍停在第一次提交，而 `feature/subtraction` 已经向前多了提交。分支只是指向提交的可移动名字，不会为每个任务复制整个仓库。

将功能分支合并进当前主分支：

```bash
git merge feature/subtraction
```

如果 `main` 没有独立提交，Git 可能进行 fast-forward，也就是直接把 `main` 指针向前移动。再次查看历史：

```bash
git log --oneline --decorate --graph --all -10
```

确认功能已进入主分支后，可以安全删除本地已合并分支：

```bash
git branch -d feature/subtraction
```

小写 `-d` 会拒绝删除尚未合并的分支，比强制删除更适合作为默认选择。

## 2. 制造一次可控冲突

先在主分支修改同一行并提交：

```bash
cat > calculator.py <<'PY'
def add(left, right):
    """Return the sum of two numbers."""
    return left + right


def subtract(left, right):
    return left - right
PY

git add calculator.py
git commit -m "docs: document add operation"
```

从上一个提交创建另一条分支，让它修改相同位置。先找主分支的父提交：

```bash
git log --oneline -2
```

建立分支并回到父提交内容：

```bash
git switch -c feature/type-hints HEAD~1
```

在这条分支中修改 `add` 的定义：

```bash
cat > calculator.py <<'PY'
def add(left: int, right: int) -> int:
    return left + right


def subtract(left, right):
    return left - right
PY

git add calculator.py
git commit -m "refactor: add type hints to add operation"
```

现在两条分支都修改了 `calculator.py` 的开头。切回主分支并尝试合并：

```bash
git switch main
git merge feature/type-hints
```

Git 很可能报告冲突。运行：

```bash
git status
```

文件中会出现类似标记：

```text
<<<<<<< HEAD
def add(left, right):
    """Return the sum of two numbers."""
=======
def add(left: int, right: int) -> int:
>>>>>>> feature/type-hints
```

这些标记只是 Git 展示两边内容，不能直接保留在最终代码中。

## 3. 解决冲突需要人工决定最终版本

这次希望同时保留文档字符串和类型提示，可以把文件改为：

```python
def add(left: int, right: int) -> int:
    """Return the sum of two numbers."""
    return left + right


def subtract(left, right):
    return left - right
```

使用命令写入最终内容：

```bash
cat > calculator.py <<'PY'
def add(left: int, right: int) -> int:
    """Return the sum of two numbers."""
    return left + right


def subtract(left, right):
    return left - right
PY
```

确认没有残留冲突标记：

```bash
rg -n '<<<<<<<|=======|>>>>>>>' .
```

运行测试：

```bash
python3 -m unittest -v
```

暂存并完成合并提交：

```bash
git add calculator.py
git commit
```

编辑器会打开默认合并信息；也可以使用 `git commit -m "merge: combine documentation and type hints"`。完成后查看历史：

```bash
git log --oneline --decorate --graph --all -10
```

冲突不是 Git 随机失败，而是两条历史对同一位置给出了不同答案，需要人决定最终语义。

## 4. 不想继续合并时使用 `git merge --abort`

若冲突范围过大、合并方向错误或需要先讨论，可以取消当前合并：

```bash
git merge --abort
```

它会尝试恢复到开始合并前的状态。取消前先运行 `git status`，确认当前确实处于 merge 状态。

不要为了解决普通冲突直接使用会丢弃工作区内容的强制重置。`git merge --abort` 表达的意图更准确，影响范围也更清楚。

当前练习已经完成合并，无需再执行 abort。

## 5. 暂存错了，但保留工作区修改

制造一处修改：

```bash
printf '%s\n' '' '# Local experiment' >> calculator.py
git add calculator.py
```

查看：

```bash
git status
git diff --cached -- calculator.py
```

如果不想让它进入下一次提交，但还想保留文件内容：

```bash
git restore --staged calculator.py
```

再次检查：

```bash
git status
git diff -- calculator.py
```

修改仍在工作区，只是离开暂存区。这是“暂存错误”的恢复方式。

## 6. 明确不要某个未暂存修改

先查看准备丢弃的内容：

```bash
git diff -- calculator.py
```

确认只是刚才追加的实验行后，执行：

```bash
git restore calculator.py
```

这会让工作区文件恢复到暂存区或最近提交的版本。未暂存修改会丢失，因此必须先看 diff。

如果文件中同时有重要修改和错误修改，不应整文件 restore。可以手工编辑，或使用交互式恢复：

```bash
git restore -p calculator.py
```

## 7. 已共享提交应优先使用 `git revert`

假设某个提交已经推送并被其他人基于它继续开发，直接删除历史会影响协作者。此时可以创建一个反向提交：

```bash
git log --oneline -5
git show COMMIT_SHA
git revert COMMIT_SHA
```

`revert` 不会删除旧提交，而是新增一个提交抵消它的变化。审查者可以看到错误发生过，也能看到之后如何撤销。

撤销合并提交需要额外指定主线父提交，不能照搬普通 `git revert` 示例。遇到共享分支上的复杂合并撤销，应先阅读项目规则并让维护者确认方案。

## 8. 尚未共享的最后一次提交可以 amend

如果最后一次提交还没有推送，只是提交信息写错或漏了一个紧密相关的小文件，可以先修正并暂存，再执行：

```bash
git commit --amend
```

amend 会创建新的提交哈希。已经共享后再 amend，就需要改写远程历史，因此不应把它当成普通编辑按钮。

很多情况下，创建一个新的小提交比反复 amend 更容易审查。是否整理历史，应服从团队规则和分支是否共享。

## 9. `git clean` 只应先预览

Git 不跟踪的文件不受普通 restore 保护。查看未跟踪文件：

```bash
git status --short
```

预览 clean 会处理什么：

```bash
git clean -n
```

预览不会删除。未跟踪文件可能是尚未提交的源码、数据、实验结果、认证配置或本地笔记。Agent 不应自动执行实际 clean 操作，本书也不把清理命令作为日常模板。

需要清理时，优先逐个确认文件，或把重要内容先移动到项目外备份目录。

## 10. Reflog 能帮助找回被移动的引用

`git reflog` 记录本地 HEAD 和分支引用近期如何移动：

```bash
git reflog --date=local -20
```

如果误切换、误 reset 或分支指针移动，可以先找到原提交哈希，再创建救援分支：

```bash
git branch rescue/accidental-move COMMIT_SHA
git show rescue/accidental-move
```

先建救援分支的好处，是把可能丢失的提交重新变成有名字的引用，再慢慢调查。

Reflog 不是永久备份，通常只存在本地，也无法恢复从未进入 Git 的文件。发现问题后应尽快建立救援引用，不要继续执行更多历史改写命令。

## 11. 强制重置与强制推送为什么危险

强制重置可能同时改变分支指针、暂存区和工作区；强制推送则会改写远程分支历史。它们在某些维护场景确实有用途，但影响范围远大于普通 restore、revert 和 merge abort。

多人共享分支上，不应随意使用强制推送。即使使用带 lease 的保护形式，也仍然属于历史重写。执行前必须确认：分支是否共享、远程当前指向哪里、哪些提交会失去引用、是否有备份分支，以及团队是否允许。

本书不把这些命令作为新手恢复流程。遇到需要它们的场景，应先停下来保存 `git status`、`git log --graph --all` 和 `git reflog` 输出，再设计恢复方案。

## 12. 按问题所在层次选择恢复方式

可以用下面的顺序判断：

```text
只是暂存错了，修改要保留
→ git restore --staged 文件

未暂存修改明确不要
→ 先 git diff，再 git restore 文件

合并进行中但不想继续
→ git merge --abort

共享提交需要撤销
→ git revert 提交

本地引用误移动
→ git reflog，先创建 rescue 分支

准备清理未跟踪文件
→ 只先使用 git clean -n 预览
```

每一种方式都对应明确层次。没有先判断问题位置，就不要执行恢复命令。

## 13. AI CLI 的分支与恢复边界

可以明确要求：

```text
只在当前任务分支修改，不要切换分支。
不要执行 merge、rebase、reset、clean、commit、push 或强制推送。
需要恢复文件时，先展示 diff，说明将丢失哪些内容并等待确认。
遇到冲突只分析双方差异，不要擅自选择业务语义。
```

AI 可以帮助解释冲突和列出恢复选项，但最终选择通常需要理解需求、分支共享状态和团队历史规则的人来决定。
