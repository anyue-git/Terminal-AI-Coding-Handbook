# 02 日常提交与复核流程

上一章的练习仓库已经存在一个基础提交，并切换到 `feature/subtraction` 分支。工作区中新增了减法函数，还有一份不准备提交的个人笔记。本章从这个状态继续，完整走一遍“修改、测试、检查、暂存、提交、复核”的日常流程。

先进入仓库：

```bash
cd ~/terminal-practice/git-workflow-demo
pwd
git status
git branch --show-current
```

预期当前分支是：

```text
feature/subtraction
```

工作区中应至少有 `calculator.py` 的修改和未跟踪的 `notes.txt`。如果状态不同，不要机械继续，先确认是否已经在前一章做过额外提交或切换了分支。

## 1. 开始任务前先确认四件事

真实项目中，进入目录后先运行：

```bash
pwd
git status
git branch --show-current
git remote -v
```

这四条命令分别确认：当前路径、工作区状态、当前分支和远程仓库。很多误操作不是因为 Git 命令本身错误，而是因为用户站在另一个仓库、另一个分支，或者远程指向了另一个项目。

如果 `git status` 已经显示来源不明的修改，不要让 AI Agent 顺手“整理”。先判断这些变化属于当前任务、上一个任务还是其他人的工作。必要时先建立新的 worktree 或与协作者确认。

## 2. 先把需求落实为代码和测试

当前 `calculator.py` 已有减法函数，但测试还没有覆盖。追加测试：

```bash
python3 - <<'PY'
from pathlib import Path

path = Path("test_calculator.py")
text = path.read_text()
text = text.replace(
    "from calculator import add",
    "from calculator import add, subtract",
)
text = text.replace(
    "    def test_add(self):\n        self.assertEqual(add(2, 3), 5)\n",
    "    def test_add(self):\n"
    "        self.assertEqual(add(2, 3), 5)\n\n"
    "    def test_subtract(self):\n"
    "        self.assertEqual(subtract(7, 2), 5)\n",
)
path.write_text(text)
PY
```

查看修改：

```bash
git status --short
git diff -- calculator.py test_calculator.py
```

接着运行测试：

```bash
python3 -m unittest -v
```

预期看到两个测试通过。真实项目中，应运行与任务直接相关的测试，并记录未运行部分和环境限制。Mac 上无法执行 CUDA 测试时，只能写“未验证 GPU 路径”，不能把普通单元测试通过描述成全部功能已经验证。

## 3. 用不同粒度查看工作区

首先看文件状态：

```bash
git status --short
```

常见状态包括：

```text
 M calculator.py
 M test_calculator.py
?? notes.txt
```

再看文件类型变化：

```bash
git diff --name-status
```

然后看规模：

```bash
git diff --stat
```

最后看具体内容：

```bash
git diff
```

这四步分别回答：哪些文件变了、是新增修改还是删除、改动有多大、具体改了什么。不要只看 `--stat`，因为几行差异也可能包含密钥、错误逻辑或被削弱的测试。

审查时重点检查：是否修改范围正确，是否出现意外删除，是否改动依赖和锁文件，是否产生日志或缓存，是否有大范围无关格式化，是否加入真实路径、Token 或内部地址。

## 4. 精确暂存本次需要的文件

这次只提交功能与测试，不提交 `notes.txt`：

```bash
git add calculator.py test_calculator.py
```

检查状态：

```bash
git status
```

`calculator.py` 和 `test_calculator.py` 应位于已暂存区域，`notes.txt` 仍是未跟踪文件。

查看下一次提交会包含什么：

```bash
git diff --cached --name-status
git diff --cached
```

这个检查不能省略。工作区 diff 与 cached diff 不是同一件事：前者显示尚未暂存的变化，后者显示即将进入提交的内容。

如果误把 `notes.txt` 暂存，可以执行：

```bash
git restore --staged notes.txt
```

文件仍保留在磁盘，只是退出暂存区。

## 5. 一个文件混有两类修改时使用 `git add -p`

有时同一个文件同时包含任务修改和临时调试。可以交互式选择差异块：

```bash
git add -p calculator.py
```

常见选项：

```text
y    暂存当前差异块
n    跳过当前差异块
s    尝试拆分为更小块
q    退出
?    查看帮助
```

`git add -p` 适合已经理解 diff 的读者。不要为了制造“漂亮提交”而把互相依赖的代码和测试拆开，也不要在看不懂差异时一路按 `y`。

当前练习已经精确暂存，无需重复执行交互暂存。

## 6. 创建一个目的清楚的提交

提交前再运行测试并检查暂存区：

```bash
python3 -m unittest -v
git diff --cached --check
git diff --cached
```

`git diff --cached --check` 可以发现部分空白问题，但不能判断业务逻辑是否正确。

创建提交：

```bash
git commit -m "feat: add subtraction operation"
```

提交信息应说明这次改变的目的。团队可能采用 Conventional Commits，也可能有自己的规范。常见前缀包括 `feat`、`fix`、`docs`、`test`、`refactor` 和 `chore`，但清楚比机械套前缀更重要。

避免只写：

```text
update
changes
final
AI changes
```

这些信息无法帮助未来的读者理解提交意图。

## 7. 提交后必须再检查一次

运行：

```bash
git status
git log -1 --stat
git show --stat HEAD
```

`git status` 应显示工作区仍有 `notes.txt`，但功能修改已经提交。查看完整提交内容：

```bash
git show HEAD
```

如果发现提交遗漏测试、包含无关文件或改错内容，应先判断提交是否已经共享到远程。尚未共享时可以补充提交，必要时再谨慎评估 amend；已经共享时通常更适合创建新的修复提交，而不是随意改写历史。

## 8. `.gitignore` 管理不应进入仓库的文件

个人笔记不准备提交，可以创建 `.gitignore`：

```bash
printf '%s\n' 'notes.txt' > .gitignore
```

查看状态：

```bash
git status --short
```

此时 `notes.txt` 不再显示，但 `.gitignore` 是一个新的项目文件。它应该进入仓库，让团队共享忽略规则：

```bash
git add .gitignore
git diff --cached
git commit -m "chore: ignore local notes"
```

常见忽略内容包括：

```gitignore
.env
.venv/
__pycache__/
node_modules/
*.log
```

`.gitignore` 只影响尚未跟踪的文件。已经提交过的文件，后来加入忽略规则不会自动从历史消失。敏感凭据一旦进入提交或远程仓库，应立即撤销和轮换，不能把 `.gitignore` 当成安全保险箱。

## 9. 推送前检查分支、提交和远程

本地练习仓库还没有远程，所以不要执行 push。真实项目推送前运行：

```bash
git status
git branch --show-current
git log --oneline --decorate -5
git remote -v
```

首次推送新分支通常使用：

```bash
git push -u origin feature/subtraction
```

之后可使用 `git push`。推送会把本地提交共享给远程，可能触发 CI、通知协作者或暴露提交中的敏感信息，因此不是无需检查的保存按钮。

`git pull` 也不是纯查看操作。它通常会 fetch 后再 merge 或 rebase，可能改变当前分支。只想观察远程更新时，可以先用 `git fetch`，再比较远程分支。

## 10. AI CLI 的安全提交流程

Agent 适合修改代码、运行测试和整理差异，但默认不应替用户执行所有 Git 写操作。可以明确要求：

```text
请修改并运行测试，但不要执行 git add、commit、push、reset、clean、merge 或 rebase。
完成后列出所有变更文件、每个文件的目的、实际运行的测试、失败项和未验证内容。
```

人工随后执行：

```bash
git status --short
git diff --stat
git diff
git add 明确文件
git diff --cached
git commit -m "明确说明"
```

成熟团队可以让自动化创建提交或 PR，但 cached diff、测试证据和权限边界仍然需要明确的质量关口。

## 11. 本章形成的日常流程

一套可重复使用的顺序是：

```text
确认目录、分支和现有修改
→ 完成一个小任务
→ 运行相关测试
→ 查看状态、规模和完整 diff
→ 精确暂存
→ 查看 cached diff
→ 创建提交
→ 提交后重新检查
→ 确认远程后再推送
```

对应命令可以写成：

```bash
cd PROJECT_PATH
pwd
git status
git branch --show-current

# 修改并测试

git status --short
git diff --stat
git diff

git add PATH_1 PATH_2
git diff --cached

git commit -m "type: concise description"
git status
git log -1 --stat
```

这是一套检查顺序，不是应整块复制执行的脚本。
