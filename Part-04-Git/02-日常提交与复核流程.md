# 02 日常提交与复核流程

上一章的练习仓库已经存在基础提交，并在 `feature/subtraction` 分支中加入了减法函数；工作区里还有一份不准备提交的 `notes.txt`。本章沿用这个现场，完成一次从修改、测试和差异审查，到精确暂存、提交、提交后复核与推送判断的完整流程。核心不是记住更多 Git 子命令，而是把“工作区里发生了什么”和“下一次提交究竟会包含什么”分开验证。

## 1. 建立现场并完成一个可验证任务

进入练习仓库后先确认路径、分支和现有修改。真实项目还应查看远程地址，因为很多误操作并非命令语法错误，而是站在另一个仓库、另一个分支，或准备把提交推到错误的远程。

```bash
cd ~/terminal-practice/git-workflow-demo
pwd
git status
git branch --show-current
git remote -v
```

当前分支应为 `feature/subtraction`，状态中至少应出现 `calculator.py` 的修改和未跟踪的 `notes.txt`。若现场不同，先弄清哪些改动属于前一章、当前任务或其他人的工作，不要让 Agent 顺手整理来源不明的变化。

为减法函数补充测试：

```bash
python3 - <<'PY'
from pathlib import Path

path = Path("test_calculator.py")
text = path.read_text()
text = text.replace(
    "from calculator import add",
    "from calculator import add, subtract",
)
text = text.replace(
    "    def test_add(self):\n        self.assertEqual(add(2, 3), 5)\n",
    "    def test_add(self):\n"
    "        self.assertEqual(add(2, 3), 5)\n\n"
    "    def test_subtract(self):\n"
    "        self.assertEqual(subtract(7, 2), 5)\n",
)
path.write_text(text)
PY

python3 -m unittest -v
```

预期两个测试通过。真实项目应运行与任务直接相关的测试，并记录没有运行的部分和环境限制；Mac 上没有 CUDA 时，只能说明 GPU 路径尚未验证，不能把普通单元测试通过写成“全部功能已验证”。

## 2. 从文件清单逐步读到完整差异

不要一开始就在很长的 diff 中寻找方向，也不要只看一行统计便接受修改。下面四个视角依次回答“哪些文件变了、变化类型是什么、改动规模多大、具体改了什么”：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

练习中应看到两个已跟踪文件发生修改，以及 `notes.txt` 仍未跟踪。审查时重点看是否超出任务范围、是否意外删除文件、是否改动依赖或锁文件、是否产生缓存和日志、是否出现大范围无关格式化，以及 diff 中有没有真实路径、Token、内部地址或被削弱的测试。`--stat` 只能说明规模，几行变化同样可能包含关键逻辑或凭证。

需要只看目标文件时，可以缩小范围：

```bash
git diff -- calculator.py test_calculator.py
```

## 3. 暂存区是下一次提交的草稿

这次只提交功能和测试，不提交个人笔记，因此显式写出文件名：

```bash
git add calculator.py test_calculator.py
git status
git diff --cached --name-status
git diff --cached
```

工作区 diff 与 cached diff 不是同一份内容：`git diff` 显示尚未暂存的已跟踪变化，`git diff --cached` 显示下一次提交准备包含的内容。提交前必须阅读后者，而不是假设刚才的 `git add` 正好选中了预期文件。

误暂存某个文件但希望保留磁盘内容时，使用：

```bash
git restore --staged notes.txt
```

如果同一个文件混有任务修改和临时调试，可以交互式选择差异块：

```bash
git add -p calculator.py
```

常用选项是 `y` 暂存当前块、`n` 跳过、`s` 尝试拆分、`q` 退出、`?` 查看帮助。交互暂存适合已经理解 diff 的场景；不要为了制造“漂亮提交”把互相依赖的代码和测试拆散，也不要在看不懂变化时一路按 `y`。当前练习已按文件精确暂存，不需要重复执行 `git add -p`。

## 4. 提交前后都要验证

提交前再次运行测试，同时检查尚未暂存和已经暂存的差异中是否存在尾随空格、错误缩进或残留冲突标记，再阅读真正准备提交的内容：

```bash
python3 -m unittest -v
git diff --check
git diff --cached --check
git diff --cached
```

两个 `--check` 分别检查工作区与暂存区，但只能发现部分文本格式问题，不能判断业务逻辑是否正确。确认后创建目的清楚的提交：

```bash
git commit -m "feat: add subtraction operation"
```

团队可能采用 Conventional Commits，也可能有自己的格式；清楚说明改变目的比机械套前缀更重要。`update`、`changes`、`final` 或 `AI changes` 无法帮助未来读者理解提交。

提交完成并不代表检查结束：

```bash
git status
git log -1 --stat
git show HEAD
```

此时功能和测试应已进入提交，`notes.txt` 仍留在工作区。若发现遗漏或混入无关内容，先判断提交是否已经共享。尚未共享时可以补充新提交，必要时再谨慎评估 amend；已经推送并被协作者使用时，通常更适合新增修复提交，而不是随意改写历史。

## 5. 忽略本地文件，并在共享前核对远程

个人笔记不应反复出现在状态中，可以为项目建立共享忽略规则，并显式查看规则是否真的命中：

```bash
printf '%s\n' 'notes.txt' > .gitignore
git status --short
git status --ignored --short
git add .gitignore
git diff --cached
git commit -m "chore: ignore local notes"
```

普通 `git status --short` 中 `notes.txt` 应消失；带 `--ignored` 时可能看到 `!! notes.txt`，这说明当前规则已匹配该文件。常见忽略项包括 `.env`、`.venv/`、`__pycache__/`、`node_modules/` 和 `*.log`，但规则必须符合项目实际。`.gitignore` 只影响尚未跟踪的文件；已经进入提交或远程历史的凭据不会因为后来加入忽略规则而消失，必须立即撤销和轮换。

本地练习仓库没有远程，因此不要执行 push。真实项目共享前应确认状态、当前分支、最近提交和远程：

```bash
git status
git branch --show-current
git log --oneline --decorate -5
git remote -v
```

首次推送新分支通常使用：

```bash
git push -u origin feature/subtraction
```

之后可直接 `git push`。推送可能触发 CI、通知协作者并公开提交中的敏感信息，它不是无条件安全的保存按钮。`git pull` 也不是纯查看操作，通常会在 fetch 后 merge 或 rebase；只想观察远程变化时，先 `git fetch` 再比较分支。

## 6. Agent 可以实施，但提交边界由人控制

让 AI CLI 修改代码时，可以明确要求它运行测试和整理证据，但不执行历史或共享操作：

```text
请修改并运行测试，但不要执行 git add、commit、push、reset、clean、merge 或 rebase。
完成后列出所有变更文件、每个文件的目的、实际运行的测试、失败项和未验证内容。
```

人工随后阅读真实状态和差异，再选择文件进入暂存区：

```bash
git status --short
git diff --stat
git diff
git add PATH_1 PATH_2
git diff --cached
git commit -m "明确说明"
```

成熟团队可以让自动化创建提交或 PR，但测试证据、cached diff、权限范围和合并关口仍需明确，不能用 Agent 的总结替代仓库中的实际记录。

## 7. 一套可以重复使用的日常顺序

```text
确认目录、分支、远程和现有修改
→ 完成一个范围清楚的小任务
→ 运行相关测试并记录限制
→ 从文件清单读到完整工作区 diff
→ 精确暂存
→ 阅读 cached diff
→ 创建提交
→ 检查提交与剩余工作区
→ 确认远程和分支后再推送
```

对应命令可以作为检查清单，但不要整块当脚本执行：

```bash
cd PROJECT_PATH
pwd
git status
git branch --show-current

# 修改并测试后：
git status --short
git diff --stat
git diff
git diff --check

git add PATH_1 PATH_2
git diff --cached --check
git diff --cached

git commit -m "type: concise description"
git status
git log -1 --stat
```
