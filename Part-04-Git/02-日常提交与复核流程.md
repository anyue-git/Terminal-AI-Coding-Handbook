# 02 日常提交与复核流程

一套稳定的 Git 工作流，比记住很多零散命令更重要。

```text
确认状态
→ 创建任务分支
→ 修改与测试
→ 查看 diff
→ 精确暂存
→ 检查 cached diff
→ 提交
→ 再检查
→ 决定是否推送
```

---

## 1. 开始前确认目录、分支和工作区

```bash
cd PROJECT_PATH
pwd
git status
git branch --show-current
git remote -v
```

确认：

- 当前目录正确；
- 当前分支符合任务；
- 没有来源不明的未提交修改；
- 远程仓库不是另一个项目。

创建分支：

```bash
git switch -c fix/login-validation
```

分支名应描述任务，不要写 `new-branch`、`final-2` 或 `ai-test`。

---

## 2. 修改后先检查工作区

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

检查：

- 是否只修改预期文件；
- 是否出现意外删除；
- 是否修改依赖和锁文件；
- 是否产生日志、缓存和大文件；
- 是否写入密码、Token、私钥或内部地址；
- 是否存在大范围无关格式化；
- 测试是否被弱化。

查看单个文件：

```bash
git diff -- src/app.py
```

---

## 3. 运行与任务直接相关的验证

根据项目运行真实命令，例如：

```bash
python -m pytest tests/test_app.py
```

```bash
npm test
```

记录：

```text
执行命令
退出状态
通过与失败数量
未运行部分
环境限制
```

不能在 Mac 运行 CUDA 测试时，要写清楚“未验证”，不能写成“测试通过”。

---

## 4. 精确暂存

```bash
git add src/app.py tests/test_app.py
```

检查下一次提交：

```bash
git status
git diff --cached --name-status
git diff --cached
```

暂存错了，但要保留工作区修改：

```bash
git restore --staged PATH_TO_FILE
```

一个文件混有多类修改时：

```bash
git add -p
```

常用选项：

```text
y  暂存当前块
n  跳过
s  尝试拆分
q  退出
?  查看帮助
```

---

## 5. 创建清晰提交

```bash
git commit -m "fix: validate login input"
```

提交信息应说明这次改变的目的。

常见前缀：

```text
feat     新功能
fix      修复
refactor 重构
docs     文档
test     测试
chore    构建或维护
```

避免：

```text
update
changes
final
AI changes
```

提交最好只有一个主要目的，并让实现、测试和文档处于可理解的组合中。

---

## 6. 提交后再检查

```bash
git status
git log -1 --stat
git show --stat HEAD
git show HEAD
```

如果工作区仍有修改，判断它们属于：

- 遗漏内容；
- 下一个独立提交；
- 不应保留的临时文件。

不要为了把一切塞进一个提交而不断 amend。小而清楚的补充提交通常比一次无法审查的大提交更好。

---

## 7. 推送前检查

```bash
git status
git branch --show-current
git log --oneline --decorate -5
git remote -v
```

首次推送新分支：

```bash
git push -u origin fix/login-validation
```

后续通常：

```bash
git push
```

推送会把提交共享出去。确认分支、远程和提交历史无误后再执行。

---

## 8. `.gitignore` 不是安全保险箱

`.gitignore` 只影响尚未跟踪的文件。

```gitignore
.env
.venv/
__pycache__/
node_modules/
*.log
```

文件如果已经进入 Git，后来加入 `.gitignore` 不会自动从历史消失。

从索引移除但保留本地文件：

```bash
git rm --cached PATH_TO_FILE
```

敏感凭据一旦提交，应立即撤销和轮换，而不是只删除文件。

---

## 9. AI CLI 的安全提交流程

推荐规则：

```text
请修改并测试，但不要执行 git add、commit、push、reset、clean、merge 或 rebase。
完成后列出变更文件、修改目的、测试结果和未解决风险。
```

人工执行：

```bash
git status --short
git diff
git add 明确文件
git diff --cached
git commit -m "明确说明"
```

在充分成熟的自动化环境中，可以让 Agent 准备提交信息或暂存建议，但 `git diff --cached` 仍应是质量关口。

---

## 10. 可直接使用的日常模板

```bash
cd PROJECT_PATH
pwd
git status
git branch --show-current

git switch -c TYPE/SHORT_DESCRIPTION

# 修改并运行真实测试

git status --short
git diff --stat
git diff

git add PATH_1 PATH_2
git diff --cached

git commit -m "type: concise description"
git status
git log -1 --stat

git push -u origin TYPE/SHORT_DESCRIPTION
```

它是流程模板，不是应整块无脑执行的脚本。
