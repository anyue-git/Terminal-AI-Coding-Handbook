# 04 Pull Request 与多人协作

Pull Request（PR）围绕任务分支相对于目标分支的差异展开讨论、检查和合并。它不是单纯的上传按钮，也不只属于大型团队；只要改动需要自动测试、人工复核、讨论记录或受控合并，PR 就有价值。

本章假设远程仓库已经存在，重点说明怎样把本地证据整理成可审查的 PR，以及如何处理评论、后续更新和并行任务。

## 1. 创建 PR 前查看完整分支差异

假设目标分支是 `main`，任务分支是 `feature/type-hints`。PR 展示的是任务分支相对于目标分支的最终差异，而不只是最后一次提交。推送前检查：

```bash
git status
git branch --show-current
git log --oneline --decorate --graph -10
git diff main...HEAD --stat
git diff main...HEAD
git remote -v
```

三点号常用于查看当前分支从共同祖先以来引入的变化。确认当前分支只处理一个主题，没有混入无关文件或敏感信息，提交历史可以理解，测试和未验证内容已经记录。目标分支若是 `master`、`develop` 或发布分支，应按真实仓库调整。

首次推送任务分支：

```bash
git push -u origin feature/type-hints
```

`-u` 建立上游关系，之后可以直接运行 `git push`。推送只更新远程任务分支，不等于已经合入主分支；同时使用个人 fork、公司仓库和多个账号时，先确认 `origin` 的地址。

## 2. PR 描述把改动变成可审查证据

提交信息说明某一次提交的目的，PR 描述则解释整个任务为何发生、最终改变了什么、怎样验证，以及还存在哪些风险和未处理内容。一个实用结构是：

```md
## 变更内容
说明用户可见行为和主要文件变化。

## 为什么要改
说明问题、根因或需求背景。

## 如何验证
列出实际运行的命令和结果。

## 风险与影响范围
说明模块、数据、兼容性和回滚方式。

## 未处理内容
写清不在本次范围内和仍未验证的部分。
```

例如，类型标注任务可以写明只修改函数签名和文档字符串，运行了 `python3 -m unittest -v`，两个测试通过，减法函数暂未补充类型标注。`please review`、`fix bug` 或 `AI generated` 无法告诉审查者根因、证据和风险。

Draft PR 表示当前不应合并。方向需要提前确认、任务较大需阶段展示、自动检查仍在运行、AI 只完成初稿或已知尚缺测试时，都可以使用 Draft。它不是低质量免责标签，描述仍要写明完成部分、已知缺口和希望审查者先看的内容。

## 3. 自动检查与人工审查解决不同问题

CI 适合检查格式、测试、构建、类型和其他能够机械判断的规则。自动流程无法独立判断需求是否理解正确、教程是否适合新手、测试是否真的覆盖目标，或某个运维风险是否已经被团队接受。

人工审查关注真实需求、架构、边界条件、权限风险、测试质量、无关重构、文档与迁移、回滚方式，以及 PR 描述是否准确反映实际内容。AI 可以归纳差异和寻找遗漏，最终批准仍由理解项目目标与风险的人作出。

## 4. Review Comment 先分类，再实施

收到评论后，先区分必须修复、建议优化、需要讨论、信息不足和与本次任务无关。还要检查评论之间是否冲突，采纳后会不会扩大范围，是否需要新增测试，以及意见属于局部实现还是设计决定。

让 Agent 协助时，第一轮只分析：

```text
读取当前 PR 中未解决的审查评论，只做分析，不修改代码。
逐条列出文件和位置、核心诉求、风险、是否建议采纳，以及需要运行的验证。
指出评论之间是否冲突，哪些需要维护者决定。
```

人工选择要处理的意见后，再限定实施范围：

```text
只处理评论 1 和评论 3。
允许修改 src/parser.py 与 tests/test_parser.py。
评论 2 暂不处理，不扩大到其他模块，不提交或推送。
完成后运行指定测试并汇报 diff。
```

回复评论时写明修改文件、行为变化、增加的边界测试和实际验证结果。只回复 `done` 会迫使审查者重新寻找全部证据。

## 5. 后续修改继续进入同一任务分支

PR 创建后，相关修正通常继续提交到原任务分支：

```bash
git status
git diff
git add 明确文件
git diff --cached
git commit -m "fix: address parser review feedback"
git push
```

远程 PR 会自动更新差异，并可能重新触发 CI。大任务可以保留多个有意义的提交，也可以在合并时 squash；是否整理历史应服从团队规范，而不是为了让提交图整齐就改写已经共享的历史。

合并前确认需求、自动检查、人工审查、评论结论、敏感信息、文档与配置、未验证内容和回滚方式。数据库迁移、权限、生产配置、依赖主版本、公开 API 或大规模数据处理还需要确认执行顺序与兼容窗口。CI 全绿只表示自动规则通过。

常见合并方式各有取舍：Merge commit 保留分支提交并增加合并节点；Squash merge 将 PR 的最终变化压成一个目标分支提交；Rebase merge 把任务提交线性放到目标分支顶部。选择时考虑审计、回滚、提交质量和发布工具。

## 6. 合并后更新本地，并隔离并行任务

PR 合并后，切回目标分支，在干净工作区中快进更新：

```bash
git switch main
git status
git pull --ff-only
git branch -d feature/type-hints
```

`--ff-only` 会在本地存在独立提交时停止，而不是自动创建合并提交。删除本地任务分支前确认 PR 已合并，分支上也没有仍需保留的提交。远程任务分支是否自动删除取决于托管平台和仓库设置；手工删除前同样要确认没有其他人仍依赖该分支。

多人或多个 Agent 并行时，每个任务至少使用独立分支。需要同时编辑时使用 Worktree：

```bash
git worktree add ../project-task-a -b task/a main
git worktree add ../project-task-b -b task/b main
git worktree list
```

每个目录有独立工作区和分支，但共享同一仓库对象，也可能共享端口、数据库和外部服务。即使文件目录已经隔离，两个任务同时修改同一接口、数据格式或核心模块，合并时仍可能出现语义冲突；并行前应约定接口、文件边界和依赖顺序。任务完成并确认工作区干净后，使用 `git worktree remove PATH` 清理，不直接在 Finder 中删除仍含未提交内容的 Worktree。

一条可审查的协作链最终应做到：本地完整差异与测试已经确认，PR 描述准确，自动检查与人工审查各自完成，评论经过分类处理，合并策略符合项目要求，合并后的本地分支和 Worktree 也得到清理。PR 的价值在于把代码、测试、风险、讨论和合并决定放进同一个可追踪边界。
