# 04 Pull Request 与多人协作

Pull Request（PR）是围绕分支差异进行讨论、检查和合并的协作机制，不只是“上传代码”。

```text
任务分支
→ 提交并推送
→ 创建 PR
→ 自动检查与人工审查
→ 修改并继续提交
→ 合并
```

---

## 1. PR 的核心是分支差异

创建 PR 前检查：

```bash
git status
git branch --show-current
git log --oneline --decorate -5
git diff main...HEAD --stat
git diff main...HEAD
```

确认：

- 当前不是主分支；
- 一个分支只做一个主题；
- 没有无关文件和敏感信息；
- 提交历史可理解；
- 测试结果明确。

---

## 2. PR 描述应帮助审查

推荐结构：

```md
## 变更内容

## 为什么要改

## 如何验证

## 风险与影响范围

## 未处理内容
```

不要只写 `please review` 或 `fix bug`。审查者需要知道用户行为、根因、测试、影响范围和回滚风险。

---

## 3. Draft PR 用于提前暴露方向

Draft PR 适合：

- 工作尚未完成；
- 希望尽早获得方向反馈；
- 自动检查仍在运行；
- AI 已完成初稿但人工复核未结束；
- 大任务需要阶段性展示 diff。

它不是“低质量 PR”，而是明确告诉团队当前还不能合并。

---

## 4. Review 不只是找语法错误

代码审查应关注：

- 是否解决真实需求；
- 边界条件和回归；
- 权限、安全和数据风险；
- 性能；
- 测试覆盖；
- 可维护性；
- 无关改动；
- 文档和迁移是否同步。

AI 可以提供第二意见，但不能替代理解项目目标的人做最终批准。

---

## 5. 处理审查意见

先分类：

```text
必须修复
建议优化
需要讨论
信息不足
不在本次范围
```

不要机械接受所有评论。每条意见都要判断是否正确、是否扩大范围、是否需要新增测试，以及是否与其他建议冲突。

完成后回复：改了什么、为什么这样改、怎样验证。

---

## 6. AI 处理 Review Comment 的方式

不要直接要求：

```text
把所有评论都修掉。
```

先要求只读分析：

```text
读取未解决评论并逐条分类。
不要修改代码。
说明每条评论对应的文件、风险、是否建议采纳，以及需要的验证。
```

确认后再处理选中的评论，避免相互冲突或范围漂移。

---

## 7. 合并策略

常见方式：

```text
Merge commit
→ 保留分支提交和合并节点

Squash merge
→ 把整个 PR 合成一个提交

Rebase merge
→ 让提交线性排列到目标分支顶部
```

团队应统一策略。不要为了追求漂亮提交图，在共享分支上随意改写历史。

---

## 8. 合并前最后检查

```text
需求满足
相关测试通过
重要评论已处理
没有无关或敏感文件
文档已同步
迁移和回滚明确
```

涉及数据库、权限、生产配置、依赖主版本或接口删除时，应额外确认部署顺序和回滚方案。

---

## 9. 多人和多 Agent 并行

推荐：

- 每个任务使用独立分支；
- 最好使用独立 worktree；
- 不共享未提交工作区；
- 提前声明接口和文件边界；
- 最后由一个集成负责人合并；
- 实现者之外应有独立复核。

多个 Agent 同时修改同一工作区，不是协作，而是让 diff 失去来源。

---

## 10. 合并后清理

```bash
git switch main
git pull --ff-only
git branch -d feature/name
```

`-d` 会拒绝删除尚未合并的分支，比 `-D` 更安全。

PR 的真正价值是把“模型说完成了”转化为可检查的差异、测试和讨论证据。
