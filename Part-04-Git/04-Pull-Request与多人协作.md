# 04 Pull Request 与多人协作

Pull Request，简称 PR，是围绕一条分支相对于目标分支的差异进行讨论、检查和合并的协作机制。它不是单纯的“上传按钮”，也不是只有大型团队才需要。只要一个改动需要自动测试、人工复核、留下讨论记录或控制合并时机，PR 就有价值。

前面三章一直在本地练习仓库中工作。创建真实 PR 需要远程仓库，因此本章不会要求把练习项目上传到任何平台，而是说明在已有 GitHub 仓库中的完整流程，以及如何把本地证据整理成可审查的 PR。

## 1. PR 比较的是两个分支

假设目标分支是 `main`，任务分支是 `feature/type-hints`。PR 展示的是任务分支相对于 `main` 新增的提交和最终文件差异。

创建 PR 前，先在本地确认：

```bash
git status
git branch --show-current
git log --oneline --decorate --graph -10
git diff main...HEAD --stat
git diff main...HEAD
```

三点号 `main...HEAD` 常用于查看当前分支从共同祖先以来相对主分支引入的变化。它比单看最后一个提交更接近 PR 的整体差异。

检查时要回答：当前是否真的是任务分支，分支是否只处理一个主题，是否混入无关文件，提交历史是否能理解，测试证据是否完整，以及是否出现敏感信息。

如果目标分支不是本地 `main`，应根据仓库实际分支和远程状态调整命令。不要因为教程使用 `main`，就在采用 `master`、`develop` 或发布分支的项目里照抄。

## 2. 推送任务分支

确认远程：

```bash
git remote -v
```

确认当前分支：

```bash
git branch --show-current
```

首次推送一个新分支通常使用：

```bash
git push -u origin feature/type-hints
```

`-u` 建立上游关系，之后通常可以直接 `git push`。推送前必须确认 `origin` 指向正确仓库，尤其是同时使用个人 fork、公司仓库和多个 GitHub 账号时。

推送只把提交发送到远程分支，不等于已经合并进主分支。接下来还需要在 GitHub、GitLab 或团队平台上创建 PR。

## 3. 一份可审查的 PR 描述应回答什么

PR 描述不是重复提交信息，而是帮助审查者理解改动。一个实用结构如下：

```md
## 变更内容

说明用户可见行为和主要文件变化。

## 为什么要改

说明问题、根因或需求背景。

## 如何验证

列出实际运行的命令和结果。

## 风险与影响范围

说明可能影响的模块、数据、兼容性和回滚方式。

## 未处理内容

明确不在本次范围内的内容和仍未验证的部分。
```

例如：

```md
## 变更内容

为计算器的加法函数补充整数类型标注，并保留已有文档字符串。

## 为什么要改

调用方和静态检查工具此前无法从函数签名判断参数类型。

## 如何验证

- `python3 -m unittest -v`
- 2 个测试通过

## 风险与影响范围

只修改函数签名和文档，不改变运行逻辑。

## 未处理内容

减法函数暂未补充类型标注。
```

“please review”“fix bug”或“AI generated”无法告诉审查者问题根因、测试和风险，也不能代替人工解释。

## 4. Draft PR 适合还在进行中的工作

Draft PR 明确表示当前分支尚不应合并。它适合以下情况：方向需要提前确认，任务较大需要阶段性展示，自动检查仍在运行，AI 已经完成初稿但人工复核未结束，或者已知还有测试和文档没有完成。

Draft 并不是低质量内容的免责标签。即使处于 Draft，描述仍应说明当前完成了什么、哪些部分不稳定、希望审查者先看什么。这样团队可以尽早发现方向错误，而不是等所有代码写完后才推翻设计。

当前这本手册的 V2.0 重写就使用 Draft PR：分支持续积累批次修改，每批完成后运行 Markdown 检查，但在整本书人工通读之前不进入正式合并状态。

## 5. 自动检查和人工审查各自负责什么

CI 可以稳定检查格式、测试、构建、类型和安全规则。例如本书的 Markdown Check 会检查标题、链接、代码围栏和目录引用。自动检查适合发现可机械判断的问题，但不能确认教程是否真正适合新手，也不能判断一句技术解释是否容易误导。

人工审查应关注：

- 改动是否解决真实需求；
- 实现是否符合项目架构；
- 边界条件、权限和数据风险；
- 测试是否覆盖关键行为；
- 是否存在无关改动或过度重构；
- 文档、迁移和配置是否同步；
- 回滚是否可行；
- 提交和 PR 描述是否准确反映实际内容。

AI 可以提供第二意见、归纳差异和检查遗漏，但最终批准应由理解项目目标和风险的人完成。

## 6. 怎样处理 Review Comment

收到审查意见后，不要立即逐条机械照做。先分类：

```text
必须修复
建议优化
需要讨论
信息不足
与本次任务无关
```

每条评论都要判断：意见是否正确，是否与其他评论冲突，采纳后是否扩大范围，是否需要新增测试，以及它是局部实现问题还是设计决策。

修改后应回复具体结果，例如：

```text
已在 src/parser.py 中改为显式处理空字符串，并在 tests/test_parser.py 增加两个边界测试。
运行 `python -m pytest tests/test_parser.py`，12 个测试通过。
```

只回复“done”会让审查者重新寻找变化和验证证据。

## 7. 让 AI 处理审查意见时先做只读分析

不要直接给 Agent 一句“把所有评论修掉”。评论可能互相冲突，也可能要求超出本次范围。

先要求：

```text
读取当前 PR 中未解决的审查评论，只做分析，不要修改代码。
逐条列出评论对应的文件和位置、核心诉求、风险、是否建议采纳，以及需要运行的验证。
指出评论之间是否冲突，哪些需要维护者做决定。
```

人工确认要处理的评论后，再限定文件和步骤：

```text
只处理评论 1 和评论 3。
允许修改 src/parser.py 与 tests/test_parser.py。
不要处理评论 2，不要扩大到其他模块，不要提交或推送。
完成后运行指定测试并汇报 diff。
```

这种方式让 Agent 成为执行者和分析助手，而不是让它替团队决定所有审查意见的优先级。

## 8. PR 更新通常继续向同一分支提交

PR 创建后，不需要每次修改都新建一个 PR。继续在任务分支修改、测试和提交，然后 push：

```bash
git status
git diff
git add 明确文件
git diff --cached
git commit -m "fix: address parser review feedback"
git push
```

远程 PR 会自动显示新提交和更新后的差异。每次推送都可能重新触发 CI，因此不要在没有本地检查的情况下频繁推送明显错误的中间状态。

大任务可以保留多个有意义的提交，也可以在合并时选择 squash。提交策略应由团队统一，而不是为了让提交图“看起来漂亮”随意重写已共享历史。

## 9. Merge、Squash 和 Rebase 合并的区别

常见合并方式包括：

```text
Merge commit
→ 保留任务分支上的提交，并增加一个合并节点

Squash merge
→ 把整个 PR 的最终变化压成一个目标分支提交

Rebase merge
→ 把任务分支提交线性放到目标分支顶部
```

Merge commit 能保留分支结构，Squash 让主分支历史更紧凑，Rebase merge 保留多个线性提交。没有一种方式适合所有项目。

选择时要考虑团队的审计需求、提交质量、回滚方式和发布工具。不要为了追求线性历史，在共享分支上未经协商地强制 rebase 和 force push。

## 10. 合并前最后检查

在 GitHub 点击合并前，至少确认：

```text
需求已经满足
相关自动检查通过
人工审查已完成
重要评论已解决或有明确结论
PR 中没有无关文件和敏感信息
文档、配置和迁移已同步
未验证内容已写清楚
部署与回滚方式明确
```

涉及数据库迁移、权限、生产配置、依赖主版本、公开 API 删除或大规模数据处理时，还要确认执行顺序、兼容窗口和故障恢复。

“CI 全绿”只证明自动规则通过，不代表产品行为和运维风险已经被理解。

## 11. 合并后怎样更新本地仓库

PR 合并后，先切回目标分支：

```bash
git switch main
```

确认工作区干净，再更新：

```bash
git status
git pull --ff-only
```

`--ff-only` 只允许快进，不会悄悄创建本地合并提交。如果本地 `main` 有独立提交，它会停止并要求你先处理差异。

删除已经合并的本地任务分支：

```bash
git branch -d feature/type-hints
```

远程分支是否自动删除取决于平台和仓库设置。删除前先确认 PR 已合并，且分支上没有仍需保留的提交。

## 12. 多人或多 Agent 并行时使用独立工作区

多人并行的基本原则是每个任务使用独立分支。多个 Agent 同时写同一个工作区，会让文件变化互相覆盖，最终 diff 也难以说明每项变化来自哪里。

需要同时处理多个任务时，可以使用 Git worktree：

```bash
git worktree add ../project-task-a -b task/a main
git worktree add ../project-task-b -b task/b main
```

这样两个目录分别检出不同分支。每个 Agent 只进入自己的 worktree，任务完成后由人工审查和集成。

并行前还应约定接口、文件边界和依赖顺序。不同分支都修改同一个核心文件时，即使工作区隔离，最后仍可能产生语义冲突。

## 13. 一个 PR 从开始到结束的完整路径

```text
确认需求和目标分支
→ 创建任务分支
→ 修改并运行测试
→ 查看工作区 diff
→ 精确暂存并提交
→ 推送远程分支
→ 创建 Draft 或正式 PR
→ CI 与人工审查
→ 处理选定评论并继续提交
→ 合并前复核
→ 合并
→ 更新本地主分支并清理任务分支
```

在这个流程中，PR 的价值是把“代码已经写完”转化为一组可以检查的证据：分支差异、提交、测试结果、自动检查、审查评论和最终合并记录。
