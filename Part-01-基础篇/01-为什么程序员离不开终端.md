# 01 为什么程序员离不开终端

很多人第一次看到终端，会觉得它只是把鼠标点击换成了键盘输入。真正使用一段时间后会发现，终端的优势并不在于“看起来专业”，而在于操作能够被准确写下来、重复执行、组合成流程，并留下可检查的记录。

图形界面很适合浏览文件、调整少量设置和完成一次性的可视化操作；终端更擅长处理项目、远程机器、日志、批量文件和自动化任务。两者不是互相替代的关系。理解底层命令以后，你使用 VS Code、Docker Desktop 或 Git 客户端时，也更容易知道界面背后发生了什么。

## 1. 很多开发工具本来就从命令行工作

Git、SSH、Python、Node.js、Docker、ffmpeg、Claude Code 和 Codex CLI 都可以直接在终端中运行。图形化工具通常是在这些能力之上增加按钮、菜单和状态显示。

例如，VS Code 中点击“提交”，背后仍然需要 Git 判断哪些文件发生变化、哪些内容进入暂存区以及提交记录写到哪里。Remote SSH 插件也仍然需要建立 SSH 连接。界面可以降低使用门槛，但遇到认证、路径或权限问题时，终端输出往往提供更直接的线索。

先看一个普通 Git 项目中的检查过程：

```bash
pwd
git status
git diff --stat
```

可能看到：

```text
/Users/NAME/Projects/demo
On branch fix/readme
Changes not staged for commit:
  modified: README.md

 README.md | 8 +++++---
 1 file changed, 5 insertions(+), 3 deletions(-)
```

这几行告诉你当前项目、所在分支、变化文件和大致改动规模。相比只看到一个“有未提交更改”的图标，文字输出更容易复制到记录中，也更适合远程排错。

## 2. 命令可以准确复现

图形界面中的操作常常依赖当时打开了哪个窗口、点了哪个菜单。命令会把动作和参数直接写出来。例如：

```bash
python3 -m unittest -v
```

这条命令明确使用当前环境中的 `python3`，以模块方式启动 `unittest`，并显示详细测试结果。团队成员看到同一条命令，通常能在自己的环境中尝试复现。

命令也可以进入 README、脚本、CI 或问题记录。某次测试失败时，保存“执行了什么命令、在哪个目录、输出是什么”，比只写“我点了运行但失败了”更容易继续调查。

## 3. 小工具可以组成完整流程

许多 Unix 工具只负责一类工作。`find` 查找文件，`grep` 或 `rg` 筛选文字，`sort` 排序，`wc` 统计数量。它们可以通过管道连接，让前一个命令的输出成为后一个命令的输入。

在练习目录中统计 Markdown 文件数量：

```bash
find . -type f -name '*.md' | wc -l
```

假设输出：

```text
12
```

这不是一个专门安装的“Markdown 计数软件”，而是两个小工具完成的组合。再例如，找出包含 `TODO` 的 Python 文件：

```bash
rg -l 'TODO' --glob '*.py'
```

命令组合很强，也会放大错误。初学阶段不需要急着写复杂的一行命令。先分别运行每一步，确认中间输出，再决定是否连接起来。

## 4. 远程机器通常离不开终端

服务器和 GPU 工作站经常没有你熟悉的桌面环境。通过 SSH 登录后，主要交互方式就是终端：

```bash
ssh USER@SERVER_IP
```

登录成功后，先运行：

```bash
hostname
whoami
pwd
```

窗口仍然显示在 Mac 上，但命令已经在远程 Linux 中执行。此时安装软件、修改文件和启动训练，影响的是远程机器。终端让你能够使用同一套基本操作在本地与远程环境之间工作，但也要求你始终知道当前连接到了哪里。

## 5. AI 编程工具让终端知识变得更重要

AI 可以生成命令、修改代码和运行测试，但它不能替你承担执行结果。Agent 收到“清理项目”后，可能建议删除构建产物；这个建议是否安全，取决于当前目录、匹配范围、文件是否可恢复以及命令有没有超出项目边界。

使用 AI CLI 时，至少要能回答：

- 当前是哪台机器、哪个目录；
- Agent 能读取和修改哪些文件；
- 命令会不会访问网络、凭证或系统服务；
- 修改后怎样查看真实 diff；
- 测试在哪里运行；
- 方向错误时怎样停止。

例如 Agent 准备批量处理日志时，不要直接批准一个含通配符的写操作。先让它列出匹配对象，或者自己运行只读命令：

```bash
find . -type f -name '*.log' -print
```

确认范围后，再决定哪些文件可以移动、归档或删除。AI 提高了操作速度，因此更需要在执行前看清范围。

## 6. 自动化会同时放大正确和错误

手工改错一个文件和脚本一次改错一千个文件，可能只差一个循环或通配符。可靠的终端流程通常包含几个阶段：

```text
确认环境和目录
→ 预览将要处理的对象
→ 执行尽可能小的操作
→ 检查输出和文件变化
→ 保留恢复手段
```

Git、备份、测试、dry run、日志和 checkpoint 都属于恢复手段。它们不是“出了问题以后再考虑”的附加项，而是自动化能够放心扩大规模的前提。

例如准备批量重命名前，可以先打印旧名称和计划中的新名称，而不是直接移动文件。准备同步目录时，先使用工具提供的预览模式。准备让 Agent 修改十个文件时，先让它完成一个文件并展示结果。

## 7. 终端让问题更容易被看见

命令失败时通常会返回错误信息和退出状态。例如：

```bash
cd does-not-exist
```

会显示：

```text
cd: no such file or directory: does-not-exist
```

这说明路径无法解析，而不是“电脑坏了”。类似地，`command not found` 通常意味着命令名称、安装位置或 PATH 有问题；`permission denied` 则提示当前用户没有所需权限，或文件缺少执行权限。

学终端的重要部分不是避免所有报错，而是逐渐学会根据报错判断应该检查哪一层。不断重装软件、重复执行或直接加 `sudo`，往往会把原本清楚的问题变得更复杂。

## 8. 第一阶段只需要形成几项习惯

刚开始不需要背几十条命令。先熟悉下面这些动作：

```bash
hostname
pwd
ls -la
git status
```

它们分别帮助你确认机器、目录、文件和项目状态。再记住 `Ctrl + C` 可以中断多数前台程序，长命令输错时可以先取消而不是勉强执行。

每次操作时多问一句：“这条命令会在哪个位置处理哪些对象？”随着使用次数增加，命令自然会记住。终端更像一种操作计算机的语言，不需要学完整本词典才开始说第一句话。
