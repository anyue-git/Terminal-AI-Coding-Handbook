# 05 复杂任务拆分与独立复核

> 最近核对：2026-07-30

小任务可以直接做，例如改一句提示、补一个明确测试、修一个拼写错误。复杂任务不同，它可能同时涉及接口、配置、数据、兼容性、权限和远程环境。把所有要求塞进一条超长 Prompt，然后让 Agent 一口气改完，通常会得到一个难以验证的大 diff。

更可靠的做法是把复杂任务拆成一系列可以检查的决策：

```text
需求澄清
→ 现实调查
→ 方案选择
→ 批次计划
→ 小批实施
→ 阶段验证
→ 独立复核
→ 人工整合
```

## 1. 哪些任务必须先停在分析阶段

出现以下任意情况，不应直接开始修改：

- 修改多个模块；
- 改变公开接口或配置格式；
- 涉及数据库、网络、权限或敏感信息；
- 需要兼容旧版本；
- 同时包含重构与新功能；
- 测试范围很大或环境不完整；
- 需求中存在“最好”“智能”“兼容一下”等模糊表达；
- 失败后很难恢复；
- 涉及远程主机、GPU、Docker Volume 或生产服务。

复杂度不只看文件数量。修改一个防火墙规则可能只改一行，却比修改十个本地测试文件风险更高。

## 2. 先定义目标、非目标和验收标准

第一轮只整理需求：

```text
先不要修改代码。

请把需求整理成：
1. 目标；
2. 非目标；
3. 用户可观察行为；
4. 验收标准；
5. 必须保持的旧行为；
6. 待确认问题；
7. 风险与回滚要求。

不要自行补充产品规则。
```

例如：

```text
目标：拒绝缺少必填字段的 API 请求。
非目标：不重构全部请求处理模块。
兼容约束：旧客户端已有可选字段继续有效。
验收：新增校验测试通过，旧兼容测试不回归。
未知：无效请求的错误码尚未确认。
```

没有非目标时，Agent 容易把“顺便整理”发展成第二个项目。

## 3. 建立现实地图，而不是依靠常见经验

只读调查应找到：

- 入口；
- 核心实现；
- 配置与数据模型；
- 调用方；
- 测试；
- 兼容行为；
- 项目规则；
- 相关 Git 历史或文档。

Prompt：

```text
只读调查当前实现，不要修改文件。

每个结论给出文件路径、符号或测试证据。
将输出分成：
- 已确认事实；
- 合理推测；
- 尚缺证据；
- 需要人工回答的问题。
```

“通常这种项目会……”只能作为假设，不能当作当前仓库事实。

## 4. 比较方案并说明为什么不做更大改动

复杂任务至少要比较：

```text
最小修改
→ 在现有结构中修复

结构性修改
→ 抽取新层或重构接口

暂缓实施
→ 先补测试、日志或监控
```

不必机械凑三套方案，但推荐方案必须回答：

- 为什么适合当前需求；
- 为什么风险可控；
- 为什么暂不采用更大方案；
- 需要修改哪些文件；
- 如何验证；
- 如何回滚。

## 5. 为任务设置批次预算

开始前限定：

```text
最多 4 个实施批次；
每批最多修改 3 个文件；
每批必须有验证命令；
超过范围必须停止并重新计划。
```

这不是绝对数字，而是防止任务在执行中无限扩张。

典型批次：

```text
批次 1：补失败测试
批次 2：修改核心逻辑
批次 3：适配调用方或配置
批次 4：文档与清理
```

每批结束检查：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

并运行最相关测试。

## 6. 维护证据账本

长任务中维护：

```text
已确认事实：

未确认假设：

人工决定：

当前批次：

实际修改：

测试证据：

未验证：

新发现风险：
```

当新证据推翻旧假设时，明确更新，不要继续沿用旧结论。

## 7. 每个批次都必须有进入条件和退出条件

例如：

```text
批次 2：核心实现

进入条件：
- 回归测试已确认因目标问题失败；
- 接口规则已确认；
- 修改文件已限定。

退出条件：
- 目标测试通过；
- 相关测试通过；
- diff 未扩大到其他模块；
- 未新增依赖；
- 未验证部分已记录。
```

进入条件不满足时，不应继续。

## 8. 测试结果要绑定当前批次

每批报告：

```text
测试命令：
运行环境：
退出状态：
通过/失败/跳过：
关键警告：
覆盖本批哪些行为：
没有覆盖什么：
```

避免引用修改前或其他分支的旧测试结果。

## 9. 为什么需要独立复核

实施者已经接受了一套问题解释和方案，容易在复核时再次同意自己。独立复核最好使用新会话或另一个工具，只提供：

- 原始需求；
- 当前 diff；
- 测试结果；
- 必要文件；
- 已知限制。

不要先附上“已经完整解决”“没有风险”等实施者结论。

复核 Prompt：

```text
你没有参与实现，只负责只读审查，不要修改文件。

请检查：
1. 是否满足原始需求；
2. 是否有范围外修改；
3. 逻辑、兼容性、错误处理和安全问题；
4. 测试是否足以支持完成结论；
5. 是否存在更小的修复；
6. 哪些内容无法验证。

每条发现给出文件和位置，并分类为：
- 已确认问题；
- 可能问题；
- 无法验证；
- 可选改进。
```

## 10. 多 Agent 不是让所有人同时写代码

稳妥分工：

```text
Agent A
→ 只读调查与方案

Agent B
→ 在独立分支或 Worktree 实施

Agent C
→ 只读复核 diff 与测试

人
→ 选择方案、批准高风险操作、整合和提交
```

多个 Agent 不应同时编辑同一个未提交工作区。

需要比较两个方案时，可以建立两个 Worktree：

```bash
git worktree add ../project-option-a -b experiment/option-a
git worktree add ../project-option-b -b experiment/option-b
```

Worktree 只隔离代码工作区，不隔离主目录、网络、Docker、凭据和数据。

## 11. 审查意见也要分类

复核报告先分为：

```text
必须修复
→ 有明确证据，影响当前需求、安全或正确性

需要确认
→ 依赖产品规则或真实环境

可选改进
→ 有价值但超出当前任务

误报
→ 与代码或需求不符
```

不要把整个报告交回实施者并要求“全部优化”。

## 12. 处理复核问题时重新进入小批闭环

对于每个必须修复的问题：

1. 确认复现或证据；
2. 写最小修复计划；
3. 限定文件；
4. 修改；
5. 运行目标测试；
6. 更新证据账本；
7. 再次复核对应 diff。

不要在“审查修复”阶段顺便重构。

## 13. 何时必须暂停

- 同一个问题连续修复仍失败；
- 文件范围不断扩大；
- Agent 开始猜测未读取代码；
- 测试环境不可靠；
- 需求冲突；
- 需要管理员权限、生产访问或不可逆迁移；
- 发现凭据或敏感数据；
- diff 已无法认真阅读；
- 任务超过预设轮数、时间或预算。

暂停后保存：

```bash
git status --short
git diff --stat
git diff
```

以及错误日志、环境和未解决问题，再重新规划。

## 14. 复杂任务的最终验收

提交前确认：

- 目标和非目标仍然成立；
- 实际 diff 与方案一致；
- 每个批次有测试证据；
- 兼容性与迁移已说明；
- 复核问题已分类处理；
- 未验证部分没有被写成已完成；
- 没有凭据、大文件和范围外修改；
- 回滚方法可执行。

复杂任务不是因为修改很多才复杂，而是因为需要管理更多相互依赖的决定。拆分的目的，是让每个决定都有证据、有边界、有退路。
