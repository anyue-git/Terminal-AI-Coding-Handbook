# 05 复杂任务拆分与独立复核

小改动可以直接做：改一句提示文字、补一个测试、修一个明确的拼写错误，通常不需要开大会。

复杂任务不一样。它可能同时碰到接口、配置、数据库、权限和测试。此时把全部需求塞进一条超长 Prompt，期待 AI 一口气交出正确答案，多少有点像把装修钥匙交出去，然后只说一句“弄好看点”。它可能很努力，但你们对“好看”的理解未必一致。

更稳妥的做法是把任务拆成几次能够检查的小决定：先确认要做什么，再理解现有代码，然后选择方案、分批修改、运行测试，最后换一个独立视角复核。

---

## 1. 哪些任务不适合直接让 AI 开始改

出现下面任意一种情况，就应该先停在分析阶段：

- 要修改多个模块；
- 会改变公共接口或配置格式；
- 涉及数据库、网络、权限或敏感信息；
- 需要兼容旧版本；
- 同时包含重构和新功能；
- 测试范围很大；
- 需求中还有“应该”“大概”“最好”之类没有说清的地方；
- 修改失败后很难恢复。

假设任务是：

> 给现有 API 增加请求参数校验，同时保持旧客户端可用。

这句话看起来不长，但至少藏着几个问题：旧客户端到底会发送什么？无效请求应该返回哪个状态码？校验放在路由层还是业务层？日志里能不能记录原始内容？这些都没弄清时，代码写得越快，返工可能越快。

---

## 2. 第一步不是写代码，而是把“完成”说清楚

先让 AI 整理任务，不要修改文件：

```text
先不要修改代码。

请把需求整理成：
1. 目标：这次必须实现什么；
2. 非目标：这次明确不处理什么；
3. 验收标准：出现什么结果才算完成；
4. 约束：不能破坏哪些现有行为；
5. 待确认问题：目前缺少哪些信息。

不要自行补充产品规则。
```

这里的“非目标”很有用。例如：

```text
目标：拒绝缺少必填字段的请求
非目标：本次不重构整个请求处理模块
约束：旧客户端发送的可选字段继续有效
验收标准：新增测试通过，旧测试不回归
```

如果没有非目标，AI 很容易顺手做一次“看起来更整洁”的大重构。顺手整理房间没问题，顺手拆承重墙就不太妙了。

---

## 3. 让结论带着文件证据回来

任务说清楚后，再让 AI 阅读项目。它至少应该找到：

- 入口文件；
- 当前请求处理逻辑；
- 数据模型或配置；
- 相关测试；
- 调用这个接口的代码；
- 与旧行为有关的 Git 历史或文档。

提示可以这样写：

```text
只读分析当前实现，不要修改文件。

请找出：
- 请求从哪里进入；
- 参数在哪里解析和校验；
- 错误响应在哪里生成；
- 哪些测试覆盖了现有行为；
- 哪些调用方可能受影响。

每个结论都给出文件路径。
没有找到证据的内容标记为“推测”。
```

“项目应该是这样设计的”不算证据。更有用的表达是：

```text
请求入口位于 src/api/routes.py
现有字段解析位于 src/api/schema.py
旧客户端兼容行为由 tests/test_legacy_client.py 覆盖
尚未找到错误响应格式的统一定义
```

文件路径让你能快速核对，也能防止 AI 把常见项目经验误当成这个项目的真实情况。

---

## 4. 先比较方案，再决定改多少

复杂任务通常不只有一种做法。至少可以比较：

- **最小修改**：只在现有入口增加校验；
- **结构性修改**：抽出统一校验层；
- **暂缓修改**：先增加日志或测试，补齐未知信息。

不需要为了形式硬凑三套方案，但必须回答两个问题：

1. 为什么选择当前方案？
2. 为什么暂时不采用更大的方案？

例如：

```text
选择最小修改，因为当前只有一个入口需要该规则，且旧客户端兼容要求尚未完全确认。
暂不抽取统一校验层，避免在需求仍有未知项时扩大改动范围。
```

“结构更漂亮”不是自动重构的通行证。代码首先要满足当前任务，其次才轮到它参加选美。

---

## 5. 一次只改一个能够验证的小批次

不要等十几个文件都改完，才第一次运行测试。更容易审查的顺序通常是：

1. 补充失败用例或最小复现；
2. 修改核心逻辑；
3. 调整调用方；
4. 更新配置和文档；
5. 最后清理确定不再需要的兼容代码。

每个批次结束后查看：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

并运行与本批次最相关的测试。

例如，第一批只增加一个能够复现问题的测试。确认它确实失败后，第二批再改实现，让这个测试通过。这样至少能证明你修的是那个问题，而不是测试本来就不会报错。

给实现者的提示可以写成：

```text
这次只完成第一批：补充能够复现问题的测试。
不要修改生产代码，不要提交或推送。

完成后汇报：
- 修改了哪些文件；
- 运行了什么测试；
- 测试为什么失败；
- 是否还有无法复现的部分。
```

下一批再明确允许修改的文件。修改范围越具体，最后的 diff 越容易看懂。

---

## 6. “测试通过”要带上证据

AI 说“测试通过”时，至少应该同时告诉你：

- 执行的命令；
- 运行环境；
- 退出状态；
- 通过、失败和跳过的数量；
- 出现了哪些警告；
- 哪些测试没有运行；
- 哪些部分受环境限制无法验证。

推荐格式：

```text
测试命令：python -m pytest tests/test_request_validation.py
结果：12 passed，退出状态 0
覆盖：必填字段、旧客户端可选字段、错误响应
未覆盖：真实生产代理层
环境限制：本地没有生产数据库
```

“代码看起来没问题”属于阅读结论，不属于测试结果。

还要确认测试针对的是当前代码。有时 Agent 修改文件后，报告的却是修改前运行过的测试；日志很热闹，证据却穿越了时间。

---

## 7. 为什么还要换一个 Agent 或新会话复核

负责实现的 Agent 已经形成了一套解释：问题在哪里、方案为什么合理、测试为什么足够。它再次审查时，很容易沿着原来的思路走一遍，然后再次同意自己。

独立复核不一定需要另一个品牌的工具，但最好使用新的会话，并只提供：

- 原始需求；
- 当前 diff；
- 测试命令和结果；
- 必要的相关文件；
- 已知限制。

不要先附上实现者的结论，例如“已经完整解决”“没有安全问题”。这会让复核者从一开始就被带向同一个答案。

可以使用下面的提示：

```text
你没有参与这次实现，只负责只读审查。不要修改文件。

请根据原始需求、当前 Git diff 和测试结果检查：
1. 是否真正满足需求；
2. 是否修改了任务范围之外的内容；
3. 是否存在逻辑、兼容性、错误处理或安全问题；
4. 测试是否足以支持“已经完成”的结论；
5. 哪些内容无法从现有证据确认。

请把发现分成：
- 已确认问题；
- 可能问题；
- 无法验证；
- 建议补充的测试。

没有证据的问题不要写成确定结论。
```

复核时可以从四个角度看，但不必假装有四位审查员坐在会议室里：

- **需求**：做的是不是用户真正要求的事；
- **代码**：逻辑、异常处理和维护性是否合理；
- **安全**：权限、输入、路径、网络和敏感信息有没有扩大风险；
- **测试**：关键行为是否真的被验证。

---

## 8. 审查意见也不能一股脑全修

复核报告可能混合了真实问题、推测和个人偏好。先分类：

```text
必须修复
需要确认
可选改进
误报
```

对于“必须修复”，要求提供：

- 对应文件或复现方式；
- 为什么影响当前需求；
- 最小修复范围；
- 应补充的测试。

不要把整份报告直接交回实现者，要求“全部优化”。否则一个原本很小的修复，可能在第二轮膨胀成新的重构项目。

可选改进可以记录下来，不必假装每条建议都必须在当前 Pull Request 中完成。

---

## 9. 什么时候该让 AI 停下来

出现下面情况时，应暂停自动修改：

- 同一个错误连续修复仍然失败；
- 修改范围不断向外扩张；
- Agent 开始猜测没有读取的代码；
- 需要管理员权限、生产访问或不可逆数据迁移；
- 测试环境本身不可靠；
- 需求之间出现冲突；
- diff 已经大到人无法认真审查。

暂停不是认输，而是重新确认需求、环境和证据。Agent 连续撞墙时，继续给它更多权限，通常只会让墙和项目一起受伤。

## 10. Git 怎样配合复杂任务

较大的任务适合放在独立分支中，并按可以解释的批次提交。例如：

```text
test: reproduce request validation bug
fix: validate required request fields
test: cover legacy client payload
 docs: document validation errors
```

实际项目可以使用中文提交信息，也可以遵循项目已有规范。重点不是固定前缀，而是让每个提交回答“这一批为什么存在”。

避免两个极端：

- 把所有内容压成一个巨大提交，没人能看懂；
- 每改一行就提交一次，产生几十个没有独立意义的碎片。

提交前至少检查：

```bash
git status --short
git diff --cached --name-status
git diff --cached
```

复杂任务最终是否创建 Pull Request，取决于仓库协作方式；但修改范围较大、风险较高时，Pull Request 通常更方便复核和保留讨论记录。

## 11. 一份可以直接使用的任务模板

```text
任务目标：

非目标：

验收标准：

不能破坏的现有行为：

允许修改的文件：

禁止操作：
- 不提交或推送；
- 不安装依赖；
- 不访问生产环境；
- 不修改系统配置；

当前批次：

需要运行的测试：

完成后请汇报：
1. 修改文件；
2. 测试命令和退出状态；
3. 已验证内容；
4. 未验证内容；
5. 风险和回滚方式。
```

不需要每次把所有空格都填满。这个模板的作用是提醒你：任务边界、验证方法和停止条件，不能只存在脑子里。

---

## 12. 怎样判断这次任务可以收尾

通常应能回答下面这些问题：

- 要解决的问题和非目标是什么；
- 修改依据来自哪些文件；
- 为什么选择当前方案；
- 每一批具体改了什么；
- 运行了哪些测试；
- 当前 diff 是否经过人工查看；
- 独立复核发现了什么；
- 怎样回滚；
- 还有哪些风险没有验证。

不一定每项都完美，也不一定每个项目都需要正式文档。但缺少的部分要明确写出来，不能用一句“应该没问题”代替。

复杂任务真正需要的，不是让 AI 一次写更多代码，而是让每一步都能看懂、能验证，也能在走错时退回来。
