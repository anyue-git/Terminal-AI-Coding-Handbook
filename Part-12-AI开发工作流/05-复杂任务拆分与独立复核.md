# 05 复杂任务拆分与独立复核

> 最近核对：2026-07-30

改一处文案、补一个明确测试，通常可以直接完成。复杂任务的难点不一定是文件多，而是多个决定互相依赖：接口怎样变化、旧行为是否保留、数据如何迁移、远程环境能否验证、失败后是否能恢复。把这些问题塞进一条长 Prompt，Agent 往往会在尚未确认需求时开始实现，最后留下一个难以判断对错的巨大 diff。

通用闭环已经在上一章说明。本章只讨论复杂任务额外需要的三样东西：决策边界、证据账本和独立复核。

## 1. 先判断哪些决定还不能交给实现

出现公开接口或配置格式变化、数据库和网络操作、权限与敏感信息、旧版本兼容、远程主机、GPU、Docker Volume、生产服务，或者需求本身明显含糊时，第一轮应停在分析阶段。复杂度来自错误成本和恢复难度；一行防火墙规则可能比修改十个本地测试文件更复杂。

开始前把需求整理成目标、非目标、可观察行为、验收标准、兼容约束和待确认问题。例如：

```text
目标：拒绝缺少必填字段的 API 请求。
非目标：不重构整个请求处理模块。
兼容约束：旧客户端已有可选字段继续有效。
验收：新增校验测试通过，旧兼容测试不回归。
待确认：无效请求应返回哪个错误码。
```

错误码尚未确认时，实现不能替产品规则作决定。类似的未知项应明确留给人，而不是让 Agent 从常见做法中补齐。

## 2. 项目地图和证据账本要随着任务更新

只读调查需要找到入口、实现、配置、数据模型、调用方、测试和相关项目规则。每条结论区分为已确认事实、合理推测和仍缺证据。现实地图不求覆盖整个仓库，只要足以解释本次行为从哪里进入、在哪里决定、怎样验证。

长任务可以维护一份很短的证据账本：

```text
已确认事实：
未确认假设：
人工决定：
当前批次：
实际修改：
测试证据：
未验证：
新发现风险：
```

账本不是周报。它的作用是防止早期假设在后续阶段被当成事实。新证据推翻旧结论时，直接改掉对应条目，并说明因此需要重排哪个批次。

方案比较也不必机械凑三套。推荐方案需要说明修改范围、兼容影响、验证方法和回滚方式，并解释为什么当前不采用更大的重构。没有足够证据时，“暂缓实现并补信息”也是有效方案。

## 3. 用批次预算限制任务膨胀

复杂任务可以预先约定实施预算，例如最多四个批次、每批最多改三个文件，每批都有一条目标测试。数字不是质量标准，只是让范围扩大变得可见。常见顺序是失败测试、核心实现、调用方或配置、最后再处理必要文档。

每个批次都应有进入条件和退出条件。核心实现只有在需求规则和回归测试已经确认后才开始；结束时查看当前差异并运行与本批最相关的测试：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

测试记录要与当前分支、当前机器和当前代码对应。另一分支昨天通过的结果，不能证明现在的修改已经通过。每批至少记录：

```text
测试命令：
运行环境：
退出状态：
通过 / 失败 / 跳过数量：
关键警告：
覆盖本批哪些行为：
仍未覆盖什么：
```

失败时先判断是本批引入、原有问题、环境依赖、测试不稳定还是需求冲突，再决定是否修改；通过削弱断言、增加无理由的 skip 或扩大异常捕获，只会把错误藏起来。

## 4. 独立复核需要新的阅读路径

实施者已经接受了一套问题解释，很容易在复核时继续沿用同样假设。独立复核可以使用新会话或另一工具，只提供原始需求、当前 diff、测试结果、相关文件和已知环境限制，不先附上“已经完整解决”的结论。

```text
只读审查当前修改，不改文件。
检查需求覆盖、范围外修改、逻辑与兼容性、错误处理、安全问题和测试缺口。
每条发现引用文件与位置，并分为：
- 已确认问题；
- 需要进一步验证；
- 无法在当前环境确认；
- 可选改进。
```

复核意见仍要由人判断。报告中的“可能问题”不能直接变成自动修改任务；已确认问题则重新进入一个小批次，只处理对应差异并运行目标测试。

## 5. 多 Agent 用职责和 Worktree 分开

较清楚的三方结构是：Agent A 只读调查和比较方案，Agent B 在任务分支实施，Agent C 只读复核，人负责产品决定、风险批准、整合和提交。多个 Agent 同时写同一未提交工作区，会让测试和 diff 失去明确归属。

需要比较两个实现时，建立独立 Worktree：

```bash
git worktree add ../project-option-a -b experiment/option-a
git worktree add ../project-option-b -b experiment/option-b
```

两边使用相同需求和测试。Worktree 隔离代码目录，却通常共享 HOME、凭据、网络、Docker、数据库和数据；它防止文件覆盖，不提供完整安全隔离。

方案比较结束后，由人选择要保留的实现并在集成分支重新验证。不要把两个 Agent 的总结并排放在一起就当作完成比较，真正需要比较的是代码、测试、性能数据和兼容结果。

## 6. 知道什么时候暂停

同一个问题反复修复仍失败、文件范围不断扩大、Agent 开始猜测未读取代码、测试环境不可靠、需求互相冲突、需要管理员或生产权限、发现凭据、diff 已经无法认真阅读，或者任务超过约定时间和预算时，都应该暂停。

暂停时保留当前状态：

```bash
git status --short
git diff --stat
git diff
```

同时保存错误日志、运行环境和尚未解决的问题。重新规划时从这些证据继续，而不是要求 Agent“换个思路全部重做”。

最终验收要回答几个具体问题：目标和非目标是否仍然成立；实际 diff 是否符合批准方案；每个批次是否有当前测试证据；兼容、迁移和回滚是否可执行；复核问题是否已经分类处理；未验证内容有没有被误写成已完成；是否混入凭据、大型生成物或范围外文件。复杂任务之所以需要拆分，是因为它包含更多相互依赖的决定；拆分的价值，是让这些决定逐个留下证据和退路。
