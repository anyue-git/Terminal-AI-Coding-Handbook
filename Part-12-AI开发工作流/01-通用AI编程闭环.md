# 01 通用 AI 编程闭环

> 最近核对：2026-07-30
>
> 本章不依赖某一个模型或客户端。Claude Code、Codex CLI、Grok Build 以及其他能读取文件、修改代码和执行命令的 Agent，都可以使用同一套工作闭环。

AI 编程真正需要管理的，不是“模型有没有说完成”，而是需求、代码、命令、测试、差异和最终提交能不能互相对上。一个可靠任务通常经过：

```text
定义完成标准
→ 建立现实基线
→ 只读调查
→ 选择方案
→ 小批实施
→ 证据验证
→ 独立复核与人工提交
```

这里的闭环不等于让 Agent 无人监督地从头跑到尾。恰恰相反，每个阶段都应产生能够检查的输出；方向错误时，应当能退回上一阶段，而不是继续叠加修改。

本章使用一个贯穿案例：

> 修复文本解析器把制表符当作普通字符，导致列切分错误的问题，并补充回归测试。

## 1. 第一阶段：把“完成”写成可以验收的结果

下面这句不够清楚：

```text
帮我优化一下解析器。
```

“优化”可能被理解为修 Bug、提高性能、重构目录、调整接口或全部一起做。更可执行的任务单是：

```text
目标：
修复解析器读取包含制表符的输入时列切分错误的问题。

预期行为：
制表符应按照现有空白分隔规则处理，不改变逗号、空格和空行的既有行为。

允许修改：
- src/parser.py
- tests/test_parser.py

禁止修改：
- 依赖和锁文件；
- CI；
- 其他解析功能；
- Git 历史和远程仓库。

验收标准：
- 新增一个能在修改前稳定失败的回归测试；
- 修改后该测试通过；
- 现有解析器测试全部通过；
- Git diff 只包含允许文件；
- 不执行 git add、commit 或 push。
```

任务单至少回答六个问题：

1. 当前现象是什么；
2. 正确行为是什么；
3. 哪些内容允许改变；
4. 哪些内容明确不改变；
5. 用什么证据证明完成；
6. 哪些决定必须由人完成。

若需求本身仍有歧义，先把歧义列出来。不要要求 Agent 在缺少产品规则时自行“合理推断”，然后再把推断写进代码。

## 2. 第二阶段：建立现实基线

启动 Agent 前，先在 **当前项目根目录的 Shell** 中执行：

```bash
hostname
whoami
pwd
git branch --show-current
git status --short
git rev-parse --short HEAD
```

这组命令回答：

```text
在哪台机器
以哪个用户
位于哪个项目
当前是什么分支
工作区是否已有修改
源码基线是哪一个提交
```

如果项目已有测试，再运行最小基线：

```bash
python -m pytest tests/test_parser.py -q
```

记录真实结果，例如：

```text
机器：MacBook
目录：/Users/me/Projects/parser-demo
分支：main
HEAD：4a1b29f
工作区：干净
基线测试：17 passed，退出状态 0
```

基线很重要。修改后某项测试失败时，只有知道它修改前是否通过，才能判断是不是本次任务引入。

已有未提交修改时，不要假设新建分支就能自动隔离。未提交修改仍属于同一个工作区，会跟着分支切换。先判断它们是否属于当前任务；必要时创建独立 Worktree、提交已有工作，或暂停当前任务。

## 3. 第三阶段：只读调查真实项目

第一轮让 Agent 只调查，不修改：

```text
当前阶段只读。不要修改文件、安装依赖、执行 Git 写操作或访问外部服务。

请找出：
1. 解析器真实入口；
2. 制表符和其他空白字符的处理逻辑；
3. 现有相关测试；
4. 调用该解析器的主要入口；
5. 当前行为是否能从代码或测试中确认；
6. 建议的最小修改范围。

每个结论给出文件路径和相关符号。
把内容分成：
- 已确认事实；
- 合理推测；
- 尚缺证据。
```

一个合格调查结果应类似：

```text
已确认：
src/parser.py 的 split_fields() 只按普通空格切分。

tests/test_parser.py 覆盖逗号和连续空格，但没有制表符用例。

合理推测：
调用方可能期望所有空白字符都等价，但尚未找到公开接口文档。

尚缺证据：
是否应保留字段内部制表符，需要产品规则或历史测试确认。
```

“通常项目会这样设计”不属于当前仓库证据。文件路径、函数、测试和可复现输入才是证据。

## 4. 第四阶段：比较方案，而不是直接接受第一种写法

简单 Bug 也可能有多个方案：

```text
方案 A：只修正现有分隔逻辑
→ 修改最小，回归风险低

方案 B：重写整个词法解析层
→ 结构可能更统一，但范围明显扩大

方案 C：先补测试和日志，不立即修改
→ 适合需求仍不确定
```

要求 Agent 给出：

```text
推荐方案；
为什么选它；
为什么不选更大的方案；
预计修改文件；
验证命令；
已知风险；
回滚方法。
```

本例更可能选择方案 A，因为当前目标只涉及一个明确行为。重构不是奖励项目，而是另一项需要独立验收的工作。

计划应具体到文件和验证方法：

```text
1. 在 tests/test_parser.py 增加制表符回归测试；
2. 运行目标测试，确认修改前因为目标问题失败；
3. 在 src/parser.py 做最小修复；
4. 重新运行目标测试；
5. 运行完整解析器测试；
6. 查看 Git diff；
7. 使用新会话做只读复核。
```

## 5. 第五阶段：创建隔离的 Git 起点

确认工作区状态后，在 **项目根目录** 创建任务分支：

```bash
git switch -c fix/parser-tab-handling
```

再次确认：

```bash
git branch --show-current
git status --short
git rev-parse --short HEAD
```

分支名描述任务，不描述工具：

```text
fix/parser-tab-handling
```

比：

```text
claude-test-final-3
```

更容易在未来理解。

Git 分支主要隔离已跟踪源码历史。它不能自动恢复：

- 数据库写入；
- Docker Volume；
- 远程服务器操作；
- 项目外文件；
- 已上传到外部服务的数据；
- 未保存的训练状态。

高影响任务还需要备份、dry run、checkpoint 或独立测试环境。

## 6. 第六阶段：先产生能够证明问题的失败测试

给 Agent 的第一批实施任务：

```text
这次只修改 tests/test_parser.py。

增加一个能够稳定复现制表符列切分错误的最小回归测试。
不要修改生产代码，不要降低现有断言强度。

运行该测试并汇报：
- 测试名称；
- 测试输入；
- 预期行为；
- 执行命令；
- 退出状态；
- 关键失败信息；
- 失败是否确实来自目标问题。
```

测试失败不自动证明测试正确。下面这些失败都不算有效复现：

```text
导入路径错误
依赖没有安装
测试数据文件不存在
语法错误
运行了错误解释器
```

有效证据应类似：

```text
命令：python -m pytest tests/test_parser.py::test_tab_delimited_fields -q
结果：1 failed，退出状态 1
失败原因：实际得到一个字段，预期得到三个字段
```

确认失败原因与需求一致后，再进入实现阶段。

## 7. 第七阶段：只做当前批次的最小实现

第二批任务：

```text
现在允许修改：
- src/parser.py
- tests/test_parser.py

只修复刚才回归测试覆盖的制表符行为。
不要重构其他解析逻辑，不要修改依赖、CI 或公开接口。

完成后依次运行：
1. 目标回归测试；
2. tests/test_parser.py；
3. 项目已有的相关静态检查。

不要执行 git add、commit 或 push。
```

一次只推进一个可验证批次。复杂任务可以拆成：

```text
失败测试
→ 核心实现
→ 调用方适配
→ 配置迁移
→ 文档
→ 清理旧代码
```

每批结束后都要检查差异和测试。不要等十几个文件全部改变后，才第一次判断方向是否正确。

## 8. 测试报告必须能够被复核

“测试通过”至少要附带：

```text
执行机器
项目目录
解释器或运行环境
完整测试命令
退出状态
通过、失败、跳过数量
重要警告
未运行的测试
环境限制
```

例如：

```text
机器：macOS arm64
解释器：/Users/me/Projects/parser-demo/.venv/bin/python
命令：python -m pytest tests/test_parser.py -q
结果：18 passed，退出状态 0
未运行：完整仓库集成测试
限制：未在 Ubuntu 上验证
```

测试范围通常由小到大：

```bash
python -m pytest \
  tests/test_parser.py::test_tab_delimited_fields -q

python -m pytest tests/test_parser.py -q

python -m pytest -q
```

只有实际运行过的部分才能写成已验证。阅读代码认为“应该没问题”属于分析结论，不是测试结果。

## 9. Agent 交卷后，用 Git 查看现场

在 Shell 中运行：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

检查：

- 是否只修改允许文件；
- 是否发生意外删除或重命名；
- 是否出现无关格式化；
- 是否改变依赖或锁文件；
- 是否留下调试输出、缓存或日志；
- 测试是否被删除、跳过或削弱；
- 是否加入真实路径、凭据或内部地址；
- 实现是否真的对应原始需求。

Agent 的总结是它对修改的解释，Git diff 才是工作区真实状态。

需要检查暂存区时使用：

```bash
git diff --cached --name-status
git diff --cached
```

需要比较任务分支与 `main`：

```bash
git diff main...HEAD --stat
git diff main...HEAD
```

## 10. 建立一份证据账本

中型以上任务可以在任务记录中维护：

```text
需求：
- 制表符按空白分隔
- 其他解析行为不变

基线：
- HEAD 4a1b29f
- 17 tests passed

已确认事实：
- split_fields() 只处理普通空格

实际修改：
- src/parser.py
- tests/test_parser.py

验证：
- 新测试修改前失败
- 修改后 18 tests passed

未验证：
- 完整仓库集成测试
- Ubuntu 环境

风险：
- 可能影响字段内部制表符，需确认接口规则
```

这份记录不是为了增加文书工作，而是防止长会话里“已确认事实、猜测和旧结论”逐渐混在一起。

## 11. 用新会话做独立复核

实施者已经形成自己的解释，容易再次同意自己。修改完成后，使用新会话或另一个 Agent，只提供：

- 原始需求；
- 当前 diff；
- 测试命令和结果；
- 必要文件；
- 已知限制。

复核 Prompt：

```text
你没有参与本次实现，只负责只读审查。不要修改文件。

请根据原始需求、当前 Git diff 和测试结果检查：
1. 是否真正满足需求；
2. 是否存在范围外修改；
3. 是否遗漏边界条件、错误处理或兼容性；
4. 测试是否足以支持完成结论；
5. 是否有安全、性能或维护风险；
6. 哪些内容无法从现有证据确认。

每个发现给出文件和位置，并分类为：
- 已确认问题；
- 可能问题；
- 无法验证；
- 可选改进。
```

不要先把实施者的总结当作事实交给复核者。原始需求、代码差异和测试证据更重要。

## 12. 审查意见也要分类

独立复核可能包含真实问题、偏好和误报。处理前分成：

```text
必须修复
→ 有明确证据，影响需求或安全

需要确认
→ 取决于产品规则或环境

可选改进
→ 有价值，但不属于当前任务

误报
→ 与实际代码或需求不符
```

不要把整份复核报告交回实施者并要求“全部优化”。那会让一个小任务膨胀成无法审查的大重构。

## 13. 人工决定暂存、提交和推送

准备提交前确认：

- 原始需求已经满足；
- diff 已人工阅读；
- 关键测试已运行；
- 未验证部分已写明；
- 没有凭据、大型生成物或无关文件；
- 提交只包含一个清楚目的。

精确暂存：

```bash
git add src/parser.py tests/test_parser.py
```

检查：

```bash
git diff --cached --name-status
git diff --cached
```

提交：

```bash
git commit -m "fix: handle tab-delimited fields"
```

提交后再次验证：

```bash
git status
git show --stat --oneline HEAD
```

是否推送、创建 PR 或合并，是新的影响范围，不应仅因为代码生成结束而自动执行。

## 14. 明确停止条件

出现下面情况时，停止自动修改并退回调查阶段：

- 同一个错误连续修复仍失败；
- 修改文件数量不断扩大；
- Agent 开始猜测没有读取的代码；
- 测试结果互相矛盾；
- 需求之间发生冲突；
- 需要管理员权限、生产访问或不可逆迁移；
- 需要读取凭据或项目外敏感内容；
- diff 已大到无法认真审查；
- 自动化达到最大轮数、时间或预算。

暂停不是失败，而是保留证据后重新缩小问题。

## 15. 一份通用任务模板

```text
任务目标：

当前现象：

预期行为：

非目标：

允许修改：

禁止修改：

运行环境：
- 主机：
- 工作目录：
- 分支：
- 基线提交：

验收标准：

第一阶段只读调查：
- 找到入口、实现、测试和调用方；
- 给出文件路径；
- 区分事实、推测和未知。

实施方式：
- 每次只完成一个可验证批次；
- 每批结束后报告修改文件、命令、退出状态和测试结果；
- 需要扩大范围、安装依赖、访问网络或提高权限时停止。

Git 边界：
- 不要 add、commit、push、reset、clean 或 rebase。

完成报告：
- 实际修改；
- 验证证据；
- 未验证部分；
- 风险；
- 建议下一步。
```

## 16. 闭环真正闭在哪里

任务完成时，下面这些内容应能一一对应：

```text
需求
→ 说明要改变什么行为

调查
→ 找到当前真实实现

计划
→ 限定文件、命令和风险

修改
→ Git diff 与计划一致

验证
→ 测试和检查支持完成结论

复核
→ 独立视角检查遗漏

提交
→ 记录人工确认后的版本
```

其中一环对不上，就返回前面重新确认。闭环的价值是让你始终知道：目前完成到哪里、凭什么相信结果、出现问题应该退回哪一步。
