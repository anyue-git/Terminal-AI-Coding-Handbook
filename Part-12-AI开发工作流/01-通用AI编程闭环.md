# 01 通用 AI 编程闭环

不同 AI 编程工具的按钮和命令不一样，但一项修改从开始到完成，通常都应该经历同一条路线：先弄清问题，再调查项目；修改后运行测试、检查差异，最后才决定是否提交。

这里的“闭环”，不是让 Agent 从头自动跑到尾，而是每一步都有结果可看，发现方向不对时也能停下来。

本章用一个小任务贯穿：

> 修复解析器无法正确处理制表符的问题，并补充测试。

---

## 1. 先把任务说成可以验收的话

“帮我优化一下解析器”太模糊。Agent 不知道你想修错误、提速，还是顺便重写整个模块。

更合适的任务描述是：

```text
目标：修复解析器读取包含制表符的输入时产生错误结果的问题。

允许修改：
- src/parser.py
- tests/test_parser.py

禁止修改：
- 依赖和锁文件；
- CI 配置；
- 其他解析功能。

验收方式：
- 新增一个能够复现问题的测试；
- 修复后新测试和现有解析器测试全部通过。

不要执行 git add、commit 或 push。
```

任务描述至少要回答：改什么、不改什么、怎样证明改好了，以及哪些决定必须由人确认。

---

## 2. 让 Agent 先读项目，不要刚进门就搬家具

第一轮只做调查：

```text
当前阶段只读，不要修改文件。

请找出：
1. 解析器入口；
2. 制表符相关处理逻辑；
3. 现有测试；
4. 可能受影响的调用方；
5. 建议修改的文件。

每个结论都给出文件路径，没有证据的内容标记为推测。
```

同时让它检查基本状态，或者自己在终端运行：

```bash
pwd
git status
git branch --show-current
```

这里要确认三件事：当前目录是不是项目、工作区是否已有未提交修改、当前分支是否适合做这项任务。

如果原本就有未提交内容，先弄清它们属于什么。新建分支不会自动把这些修改隔离掉；它们会跟着工作区一起过去。

---

## 3. 计划要具体到文件和验证方法

调查结束后，计划不需要写成长篇方案书，但至少要说明：

- 准备修改哪些文件；
- 每个文件为什么要改；
- 先写测试还是先改实现；
- 准备运行什么命令；
- 哪些行为可能受到影响；
- 哪些部分目前无法验证。

例如：

```text
1. 在 tests/test_parser.py 增加包含制表符的失败用例；
2. 运行该测试，确认它在修改前失败；
3. 在 src/parser.py 修正空白字符处理；
4. 重新运行目标测试；
5. 运行完整解析器测试；
6. 查看 Git diff，确认没有改变其他语法规则。
```

这份计划的价值不是“显得正式”，而是提前暴露方向错误。等十个文件都改完才发现理解错了，体验会比现在多问一句丰富得多。

---

## 4. 给任务一个清楚的 Git 起点

确认工作区状态后，可以创建任务分支：

```bash
git switch -c fix/parser-tab-handling
```

分支名写任务内容，不写模型名称。以后看到 `fix/parser-tab-handling`，还能知道它在修什么；看到 `ai-test-final-3`，通常只能感受到当时的人有点着急。

再次确认：

```bash
git status
git branch --show-current
```

Git 分支方便比较和回退已跟踪源码，但它不是万能备份。数据库、未跟踪文件、远程服务和项目外的数据，需要另外保护。

---

## 5. 先让测试复现问题，再修改实现

对于能够测试的问题，优先让 Agent 先补失败用例：

```text
现在只修改 tests/test_parser.py。
增加一个能够复现制表符问题的最小测试，不要修改生产代码。
完成后运行该测试，并报告命令、退出状态和失败原因。
```

测试在修复前失败，说明它确实碰到了问题。接着再允许修改实现：

```text
现在允许修改 src/parser.py。
只修复刚才测试覆盖的问题，不重构其他解析逻辑。
完成后重新运行目标测试和现有解析器测试。
```

复杂任务不一定都能严格测试先行，但“一次只完成一个能验证的小步骤”仍然适用。这样某一步失败时，不需要在整片修改中寻找是哪一铲子挖歪了。

---

## 6. “测试通过”必须附带真实信息

Agent 的总结里至少应该包含：

```text
测试命令：python -m pytest tests/test_parser.py
结果：18 passed，退出状态 0
未运行：完整项目测试
环境限制：仅在当前 macOS Python 环境验证
```

根据项目情况，可以继续运行：

```bash
python -m pytest tests/test_parser.py
python -m pytest
```

测试范围应从最相关的用例逐渐扩大。不是每个小改动都必须立刻跑完整仓库测试，但没跑的部分要明确写出来。

“代码看起来正确”是阅读判断；“测试通过”是带命令和结果的证据。两者不能互相冒充。

---

## 7. Agent 交卷后，真正的检查才开始

运行：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

重点查看：

- 是否只修改了允许的文件；
- 有没有意外删除或大范围格式化；
- 是否留下调试输出；
- 是否加入真实路径、Token 或其他敏感信息；
- 是否改动依赖或锁文件；
- 测试有没有被削弱；
- 注释和代码是否一致。

`git diff --stat` 能快速看出改动规模，`git diff` 才能看到具体内容。前者像账单总额，后者才是消费明细；只看总额，很难知道钱花在哪了。

可以让 Agent 做一次只读自查：

```text
现在停止修改，只审查当前 Git diff。
检查功能错误、边界条件、不必要修改、安全问题和测试缺口。
把已确认问题、可能问题和无法验证的内容分开。
```

但同一会话容易沿用自己的原始假设。修改较大时，使用新的会话或另一个 Agent 独立复核更可靠。

---

## 8. 提交是人的决定，不是流程的自动结尾

准备提交前，至少确认：

- 修改范围正确；
- 需要运行的测试已经运行；
- diff 已经人工阅读；
- 没有敏感文件或意外大文件；
- 提交内容只围绕一个清楚的任务。

只暂存确认过的文件：

```bash
git add src/parser.py tests/test_parser.py
```

检查暂存区：

```bash
git diff --cached --name-status
git diff --cached
```

确认后再提交：

```bash
git commit -m "修复解析器的制表符处理"
```

默认不要让 Agent 自动 push。提交已经会改变本地历史，push 还会影响远程仓库，两者不应因为“前面测试绿了”就自动打包批准。

---

## 9. 连续修不好时，不要继续往上叠补丁

出现下面情况时先停：

- 同一个错误连续修改仍然失败；
- 修改文件越来越多；
- Agent 开始猜测没有读取的代码；
- 测试结果互相矛盾；
- 需要管理员权限或生产环境访问；
- diff 已经大到自己看不懂。

此时先保存错误信息，重新缩小问题：

```bash
git status --short
git diff --stat
git diff
```

然后回到只读调查，确认最小复现和真实调用链。不断在错误方向上添加补丁，通常不会突然拼出正确答案，只会得到一个更有层次感的错误。

---

## 10. 一份可以直接改写的任务模板

```text
任务目标：

非目标：

允许修改：

禁止修改：

验收方式：

第一阶段只读分析：
- 找到相关入口、实现和测试；
- 给出文件路径；
- 区分事实和推测。

确认计划后再分批修改。每一批结束后：
- 运行相关测试；
- 报告命令和退出状态；
- 列出修改文件；
- 说明未验证部分。

不要执行 git add、commit 或 push。
```

模板不是每次都要逐字复制。它只是提醒你，任务范围、验证方法和停止条件不能全部留在脑子里。

---

## 11. 闭环到底闭在哪里

一项修改真正完成，不是因为 Agent 输出了“任务完成”，而是因为下面几件事能够互相对上：

- 需求说明了要解决什么；
- 项目调查找到了真实实现；
- 计划限定了修改范围；
- diff 显示实际改动与计划一致；
- 测试为关键行为提供证据；
- 人工或独立复核检查了遗漏；
- Git 提交记录了最终确认的版本。

其中任何一环对不上，就回到前面重新确认。闭环的意义不是让过程显得复杂，而是让你始终知道：现在做到了哪一步，凭什么认为它正确，出错后应该退回哪里。
