# 01 通用 AI 编程闭环

> 最近核对：2026-07-30
>
> 本章不依赖某一个模型或客户端。Claude Code、Codex CLI、Grok Build 以及其他能够读取文件、修改代码和执行命令的 Agent，都可以使用同一套方法。

AI 编程任务是否完成，最终取决于需求、代码变化、测试和提交能否互相对应。一个实用的工作闭环可以概括为：

```text
写清预期行为和验收标准
→ 记录当前项目基线
→ 只读调查真实实现
→ 选择范围合适的方案
→ 分批修改并运行测试
→ 阅读 Git diff 和验证证据
→ 独立复核后由人决定提交
```

下面用一个贯穿案例说明：文本解析器没有把制表符视为分隔符，需要补充回归测试并做最小修复。

## 1. 让任务具有可观察的完成状态

“帮我优化一下解析器”可能指修 Bug、提高性能、重构目录或改变接口，无法直接验收。开始工作前，把需求缩成一段能够和代码、测试对应的说明：

```text
目标行为：
解析器读取包含制表符的输入时，应沿用现有空白分隔规则。
逗号、普通空格和空行的既有行为保持不变。

允许修改：
- src/parser.py
- tests/test_parser.py

完成证据：
- 新测试在修复前稳定失败；
- 修复后解析器相关测试通过；
- Git diff 只包含允许文件。

仍由人决定：
- Git 暂存、提交、推送和合并。
```

需求中尚未确定的产品规则应单独列出。例如“字段内部的制表符是否也要拆分”如果没有接口文档或历史测试，就还不是实现事实。

进入项目根目录后记录现实基线：

```bash
hostname
whoami
pwd
git branch --show-current
git status --short
git rev-parse --short HEAD
python -m pytest tests/test_parser.py -q
```

记录真实结果，而不是写一句“环境正常”：

```text
机器：macOS arm64
目录：/Users/me/Projects/parser-demo
分支：main
HEAD：4a1b29f
工作区：干净
基线测试：17 passed，退出状态 0
```

已有未提交修改时，新建分支不会自动隔离它们。需要先弄清旧修改是否属于当前任务，或者使用独立 Worktree、保存已有工作后再开始。

## 2. 调查项目，并选择与问题相称的方案

第一轮让 Agent 只读查找入口、实现、测试和调用方：

```text
当前阶段只读，不修改文件、安装依赖或执行 Git 写操作。

请查明：
1. 解析器入口和制表符处理逻辑；
2. 现有相关测试与主要调用方；
3. 当前行为能够从哪些文件或测试确认；
4. 最小修改范围。

每个结论引用文件与符号，并区分已确认事实、合理推测和未知项。
```

合格的结果应指出具体文件和函数，例如 `src/parser.py` 的 `split_fields()` 只处理普通空格，`tests/test_parser.py` 尚无制表符用例。诸如“多数解析器都这样设计”只能算一般经验，不能替代当前仓库证据。

有了项目地图后，再比较方案。这个问题可能有三条路线：修改现有分隔逻辑；重写词法解析层；或者先补测试和日志，等待产品规则确认。任务只涉及一个明确行为时，第一条通常范围最小；大重构需要自己的需求和验收，不应作为修复 Bug 的附赠工程。

计划最终要落到文件和验证：在哪个测试文件复现，哪个实现文件修改，依次运行哪些测试，哪些风险仍未确认。计划无法指向具体代码和证据时，说明调查还没有结束。

## 3. 在清楚的起点上分批实施

工作区状态确认后建立任务分支：

```bash
git switch -c fix/parser-tab-handling
git branch --show-current
git status --short
git rev-parse --short HEAD
```

第一批只增加回归测试：

```text
只修改 tests/test_parser.py。
增加一个稳定复现制表符切分错误的最小测试。
运行该测试，并报告完整命令、退出状态和关键失败信息。
完成后停止。
```

测试失败还要看原因。导入错误、缺少依赖、错误解释器或测试数据不存在，都没有证明目标 Bug。有效的失败证据应接近：

```text
命令：python -m pytest tests/test_parser.py::test_tab_delimited_fields -q
结果：1 failed，退出状态 1
原因：实际得到一个字段，预期得到三个字段
```

确认测试准确后，再允许修改实现：

```text
允许修改 src/parser.py 和 tests/test_parser.py。
只处理刚才测试覆盖的制表符行为，保持其他解析逻辑和公开接口不变。
完成后运行目标测试、整个解析器测试和项目现有静态检查。
不要执行 Git 暂存、提交或推送。
```

实现完成后由小到大运行：

```bash
python -m pytest \
  tests/test_parser.py::test_tab_delimited_fields -q

python -m pytest tests/test_parser.py -q
python -m pytest -q
```

复杂任务同样可以拆成失败测试、核心实现、调用方适配、配置迁移和文档等批次。每批都要有明确结束状态；等十几个文件一起变化后再第一次看 diff，会让错误方向更难撤回。

## 4. 用工作区和测试证据判断结果

Agent 的总结只是解释，工作区状态才说明实际发生了什么：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

检查允许文件之外是否有变化，是否发生意外删除、重命名或大范围格式化，依赖和锁文件是否被改动，测试是否被跳过或削弱，以及是否留下日志、缓存、真实路径或凭据。

测试记录至少包含执行机器、解释器或环境、完整命令、退出状态、通过与失败数量以及未运行部分：

```text
机器：macOS arm64
解释器：/Users/me/Projects/parser-demo/.venv/bin/python
命令：python -m pytest tests/test_parser.py -q
结果：18 passed，退出状态 0
未运行：完整集成测试
限制：尚未在 Ubuntu 验证
```

中型以上任务可以维护一份简短证据账本：需求、基线、已确认事实、实际修改、测试结果、未验证内容和新发现风险。它不需要写成长报告，作用是让后续会话知道哪些结论有证据，哪些仍是猜测。

实现者已经形成了一套解释，最终复核适合交给新会话或另一 Agent。给复核者原始需求、当前 diff、测试结果、相关文件和环境限制，请它只读查找范围外修改、边界遗漏、兼容问题和测试缺口。每条意见仍需引用代码或证据；“可能问题”不能直接批量转成自动修复。

可复制的调查、实施、复核和交接 Prompt 统一放在[通用 Prompt 模板库](02-通用Prompt模板库.md)，本章不再重复一整套表单。

## 5. 设定停止条件，并把 Git 写操作留到最后

出现以下情况时，继续让 Agent 自动修改通常只会扩大现场：同一错误反复修复仍失败；文件范围持续增长；Agent 开始猜测未读取的代码；测试结果互相矛盾；需求发生冲突；任务需要管理员或生产权限；发现凭据；diff 已经大到无法认真阅读；或者自动化达到时间、轮数和预算上限。

暂停时保留当前 diff、错误日志和测试结果，回到调查或缩小问题。暂停不是丢弃进度，而是避免把不确定性继续写入代码。

准备提交前，人工确认需求与 diff 一致、关键测试已运行、未验证内容已写明，且候选提交没有无关文件。随后精确暂存：

```bash
git add src/parser.py tests/test_parser.py
git diff --cached --name-status
git diff --cached
```

确认后提交并查看结果：

```bash
git commit -m "fix: handle tab-delimited fields"
git status
git show --stat --oneline HEAD
```

推送、创建 PR 和合并会扩大影响范围，应在当前提交已经通过复核后单独决定。完整闭环最终要做到：需求描述的行为能在代码中找到，调查结论能引用真实文件，计划与 diff 一致，测试支持完成结论，复核意见得到分类处理，提交记录的是人工确认后的版本。
