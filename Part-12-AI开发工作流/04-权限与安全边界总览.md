# 04 权限与安全边界总览

> 最近核对：2026-07-30

AI CLI 能读取文件、执行命令、访问网络、调用扩展，也可能通过 Docker、SSH 或云工具影响项目之外的资源。判断一次任务是否安全，不能只看客户端名称或某个“安全模式”，而要把几层能力放在一起看：

```text
任务指令：希望 Agent 做什么
审批策略：哪些动作必须先问人
Sandbox 与规则：进程技术上能够访问哪里
系统与外部工具：当前用户、Docker、SSH、MCP 实际拥有什么能力
恢复手段：源码、数据和外部操作能否撤销
```

某一层很宽，其他层写得再谨慎，最终影响范围仍可能很大。本章建立共同模型；Claude Code、Codex CLI 和 Grok Build 的具体模式与参数由各自专章说明。

## 1. Prompt、审批与 Sandbox 各管一层

Prompt 中写“只修改 `src/parser.py`”是在描述任务。审批策略决定执行命令前是否询问，Sandbox 则决定进程即使获准后能接触哪些路径、网络或系统资源。三者不能互相替代。

例如，自动批准 `pytest` 不表示测试只能读取项目目录；测试代码仍可能启动 Docker、联网或写数据库。反过来，Sandbox 限制了工作区，也不表示工作区内的每项删除和覆盖都符合任务。较稳妥的组合是：任务范围写清楚，客户端只开放必要工具和路径，操作系统用户本身也不拥有无关高权限。

启动 Agent 前先确认现场：

```bash
hostname
whoami
pwd
git status --short
```

项目根目录通常是合适入口。家目录、Downloads 或包含多个仓库的父目录，会让相对路径和可读取内容都变得模糊。读取范围可以大于写入范围，例如 Agent 需要查看 `src/` 和 `tests/`，但本次只允许修改两个文件。

任务结束后查看真实变化：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
find . -type f -size +50M -print
```

普通 diff 主要覆盖已跟踪文件；未跟踪文件、大模型、日志和缓存还需要从状态与文件清单中检查。

## 2. Shell、网络和凭据要看实际执行上下文

批准一条 Shell 命令时，先弄清它在哪台机器、以哪个用户、在什么目录运行，变量展开后指向哪里，以及会改变文件、服务、网络还是数据。`sudo`、递归删除、Git 历史改写、系统服务、数据库迁移、Docker Volume 删除和生产操作，不适合成为普通自动批准项。

网络权限既包括下载，也包括上传。读取公开文档、从锁文件安装依赖、把日志发送到第三方和上传整个私有仓库，风险完全不同。使用企业 Gateway、CC Switch 或 Cockpit Tools 时，还要确认请求最终经过哪个 Provider、Base URL 和日志系统。

程序需要使用凭据，不代表模型需要看到凭据正文。任务可以只说明变量名：

```text
程序从 MY_API_TOKEN 环境变量读取凭据。
不要读取、打印、记录或修改它的真实值。
```

检查变量是否存在时，避免输出内容：

```bash
if [ -n "${MY_API_TOKEN:-}" ]; then
  echo 'MY_API_TOKEN is set'
else
  echo 'MY_API_TOKEN is not set'
fi
```

API Key、OAuth/Refresh Token、Cookie、SSH 私钥、数据库密码、云凭据和完整 `env` 输出都不应进入对话、日志或 diff。秘密一旦泄露，需要在对应平台撤销或轮换；删除本地文件无法收回已经发送出去的值。

## 3. Git、Worktree 和容器的保护范围有限

Git 擅长恢复已跟踪源码和比较提交，却不能自动恢复数据库、Docker Volume、数据集、模型、远程机器数据、已经上传到外部服务的内容或中断的训练。源码依赖 Git，数据和运行状态依赖备份与 checkpoint，权限控制则负责在操作发生前缩小范围。

Worktree 可以防止两个 Agent 同时编辑同一目录，但通常仍共享 HOME、环境变量、SSH 密钥、Docker daemon、网络、数据和部分仓库元数据。它适合方案隔离，不适合运行来源不明的高权限代码。

容器也要看具体配置。下面这些设置会明显扩大宿主影响：

- `--privileged`；
- 挂载 Docker Socket；
- 挂载整个 `$HOME`、`~/.ssh` 或云凭据目录；
- host network 或共享宿主设备；
- 容器内 root 写入 Bind Mount。

运行 Agent 生成的代码前，应检查挂载、网络、用户和设备权限。容器能方便复现环境，但不会自动把不可信任务变成安全任务。

## 4. 远程机器与扩展会把能力链拉长

在 Ubuntu GPU 主机启动 Agent 时，先确认主机和显卡现场：

```bash
hostname
whoami
pwd
git status --short
nvidia-smi
```

训练代码修改与系统管理应拆开。普通项目任务不需要同时获得 SSH、防火墙、Tailscale、驱动、系统服务、其他 GPU 进程和整个 `datasets`、`models`、`runs` 目录的控制权。只有一条 SSH 连接时，修改网络和远程登录配置尤其危险，因为操作失败可能连同修复通道一起关闭。

MCP、Hooks、Plugins 和 Skills 会增加自动命令、外部服务、可读取目录和日志。启用前需要知道来源、作用域、读写工具、网络目标、凭据来源、自动执行时机和卸载方法。仓库中的扩展配置可能随项目一起加载，因此克隆陌生项目后，不应在尚未阅读配置时直接授予高权限。

## 5. 高影响操作使用变更卡片

自动批准适合读取当前项目、修改明确文件、运行固定测试和生成报告。命令影响较大或无法一眼判断时，让 Agent 先填写一张变更卡片：

```text
主机与用户：
工作目录：
完整命令：
读取内容：
修改内容：
网络目标：
需要权限：
可能中断：
备份或 dry run：
成功怎样验证：
失败怎样恢复：
```

这张卡片的作用是暴露隐含影响，不是增加审批仪式。命令的目标、恢复和验证仍说不清时，就不应执行。基础设施任务还应保留第二条 SSH 会话或本机控制台，把不可逆步骤留给单独的人工确认。

独立复核通常只需要原始需求、相关文件、Git diff 和测试结果，不需要写权限、生产凭据或系统管理能力。安全检查结束时，除了 diff，还应查看新大文件、日志中的秘密、后台进程、容器与端口、远程服务状态、API 用量和临时凭据。权限控制不是启动前选择一次模式，而是随着任务从调查进入修改、测试和远程操作不断重新确认范围。
