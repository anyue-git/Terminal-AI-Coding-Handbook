# 04 权限与安全边界总览

AI 编程工具不只是聊天框。它可以读文件、改代码、运行命令，有些还能访问网络或调用外部工具。

这也是它好用的原因：你不用把每个文件手工复制过去，它可以自己调查项目并完成修改。但同一套能力用错地方，也可能把一次错误判断变成真实的文件覆盖、依赖升级或远程操作。

所以，判断一个 AI CLI 是否“安全”，不能只看工具名字。更有用的问题是：它现在能碰哪些东西，执行前会不会询问，以及即使得到允许后有没有技术限制。

---

## 1. 先分清权限、审批和 Sandbox

这三个词经常挤在同一个设置页面里，但意思不同。

### 权限范围

权限范围决定工具**可以尝试做什么**，例如：

- 读取哪些目录；
- 修改哪些文件；
- 执行哪些 Shell 命令；
- 是否能访问网络；
- 是否能调用 MCP、Hook、浏览器或云服务。

### 审批

审批决定工具准备执行某个操作时，**要不要先问你**。

例如，它想运行测试，可以每次弹出确认；也可以对符合规则的命令自动放行。审批回答的是“这一步需不需要人工点头”。

### Sandbox

Sandbox（沙箱）是一层技术限制。即使你已经批准操作，它仍可能限制工具只能访问项目目录、不能联网，或不能写入系统路径。

可以把三者想成进办公楼：

```text
权限范围
→ 门禁卡允许去哪些楼层

审批
→ 每次进门是否要找你签字

Sandbox
→ 楼里实际有哪些门被锁住
```

签字不等于所有门都会打开；门禁卡范围很大，也不代表每次操作都会自动执行。不同工具的具体实现不同，但这个区分基本通用。

---

## 2. Agent 常见的五类能力

日常使用中，最常见的是：

1. 读取文件；
2. 创建、修改或删除文件；
3. 执行 Shell 命令；
4. 访问网络；
5. 调用外部工具或远程服务。

它们不是一项总开关。一个工具可能能读项目但不能写；能运行测试但不能联网；能修改当前工作区，却不能碰父目录。

看到权限请求时，不要只问“这个工具靠谱吗”，而要问：

> 当前这一步真的需要哪种能力？范围能不能再小一点？

---

## 3. 从正确目录启动，先管住读取范围

读取权限决定 Agent 能看到什么。源码本身通常不是问题，真正容易混进去的是项目外的内容，例如：

- 主目录中的个人文件；
- `.env` 和其他环境配置；
- SSH 或云平台凭据；
- 未纳入项目的商业资料；
- 浏览器会话、聊天记录和下载文件。

启动 AI CLI 前先检查：

```bash
pwd
ls -la
git status
```

尽量在项目根目录启动，不要在 `~`、桌面根目录或装着许多无关项目的父目录中直接运行。

“它只是读取，不会修改”不代表没有风险。敏感内容一旦进入上下文，后续摘要、日志或工具调用就可能继续带着它走。钥匙不一定被偷走才算泄露，把钥匙照片发进群里也不太理想。

---

## 4. 写入范围要具体到文件或目录

写入权限决定 Agent 能改什么。最容易失控的情况不是“它完全乱写”，而是任务边界太模糊，例如：

> 帮我把这个项目整理一下。

这句话可能被理解为改格式、重命名、删除旧文件、升级依赖，甚至重构目录。

更清楚的写法是：

```text
只允许修改：
- src/parser.py
- tests/test_parser.py

不要修改其他文件，不要删除未跟踪文件。
完成后列出全部修改路径。
```

复杂任务最好放在独立 Git 分支中。Agent 完成后检查：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

还要留意大文件、生成物和锁文件。有些改动只有一行代码，却顺手生成了几百 MB 缓存；Git diff 看起来很安静，磁盘已经开始有意见。

---

## 5. Shell 命令的风险由上下文决定

Agent 能执行命令后，就从“给建议”变成了“实际操作”。但不能只根据命令名称判断危险程度。

同一个命令的影响取决于：

- 当前目录；
- 参数和通配符；
- 变量展开后的真实路径；
- 当前用户；
- 目标主机；
- 是否使用管理员权限；
- 是否能撤销。

例如，删除临时测试目录和删除家目录中的数据，命令形式可能很像，后果完全不是一个级别。

下面这些操作不适合在普通自动批准模式下随意执行：

- 删除或覆盖大量文件；
- `sudo` 和系统配置修改；
- 防火墙、SSH、驱动和系统服务修改；
- Git 历史重写与强制推送；
- 数据库迁移；
- 批量升级依赖；
- 对远程机器执行高影响命令。

批准前让 Agent 先说明：

```text
准备执行的完整命令是什么？
在哪台机器、哪个目录运行？
会修改哪些文件或服务？
失败后怎样恢复？
有没有只读检查或 dry run？
```

无法说明作用范围的命令，不要因为它看起来“很像常见命令”就直接通过。

---

## 6. 网络访问要搞清楚“下载什么”和“上传什么”

网络能力可以用于查文档、下载依赖、访问 API、连接远程主机，也可能上传日志和源码。

批准网络访问前至少确认：

- 目标域名是什么；
- 是下载还是上传；
- 发送的数据里是否包含源码、日志或凭据；
- 是否经过代理；
- 是否会产生费用；
- 是否会连接生产或内部服务。

查一个公开文档页面和把完整项目上传给第三方分析，不能因为都叫“联网”就放在同一档处理。

对于包管理器，还要区分“安装项目已有锁文件中的依赖”和“随意升级全部依赖”。前者范围通常更明确，后者可能改变大量版本和锁文件。

---

## 7. 凭据可以被使用，不代表必须被看见

常见敏感信息包括：

- API Key 和访问令牌；
- 数据库密码；
- SSH 私钥；
- 云平台凭据；
- 浏览器 Cookie 或会话信息；
- 内部服务地址。

Agent 通常只需要知道“凭据由环境变量提供”，不需要把真实值放进 Prompt。

例如，可以说：

```text
程序从 MY_API_TOKEN 环境变量读取凭据。
不要打印、读取或写入该变量的实际值。
```

不要把真实密钥粘贴进：

- Prompt；
- 仓库；
- 日志；
- 截图；
- Issue 或 Pull Request。

检查可疑文件是否已被 Git 跟踪：

```bash
git ls-files | grep -E '(^|/)(\.env|id_rsa|id_ed25519|credentials)'
```

这只是一个粗略筛查，不可能覆盖所有命名。更重要的是理解项目实际使用哪些凭据文件。

已经泄露的密钥不能只靠删除文件解决，还需要在对应平台撤销或轮换。

---

## 8. Git 能帮你看改动，但不是万能时光机

Git 很适合比较和恢复已跟踪的源码，但它未必能恢复：

- 未跟踪文件；
- 数据库内容；
- Docker Volume；
- 远程机器上的独立数据；
- 已上传到外部服务的内容；
- 被强制推送覆盖的远程历史。

所以三件事要分开：

```text
Git
→ 管源码版本和 diff

备份与 checkpoint
→ 管数据和运行状态恢复

权限控制
→ 限制误操作能够影响多大范围
```

有 Git 不等于可以随便执行破坏性命令。安全带很好用，但不是为了鼓励你闭眼开车。

---

## 9. 本地项目、远程开发机和生产环境不是同一回事

同一条命令，在练习目录和生产服务器上的风险完全不同。

大致可以这样理解：

```text
本地临时目录
< 本地真实项目
< 个人远程开发机
< 团队共享环境
< 生产环境
```

在远程机器运行 AI CLI 前，先确认：

```bash
hostname
whoami
pwd
git status
```

不要只凭终端窗口颜色或标签判断。窗口写着“测试机”，并不能阻止你实际登录生产机。

个人 Ubuntu GPU 机器上，也不要默认允许 Agent 修改 SSH、防火墙、NVIDIA 驱动、系统服务或共享数据集。训练代码和系统管理最好分成不同任务，权限也分开给。

---

## 10. 自动批准适合重复的小动作，不适合高风险决定

自动批准可以减少反复点击，适合范围明确、容易回滚的任务，例如：

- 在隔离工作区读取源码；
- 修改指定文件；
- 运行固定测试；
- 执行格式检查；
- 生成可以人工审查的输出。

下面这些通常不应直接自动批准：

- 清理和批量删除；
- 大规模依赖升级；
- 数据库迁移；
- 发布和部署；
- 防火墙、权限、SSH 和驱动修改；
- 处理真实凭据；
- 对远程服务执行写操作。

自动批准只代表“不再逐次问你”，不代表命令因此变安全。把确认框关掉，风险不会害羞地跟着一起消失。

---

## 11. 最小权限怎样落到实际流程里

最小权限不是永远只读，而是每一步只开放当下需要的能力。

一个常见流程是：

1. 先只读项目，找入口和测试；
2. 确认方案后，只允许修改指定文件；
3. 只运行约定的测试命令；
4. 人工查看 `git diff`；
5. 由人决定是否暂存、提交和推送。

这比任务开始时一次性开放文件、Shell、网络和远程权限更容易控制。

可以使用下面的提示模板：

```text
第一阶段只读分析，不要修改文件、安装依赖或访问外部服务。

请说明：
- 需要读取哪些路径；
- 计划运行哪些只读命令；
- 哪些信息仍然不确定。

确认方案后，只允许修改：
- PATH_A
- PATH_B

禁止：
- 删除未跟踪文件；
- 修改项目外文件；
- 执行 git commit 或 push；
- 读取凭据；
- 修改系统配置。

完成后汇报修改文件、执行命令、测试结果和未验证部分。
```

## 12. 看到权限请求时，先问这几个问题

不需要每次背一长串安全条款。看到命令或权限请求时，快速回答：

1. 为什么需要这项能力？
2. 它作用于哪台机器、哪个目录或服务？
3. 会读取、修改或上传什么？
4. 是否涉及凭据、网络或远程环境？
5. 出错后能否恢复？
6. 有没有范围更小的替代方案？
7. 执行后怎样验证结果？

其中一项完全说不清时，先拒绝，让 Agent 补充解释。

拒绝一次权限请求不会破坏项目；盲目批准一次，倒是有机会给你安排一段难忘的排错时光。

---

## 13. 已经发生误操作时，不要马上让 Agent继续“抢救”

发现异常后，第一步是停止扩大影响，而不是连续尝试更多命令。

建议顺序：

1. 停止当前任务；
2. 保存终端输出和日志；
3. 查看 `git status` 与 `git diff`；
4. 判断是否影响未跟踪文件、数据或远程服务；
5. 备份当前状态；
6. 再选择恢复方式。

如果涉及远程机器、数据库、权限或网络配置，尽量保留当前连接和现场信息。不要在唯一 SSH 会话里一边改网络，一边相信“应该还能连回来”。

对于源码，可以先查看：

```bash
git status --short
git diff --name-status
git diff
```

不要直接使用会丢失修改的恢复命令，除非已经确认哪些内容可以舍弃。

---

## 14. 新手可以先记住这六条

刚开始使用 AI CLI，不需要一次记住所有权限术语。先做到：

```text
在项目目录启动
先只读调查
只开放当前步骤需要的权限
限制允许修改的路径
测试后查看 diff
提交和推送由人决定
```

再补两条底线：不要把真实凭据交给 Agent，不要把生产环境当练习场。

工具的权限系统再复杂，也是在帮助你回答同一个问题：这一步最多可以影响到哪里？只要范围清楚、证据可查、出错能停下来，AI CLI 就更像一个受控助手，而不是拿着万能钥匙在项目里自由参观。
