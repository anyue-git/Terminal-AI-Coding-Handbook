# 02 通用 AI 编程 Prompt 模板库

Prompt 不是咒语。把模板完整复制进去，并不会自动召唤出一个永不犯错的程序员。

它更像任务单：告诉 Agent 现在要做什么、能碰哪里、怎样验证，以及什么时候应该停下来问你。

本章模板适用于 Claude Code、Codex CLI、Grok CLI 和其他能够读取项目、修改文件或执行命令的 Agent。不同工具的权限名称可能不同，但任务边界的写法基本相通。

---

## 1. 先学会改模板

模板中的方括号是占位内容，必须替换：

```text
[问题描述]
[文件路径]
[测试命令]
[模块名称]
```

例如：

```text
允许修改：
- [文件 1]
- [文件 2]
```

应该改成：

```text
允许修改：
- src/parser.py
- tests/test_parser.py
```

不确定路径时，不要瞎填。先使用“只读调查”模板，让 Agent 找出相关文件。

一条好 Prompt 通常包含五样东西：

```text
目标
范围
禁止事项
验证方法
停止条件
```

简单任务不必写成合同。复杂任务也不要把调查、实现、部署和提交全部塞进一条 Prompt；分阶段更容易检查。

---

## 2. 最常用的短模板

```text
目标：
[希望得到的结果]

当前阶段：
[只读分析 / 计划 / 修改 / 测试 / 审查]

允许范围：
[文件、目录或命令]

禁止：
[不能做的事]

验证：
[测试或检查命令]

完成后请汇报：
- 修改文件；
- 执行命令；
- 测试结果；
- 未验证部分；
- 风险。

遇到需要扩大范围、安装依赖、访问外部服务或修改系统配置时，先停下来说明理由。
```

例如修复一个小 Bug：

```text
目标：修复解析器无法处理制表符的问题。

允许修改：
- src/parser.py
- tests/test_parser.py

禁止：
- 修改依赖；
- 大范围格式化；
- git add、commit 或 push。

验证：
python -m pytest tests/test_parser.py

如果必须修改其他文件，先说明原因，不要直接实施。
```

## 3. 第一次阅读项目

适合刚打开陌生仓库时使用：

```text
当前阶段只读，不要修改文件、安装依赖或执行 Git 写操作。

请阅读 README、依赖声明、测试配置、项目入口和与当前任务相关的模块。

请说明：
1. 项目解决什么问题；
2. 主要目录和入口；
3. 当前任务涉及哪些模块；
4. 怎样启动和测试；
5. 哪些结论有文件证据；
6. 哪些内容仍不确定；
7. 下一步建议阅读哪些文件。
```

不要要求 Agent 第一次进入项目就“完整理解全部代码”。大型仓库连人都做不到，Agent 也不会因为 Prompt 写得坚定就突然获得全知视角。

## 4. 分析 Bug，但先别改

```text
目标：分析下面的问题，当前阶段不要修改代码。

现象：
[报错、异常结果或用户反馈]

复现步骤：
[怎样触发]

预期行为：
[本来应该怎样]

请完成：
1. 找出最可能的调用链；
2. 区分直接原因和根本原因；
3. 给出文件路径和证据；
4. 判断能否稳定复现；
5. 建议一个最小回归测试；
6. 给出最小修复范围；
7. 标明缺失信息。

禁止修改文件、安装依赖、删除测试或扩大到无关重构。
```

错误日志最好保留原文，但粘贴前先删除 Token、Cookie、私人地址和其他敏感信息。

---

## 5. 先添加失败测试

```text
只修改测试文件，添加一个能够稳定复现问题的最小回归测试。

要求：
- 不修改生产代码；
- 测试在当前实现下应失败；
- 失败原因必须与问题一致；
- 不降低现有断言强度；
- 如果无法稳定复现，停止并说明缺少什么。

完成后汇报：
- 测试文件和测试名称；
- 测试意图；
- 执行命令；
- 退出状态和关键失败信息。
```

测试失败并不自动证明测试正确。它必须因为目标问题失败，而不是因为导入路径写错或环境根本没装好。

---

## 6. 做最小修复

```text
现在只修复刚才回归测试覆盖的问题。

允许修改：
- [生产代码文件]
- [测试文件]

禁止：
- 修改其他模块；
- 更新依赖；
- 大范围格式化；
- 删除或跳过测试；
- 未经说明改变公开接口；
- git add、commit 或 push。

完成后运行：
[测试命令]

请汇报修改文件、核心变化、测试结果、未验证部分和剩余风险。
```

“最小修复”不是越少行越好，而是只处理当前问题，不顺手开展第二个项目。

---

## 7. 规划新功能

```text
任务目标：
[描述用户最终能看到或使用的行为]

当前阶段只制定计划，不要修改文件。

请给出分阶段方案，每个阶段说明：
- 要实现的行为；
- 可能修改的文件；
- 接口或数据变化；
- 测试方法；
- 风险；
- 回滚方式；
- 何时需要人工确认。

请区分：
1. 本次必须完成；
2. 可选优化；
3. 明确不在本次范围。

需求有歧义时先提问，不要自行编造产品规则。
```

---

## 8. 做重构但保持行为不变

```text
目标：重构 [模块名称]，保持外部行为不变。

当前阶段先只读分析：
1. 找出公开接口；
2. 找出已有行为测试；
3. 识别缺失的关键回归测试；
4. 把重构拆成可以分别验证的小步骤；
5. 说明怎样证明行为没有变化。

限制：
- 不新增功能；
- 不升级依赖；
- 不改公开接口名称；
- 不格式化无关文件；
- 每一批完成后停下来汇报。
```

重构的难点不是把代码变漂亮，而是证明外部行为没有偷偷跟着装修。

## 9. 审查当前改动

```text
你只负责审查，不要修改文件。

请阅读原始需求、当前 git status、git diff 和测试结果。

检查：
- 是否满足需求；
- 是否存在范围外修改；
- 逻辑和边界条件；
- 错误处理和兼容性；
- 安全与敏感信息；
- 性能风险；
- 测试缺口；
- 文档与实现是否一致。

每条问题引用具体文件和位置，并分为：
- 已确认问题；
- 可能问题；
- 无法验证；
- 可选改进。

没有证据的问题不要写成确定结论。
```

独立审查最好使用新会话，避免复核者继承实现阶段的自我解释。

## 10. 分析测试失败

```text
测试失败后先不要修改代码。

请把失败判断为以下一种或多种：
- 本次修改引起；
- 修改前已经存在；
- 环境或依赖问题；
- 测试本身不稳定；
- 需求与测试冲突；
- 暂时无法判断。

每个判断提供证据，并给出下一条最小验证命令。

不要通过删除断言、跳过测试、扩大异常捕获或直接改预期结果来让测试变绿。
```

---

## 11. 排查 Python 环境

```text
先不要安装、升级或卸载任何包，也不要修改系统 Python。

请检查：
- 当前目录；
- python 实际路径和版本；
- pip 属于哪个 Python；
- 虚拟环境是否激活；
- 目标包的安装位置和导入位置；
- 是否有同名文件遮蔽包。

请区分环境选择错误、包未安装、版本冲突和代码导入问题，并给出最小修复方案。
```

常用证据命令可以包括：

```bash
which python
python --version
python -m pip --version
python -c "import sys; print(sys.executable); print(sys.path)"
```

## 12. 排查 GPU 环境

```text
先不要重装驱动或整体重建环境。

请分层检查：
1. 系统是否识别 GPU；
2. 驱动状态；
3. 当前 Python 解释器；
4. 深度学习框架版本和构建信息；
5. 框架能否实际使用 GPU；
6. 模型与数据是否位于同一设备。

请区分驱动、Python 环境、框架安装和代码设备选择问题，并给出最小验证步骤。
```

不要因为 `nvidia-smi` 正常，就直接宣布 PyTorch 环境正常。它们检查的不是同一层。

---

## 13. 排查 Docker

```text
先不要删除容器、镜像或 Volume。

请只读检查：
- Docker 客户端和服务端状态；
- 当前 Context；
- 容器状态和日志；
- Compose 配置；
- 端口映射；
- Bind Mount 和 Volume；
- 应用实际监听地址。

先给出根因假设和验证步骤。任何可能影响持久数据的操作必须单独说明风险并等待确认。
```

---

## 14. 生成任务交接摘要

```text
请生成当前任务的交接摘要，不要修改文件。

包含：
- 最终目标；
- 当前分支和 Git 状态；
- 已完成内容；
- 已修改文件；
- 已运行测试及结果；
- 当前错误；
- 未解决风险；
- 下一步；
- 必须继续遵守的限制；
- 恢复工作前应重新运行的检查命令。
```

交接摘要应记录事实，不要只写“进展顺利”。顺利到哪里、还差什么，才是下一位接手者需要的内容。

---

## 15. 编写面向小白的技术文档

```text
请为 [主题] 编写面向新手的技术章节。

要求：
- 第一次出现术语时先用容易理解的话解释；
- 给出最小可运行示例；
- 说明命令在哪个系统执行；
- 区分默认行为和绝对行为；
- 给出验证方法和恢复办法；
- 版本敏感内容注明核对日期并优先引用官方来源；
- 危险操作紧邻说明可能影响什么；
- 不编造参数；
- 不机械套固定小节；
- 可以有少量帮助理解的比喻，但不能牺牲准确性；
- 避免口水话、连续箭头和重复的“核心结论”。
```

## 16. 什么时候应该让 Agent 停下来

可以把下面一段加到复杂任务末尾：

```text
出现以下情况时停止实施并询问：
- 需要修改允许范围之外的文件；
- 需要安装或升级依赖；
- 需要管理员权限；
- 需要访问外部服务或生产环境；
- 需要删除数据或未跟踪文件；
- 测试结果与预期矛盾；
- 连续修复仍然失败；
- 无法从项目中找到足够证据。
```

Prompt 写得再完整，也不能代替权限配置、Sandbox、Git diff 和真实测试。任务单能告诉 Agent 应该往哪走，但护栏和刹车仍然要装在车上。
