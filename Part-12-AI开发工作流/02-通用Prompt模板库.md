# 02 通用 AI 编程 Prompt 模板库

> 最近核对：2026-07-30
>
> 这些模板适用于 Claude Code、Codex CLI、Grok Build 和其他能够读取项目、修改文件或执行命令的 Agent。模板描述任务边界，不替代各客户端自己的权限、Sandbox 和项目规则。

Prompt 不是咒语，而是一张任务单。它的价值不在于字数，而在于让 Agent 明白当前阶段、运行位置、允许范围、验证方法和停止条件。中型以上任务不要把“理解项目、诊断问题、制定计划、写测试、实施、验证和审查”全部塞进一条 Prompt；阶段越清楚，结果越容易检查。

```text
了解陌生项目
→ 诊断或澄清需求
→ 比较方案
→ 写失败测试
→ 最小实施
→ 验证
→ 审查 diff
→ 准备发布或自动化
```

## 1. 先写一份可复用的任务合同

中型以上任务可以从下面的任务头开始，再根据当前阶段删减：

```text
任务目标：
[最终需要得到的行为]

当前阶段：
[只读调查 / 计划 / 实施 / 测试 / 审查]

运行位置：
- 主机：[Mac / Ubuntu / 容器 / 远程服务器]
- 工作目录：[绝对路径或项目根目录]
- Git 分支：[分支名]

允许读取：
[文件、目录]

允许修改：
[文件、目录]

允许执行：
[测试、只读命令、必要工具]

禁止：
[不能修改、删除、读取或执行的内容]

验收方式：
[测试、检查命令和预期结果]

停止条件：
需要扩大范围、安装依赖、访问外部服务、使用 sudo、修改系统配置或执行 Git 写操作时，先停止并说明理由。

完成后汇报：
- 实际修改或发现；
- 文件路径；
- 执行命令和退出状态；
- 测试结果；
- 未验证部分；
- 风险和需要人工决定的下一步。
```

运行位置不能省略。同一条命令在 Mac、Ubuntu GPU 节点、容器和生产服务器上的含义可能完全不同；读取范围和写入范围也应分开，避免 Agent 因为需要理解多个模块就获得修改整个仓库的许可。

## 2. 调查项目、分析 Bug 与澄清需求

第一次阅读陌生项目时，目标是围绕当前任务建立局部地图，而不是声称“完整理解全部代码”：

```text
当前阶段只读，不要修改文件、安装依赖、访问外部服务或执行 Git 写操作。

请先检查项目规则、README、依赖声明、测试配置和入口文件，然后说明：
1. 项目解决什么问题；
2. 主要目录与入口；
3. 当前任务涉及哪些模块；
4. 怎样启动和测试；
5. 相关配置从哪里加载；
6. 哪些结论有文件证据；
7. 哪些内容仍不确定；
8. 下一步建议阅读哪些文件。

每个结论给出文件路径或符号。不要声称已经理解未读取的目录。
```

Bug 分析阶段应把现象、最小复现、预期行为和环境交给 Agent，但暂不允许修改：

```text
目标：分析下面的问题，当前阶段不要修改代码。

现象：
[错误原文或异常结果]

复现步骤：
[最小复现]

预期行为：
[正确结果]

已知环境：
[系统、解释器、版本、主机]

请完成：
1. 找出最可能的调用链；
2. 区分直接原因、根本原因和环境问题；
3. 给出文件路径和证据；
4. 判断能否稳定复现；
5. 建议最小回归测试；
6. 给出最小修复范围；
7. 标明缺失信息和替代假设。

禁止修改文件、升级依赖、删除测试或扩大到无关重构。
```

日志在粘贴前应删除 Token、Cookie、私人地址、数据库连接串和用户数据。需求本身含有“优化一下”“更智能”“最好兼容”等模糊词时，先整理规格：

```text
先不要修改代码。
请把下面的需求整理成：
1. 目标；
2. 非目标；
3. 用户可观察行为；
4. 验收标准；
5. 必须保持的兼容行为；
6. 风险；
7. 待确认问题。

原始需求：
[粘贴需求]

不要自行补充产品规则。缺少信息时，把不同解释及其影响列出来。
```

## 3. 从方案选择进入小批实施

需要比较方案时，不必机械凑三套，但推荐方案必须解释修改规模、验证和回滚：

```text
当前阶段只制定方案，不要修改文件。

根据已经确认的需求和项目调查，给出可行方案。每个方案说明：
- 核心做法；
- 修改文件；
- 接口或数据变化；
- 优点；
- 风险；
- 验证方式；
- 回滚方式。

请推荐一个方案，并解释为什么不采用范围更大的方案。把内容分成：
- 本次必须完成；
- 可选优化；
- 明确不在本次范围。
```

Bug 修复可以先只添加失败测试：

```text
这次只修改测试文件，添加一个能够稳定复现目标问题的最小回归测试。

要求：
- 不修改生产代码；
- 测试在当前实现下应失败；
- 失败必须来自目标问题；
- 不降低现有断言强度；
- 不使用无理由的 skip、xfail 或宽泛异常捕获；
- 无法稳定复现时停止并说明缺少什么。

完成后汇报测试路径与名称、输入和预期行为、执行命令、退出状态、关键失败信息，以及为什么确认它复现了目标问题。
```

测试准确后，才进入最小修复：

```text
现在只修复已由回归测试覆盖的问题。

允许修改：
- [生产代码]
- [测试文件]

禁止：
- 修改其他模块；
- 更新依赖或锁文件；
- 大范围格式化；
- 删除、跳过或削弱测试；
- 未经说明改变公开接口；
- git add、commit、push、reset、clean 或 rebase。

完成后依次运行：
1. 目标测试；
2. 相关模块测试；
3. [静态检查或完整测试]。

报告实际修改、命令、退出状态、测试数量、未验证部分和剩余风险。
```

最小修复不是行数最少，而是只解决当前任务。行为保持型重构则应先识别公开接口和现有测试，再分批实施：

```text
目标：重构 [模块]，保持外部行为不变。

第一阶段只读分析：
1. 找出公开接口；
2. 找出现有行为测试；
3. 识别关键测试缺口；
4. 把重构拆成可单独验证的批次；
5. 说明怎样证明行为没有改变。

限制：
- 不新增功能；
- 不升级依赖；
- 不改变公开名称和数据格式；
- 不格式化无关文件；
- 每批完成后停止并汇报 diff 和测试。
```

若当前测试不足以证明行为不变，应先补 characterization test，而不是先开始大规模重构。

## 4. 分析失败、审查 diff 与准备 PR

测试失败后先分类，不要立即让 Agent“修到全部通过”：

```text
测试失败后先不要修改代码。

测试命令：
[COMMAND]

失败输出：
[脱敏日志]

请判断属于以下哪类：
- 本次修改引起；
- 修改前已存在；
- 环境或依赖问题；
- 测试不稳定；
- 测试运行方式错误；
- 需求与测试冲突；
- 暂时无法判断。

每个判断提供证据，并给出下一条范围最小的验证命令。不要通过删除断言、跳过测试、扩大异常捕获或直接改预期结果来让测试变绿。
```

完成修改后，最好使用新会话或另一个工具只读审查：

```text
你只负责只读审查，不要修改文件。

输入：
- 原始需求；
- git status；
- 当前 git diff；
- 测试命令和结果；
- 已知环境限制。

检查：
- 是否满足需求；
- 是否存在范围外修改；
- 逻辑、边界条件和错误处理；
- 兼容性和数据迁移；
- 权限、路径、网络和敏感信息；
- 性能与资源风险；
- 测试缺口；
- 文档和实现是否一致。

每条发现引用具体文件和位置，并分类为已确认问题、可能问题、无法验证或可选改进。没有证据的问题不要写成确定结论。
```

准备 Pull Request 前仍只生成证据和摘要，不自动提交或推送：

```text
当前阶段只读，不要提交、推送或创建 PR。

请根据目标分支 [BASE] 审查当前任务分支：
1. 汇总实际改动；
2. 对照原始需求检查完成度；
3. 列出测试命令和结果；
4. 检查凭据、大文件、生成物和范围外修改；
5. 标明 breaking change、迁移和回滚方式；
6. 给出适合 PR 描述的摘要；
7. 列出仍需人工确认的事项。

不要把未运行的测试写成已通过。
```

## 5. 非交互、远程机器和计划预算

非交互任务必须定义稳定输出，而不能依赖人中途追问：

```text
这是自动化只读审查任务。

禁止修改文件、安装依赖、访问未授权网络、创建提交或推送。只检查 [明确范围]。

输出必须包含：
- 状态：pass / fail / unknown；
- 已确认问题；
- 证据文件和位置；
- 执行过的命令；
- 未验证部分；
- 建议的人工下一步。

如果缺少信息或命令失败，不要猜测，返回 unknown 并说明原因。
```

脚本层还应设置外部超时、最大轮数或预算、临时会话或隔离工作区、稳定 JSON/JSONL/Schema、可靠退出状态，以及日志与敏感信息过滤。具体参数见 Codex `exec`、Grok Headless 和各工具非交互章节。

在个人 Ubuntu GPU 机器运行 Agent 时，显式标明远程环境：

```text
当前主机：[HOSTNAME]
当前目录：[PROJECT_PATH]
这是个人 Ubuntu GPU 开发机，不是本地 Mac。

只允许处理当前项目目录。禁止：
- 读取 ~/.ssh、浏览器、云凭据和其他项目；
- 修改 SSH、防火墙、驱动、CUDA、系统服务和用户账户；
- 删除 datasets、models、runs 或 checkpoint；
- 停止其他 GPU 进程；
- 修改 Docker daemon 或挂载 Docker Socket；
- git commit 或 push。

需要系统级修改时，停止并给出只读证据、完整命令、影响、回滚方式和人工确认点。
```

复杂任务还可以限制计划规模：

```text
当前阶段只制定最多 [N] 个实施批次，不要修改文件。

每个批次必须只有一个清楚目标，列出允许修改文件、验证命令和失败后退回位置，并且不依赖尚未确认的假设。如果任务无法在 [N] 个批次内安全描述，请停止并说明还需要拆分什么。
```

## 6. Prompt 长度、敏感信息与完成报告

很小的任务无需套完整模板，例如：

```text
只修改 README.md 中的安装示例，把旧命令替换为当前命令。
不要修改其他文件，不要提交。
修改后显示 diff，并检查 Markdown 链接。
```

高风险任务则需要“只读调查 → 风险与备份 → dry run → 人工确认 → 单步执行 → 验证 → 回滚检查”。Prompt 长度应由风险、歧义和验证难度决定，而不是为了显得专业。

不要在 Prompt 中放入真实 API Key、Token、Cookie、Session、SSH 私钥、未脱敏数据库连接串、整份环境变量、内部客户数据、与任务无关的大量源码或来源不明的账号缓存。Agent 通常只需要知道：

```text
凭据由 MY_API_TOKEN 环境变量提供。
不要读取、打印或保存其真实值。
```

一条 Prompt 的合格结果至少应说明阶段是否完成、实际修改或发现、文件路径、执行命令、退出状态、测试结果、未验证部分、风险和需要人工决定的下一步。只说“已完成”“应该没问题”或“优化成功”，不构成可复核结果。
