# 03 基础设施与远程开发 Prompt 模板

基础设施问题和普通代码 Bug 有一个明显区别：改错代码，通常还能用 Git 看见；改错 SSH、防火墙、驱动、磁盘或 Docker Volume，可能直接让连接中断、环境损坏，甚至把数据一起带走。

所以这类 Prompt 的第一句话通常不该是“帮我修好”，而应该是：

> 先只读检查，说明问题位于哪一层，再给出范围最小的下一步。

本章的模板适用于 SSH、rsync、Homebrew、Python、Docker、GPU 和远程训练。方括号中的内容要替换成自己的真实信息，但不要把密码、Token、私钥或完整环境变量粘贴进去。

---

## 1. 基础设施任务先用这段开场

遇到暂时看不懂的问题，可以先发：

```text
当前阶段只做诊断，不要修改文件、安装软件、重启服务或执行需要管理员权限的命令。

请先说明：
1. 问题可能位于哪一层；
2. 需要查看哪些只读信息；
3. 每条检查命令会读取什么；
4. 不同输出分别意味着什么；
5. 哪一步之后才需要讨论修改。

如果涉及凭据、远程连接、系统服务、网络规则、数据删除或驱动，请单独标明风险。
```

这段话的作用，是防止 Agent 看见一个报错就开始“重装大法”。重装有时确实能解决问题，但它也很擅长把原来的证据一起解决掉。

---

## 2. SSH 连不上时，先判断卡在哪一层

SSH 连接会经过主机名解析、网络、端口、服务端程序、主机身份和用户认证。只看到一句 `Connection refused` 或 `Permission denied`，还不能直接判断该改哪个配置。

```text
请分析下面的 SSH 错误和调试输出：

[粘贴已经脱敏的错误信息]

当前阶段不要修改 SSH 配置、删除 known_hosts、重启服务、调整防火墙或开放公网端口。

请按顺序判断问题位于：
1. 主机名解析；
2. 网络可达性；
3. 目标端口；
4. SSH 服务是否监听；
5. 主机指纹；
6. 用户名和密钥认证；
7. 登录后的 Shell 环境。

每次只给一组范围最小的只读检查，并说明不同结果如何影响下一步判断。
```

不要为了省事直接关闭主机密钥检查，也不要把“把 22 端口暴露到公网”当作个人设备的默认方案。同一局域网可以直接连接；异网优先使用可信的组网工具或 VPN，再运行普通 OpenSSH。

---

## 3. 审查 SSH Config，不要让 Agent 直接覆盖

SSH Config 中的通配规则可能互相影响。一个看似无关的 `Host *`，就可能改变多个主机别名。

```text
请只读审查下面这份 SSH Config，不要修改原文件：

[粘贴已脱敏的配置；不要包含私钥内容]

重点检查：
- Host；
- HostName；
- User；
- Port；
- IdentityFile；
- IdentitiesOnly；
- ProxyJump；
- 通配规则和出现顺序。

请输出：
1. 每个主机别名最终会连接到哪里；
2. 哪些配置可能互相覆盖；
3. 是否引用了不存在或权限不当的密钥路径；
4. 最小修改建议；
5. 修改后怎样使用 ssh -G 验证最终配置。
```

只提供私钥的路径，例如 `~/.ssh/id_ed25519_gpu`，不要把私钥正文交给 Agent。

---

## 4. 让 rsync 先排练，再正式搬家

rsync 很适合同步 Mac 和 Ubuntu，但源路径末尾的 `/`、排除规则和 `--delete` 都可能改变结果。

```text
请根据下面的信息生成 rsync 同步方案：

源目录：[SOURCE_PATH]
目标主机别名：[SSH_ALIAS]
目标目录：[TARGET_PATH]
方向：[Mac 到 Ubuntu / Ubuntu 到 Mac]
需要排除：[列出虚拟环境、缓存、日志、模型、数据或敏感文件]

要求：
1. 第一条命令必须使用 --dry-run；
2. 默认不要使用 --delete；
3. 解释源路径末尾斜杠的影响；
4. 不同步 .git、虚拟环境、.env、缓存、数据集和大型模型；
5. 给出执行前和执行后的只读验证方法；
6. 如果目标目录可能包含独立生成的结果，明确提醒不要覆盖或删除。
```

拿到命令后，先阅读 dry run 输出。`--dry-run` 不是装饰品，它是 rsync 正式开工前的彩排。

---

## 5. Homebrew 或 PATH 混乱时，先找出实际执行的是谁

常见现象是“明明安装了，终端却找不到”，或者同一条命令在两个终端里版本不同。问题经常不在软件本身，而在 PATH、Shell 配置或 ARM/Intel 架构混用。

```text
请只读诊断 Homebrew 与 PATH 问题，不要执行安装、卸载、upgrade、cleanup、link、unlink 或服务重启。

目标命令：[COMMAND]
错误现象：[ERROR_OR_BEHAVIOR]

请检查并解释：
- 当前 Mac 架构；
- brew --prefix；
- type -a [COMMAND]；
- command -v [COMMAND]；
- echo "$PATH"；
- brew info [FORMULA]；
- 是否同时存在 Apple Silicon 与 Intel/Rosetta 安装；
- 哪个 Shell 配置文件实际生效。

最后给出范围最小的修改方案、验证方法和回滚方式。
```

不要在没弄清现有路径前，连续往 `.zshrc` 末尾追加多行 PATH。配置文件不是许愿池，投得越多不一定越灵。

---

## 6. Python 报缺包，先确认当前 Python 是哪一个

`pip install` 成功但 `import` 失败，常见原因是 pip 和 Python 不属于同一环境。

```text
请分析下面的 Python 环境问题：

项目目录：[PROJECT_PATH]
错误信息：[ERROR]
目标包：[PACKAGE]

当前阶段不要安装、升级或卸载任何包，也不要修改系统 Python。

请先检查并解释：
- pwd；
- type -a python python3 pip pip3；
- python --version；
- python -c "import sys; print(sys.executable); print(sys.prefix); print(sys.base_prefix)"；
- python -m pip --version；
- python -m pip show [PACKAGE]；
- 是否有同名文件或目录遮蔽目标包。

请判断问题属于：
1. 解释器选错；
2. 虚拟环境未激活；
3. 包没有安装到当前环境；
4. 依赖版本冲突；
5. 同名文件遮蔽；
6. 项目自身导入路径错误。

最后给出最小修复方案和验证命令。不要建议 sudo pip install。
```

Mac 和 Ubuntu 应分别创建 Python 环境，不要把一台机器的 `.venv` 直接复制到另一台。

---

## 7. Docker 启动失败，先分清是镜像、容器还是应用

“容器启动不了”可能是镜像构建失败、环境变量缺失、端口冲突、Volume 权限、应用崩溃，或者健康检查没有通过。

```text
请分析下面的 Docker 或 Compose 问题：

[粘贴已脱敏的错误、Compose 片段和相关日志]

当前阶段只读诊断。不要执行 system prune，不要删除容器、镜像、Volume、Bind Mount 数据目录或网络。

请按层检查：
- docker version；
- docker context show；
- docker ps -a；
- docker compose config；
- docker compose ps；
- 相关服务日志；
- 端口映射和应用监听地址；
- Volume 与 Bind Mount；
- 环境变量是否缺失；
- 健康检查。

请区分：
1. 镜像构建失败；
2. 容器进程退出；
3. 应用只监听容器内错误地址；
4. 端口冲突；
5. 数据挂载或权限问题；
6. 依赖服务未就绪。

每个根因假设给出验证方法。涉及持久数据的操作必须单独说明影响并等待确认。
```

不要把 Docker Socket、整个用户主目录、`~/.ssh` 或云凭据目录挂进不可信容器。容器也不是运行任意不可信代码的绝对安全边界。

---

## 8. GPU 不可用时，逐层检查，不要先重装驱动

GPU 问题至少涉及系统驱动、Python 环境、深度学习框架和代码设备选择。`nvidia-smi` 正常，只能说明其中一层大体正常。

```text
请分层分析 GPU 不可用问题：

系统：[Ubuntu 版本]
Python 环境：[环境名称或解释器路径]
框架：[PyTorch 等]
错误信息：[ERROR]

当前阶段不要重装驱动、CUDA Toolkit 或整个 Python 环境。

请依次检查：
1. 系统能否识别 NVIDIA GPU；
2. 驱动与 nvidia-smi 状态；
3. 当前 Python 解释器；
4. 框架版本和构建对应的 CUDA 信息；
5. 框架能否实际使用 GPU；
6. 代码中的模型和数据是否位于同一设备；
7. 如果在容器中运行，容器是否获得 GPU 设备。

请给出每层的最小检查命令、判断标准和下一步。
不要把 nvidia-smi 显示的 CUDA Version 当作系统 CUDA Toolkit 的已安装版本。
```

适合提供给 Agent 的证据通常包括：

```bash
nvidia-smi
which python
python --version
python -c "import torch; print(torch.__version__); print(torch.version.cuda); print(torch.cuda.is_available())"
```

不要粘贴完整环境变量；其中可能有 Token 和内部地址。

---

## 9. 远程训练前，让 Agent 只做启动审查

长任务最怕跑了几个小时后才发现目录、配置或输出路径写错。

```text
请只读审查下面的远程训练方案，不要启动训练，也不要修改系统配置：

训练命令：[COMMAND]
项目目录：[PROJECT_PATH]
配置文件：[CONFIG_PATH]
数据集路径：[DATA_PATH]
输出目录：[OUTPUT_PATH]

请检查：
- 当前主机、用户和目录；
- Git 分支、提交和未提交修改；
- Python 解释器；
- GPU 可见性；
- 数据集和模型路径；
- 输出目录是否可能覆盖旧实验；
- 日志保存位置；
- 磁盘空间；
- 是否在 tmux 中运行；
- checkpoint 保存频率；
- SSH 断开、程序崩溃和机器重启分别怎样恢复。

最后生成一份启动前检查清单，并标明哪些内容已经验证、哪些只是推测。
```

tmux 能防止 SSH 窗口断开带走进程，但机器关机后它也会一起下班。训练恢复仍然要靠 checkpoint。

---

## 10. 修改 SSH、服务或防火墙前，只让 Agent 审查方案

这类修改可能让当前连接立即失效。尤其在远程机器上，不要让 Agent 在唯一 SSH 会话中边改边试。

```text
请审查下面的服务、SSH 或防火墙变更方案，不要执行命令，也不要生成一键批量脚本：

[粘贴已脱敏的方案或配置差异]

必须说明：
1. 当前连接可能怎样受到影响；
2. 是否需要保留第二个已登录会话；
3. 修改前应备份哪些文件；
4. 配置语法如何在不应用的情况下验证；
5. 应按什么顺序做单步修改；
6. 每一步怎样确认生效；
7. 如何回滚；
8. 哪一步可能把我锁在远程机器外；
9. 是否存在不暴露公网端口的替代方案。
```

即使 Agent 给出的方案看起来合理，系统级修改也应由人逐步执行和验证。

---

## 11. 生成基础设施任务交接记录

基础设施排错经常跨多次会话。交接记录能避免下一次重新猜一遍。

```text
请根据现有证据生成任务交接摘要，不要执行任何操作。

包含：
- 最终目标；
- 当前机器、用户和目录；
- 当前连接方式；
- 已确认事实；
- 已排除原因；
- 实际修改过的文件、服务和端口；
- 已运行的验证命令及结果；
- 当前仍存在的错误；
- 回滚方法；
- 下一步最小检查；
- 继续操作前必须保留的限制；
- 已脱敏但仍需注意的版本信息。
```

“试了很多办法，还是不行”不算交接记录。下一位接手者需要知道具体试过什么、得到什么结果。

---

## 12. 基础设施任务什么时候必须停下来

可以把下面一段附在高风险任务末尾：

```text
出现以下情况时停止并询问，不要继续自动操作：
- 需要管理员权限；
- 需要重启 SSH、网络或关键系统服务；
- 需要修改防火墙或开放公网端口；
- 需要删除容器、Volume、数据目录、模型或 checkpoint；
- 需要重装驱动或整体重建环境；
- 需要读取私钥、Token、密码或完整环境变量；
- 需要操作 Docker Socket；
- 当前只有一个远程连接入口；
- 实际机器、用户或目录与预期不一致；
- 检查结果互相矛盾。
```

这些模板不会自动让基础设施操作变安全。它们只是先把 Agent 的判断过程摊在桌面上，让你有机会在真正动手前发现问题。

基础设施排错可以记成一句话：先定位层级，再做最小修改；先保住连接和数据，再谈方便。电脑偶尔会闹脾气，但别因为它咳嗽两声就直接安排全身手术。
