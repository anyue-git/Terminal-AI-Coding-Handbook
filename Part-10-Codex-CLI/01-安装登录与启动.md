# 01 安装、认证与第一次启动

> 最近核对：2026-07-30  
> Codex CLI 更新较快。安装和认证命令以本机 `codex --help`、`codex login --help` 与 OpenAI 当前官方文档为准。

第一次使用 Codex CLI，需要确认四件事：终端实际运行哪一份 `codex`，当前采用 ChatGPT、Platform API Key 还是企业 Access Token 登录，用量与管理策略由哪个账户体系承担，以及 Codex 从哪个项目目录加载代码和指令。本章只建立这条基础链；完整修改练习见[Codex CLI 与 Git 协作案例](04-Codex与Git协作案例.md)。

## 1. 安装完成后确认实际运行的是哪一份客户端

安装前检查系统、架构、Shell、Git 和已有命令：

```bash
hostname
uname -s
uname -m
git --version
printf '%s\n' "$SHELL"

type -a codex 2>/dev/null
command -v codex 2>/dev/null
codex --version 2>/dev/null || true
```

OpenAI 当前为 macOS 与 Linux 提供独立安装器，安装与更新使用同一入口：

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

执行前确认地址来自当前官方安装页，并遵守组织的软件安装要求。npm 也是官方安装路线：

```bash
node --version
npm --version
npm prefix -g
npm install -g @openai/codex
```

npm 全局目录出现权限问题时，应修正 Node 来源、prefix 和 PATH，不用 `sudo npm install -g` 把包强行写入系统目录。Homebrew 的具体入口可能随发布方式变化，使用时从当前安装页选择。

安装后检查 Shell 最终选择的文件：

```bash
type -a codex
command -v codex
codex --version
codex --help
printf '%s\n' "$PATH" | tr ':' '\n'
ls -l "$(command -v codex)"
```

独立安装器、npm、Homebrew 或旧测试版同时存在时，Shell 会按 PATH 顺序选择其中一份。继续安装更多副本不会解决版本混乱，应先决定保留哪种来源，再处理其他入口。Mac 与 Ubuntu 也要分别安装；通过 SSH 在 Ubuntu 执行安装不会改变 Mac，另一平台的二进制和全局包目录也不能直接复制使用。

## 2. 登录方式决定账户、用量和管理边界

默认的 ChatGPT 登录通过浏览器完成：

```bash
codex login
```

这条路线使用所选 ChatGPT 账户和工作区，Codex 访问能力、管理权限和数据处理规则随该工作区生效。ChatGPT 计划包含的 Codex 权益不会变成可交给任意第三方程序使用的 Platform API Key。

采用 OpenAI Platform API Key 时，通过标准输入交给登录命令：

```bash
printenv OPENAI_API_KEY | codex login --with-api-key
```

API Key 路线按 Platform 组织、项目、标准 API 价格和数据设置运行，不消耗 ChatGPT 计划中包含的 Codex 用量；部分依赖 ChatGPT 工作区或云端服务的能力也可能不可用。Key 不应写进命令参数、项目文件或截图。

部分 ChatGPT Enterprise 工作区可以由管理员允许成员创建 Codex Access Token，用于可信的非交互本地工作流：

```bash
printenv CODEX_ACCESS_TOKEN | codex login --with-access-token
```

Access Token 用来让自动化继承 ChatGPT 工作区控制和 Codex 权益，不是普通 Platform API Key，也不能通过 Cookie、Session 或网页登录缓存自行提取。它适合可信脚本、调度器和私有 CI Runner，不适合暴露给不可信或公共执行环境。

查看当前认证方式或退出：

```bash
codex login status
codex logout
```

Codex CLI 与 IDE 扩展可能共享登录缓存；从任一端 logout 后，另一端也可能需要重新登录。凭据可能进入操作系统凭据库，也可能保存到 `~/.codex/auth.json`。文件位置、Keyring、`CODEX_HOME` 和多实例由[Codex 的 TOML、Profile 与凭证](../Part-10C-配置凭证与多实例/02-Codex-TOML配置与凭证.md)集中说明。

远程服务器或无浏览器终端优先使用当前 beta 设备码流程：

```bash
codex login --device-auth
```

设备码登录需要个人安全设置或工作区管理员允许。终端显示的网址与一次性代码只在自己的可信浏览器中使用。Mac 与 Ubuntu 可以登录同一账户，但仍可能选择不同工作区、Profile、模型和权限策略；两台机器分别确认：

```bash
hostname
type -a codex
codex --version
codex login status
```

Git 仓库、`AGENTS.md`、测试、依赖声明和不含秘密的项目配置可以共享；客户端二进制、npm 全局目录、`auth.json`、整个 `~/.codex`、`.venv` 和平台缓存不直接同步。个人设备优先分别登录，组织自动化使用正式 API Secret、Access Token 或工作负载身份。

## 3. 从项目根目录启动，并核对指令发现链

Mac 本地项目可以这样启动：

```bash
cd ~/Projects/my-project
pwd
git rev-parse --show-toplevel
git status
codex
```

SSH 登录 Ubuntu 后，先确认远程身份，再进入远端项目：

```bash
hostname
whoami
cd ~/projects/my-project
pwd
git status
codex
```

也可以显式设置工作区根：

```bash
codex --cd ~/Projects/my-project
```

启动后查看：

```text
/status
/permissions
/model
```

这些入口用于确认目录、认证、模型、Sandbox 和审批策略。第一条请求可以保持只读：

```text
检查当前项目的入口、测试命令和 AGENTS.md，只读说明，不修改文件。
```

项目根目录的 `AGENTS.md` 保存结构、测试命令、编码约定和验收要求；`/init` 可以生成初稿，但生成结果仍需通过 Git diff 审查。`AGENTS.md` 影响模型如何执行任务，不是文件系统强制隔离，Sandbox 与审批由下一章解释。

Codex 每次启动会建立指令链：先检查 `CODEX_HOME` 中的全局 `AGENTS.override.md` 或 `AGENTS.md`，再从项目根沿目录层级走到当前工作目录；每一层优先读取 `AGENTS.override.md`，否则读取 `AGENTS.md` 或配置的备用名称。更接近当前目录的指令出现在链路后面，可以覆盖前面的通用约定。异常指令因此可能来自全局目录、仓库根或当前子目录，不能只看距离当前文件最近的一份。

常用交互入口还包括 `/init`、`/review`、`/resume` 和 `/fork`。`/fork` 分叉对话上下文，不创建新的 Git 分支或工作区。完整练习直接进入[Codex CLI 与 Git 协作案例](04-Codex与Git协作案例.md)，安装章不再重复创建另一套示例项目。

## 4. 安装、认证和项目识别要分层排查

找不到命令或版本不对时检查：

```bash
type -a codex
command -v codex
printf '%s\n' "$PATH" | tr ':' '\n'
codex --version
```

用量来源与预期不一致时运行 `codex login status`，确认当前是 ChatGPT、API Key 还是 Access Token 路线。API Key 登录使用 Platform 计费而不是 ChatGPT 计划用量，属于认证边界，不是额度同步故障。

项目识别错误时检查：

```bash
pwd
git rev-parse --show-toplevel
git status
```

指令不符合预期时，检查全局与项目级 `AGENTS.override.md`、`AGENTS.md` 和当前工作目录。配置或身份切换异常时，不直接删除整个 `~/.codex`；先查看 `CODEX_HOME`、Profile、环境变量、登录状态和凭据存储。把安装来源、认证方式和项目目录分开定位，比反复重装更容易找到根因，也更容易恢复。
