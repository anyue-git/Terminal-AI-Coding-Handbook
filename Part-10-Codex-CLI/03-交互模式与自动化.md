# 03 交互模式、`codex exec` 与自动化

> 最近核对：2026-07-29  
> `codex exec` 的参数和事件格式可能继续变化。脚本进入 CI 前，应固定 Codex 版本并检查 `codex exec --help`。

Codex CLI 有两条主要路径：`codex` 是交互式 TUI，适合人在过程中澄清、审批和改变计划；`codex exec` 直接完成一次非交互任务，适合脚本、CI 和固定格式报告。两者读取同一套项目规则与配置，但 `exec` 无法依赖中途弹窗补充缺失信息，因此目录、权限、输出、超时和失败条件都要在启动前写清楚。

## 1. 先选择交互或非交互，再固定运行现场

陌生项目、歧义需求、多方案比较或测试失败需要人工判断时，使用 TUI：

```bash
cd ~/Projects/my-project
pwd
git status
codex
```

`/status`、`/permissions`、`/model`、`/init`、`/review`、`/resume` 和 `/fork` 分别用于状态、权限、模型、项目规则初稿、审查、恢复与会话分叉；`/fork` 复制上下文，不会创建 Git 分支或工作区。

固定范围的只读审查、机械修改、结构化报告、多仓库重复检查和无 TUI 环境更适合 `exec`：

```bash
codex exec "只读总结当前项目结构"
```

长 Prompt 可以从标准输入传入：

```bash
cat task.md | codex exec -
```

任务若需要频繁追问或临时调整文件范围，应先在 TUI 中澄清，而不是把不完整需求交给无人值守脚本。

自动化不能依赖调用者碰巧位于正确目录。可以显式 `cd`，也可以使用当前版本支持的 `--cd`：

```bash
PROJECT="$HOME/Projects/my-project"
cd "$PROJECT"

pwd
git branch --show-current
git status --short
codex exec "只读检查当前项目"
```

```bash
codex exec \
  --cd "$HOME/Projects/my-project" \
  "只读检查当前项目"
```

需要审计时，记录主机、目录、仓库、分支、提交、工作区、客户端版本和登录状态：

```bash
hostname
pwd
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short
codex --version
codex login status
```

`codex exec` 默认要求 Git 仓库，有助于确定项目边界。一次性非 Git 目录可以使用 `--skip-git-repo-check`，但它只跳过检查，不会生成版本记录或恢复能力。

普通 `exec` 会创建可恢复会话：

```bash
codex exec "只读分析当前测试失败"
codex exec resume --last \
  "重新检查当前 Git 状态，只执行计划中的下一步"
codex exec resume SESSION_ID "继续任务"
```

一次性任务可以使用：

```bash
codex exec --ephemeral \
  --sandbox read-only \
  "只读列出项目入口和测试命令"
```

`--ephemeral` 只决定会话是否持久化，不会回滚文件、清理日志或撤销外部副作用；恢复会话时也要重新检查目录、分支和工作区。

## 2. 非交互权限应让越界动作直接失败

只读分析可以明确写成：

```bash
codex exec \
  --sandbox read-only \
  --ask-for-approval never \
  "只读审查当前项目，不修改文件"
```

允许当前工作区修改时：

```bash
codex exec \
  --sandbox workspace-write \
  --ask-for-approval never \
  "读取 task.md 并执行；无法在现有边界内完成时停止并报告"
```

非交互任务无法等待人处理临时审批，因此 `never` 必须与有限 Sandbox 配合，让越界操作失败。旧 `--full-auto` 属于兼容入口，新脚本应显式写出 Sandbox 与审批策略。

需要读取另一个仓库时使用 `--add-dir`：

```bash
codex exec \
  --cd "$HOME/Projects/app" \
  --add-dir "$HOME/Projects/shared-lib" \
  "只读分析 app 与 shared-lib 的接口关系"
```

额外目录会进入访问范围，加入一个明确的库比开放整个 HOME 更容易审计。任务目标、允许文件、验证命令和停止条件可以使用[通用 Prompt 模板库](../Part-12-AI开发工作流/02-通用Prompt模板库.md)，这里不再复制完整任务合同。

## 3. 文本、JSONL 与 Schema 面向不同消费者

默认输出适合人在终端阅读。只保存最终消息：

```bash
codex exec \
  --output-last-message codex-report.md \
  "只读审查当前项目并生成 Markdown 报告"
```

部分版本支持 `-o` 简写。最终消息不包含完整工具过程，仍要检查进程退出状态和真实项目结果。

机器读取可以使用 JSON Lines 事件流：

```bash
codex exec --json "只读检查当前项目" > codex-events.jsonl
status=$?
printf 'codex exit status: %s\n' "$status"
```

每一行是独立 JSON 事件，可能出现 `thread.started`、`turn.started`、`item.started`、`item.completed`、`turn.completed` 或 `error`。可以验证语法：

```bash
python - <<'PY'
import json
from pathlib import Path

path = Path("codex-events.jsonl")
for number, line in enumerate(path.read_text().splitlines(), start=1):
    try:
        json.loads(line)
    except json.JSONDecodeError as exc:
        raise SystemExit(f"line {number}: {exc}")
print("valid jsonl")
PY
```

事件日志可能含路径、代码和模型输出，不能默认作为公共 CI 产物。

需要固定最终对象结构时准备 JSON Schema：

```bash
cat > codex-output.schema.json <<'JSON'
{
  "type": "object",
  "properties": {
    "summary": {"type": "string"},
    "files_changed": {
      "type": "array",
      "items": {"type": "string"}
    },
    "tests": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "command": {"type": "string"},
          "result": {"type": "string"}
        },
        "required": ["command", "result"],
        "additionalProperties": false
      }
    },
    "risks": {
      "type": "array",
      "items": {"type": "string"}
    }
  },
  "required": ["summary", "files_changed", "tests", "risks"],
  "additionalProperties": false
}
JSON
```

```bash
codex exec \
  --output-schema codex-output.schema.json \
  --output-last-message codex-result.json \
  "执行 task.md 中的任务，最终严格按照 Schema 输出"
```

Schema 约束最终回答格式，不验证文件范围、测试真实性或外部副作用。下游程序必须把结构化回答与退出状态和仓库证据一起判断。

## 4. 只读审计要证明工作区前后没有变化

下面的脚本把报告放到项目外的临时目录，记录运行环境、退出状态和 Git 前后状态：

```bash
cat > run-codex-audit.sh <<'SH'
#!/bin/sh
set -eu

project=${1:?usage: run-codex-audit.sh PROJECT_PATH}
output_dir=${2:-${TMPDIR:-/tmp}/codex-audit-output}

cd "$project"
mkdir -p "$output_dir"

{
  hostname
  pwd
  git branch --show-current
  git rev-parse HEAD
  codex --version
} > "$output_dir/environment.txt"

git status --short > "$output_dir/status-before.txt"

set +e
codex exec \
  --ephemeral \
  --sandbox read-only \
  --ask-for-approval never \
  --json \
  "只读审查当前项目。列出入口、测试命令、明显风险和待确认问题。" \
  > "$output_dir/events.jsonl" \
  2> "$output_dir/stderr.txt"
status=$?
set -e

printf '%s\n' "$status" > "$output_dir/exit-status.txt"
git status --short > "$output_dir/status-after.txt"

[ "$status" -eq 0 ] || exit "$status"
cmp -s "$output_dir/status-before.txt" "$output_dir/status-after.txt" || exit 2
git diff --exit-code > "$output_dir/diff.txt" || exit 3

printf 'Audit completed; inspect %s\n' "$output_dir"
SH

chmod +x run-codex-audit.sh
./run-codex-audit.sh "$PWD"
```

状态文件相同且 `git diff --exit-code` 通过，可以说明当前 Git 工作区没有被这次任务改变；数据库、网络、项目外文件和其他外部系统仍不在这组证据范围内。

## 5. 修改型任务停在可审查工作区，再综合判断成功

由人建立任务分支和任务文件：

```bash
git switch -c task/parser-tabs

cat > task.md <<'EOF'
目标：修复解析器处理制表符的问题。
允许修改：src/parser.py、tests/test_parser.py。
验证：python -m pytest tests/test_parser.py -q。
需要扩大范围时停止并报告。
EOF
```

运行：

```bash
codex exec \
  --sandbox workspace-write \
  --ask-for-approval never \
  "读取 task.md 并执行任务"
```

结束后重新读取工作区并运行测试：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
python -m pytest tests/test_parser.py -q
```

自动化到这里产生的是候选修改。暂存、提交、推送和 PR 属于后续发布流程，不应隐藏在同一次 `exec` 中。

判断一次执行是否成功，至少同时看进程退出状态、stderr、JSONL 或最终消息、测试命令、生成文件和 Git diff。只读任务要求工作区前后不变，修改任务要求变化只落在允许文件。模型总结只是其中一个输出。

外层调度还应设置最大时间、尝试次数和人工介入条件。GNU/Linux 可以使用 `timeout 20m codex exec "TASK"`；macOS 可以由 CI、Python 包装器或调度平台控制。无限重试既消耗用量，也可能让同一错误反复修改工作区。CI 中应按组织策略注入 Platform API Key 或企业 Access Token，不复制个人浏览器会话或整个 `~/.codex`；版本、凭据、日志和产物策略由 CI 明确管理。
