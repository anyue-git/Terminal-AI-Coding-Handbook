# 03 交互模式与自动化

> 最近核对：2026-07-28

Codex CLI 有两种常见使用方式：

```text
交互模式
→ 人在回路中，边看边改

codex exec
→ 固定输入，由脚本或 CI 非交互执行
```

人工参与越少，工作目录、权限、输出、超时和停止条件就越要写清楚。

---

## 1. 交互模式适合什么

```bash
cd PROJECT_PATH
pwd
git status
codex
```

适合：

- 理解陌生项目；
- 讨论方案；
- 分阶段修改；
- 观察权限申请；
- 中途纠正方向；
- 处理复杂失败。

推荐节奏：

```text
只读调查
→ 输出计划
→ 人工确认
→ 修改少量文件
→ 运行测试
→ 查看 diff
→ 再继续
```

---

## 2. 交互界面的常用命令

常见入口包括：

```text
/status
/permissions
/model
/review
/init
```

它们用于查看状态、权限、模型、审查变更和初始化 `AGENTS.md`。具体命令以当前界面帮助和 `codex --help` 为准。

---

## 3. `codex exec` 是什么

```bash
codex exec "只读检查当前项目"
```

它适合：

- CI；
- 脚本；
- 批量只读分析；
- 固定范围机械修改；
- 生成结构化报告；
- 产出可审查补丁。

不适合直接自动化生产数据库、不可逆删除、模糊重构、高权限系统配置或没有测试覆盖的依赖升级。

使用前查看：

```bash
codex exec --help
```

---

## 4. 工作目录必须显式

不要依赖脚本碰巧从哪个目录启动：

```bash
cd PROJECT_PATH
pwd
git branch --show-current
git status --short
codex exec "只读检查当前项目"
```

自动化日志至少记录：

- 当前目录；
- 当前分支；
- Git 状态；
- Codex 版本；
- 实际任务文本。

否则失败后连“它到底在哪个仓库里跑的”都说不清。

---

## 5. 自动化输入要像任务单

不要只写：

```text
帮我修一下代码。
```

更合适的是：

```text
目标：修复解析器对制表符处理错误的问题。
允许修改：src/parser.py、tests/test_parser.py。
禁止修改：依赖、CI、配置和其他目录。
验证命令：python -m pytest tests/test_parser.py -q。
输出：变更摘要、测试结果、未解决问题和风险。
不要执行 git add、commit 或 push。
```

至少要说明目标、目录、允许范围、禁止范围、验证命令、网络、依赖安装和失败停止条件。

---

## 6. JSONL 事件流和最终输出不是同一件事

当前版本支持通过 `--json` 输出 JSON Lines 事件流：

```bash
codex exec --json "TASK"
```

每一行可能代表工具调用、文件修改、消息、错误或最终结果。不要只搜索 `success` 字样就宣布任务成功。

需要约束最终回答结构时，可以使用输出 Schema；需要保存最终消息时，可以使用当前版本提供的输出文件参数。具体名称以 `codex exec --help` 为准。

结构化输出只能约束回答格式，不能证明测试真的运行、文件没有越界或命令没有副作用。

---

## 7. 恢复会话前重新检查项目

非交互会话可以恢复，但恢复的是上下文，不是文件快照。

恢复前先运行：

```bash
pwd
git status
git log -5 --oneline
```

然后要求 Codex 重新核对现实状态，不要直接沿用旧假设。

---

## 8. 自动化中的 Sandbox 与审批

自动化应显式理解：

```text
Sandbox
→ 能访问和修改什么

审批策略
→ 是否向用户请求批准
```

常见 Sandbox 是 `read-only`、`workspace-write` 和 `danger-full-access`；常见审批策略包括 `untrusted`、`on-request` 和 `never`。

非交互任务不能依赖临时弹窗。不要在普通机器上模糊组合最高权限与永不询问。

---

## 9. 认证与日志边界

本地运行通常使用本机已保存的官方认证状态。CI 中应使用组织批准的 Secret 或工作负载身份，不要复制浏览器会话或整个本机认证目录。

日志中不要输出：

- API Key；
- 完整环境变量；
- 认证文件；
- 私有源码全文；
- 用户数据。

生成的报告和构建产物也可能包含项目细节，不应默认公开上传。

---

## 10. 判断成功不能只看退出消息

自动化应分别检查：

```text
进程退出状态
标准输出和错误输出
JSONL 事件
最终消息
测试报告
生成文件
Git diff
```

预期只读时：

```bash
git diff --exit-code
```

预期修改时：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

并确认变化只发生在允许范围内。

---

## 11. 不要无限重试

自动化必须设置：

- 最大尝试次数；
- 时间限制；
- 最大任务轮数；
- 文件范围；
- 失败停止条件；
- 人工介入点。

无限重试可能重复安装依赖、消耗额度、持续修改同一文件和放大错误。

---

## 12. Git 自动化停在哪里比较合适

推荐让 Codex 自动化停在：

```text
修改工作区
+ 运行测试
+ 输出差异摘要
```

暂存、提交、推送和创建 PR 应由明确的后续流程处理，而不是因为代码生成结束就自动连成一串。

---

## 13. 一个可直接改写的脚本化任务模板

```text
目标：

工作目录：

允许修改：

禁止修改：

验证命令：

网络与依赖：

输出要求：

停止条件：
- 需要扩大范围；
- 需要更高权限；
- 连续失败；
- 测试结果与预期矛盾；
- 无法找到足够证据。

不要执行 git add、commit 或 push。
```
