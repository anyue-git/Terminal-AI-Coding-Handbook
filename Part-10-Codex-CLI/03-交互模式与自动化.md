# 03 交互模式、`codex exec` 与自动化

> 最近核对：2026-07-29
>
> `codex exec` 的参数和事件格式可能继续演进。脚本投入 CI 前，应锁定 Codex 版本并检查本机 `codex exec --help`。

Codex CLI 有两条主要使用路径：

```text
codex
→ 交互式 TUI
→ 人可以观察、纠正、审批和分阶段推进

codex exec
→ 非交互执行
→ Prompt、权限、工作目录和输出必须事先写清楚
```

二者使用同一套项目文件、模型和配置，但交互方式与风险控制不同。任务越自动化，就越不能依赖“出问题时我再看弹窗”。

## 1. 哪些任务适合交互模式

在项目根目录运行：

```bash
cd ~/Projects/my-project
pwd
git status
codex
```

交互模式适合：

- 第一次理解陌生项目；
- 需求存在歧义；
- 需要比较多个方案；
- 修改范围可能逐步变化；
- 测试失败后需要人工判断；
- 命令可能触发审批；
- 需要使用 `/review`、`/fork` 或中途纠正方向。

推荐节奏：

```text
只读调查
→ 输出文件级计划
→ 人工确认
→ 修改一个阶段
→ 运行对应测试
→ 查看 Git diff
→ 再决定是否继续
```

不要把交互模式当成“无限聊天直到代码看起来能跑”。每一阶段仍应有明确停止点和验证结果。

## 2. 交互界面中的常用入口

当前常用命令包括：

```text
/status
/permissions
/model
/init
/review
/resume
/fork
```

具体命令以界面帮助为准。它们分别解决不同问题：

```text
/status
→ 当前目录、模型、认证与配置状态

/permissions
→ 权限模式和批准边界

/model
→ 模型与推理强度

/init
→ 生成 AGENTS.md 初稿

/review
→ 对当前变更做独立审查

/resume
→ 恢复历史会话

/fork
→ 从当前上下文复制出新会话
```

`/fork` 很适合保留原始实现会话，再从同一上下文创建一个“只读审查”或“替代方案”分支。它分叉的是对话，不是 Git 分支；文件隔离仍需 Git branch 或 Worktree。

## 3. `codex exec` 是什么

最小形式：

```bash
codex exec "只读总结当前项目结构"
```

也可以从标准输入传入长任务：

```bash
cat task.md | codex exec -
```

它适合：

- CI 中的只读审查；
- 固定范围的机械修改；
- 批量生成结构化报告；
- 对多个仓库运行同一检查；
- 生成可人工审查的补丁；
- 无法使用全屏 TUI 的环境。

不适合直接无人值守执行：

- 生产数据库迁移；
- 模糊的大规模重构；
- 系统网络与防火墙修改；
- 不可逆删除；
- 自动强制推送；
- 没有测试与回滚方案的依赖升级。

## 4. 自动化首先要固定工作目录

不要让脚本依赖调用者碰巧位于哪个目录。可以先显式切换：

```bash
PROJECT="$HOME/Projects/my-project"
cd "$PROJECT"

pwd
git branch --show-current
git status --short
codex exec "只读检查当前项目"
```

也可以使用 Codex 的目录参数：

```bash
codex exec \
  --cd "$HOME/Projects/my-project" \
  "只读检查当前项目"
```

部分版本也接受简写：

```bash
codex exec -C "$HOME/Projects/my-project" "TASK"
```

自动化日志至少应记录：

```bash
hostname
pwd
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short
codex --version
codex login status
```

否则失败以后可能连“在哪台机器、哪个分支、哪个提交上执行”都无法确定。

## 5. Git 仓库检查不是多余限制

`codex exec` 默认要求工作目录处于 Git 仓库中。这样做有助于识别项目边界并使用 diff 检查结果。

对一次性非 Git 目录，当前版本提供：

```bash
codex exec --skip-git-repo-check "TASK"
```

这个参数只跳过仓库检查，不会创建恢复点或自动保护文件。使用前应明确目录内容可恢复，并避免在家目录、下载目录或系统目录中运行。

对于正式项目，不要为了省事跳过 Git 检查。先初始化仓库或进入正确目录通常更合理。

## 6. 自动化任务必须像一张执行工单

不要只写：

```text
帮我修一下代码。
```

更完整的任务应包含：

```text
目标：修复解析器无法正确处理制表符的问题。

工作目录：当前 Git 仓库根目录。

允许读取：src/parser.py、tests/test_parser.py、pyproject.toml。
允许修改：src/parser.py、tests/test_parser.py。
禁止修改：依赖、锁文件、CI、配置和其他目录。

验证命令：python -m pytest tests/test_parser.py -q。
网络：不允许。
Git：不要执行 add、commit、push、reset、clean 或 rebase。

停止条件：
- 需要修改允许范围外文件；
- 需要安装依赖；
- 现有行为与任务描述矛盾；
- 测试失败原因不是本次修改；
- 连续两次尝试仍无法通过目标测试。

最终输出：修改文件、核心差异、运行命令、退出状态、测试结果、未验证内容和风险。
```

任务文本越接近可审查工单，自动化越容易稳定复现。

## 7. 显式设置 Sandbox 与审批

只读自动分析：

```bash
codex exec \
  --sandbox read-only \
  --ask-for-approval never \
  "只读审查当前项目，不要修改文件"
```

普通工作区修改：

```bash
codex exec \
  --sandbox workspace-write \
  --ask-for-approval never \
  "按照 task.md 完成修改；无法在现有边界内完成时停止并报告"
```

非交互任务不能等待临时弹窗，因此 `never` 的含义应是“越界就失败”，而不是“把所有操作都放行”。

不要在普通机器上组合：

```text
danger-full-access
+
never
```

旧教程中的：

```bash
codex exec --full-auto
```

当前仅作为弃用兼容入口。新脚本应明确写出所需 Sandbox 和审批策略。

## 8. `--add-dir` 会扩大可访问目录

有些项目依赖同级共享库：

```text
~/Projects/app
~/Projects/shared-lib
```

可以在 `app` 中运行：

```bash
codex exec \
  --cd "$HOME/Projects/app" \
  --add-dir "$HOME/Projects/shared-lib" \
  "只读分析 app 与 shared-lib 的接口关系"
```

额外目录不是普通提示信息，而是扩大工作范围。使用前检查其中是否包含：

- 其他项目的未提交修改；
- `.env`、SSH 密钥或云配置；
- 大型数据集；
- 用户隐私文件；
- 不应由当前任务读取的源码。

不要使用 `--add-dir "$HOME"` 作为通用解决方案。

## 9. 默认会话与临时会话

普通 `codex exec` 会创建可恢复会话。适合分阶段自动化：

```bash
codex exec "只读分析当前测试失败"
```

恢复最近的 exec 会话：

```bash
codex exec resume --last \
  "重新检查当前 Git 状态，只执行计划中的下一步"
```

也可以使用具体会话 ID：

```bash
codex exec resume SESSION_ID "继续任务"
```

一次性检查不需要留在会话历史中时，使用：

```bash
codex exec --ephemeral \
  --sandbox read-only \
  "只读列出项目入口和测试命令"
```

`--ephemeral` 只控制会话持久化，不会删除 Codex 已经写入项目的文件，也不是隐私清除工具。

## 10. 恢复会话前必须重新校准现实

会话保存对话，不保存项目快照。恢复前运行：

```bash
pwd
git branch --show-current
git status
git log -5 --oneline
```

恢复提示中加入：

```text
先不要修改文件。
重新检查当前目录、Git 分支、HEAD、未提交修改、AGENTS.md、依赖文件和测试状态。
说明现实状态与旧会话假设不一致的地方，再决定是否继续。
```

自动化任务之间可能有其他人、其他 Agent 或 CI 改过文件。直接沿用旧上下文容易覆盖新变化。

## 11. 普通文本输出适合人读

默认输出适合终端查看：

```bash
codex exec "解释当前测试失败原因"
```

需要把最终回答保存到文件时，使用当前的最后消息输出参数：

```bash
codex exec \
  --output-last-message codex-report.md \
  "只读审查当前项目并生成 Markdown 报告"
```

简写可能是：

```bash
codex exec -o codex-report.md "TASK"
```

这个文件只保存最终消息，不一定包含完整工具调用过程。验证任务是否真的成功，仍需检查退出状态、测试和 Git diff。

## 12. `--json` 输出 JSON Lines 事件流

自动化系统可以使用：

```bash
codex exec --json "只读检查当前项目"
```

输出是 JSONL：每一行是一个独立 JSON 事件，可能表示：

```text
thread.started
turn.started
item.started
item.completed
turn.completed
error
```

项目和版本不同，事件细节会变化。不要把整段输出当成单个 JSON 对象，也不要只搜索 `success` 字符串。

保存事件：

```bash
codex exec --json "TASK" > codex-events.jsonl
status=$?
printf 'codex exit status: %s\n' "$status"
```

快速验证每行能否解析：

```bash
python - <<'PY'
import json
from pathlib import Path

path = Path("codex-events.jsonl")
for number, line in enumerate(path.read_text().splitlines(), start=1):
    json.loads(line)
print("valid jsonl")
PY
```

事件日志可能包含文件路径、代码片段和模型输出，不应默认上传到公共构建产物。

## 13. 输出 Schema 约束最终回答

需要机器读取固定结构时，可以准备 JSON Schema：

```bash
cat > codex-output.schema.json <<'JSON'
{
  "type": "object",
  "properties": {
    "summary": {"type": "string"},
    "files_changed": {
      "type": "array",
      "items": {"type": "string"}
    },
    "tests": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "command": {"type": "string"},
          "result": {"type": "string"}
        },
        "required": ["command", "result"],
        "additionalProperties": false
      }
    },
    "risks": {
      "type": "array",
      "items": {"type": "string"}
    }
  },
  "required": ["summary", "files_changed", "tests", "risks"],
  "additionalProperties": false
}
JSON
```

运行：

```bash
codex exec \
  --output-schema codex-output.schema.json \
  --output-last-message codex-result.json \
  "执行 task.md 中的任务，最终严格按照 Schema 输出"
```

Schema 只能约束最终回答格式，不能证明：

- 测试真的运行；
- 文件没有越界修改；
- 命令没有副作用；
- 模型总结与实际 diff 一致。

## 14. 一个完整的只读自动化练习

在独立练习仓库中创建脚本：

```bash
cat > run-codex-audit.sh <<'SH'
#!/bin/sh
set -eu

project=${1:?usage: run-codex-audit.sh PROJECT_PATH}
output_dir=${2:-codex-audit-output}

cd "$project"
mkdir -p "$output_dir"

{
  printf 'hostname: '
  hostname
  printf 'pwd: '
  pwd
  printf 'branch: '
  git branch --show-current
  printf 'head: '
  git rev-parse HEAD
  printf 'codex: '
  codex --version
} > "$output_dir/environment.txt"

git status --short > "$output_dir/status-before.txt"

set +e
codex exec \
  --ephemeral \
  --sandbox read-only \
  --ask-for-approval never \
  --json \
  "只读审查当前项目。不要修改文件、安装依赖或访问网络。列出项目入口、测试命令、明显风险和仍需人工确认的问题。" \
  > "$output_dir/events.jsonl" \
  2> "$output_dir/stderr.txt"
status=$?
set -e

printf '%s\n' "$status" > "$output_dir/exit-status.txt"
git status --short > "$output_dir/status-after.txt"
git diff --exit-code > "$output_dir/diff.txt"

if [ "$status" -ne 0 ]; then
  printf 'Codex failed with status %s\n' "$status" >&2
  exit "$status"
fi

if ! cmp -s "$output_dir/status-before.txt" "$output_dir/status-after.txt"; then
  printf 'Working tree status changed during read-only audit\n' >&2
  exit 2
fi

printf 'Audit completed; inspect %s\n' "$output_dir"
SH

chmod +x run-codex-audit.sh
```

运行：

```bash
./run-codex-audit.sh "$PWD"
```

这个脚本不仅检查 Codex 的退出状态，还比较执行前后的 Git 状态，并要求只读任务没有产生 diff。

注意：脚本把输出写进项目目录时，这些输出本身可能成为未跟踪文件。正式使用时可以把输出目录放到项目外，或预先加入经过审查的 `.gitignore`。

## 15. 修改型自动化应使用任务分支

在项目根目录由人创建分支：

```bash
git status
git switch -c task/parser-tabs
```

保存任务：

```bash
cat > task.md <<'EOF'
目标：修复解析器处理制表符的问题。
允许修改：src/parser.py、tests/test_parser.py。
验证：python -m pytest tests/test_parser.py -q。
不要修改依赖、配置和其他文件。
不要执行 Git 写操作。
需要扩大范围时停止并报告。
EOF
```

运行：

```bash
codex exec \
  --sandbox workspace-write \
  --ask-for-approval never \
  "读取 task.md 并执行任务"
```

结束后人工检查：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
python -m pytest tests/test_parser.py -q
```

自动化应该停在“工作区修改完成并提供证据”，而不是自动暂存、提交、推送和合并。

## 16. 判断成功不能只看 Codex 最后一句话

至少检查六类证据：

```text
进程退出状态
标准错误
JSONL 事件或最终消息
测试退出状态
生成文件
Git 状态与 diff
```

Shell 中保存退出状态：

```bash
codex exec "TASK"
status=$?
printf 'exit=%s\n' "$status"
```

预期只读时：

```bash
git diff --exit-code
git status --short
```

预期修改时：

```bash
git diff --name-status
git diff --stat
git diff
```

还要确认变化只发生在允许文件中。模型说“测试通过”不等于测试日志和退出状态真的存在。

## 17. 设置外部超时与重试上限

Codex CLI 的任务轮数与超时选项可能随版本变化。自动化系统仍应在外层设置限制。

GNU/Linux 可使用系统提供的 `timeout`：

```bash
timeout 20m codex exec "TASK"
```

macOS 默认没有同名 GNU `timeout`，可以由 CI 平台、Python 包装器或调度系统控制。

无论平台，都应规定：

- 最大执行时间；
- 最大尝试次数；
- 最大费用或用量；
- 允许修改的文件；
- 测试失败后的停止条件；
- 需要人工介入的情况。

不要编写“失败就无限重新让 Agent 修”的循环。它可能重复安装依赖、扩大修改范围并持续消耗额度。

## 18. CI 中的认证与秘密

CI 不应复制个人电脑的浏览器会话或整个 `~/.codex`。

可选路线取决于组织策略：

```text
OpenAI Platform API Key
→ 作为 CI Secret 注入

企业 Codex Access Token
→ 由管理员允许并在可信环境注入
```

日志中不要输出：

- `OPENAI_API_KEY`；
- `CODEX_ACCESS_TOKEN`；
- `auth.json`；
- 完整环境变量；
- 私有源码全文；
- 用户数据和数据库内容。

CI 中还应固定 Codex 版本，避免同一脚本因为 CLI 自动更新而突然改变参数或默认行为。

## 19. 自动化与 Git 写操作的边界

低风险只读命令通常可以在任务中允许：

```bash
git status
git diff
git log
git show
```

建议自动化停在：

```text
修改工作区
+
运行测试
+
输出差异和风险
```

以下操作交给明确的后续发布流程：

- `git add`；
- `git commit`；
- `git push`；
- 创建或更新 PR；
- 合并；
- 历史改写与强制推送。

这样生成代码、验证代码和发布代码之间仍有清晰的审查边界。

## 20. 可复用的 `codex exec` 任务模板

```text
任务目标：

现实状态：
- 工作目录：
- 当前分支：
- 当前 HEAD：
- 工作区是否干净：

允许读取：

允许修改：

禁止修改：

验证命令：

网络与依赖：

Git 边界：
- 不要 add、commit、push、reset、clean、rebase。

输出要求：
- 修改文件；
- 执行命令；
- 测试退出状态；
- 未验证内容；
- 风险。

停止条件：
- 需要扩大范围；
- 需要更高权限；
- 需要安装依赖；
- 现实状态与任务描述冲突；
- 测试失败原因不明确；
- 连续失败达到上限。
```
