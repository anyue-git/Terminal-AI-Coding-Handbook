# 02 服务、版本与常见故障

Homebrew 安装的内容不一定只是“运行一次就退出”的命令。有些 Formula 可以注册为 macOS 后台服务，登录后自动启动并持续监听端口；同一个软件也可能存在多个版本、多个前缀或 keg-only 安装。很多故障不是软件完全没有安装，而是启动了两份服务、PATH 指向了另一个版本，或者升级后数据与配置没有兼容。

本章先学会观察服务，再用一个可选的 Redis 练习说明启动、验证和停止。若你不需要 Redis，可以只阅读命令结构，不必为了练习安装长期不用的软件。

## 1. Formula、Cask 和 Service 是不同维度

Homebrew 中：

```text
Formula
→ 软件包定义，通常包含命令行工具、库或服务程序

Cask
→ 安装上游提供的图形应用或大型预编译软件

Service
→ 让某个已安装程序通过 macOS launchd 持续在后台运行
```

一个 Formula 可以同时提供普通命令和后台服务。例如数据库既能在当前终端手动启动，也能注册为登录后自动运行的服务。

查看某个包的信息：

```bash
brew info FORMULA
```

查看已安装内容：

```bash
brew list --formula
brew list --cask
```

Finder 中有没有应用图标，不能判断 Formula 是否存在；终端能运行一个命令，也不能证明后台服务正在工作。

## 2. 先查看现有服务，不要直接 restart

列出 Homebrew 服务：

```bash
brew services list
```

可能看到：

```text
Name       Status  User  File
redis      started student ~/Library/LaunchAgents/homebrew.mxcl.redis.plist
postgresql none
```

字段含义包括服务名、状态、运行用户和 launchd 配置位置。状态为 `started` 只表示 Homebrew/launchd 认为任务已启动，不保证应用已经成功监听端口或完成初始化。

遇到本地数据库无法连接时，不要第一反应连续执行：

```bash
brew services restart SERVICE
```

先收集：

```bash
brew services list
brew info SERVICE
lsof -nP -iTCP -sTCP:LISTEN
```

如果知道端口：

```bash
lsof -nP -iTCP:PORT -sTCP:LISTEN
```

这样可以判断服务根本未启动、启动后立即退出、监听了不同端口，还是已有另一实例占用端口。

## 3. 服务是否应该常驻

适合注册为服务的通常是：

- 本地数据库；
- Redis 等缓存；
- 明确需要随登录启动的开发组件；
- 需要持续监听、且你经常使用的个人服务。

不适合直接注册为 Homebrew 服务的包括：

- 一次性脚本；
- 临时开发服务器；
- 偶尔运行的项目工具；
- 机器学习训练；
- 需要在项目目录和虚拟环境中启动的任务。

临时程序放在普通终端运行，能直接看到日志，也容易按 `Ctrl + C` 停止。远程训练应使用 tmux、systemd、容器或作业调度器，而不是在 Mac 上用 `brew services` 管理。

## 4. 可选练习：安装并手动运行 Redis

先检查是否已安装：

```bash
brew list --versions redis
```

如果没有且你确实愿意安装这个练习软件：

```bash
brew install redis
```

先不要注册为服务，直接在前台运行：

```bash
redis-server
```

当前终端会显示日志并被占用。另开一个终端，检查默认端口：

```bash
lsof -nP -iTCP:6379 -sTCP:LISTEN
```

再测试：

```bash
redis-cli ping
```

正常结果：

```text
PONG
```

回到运行 `redis-server` 的终端，按 `Ctrl + C` 停止。再次检查端口：

```bash
lsof -nP -iTCP:6379 -sTCP:LISTEN
```

没有输出说明监听已结束。这个练习先让你理解“进程运行”和“端口监听”，再进入后台服务管理。

## 5. 使用 `brew services` 启动和停止

需要长期使用 Redis 时，可以注册为用户级服务：

```bash
brew services start redis
```

随后验证三层状态：

```bash
brew services list
lsof -nP -iTCP:6379 -sTCP:LISTEN
redis-cli ping
```

三层分别回答：

```text
launchd 是否登记任务
→ 程序是否真的监听端口
→ 应用协议是否正常响应
```

停止服务：

```bash
brew services stop redis
```

再次验证：

```bash
brew services list
lsof -nP -iTCP:6379 -sTCP:LISTEN
```

如果只是需要临时运行一次，不必注册为开机或登录自启。服务越多，端口冲突、后台耗电和升级后的兼容问题越难追踪。

## 6. `start`、`run`、`stop` 和 `restart` 的边界

Homebrew 当前手册提供的服务子命令可能包括启动、运行、停止、重启和清理等操作，具体以本机帮助为准：

```bash
brew services --help
```

概念上：

- `start` 通常注册服务并立即启动，使其在后续登录时继续受 launchd 管理；
- `run` 通常只运行而不注册为登录自启；
- `stop` 停止并取消注册；
- `restart` 会停止再启动，可能造成短暂不可用。

不同 Homebrew 版本的细节应以 `brew services --help` 为准。生产数据或重要本地数据库在 restart 前应先确认客户端、迁移状态和备份，而不是把重启当成无副作用的刷新按钮。

## 7. 服务显示 started，但应用不能使用

按顺序检查：

```bash
brew services list
brew info SERVICE
lsof -nP -iTCP:PORT -sTCP:LISTEN
```

若没有监听，寻找日志和 launchd 状态。`brew info SERVICE`、服务输出或 Formula 文档通常会给出配置与日志位置。还可以检查用户 LaunchAgents：

```bash
ls -la ~/Library/LaunchAgents | grep -i SERVICE
```

常见原因包括：

- 配置语法错误；
- 数据目录权限不正确；
- 端口被另一进程占用；
- 同一程序已经手工启动；
- 升级后需要数据迁移；
- 配置仍引用旧版本路径；
- 服务快速崩溃，但 launchd 只记录了尝试启动。

不要先删除数据目录。对于数据库，数据目录通常比 Formula 本身重要得多，卸载和重装软件也不能替代备份与迁移。

## 8. 端口被占用时找到真正的进程

假设应用提示 6379 已被占用：

```bash
lsof -nP -iTCP:6379 -sTCP:LISTEN
```

可能看到进程名、PID 和用户。继续检查：

```bash
ps -p PID -o pid,ppid,user,command
```

确认它来自：

- Homebrew service；
- 另一个包管理器；
- Docker 容器；
- 手工启动的程序；
- 旧版本残留；
- 其他用户的进程。

不要看到端口冲突就直接 `kill -9`。先使用对应工具正常停止，例如：

```bash
brew services stop SERVICE
```

若进程不受 Homebrew 管理，再依据进程来源选择安全停止方式。

## 9. 用户级服务与 sudo 服务不要混用

普通命令：

```bash
brew services start SERVICE
```

通常以当前用户身份注册在用户级 launchd 中。不要因为启动失败就改用：

```bash
sudo brew services start SERVICE
```

管理员级运行可能造成：

- root 所有的数据和日志；
- 同一服务出现用户级与系统级两份实例；
- 普通用户后续无法升级或清理；
- 端口冲突；
- 卸载 Formula 后仍残留系统任务。

先查看服务状态、端口、日志和文件所有权。只有软件的官方文档明确要求系统级服务，并且你理解 launchd 与权限影响时，才考虑管理员级配置。

## 10. 多版本 Formula 与 keg-only

Homebrew 可能提供版本化 Formula，例如：

```text
python@3.x
node@xx
postgresql@xx
```

具体可用版本会随时间变化，不应把某个当前版本永久写成通用答案。查询：

```bash
brew search python@
brew info FORMULA
```

`keg-only` 表示 Formula 安装在 Cellar 中，但没有默认链接到 Homebrew 通用前缀，因此普通 PATH 可能找不到它。查看安装提示：

```bash
brew info FORMULA
```

检查实际命令来源：

```bash
type -a COMMAND
command -v COMMAND
printf '%s\n' "$PATH" | tr ':' '\n'
```

不要因为“找不到”就强制链接 keg-only Formula。强制链接可能覆盖系统工具或另一个版本。项目需要特定版本时，优先使用项目环境、版本管理器，或者按照 `brew info` 提供的明确 PATH 设置。

## 11. `link`、`unlink` 与 `pin` 会改变什么

`brew link` 会把 Formula 的文件链接到 Homebrew 前缀；安装普通 Formula 时通常已经自动完成。手工操作前先预演：

```bash
brew link --dry-run FORMULA
brew unlink --dry-run FORMULA
```

查看当前来源：

```bash
brew info FORMULA
type -a COMMAND
```

`--overwrite` 可能删除冲突链接，`--force` 可能强制链接 keg-only Formula，都不应作为新手默认选项。

短期阻止某个 Formula 被升级：

```bash
brew pin FORMULA
brew list --pinned
```

恢复升级：

```bash
brew unpin FORMULA
```

Pin 只是本机包管理策略，不能替代项目的 Python/Node 版本声明、依赖锁文件和 CI 测试。换一台 Mac 后，它不会自动跟随项目。

## 12. 全量升级为什么容易影响项目

查看可升级项目：

```bash
brew update
brew outdated
```

无参数全量升级可能改变：

- Python 和 Node 解释器；
- 数据库主版本；
- 动态库 ABI 与路径；
- 编译工具链；
- 后台服务二进制；
- AI CLI 的运行依赖。

重要项目期间采用小范围流程：

```text
记录当前命令路径和版本
→ 选择一个明确 Formula
→ 阅读上游和 Homebrew 信息
→ 备份相关数据
→ 停止或安排服务窗口
→ 升级
→ 验证路径、端口和协议
→ 运行项目测试
```

数据库跨主版本升级可能需要导出、迁移或专用工具。不要把“brew upgrade 返回成功”当成数据已经兼容。

## 13. Apple Silicon 上的两套 Homebrew

迁移、Rosetta 或旧配置可能留下：

```text
/opt/homebrew    arm64 Homebrew
/usr/local       可能存在 Intel Homebrew
```

检查：

```bash
arch
command -v brew
type -a brew
brew --prefix
file "$(command -v brew)"
```

同一个命令在原生终端和 Rosetta 终端中可能来自不同前缀。服务也可能由另一套 Homebrew 注册，导致“当前 brew services list 看不到，但端口仍被占用”。

处理前应分别调用两套 `brew` 可执行文件记录包清单和服务，不要直接删除 `/usr/local`。那里不仅可能有 Intel Homebrew，也可能有其他软件手工安装的内容。

## 14. 卸载和 cleanup 前检查依赖与数据

查看谁依赖 Formula：

```bash
brew uses --installed FORMULA
brew deps FORMULA
```

查看服务是否运行：

```bash
brew services list
```

数据库类 Formula 还要确认：

- 数据目录位置；
- 是否已有备份；
- 是否需要迁移；
- 卸载 Formula 是否会保留数据；
- Cask 的 zap 是否会删除配置或数据。

清理旧版本前只预览：

```bash
brew cleanup -n
```

不要手工删除 Cellar 中的随机目录，也不要假设卸载程序等于安全删除数据。

## 15. AI CLI 的服务与版本边界

可以给 Agent 这样的约束：

```text
先只读检查 Homebrew 前缀、架构、命令来源、已安装版本、服务状态、端口和日志位置。
不要执行全量 upgrade、cleanup、link、unlink、pin、卸载或服务重启。
不要使用 sudo brew services，不要递归修改 Homebrew 或数据目录权限。
提出变更前说明：
- 当前运行的是哪一份程序；
- 是否存在多版本或多架构；
- 服务是否真的需要常驻；
- 是否涉及数据目录和迁移；
- 怎样验证和回滚。
```

固定排查清单：

```bash
arch
brew --version
brew --prefix
brew config
brew services list
brew outdated
type -a brew python3 node
lsof -nP -iTCP -sTCP:LISTEN
```

遇到具体服务问题，再添加：

```bash
brew info SERVICE
lsof -nP -iTCP:PORT -sTCP:LISTEN
ps -p PID -o pid,ppid,user,command
```
