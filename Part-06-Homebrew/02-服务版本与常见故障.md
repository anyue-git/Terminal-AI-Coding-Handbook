# 02 服务、版本与常见故障

Homebrew 安装的不一定只是运行一次就退出的命令。有些 Formula 可以通过 macOS launchd 持续运行；同一个软件也可能存在多个版本、多个前缀或 keg-only 安装。连接失败时，原因常常不是“软件没装”，而是服务未启动、端口被另一实例占用、PATH 指向不同版本，或者升级后的配置与数据还没有迁移。

本章用可选 Redis 练习串起软件包、前台进程、后台服务、监听端口和协议验证。没有 Redis 使用需求时，可以只阅读命令结构。

## 1. 从 Formula 到可验证的后台服务

Formula 描述软件包，Cask 安装图形应用或大型预编译程序，Service 则让某个已安装程序在后台持续运行。一个 Formula 可以同时提供普通命令和服务定义：

```bash
brew info FORMULA
brew list --formula
brew list --cask
brew services list
```

Finder 中有图标不能证明它是 Cask，终端能运行命令也不能证明后台服务健康。`brew services list` 中的 `started` 只表示 Homebrew/launchd 已登记并尝试启动任务；应用是否完成初始化，还要结合进程、端口和协议判断。

本地数据库或缓存无法连接时，先查看：

```bash
brew services list
brew services info SERVICE
brew info SERVICE
lsof -nP -iTCP -sTCP:LISTEN
```

已知端口时缩小范围：

```bash
lsof -nP -iTCP:PORT -sTCP:LISTEN
```

这些结果可以区分服务未启动、启动后立即退出、监听了其他端口、已有另一实例占用端口，以及进程存在但应用协议尚未就绪。经常使用的本地数据库和缓存适合注册服务；临时开发服务器、训练任务和依赖项目虚拟环境的程序通常更适合普通终端、tmux、容器或专门的服务管理器。

Redis 练习先确认安装状态：

```bash
brew list --versions redis
```

确实需要练习时再执行 `brew install redis`。第一次以前台方式启动：

```bash
redis-server
```

另开终端验证端口和协议：

```bash
lsof -nP -iTCP:6379 -sTCP:LISTEN
redis-cli ping
```

正常响应是 `PONG`。回到服务终端按 `Ctrl + C`，再次检查端口，可以观察进程结束后监听随之消失。

确定要长期使用时，注册用户级服务并同时验证 launchd、端口和协议：

```bash
brew services start redis
brew services list
lsof -nP -iTCP:6379 -sTCP:LISTEN
redis-cli ping
```

停止并取消注册：

```bash
brew services stop redis
brew services list
lsof -nP -iTCP:6379 -sTCP:LISTEN
```

`start` 通常注册并立即启动，`run` 通常只运行而不注册，`restart` 会造成短暂中断；具体行为查看：

```bash
brew services --help
```

数据库类服务在重启前还要考虑客户端连接、迁移、数据目录和备份。

## 2. 服务显示 started 时仍要找到真实进程和数据

应用不可用时沿同一条链查看状态、Formula 信息、端口、LaunchAgent 和进程：

```bash
brew services list
brew services info SERVICE
brew info SERVICE
lsof -nP -iTCP:PORT -sTCP:LISTEN
ls -la ~/Library/LaunchAgents | grep -i SERVICE
```

普通列表无法解释状态时，可以增加 Homebrew 与 launchctl 的调试信息：

```bash
brew services list --debug
```

调试输出可能包含用户名、路径、服务文件和本地环境，发送给别人前仍需检查和脱敏。它能帮助定位登记失败或 launchd 状态异常，但不能替代应用自己的日志和协议验证。

端口被占用时查明进程身份：

```bash
lsof -nP -iTCP:PORT -sTCP:LISTEN
ps -p PID -o pid,ppid,user,command
```

常见原因包括配置语法错误、数据目录权限、同一程序已手工启动、Docker 或另一包管理器占用端口、升级后需要迁移，以及配置仍引用旧路径。确定进程属于哪套管理方式后，再用对应工具正常停止；`kill -9` 只适合进程无法正常退出且影响已经明确的情况。

普通 `brew services start SERVICE` 以当前用户注册用户级服务。改用 `sudo brew services start SERVICE` 可能产生 root 所有的数据与日志、第二份系统级实例和端口冲突。软件确实要求系统级服务时，应按照官方说明配置；普通故障优先检查状态、日志、端口和文件所有权。

数据目录与 Formula 本身也要分开看。卸载或重新安装程序只能替换程序文件，不能恢复被删除或损坏的数据；排错时应先保护数据和配置，再处理软件包。

已经卸载 Formula，却仍看到废弃的 Homebrew 服务登记时，先核对 `brew services list`、`~/Library/LaunchAgents` 和 `brew services --help`。确认条目确实不再使用后，可以评估：

```bash
brew services cleanup
```

这个命令用于移除 Homebrew 判断为未使用的服务登记，不会修复应用数据，也不应被当成数据库故障的常规第一步。手工创建的 launchd 任务、其他包管理器的服务和仍有数据迁移需求的程序需要分别处理。

## 3. 多版本、keg-only 与升级后的故障属于同一条路径链

版本化 Formula 会变化，查询当前可用项而不是长期写死编号：

```bash
brew search python@
brew info FORMULA
type -a COMMAND
command -v COMMAND
printf '%s\n' "$PATH" | tr ':' '\n'
```

keg-only 表示软件已安装，但没有默认链接到 Homebrew 通用前缀。项目需要特定版本时，可以使用项目环境、版本管理器，或按 `brew info` 提示把对应目录加入 PATH。手工 link/unlink 前先预演：

```bash
brew link --dry-run FORMULA
brew unlink --dry-run FORMULA
```

`--overwrite` 和 `--force` 会改动更多现有链接，应在确认冲突来源后使用。`brew pin FORMULA` 只阻止当前 Mac 自动升级某个 Formula，不会成为项目版本声明，也不会随仓库同步到另一台机器。

升级后同时检查程序、路径、服务和数据迁移：

```bash
brew info FORMULA
brew list --versions FORMULA
type -a COMMAND
brew services list
```

数据库和长期服务还要阅读升级说明，确认数据格式、配置位置和客户端兼容性。重新安装 Formula 解决的是程序文件，不等于完成数据迁移。

Apple Silicon Mac 还可能同时存在 `/opt/homebrew` 的原生 Homebrew 与 `/usr/local` 中的 Intel/Rosetta 安装。当前 PATH 中的 `brew` 只能代表当前选中的那套工具；服务或端口来源不清楚时，分别核对存在的可执行文件：

```bash
for brew_path in /opt/homebrew/bin/brew /usr/local/bin/brew; do
  if [ -x "$brew_path" ]; then
    printf '\n== %s ==\n' "$brew_path"
    "$brew_path" --prefix
    "$brew_path" services list
  fi
done
```

这组命令只读记录两套前缀及其服务视图。不要因为其中一套看起来旧，就直接删除 `/usr/local`；那里还可能包含其他软件和历史数据。确认服务属于哪套 Homebrew 后，再使用同一套绝对路径执行后续管理命令。

## 4. 让排查结果能够解释下一步操作

一条可复用的顺序是：

```text
确认对象属于 Formula、Cask 还是后台 Service
→ 查看 brew services、services info 与 brew info
→ 找到真实进程和监听端口
→ 使用协议命令验证应用
→ 检查日志、配置、文件所有权和数据目录
→ 判断是否存在手工实例、Docker、另一版本、另一前缀或另一包管理器
→ 再决定 start、stop、restart、cleanup、link 或升级
```

让 Agent 协助时，可以让它只读收集状态、端口、进程、版本、前缀和日志路径。重启数据库、清理服务登记、删除数据目录、注册管理员级服务和强制链接属于后续人工决定，不应成为自动排错的第一步。
