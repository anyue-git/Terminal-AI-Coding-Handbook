# 03 依赖声明、锁定与环境复现

“我的电脑上能运行”只说明当前机器的某个环境恰好满足条件。一个真正可以交给队友、CI 和远程 Ubuntu 重建的 Python 项目，还需要记录 Python 版本、直接依赖、完整解析结果、包来源、创建命令、测试命令和平台限制。

本章先区分依赖声明、锁文件和环境快照，再分别给出 pip/venv、uv 与 Conda 项目的复现方式。

> 技术核对：2026-07。依赖工具更新较快，命令应同时参考仓库说明、本机 `--help` 和官方文档。

## 1. 三类文件解决不同问题

```text
依赖声明
→ 项目需要什么，以及允许哪些版本

锁文件
→ 某次解析最终选中了哪些精确版本、构建和来源

环境快照
→ 当前这台机器的环境中恰好装了什么
```

三者相关，但不能互相替代。一个杂乱环境的 `pip freeze` 可以记录现状，却不能说明哪些包是项目主动依赖；只有宽松的 `pyproject.toml` 声明，则不能保证几个月后解析出完全相同的传递依赖。

复现还需要项目外信息：

```text
操作系统与 CPU 架构
Python 版本
包索引或 Conda Channel
原生系统库
GPU 驱动和 CUDA 条件
创建、运行和测试命令
```

锁文件无法锁定操作系统内核、NVIDIA 驱动、Docker Engine 或本机环境变量。

## 2. 直接依赖与传递依赖

假设项目代码直接导入：

```python
import requests
from pydantic import BaseModel
```

那么 `requests` 和 `pydantic` 是直接依赖。它们继续依赖的 `urllib3`、`certifi` 等包属于传递依赖。

合理的分工通常是：

```text
项目声明
→ 记录直接依赖、Python 要求和允许版本范围

锁文件
→ 记录直接与传递依赖的完整解析结果
```

不要把开发电脑中所有已安装包都当作直接依赖。环境中可能包含编辑器插件、调试工具、Notebook 组件和其他项目残留。

## 3. `requirements.txt` 可以是声明，也可以是精确安装清单

一个简单文件可能写成：

```text
requests>=2.32,<3
pydantic>=2.10,<3
```

安装：

```bash
python -m pip install -r requirements.txt
```

这里表达的是允许范围，未来可能解析出更新的兼容版本。

也可以写成完全固定版本：

```text
requests==2.32.5
pydantic==2.11.7
```

但仅固定直接依赖，仍不一定锁住所有传递依赖。团队需要明确该文件承担哪种角色：

- 人工维护的直接依赖声明；
- 工具生成的完整约束；
- 某个部署环境的精确清单；
- 开发、测试或生产的分层 requirements 文件。

同一个仓库中多个 requirements 文件应有清楚生成关系，不能彼此独立手改后都声称是权威来源。

## 4. `pip freeze` 记录环境现状，不自动设计项目依赖

查看当前环境：

```bash
python -m pip freeze
```

写入文件：

```bash
python -m pip freeze > environment-snapshot.txt
```

它会列出当前环境中已安装的分发包和版本。适合：

- 故障排查证据；
- 迁移前临时备份；
- 对比两个环境；
- 记录一次实验所用环境；
- 为尚未规范化的旧项目保留现状。

它不会告诉你：

- 哪些包是直接依赖；
- 为什么选择某个版本；
- 哪些只是开发工具；
- 是否存在不再使用的残留包；
- 这些版本是否适合另一平台。

因此，不要在使用多年的全局环境中直接 freeze，然后把文件命名为“最终可复现依赖”。

## 5. `pyproject.toml` 记录现代 Python 项目声明

一个最小示例：

```toml
[project]
name = "demo-project"
version = "0.1.0"
requires-python = ">=3.11,<3.14"
dependencies = [
  "requests>=2.32,<3",
  "pydantic>=2.10,<3",
]
```

`requires-python` 说明项目支持的 Python 范围，`dependencies` 记录运行时直接依赖。这里通常表达允许范围，而不是把全部传递依赖固定为唯一版本。

开发和测试依赖应与运行依赖区分。不同工具可能使用标准 dependency groups、可选依赖或自己的配置表，具体结构应以项目当前工具为准。不要让多个工具同时维护互不相干的测试依赖清单。

## 6. 锁文件解决“这次究竟选了什么”

锁文件通常记录：

- 精确版本；
- 传递依赖；
- 文件哈希；
- 包来源；
- Python 与平台条件；
- 某些工具的构建或解析元数据。

它应由对应工具生成和更新，不适合手工大范围编辑。

锁文件通常进入版本控制：

```text
uv.lock
conda-lock.yaml
pixi.lock
工具生成的其他 lock 文件
```

本机环境目录通常不进入版本控制：

```text
.venv/
Conda 环境目录
缓存和下载目录
```

## 7. 用 venv 与 requirements 复现一个简单项目

项目文件：

```text
app.py
requirements.txt
README.md
```

在一台新机器中：

```bash
cd PROJECT_PATH
python3 --version
python3 -m venv .venv
source .venv/bin/activate
python -m pip --version
python -m pip install -r requirements.txt
python app.py
python -m pytest
```

若 `requirements.txt` 只写了宽松范围，安装结果可能随时间变化。需要更严格复现时，可以使用经过维护的约束文件、哈希锁定工具或迁移到带锁文件的项目管理方案。

README 不应只写：

```text
安装依赖后运行项目。
```

至少应说明 Python 版本、环境创建命令、依赖安装命令、运行入口和测试命令。

## 8. uv 项目的声明、锁定与同步

uv 项目常见：

```text
pyproject.toml
uv.lock
.venv/
```

添加依赖：

```bash
uv add requests
```

当前 uv 会更新 `pyproject.toml`、锁文件和项目环境。只检查锁文件是否与项目声明一致：

```bash
uv lock --check
```

按照现有锁文件同步，并在锁文件过期时失败：

```bash
uv sync --locked
```

运行测试：

```bash
uv run pytest
```

当前 uv 中，`uv sync` 默认进行精确同步，会移除锁文件中没有声明的额外包；`uv run` 默认使用较宽松的同步方式，确保所需包存在但通常不会清除所有额外包。CI 和正式复现流程应明确写出：

```bash
uv sync --locked
uv run pytest
```

不要依赖某个开发者本地环境恰好已经同步。

## 9. uv 锁文件不会因为上游发布新版本自动变化

已有 `uv.lock` 时，uv 会优先保留锁定版本。上游出现新版本并不自动让锁文件失效。

升级全部依赖：

```bash
uv lock --upgrade
```

只升级一个包：

```bash
uv lock --upgrade-package requests
```

升级仍受 `pyproject.toml` 中版本范围限制。依赖升级应作为独立任务：

```text
确认升级目标
→ 阅读变更说明
→ 更新锁文件
→ 检查锁文件 diff
→ 在 Mac、Ubuntu 和 CI 运行相关测试
→ 独立提交
```

不要在修复普通业务 Bug 时顺手更新全部锁定依赖。

## 10. Conda 的环境声明和新式锁文件

传统 Conda 项目常用：

```text
environment.yml
```

示例：

```yaml
name: demo
channels:
  - conda-forge
dependencies:
  - python=3.12
  - requests
  - pip
  - pip:
      - some-pip-only-package
```

创建：

```bash
conda env create -f environment.yml
```

它可以描述环境，但是否精确取决于版本和构建约束。

Conda 26.5 及以后版本加入原生锁文件支持，可记录精确包、版本、构建和 Channel，并支持多平台解析结果。先确认版本：

```bash
conda --version
```

导出锁文件的当前官方示例：

```bash
conda export --name my-env --file conda-lock.yaml
```

创建和安装方式应查看当前 `conda create --help` 与官方文档。仓库若要求兼容旧 Conda，就不能未经讨论直接改成依赖 26.5+ 锁文件的新流程。

Conda 锁文件能记录多个平台的解析结果，但仍不能保证某个包在所有平台都有可用构建，也不能替代 GPU 驱动和系统库检查。

## 11. 锁定不等于 Mac 和 Ubuntu 安装同一个二进制

同一个依赖规则可能在不同平台选择不同 wheel 或 Conda 构建：

```text
macOS arm64
Linux x86_64
Windows x86_64
```

机器学习项目还可能区分：

```text
Mac：CPU / MPS 构建
Ubuntu：CUDA 构建
```

正确流程：

```text
共享源码、声明和锁文件
→ Mac 本地创建环境
→ Ubuntu 本地创建环境
→ 各自解析或选择平台兼容构建
→ 分别运行测试
→ Ubuntu 额外验证 CUDA
```

不要提交或同步整个 `.venv`。环境中的启动脚本、绝对路径和原生二进制通常与创建它的机器绑定。

## 12. 平台条件与可选依赖

`pyproject.toml` 可以使用环境标记：

```toml
[project]
dependencies = [
  "common-package>=1",
  "mac-only-package; sys_platform == 'darwin'",
  "linux-only-package; sys_platform == 'linux'",
]
```

可选功能通常使用 extras 或 dependency groups。例如只有开发者需要的测试工具，不应无条件成为生产运行依赖。

平台标记应反映真实兼容性，不是为了让当前机器“先装过去”而随意添加。GPU 版 PyTorch、自定义 wheel 索引和本地编译扩展经常需要工具专属配置，应参考当前框架官方安装说明，避免长期复制旧 CUDA 命令。

## 13. 包来源也是复现和安全条件

同名包可能来自：

- PyPI；
- 私有 Python 索引；
- Conda Channel；
- Git 仓库；
- 本地目录；
- wheel 文件；
- 内部制品仓库。

只记录版本号不一定足够。锁文件和配置还应明确来源。

使用私有索引时，不要把凭证直接写入可提交 URL：

```text
https://USERNAME:TOKEN@private.example/simple
```

认证应使用环境变量、Keychain、凭证助手或 CI Secret，并确保错误日志不会打印完整请求头和 URL。

使用多个索引或 Channel 还会带来依赖混淆风险。团队应明确可信来源和优先级，不要为了找到一个包随意添加未知镜像。

## 14. 一份可执行的复现说明

uv 项目的 README 可以写：

```text
要求：
- Python 3.12
- uv 当前受支持版本

创建环境：
uv sync --locked

运行：
uv run python -m demo

测试：
uv run pytest

Ubuntu GPU 验证：
uv run python -c "import torch; print(torch.cuda.is_available())"
```

venv/pip 项目可以写：

```text
要求：Python 3.12

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pytest
```

Conda 项目则应写清环境文件或锁文件、最低 Conda 版本、Channel 与测试方式。

复现说明还应包含：

- 当前支持的操作系统和架构；
- 环境变量模板；
- 数据和模型从哪里获取；
- 不能提交的凭证；
- GPU 与系统依赖；
- 常见验证输出。

## 15. 依赖升级应单独审查

升级前记录现状：

```bash
python --version
python -c 'import sys; print(sys.executable)'
git status
```

选择明确范围：

```text
升级一个直接依赖
升级 Python 小版本
升级测试工具组
升级 CUDA/PyTorch 组合
```

更新后重点检查：

- 声明文件和锁文件变化规模；
- 是否更换包来源；
- 是否新增平台条件；
- Python 最低版本是否变化；
- 是否出现弃用警告；
- API、序列化格式或模型结果是否变化；
- Mac、Ubuntu 和 CI 是否都通过。

锁文件出现大量无关变化时，不要只看测试最终为绿色。先确认是否由解析器版本、索引变化或全量升级引起。

## 16. 环境复现失败时按层排查

```text
仓库是否处于正确提交
→ Python 版本是否满足要求
→ 使用的工具与项目一致吗
→ 声明和锁文件是否同步
→ 包来源是否可访问
→ 当前平台是否有兼容构建
→ 原生系统库是否齐全
→ GPU 驱动与框架构建是否匹配
→ 测试命令是否使用正确环境
```

uv 项目：

```bash
uv --version
uv lock --check
uv sync --locked
uv run python -c 'import sys; print(sys.executable)'
uv run pytest
```

venv/pip 项目：

```bash
python --version
python -c 'import sys; print(sys.executable)'
python -m pip --version
python -m pip install -r requirements.txt
python -m pytest
```

Conda 项目：

```bash
conda --version
conda info --envs
conda list
python -c 'import sys; print(sys.executable)'
```

错误发生时保留完整命令、退出状态和关键日志，不要只记录“安装失败”。

## 17. 给 AI CLI 的依赖操作边界

```text
先判断项目使用 requirements、pyproject、uv.lock、environment.yml 还是 Conda 锁文件。
说明哪份文件是权威来源，哪些是生成文件。
不要创建第二套互相竞争的依赖体系。
新增或升级前先说明：
- 为什么现有依赖不能满足；
- 准备修改哪些文件；
- 版本范围如何选择；
- 是否改变索引或 Channel；
- 是否影响 Mac、Ubuntu、GPU 和 CI；
- 运行哪些测试。
不要全量升级，不要提交 .venv，不要输出私有源凭证。
```

完成后人工检查：

```bash
git status --short
git diff -- pyproject.toml uv.lock requirements.txt environment.yml conda-lock.yaml
git diff --stat
```

并在实际环境中运行对应的锁文件检查和测试。
