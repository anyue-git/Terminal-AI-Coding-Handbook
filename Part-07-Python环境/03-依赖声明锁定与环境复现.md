# 03 依赖声明、锁定与环境复现

“我的电脑上能运行”不等于项目可以复现。

真正可复现的 Python 项目，至少要说明：

```text
需要什么 Python
→ 直接依赖是什么
→ 完整解析结果是什么
→ 包从哪里安装
→ 怎样创建、运行和测试
→ 哪些平台条件无法写进锁文件
```

先分清三个概念：

```text
依赖声明
→ 项目需要什么

锁文件
→ 某次解析最终选中了什么

环境快照
→ 当前机器上恰好装了什么
```

它们互相关联，但不能互相替代。

---

## 1. 直接依赖与传递依赖

项目代码主动使用的包叫直接依赖，例如：

```text
requests
pydantic
```

这些包继续依赖的其他包叫传递依赖。

推荐：

```text
项目声明
→ 记录直接依赖和允许版本范围

锁文件
→ 记录完整解析结果
```

不要把当前环境中的所有包都当作项目依赖。环境中可能混有编辑器、调试器、其他项目残留和临时工具。

---

## 2. `requirements.txt` 适合什么

简单示例：

```text
requests==2.32.4
pydantic>=2.10,<3
```

安装：

```bash
python -m pip install -r requirements.txt
```

它适合：

- 简单应用；
- 教学项目；
- 已有 pip 工作流；
- 部署环境要求明确；
- 团队能够维护生成关系。

需要警惕：

- 一个文件里可能混合直接依赖和传递依赖；
- `pip freeze` 输出只是当前环境快照；
- Mac 生成的完整冻结列表可能包含 Ubuntu 不兼容的包；
- 手工编辑多个 requirements 文件容易产生漂移。

---

## 3. `pip freeze` 不是项目设计

```bash
python -m pip freeze > requirements.txt
```

它会记录当前环境中的大量已安装包，但不能说明：

- 哪些是项目真正需要的；
- 哪些只是传递依赖；
- 哪些是临时工具；
- 为什么选择这些版本；
- 是否适用于其他平台。

更适合作为：

- 临时环境快照；
- 故障排查证据；
- 迁移前备份；
- 与正式锁文件进行比较。

不要把一个使用多年的杂乱环境直接 freeze 后称为“可复现配置”。

---

## 4. `pyproject.toml` 负责项目声明

现代 Python 项目通常在 `pyproject.toml` 中声明元数据和依赖：

```toml
[project]
name = "demo"
requires-python = ">=3.11,<3.14"
dependencies = [
  "requests>=2.32,<3",
  "pydantic>=2.10,<3",
]
```

这里表达的是项目允许的范围，不一定锁死每个传递依赖。

开发依赖应与运行依赖区分，具体写法取决于使用的工具。

---

## 5. 锁文件为什么重要

没有锁文件时，同一份宽松声明在不同时间可能解析出不同版本。

锁文件通常记录：

- 直接和传递依赖的具体版本；
- 文件哈希；
- 来源；
- 平台和 Python 条件；
- 解析元数据。

uv 项目常用：

```text
pyproject.toml
uv.lock
```

同步并要求不重新解析：

```bash
uv sync --locked
```

检查锁文件是否与声明一致：

```bash
uv lock --check
```

锁文件通常应进入版本控制，但 `.venv` 不应进入版本控制。

---

## 6. 锁定不等于跨平台二进制完全相同

Mac 和 Ubuntu 可以共享同一份依赖声明与锁定规则，但实际安装的 wheel 可能不同：

```text
macOS arm64
≠
Linux x86_64
```

GPU 项目还可能存在：

```text
Mac：CPU / MPS
Ubuntu：CUDA
```

所以复现必须同时记录：

- 操作系统；
- CPU 架构；
- Python 版本；
- 包索引；
- GPU 驱动与框架构建；
- 系统库。

锁文件无法替你锁定 NVIDIA 驱动、Docker Engine 或操作系统内核。

---

## 7. 环境标记与平台依赖

`pyproject.toml` 可以使用环境标记：

```toml
[project]
dependencies = [
  "common-package>=1",
  "mac-only-package; sys_platform == 'darwin'",
  "linux-only-package; sys_platform == 'linux'",
]
```

但不要为了省事，把所有平台专用包都无条件加入依赖。

GPU 版 PyTorch、自定义索引和本地编译扩展可能需要额外配置，应按照当前官方文档记录，不要长期复制旧命令。

---

## 8. 安装来源也是复现条件

同名包可能来自：

- PyPI；
- 私有索引；
- Conda Channel；
- Git 仓库；
- 本地目录；
- wheel 文件。

因此仅记录版本号仍然不够。

使用私有源时，不要把用户名、密码或 Token 写进可提交的配置。认证应交给环境变量、密钥管理器或 CI Secret。

---

## 9. 一份可执行的复现说明

README 至少应写清：

```text
要求：Python 3.12

创建环境：
uv sync --locked

运行：
uv run python -m demo

测试：
uv run pytest

Ubuntu GPU 验证：
uv run python -c "import torch; print(torch.cuda.is_available())"
```

不要只写：

```text
安装依赖后运行项目
```

别人无法从这句话判断使用哪种工具、哪个 Python、什么测试命令。

---

## 10. 依赖升级应独立进行

不要在修复一个普通 Bug 时顺手升级全部依赖。

推荐流程：

```text
先查看过期依赖
→ 选择一个升级范围
→ 更新声明和锁文件
→ 阅读变更说明
→ 运行测试
→ 检查 diff
→ 独立提交
```

升级后重点检查：

- 锁文件变化规模；
- 是否更换包来源；
- 是否引入新的平台条件；
- 是否出现弃用警告；
- 是否改变 Python 版本要求。

---

## 11. 给 AI CLI 的约束

```text
先判断本项目使用 requirements、pyproject、uv.lock 还是 environment.yml。
不要创建第二套互相竞争的依赖体系。

新增或升级依赖前，先说明：
- 为什么现有依赖不能满足；
- 准备修改哪些文件；
- 版本范围如何选择；
- 是否改变包来源；
- Mac、Ubuntu 和 CI 是否都兼容；
- 运行哪些测试。

不要直接执行全量升级，也不要输出或提交私有源凭据。
```

## 12. 最短复现检查清单

```bash
python --version
python -c 'import sys; print(sys.executable)'
python -m pip --version
git status
```

uv 项目：

```bash
uv lock --check
uv sync --locked
uv run pytest
```

pip 项目：

```bash
python -m pip install -r requirements.txt
python -m pytest
```

还应记录：

```text
操作系统
架构
Python 版本
依赖来源
GPU / 驱动条件
创建命令
测试命令
```
