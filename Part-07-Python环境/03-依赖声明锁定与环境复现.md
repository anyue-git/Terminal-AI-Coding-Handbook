# 03 依赖声明、锁定与环境复现

> 技术核对：2026-07。依赖工具更新较快，实际命令应同时参考仓库说明、本机 `--help` 和官方文档。

“我的电脑上能运行”只说明当前机器的某个环境满足条件。项目要交给队友、CI 或远程 Ubuntu 重建，还需要说明 Python 版本、直接依赖、完整解析结果、包来源、创建与测试命令，以及操作系统、CPU 和 GPU 条件。

## 1. 先找出项目真正以什么为准

依赖声明、锁文件和环境快照回答三个不同问题：

```text
依赖声明
→ 项目主动需要什么，允许哪些版本

锁文件
→ 某次解析最终选择了哪些版本、来源和传递依赖

环境快照
→ 当前机器此刻实际安装了什么
```

`pyproject.toml` 或人工维护的 requirements 往往承担声明职责；`uv.lock`、Conda 锁文件、`pixi.lock` 等记录解析结果；`python -m pip freeze` 更适合故障证据、迁移前快照和旧环境盘点。一个使用多年的开发环境可能包含 Notebook、编辑器插件和其他项目遗留包，freeze 不能自动区分哪些是本项目的直接依赖。

项目外条件同样参与复现：操作系统和 CPU 架构、Python 版本、包索引或 Conda Channel、原生系统库、GPU 驱动和 CUDA。锁文件可以描述平台条件，却不会锁住 Linux 内核、NVIDIA 驱动、Docker Engine 或本机环境变量。

`requirements.txt` 既可以写允许范围：

```text
requests>=2.32,<3
pydantic>=2.10,<3
```

也可能是工具生成的精确安装清单。团队需要明确它是直接声明、约束文件还是部署清单。现代项目常在 `pyproject.toml` 中声明 Python 与直接依赖：

```toml
[project]
name = "demo-project"
version = "0.1.0"
requires-python = ">=3.11,<3.14"
dependencies = [
  "requests>=2.32,<3",
  "pydantic>=2.10,<3",
]
```

开发、测试和运行依赖也应按照项目现有方案分组。多个工具各维护一份互不关联的清单时，环境能够安装并不说明项目已经有唯一权威来源。

跨平台依赖可以使用环境标记，而不是要求每台机器安装完全相同的二进制：

```toml
[project]
dependencies = [
  "common-package>=1",
  "mac-only-package; sys_platform == 'darwin'",
  "linux-only-package; sys_platform == 'linux'",
]
```

可选功能通常通过 extras 或 dependency groups 表达，测试工具不应无条件进入生产运行依赖。平台标记必须反映真实兼容性，不能只为绕过当前机器的安装错误而添加；GPU 版框架、自定义 wheel 索引和原生扩展还需要遵循项目与框架的当前安装方案。

包来源也是依赖的一部分。同名包可能来自 PyPI、私有索引、Conda Channel、Git 仓库、本地目录、wheel 文件或内部制品库，只记录版本号不一定能复现同一内容。私有索引凭据不要直接写入可提交 URL：

```text
https://USERNAME:TOKEN@private.example/simple
```

仓库应记录变量名称、配置模板和登录说明，让真实 Token 来自 Keychain、凭证助手、CI Secret 或受控环境变量。使用多个索引或 Channel 时还要明确可信来源和优先级，避免为了找到一个包随意添加未知镜像。

## 2. 按项目工具在干净位置重建

### venv 与 requirements

一个简单项目可以从新的目录或新的 CI runner 创建环境：

```bash
cd PROJECT_PATH
python3 --version
python3 -c 'import sys; print(sys.executable)'
python3 -m venv .venv
source .venv/bin/activate
python -m pip --version
python -m pip install -r requirements.txt
python app.py
python -m pytest
```

README 至少写明 Python 范围、环境创建、安装、运行入口和测试命令。若 requirements 只给出宽松范围，不同日期可能得到不同传递依赖；要求严格部署的项目可以维护约束文件、哈希锁定结果，或迁移到带项目锁文件的工具。

复现测试应在没有全局用户包、隐式 PATH 和本机残留文件的环境中完成。在原开发环境重新执行一次安装，无法证明声明已经完整。

### uv

uv 项目通常提交 `pyproject.toml` 与 `uv.lock`，忽略 `.venv/`。添加依赖并检查锁文件状态：

```bash
uv add requests
uv lock --check
```

按照已有锁文件同步并运行测试：

```bash
uv sync --locked
uv run pytest
```

当前 uv 的精确同步可能移除锁文件之外的额外包，这有助于发现环境中的隐式依赖。`uv run` 可以确保项目环境，但 CI 中仍适合把同步作为明确步骤。锁文件只有在重新解析时才会变化；升级全部或单个包使用：

```bash
uv lock --upgrade
uv lock --upgrade-package requests
```

升级属于独立维护任务，应同时阅读声明与锁文件 diff，并在目标平台运行相关测试。

### Conda

传统 Conda 项目常使用：

```yaml
name: demo
channels:
  - conda-forge
dependencies:
  - python=3.12
  - requests
  - pip
  - pip:
      - some-pip-only-package
```

创建环境：

```bash
conda env create -f environment.yml
```

`environment.yml` 可以描述 Python、Channel、Conda 包和必要的 pip 包，精确程度取决于版本与构建约束。较新的 Conda 版本提供原生多平台锁文件能力；本书以 26.5 及以后版本为技术核对点，实际导出行为仍以当前帮助为准：

```bash
conda --version
conda export --name my-env --file conda-lock.yaml
```

采用新锁文件前要确认团队最低 Conda 版本和目标平台是否都有对应构建。高层 `environment.yml` 与 Mac、Linux 的精确快照也可以分别维护，不必假设一份平台构建清单能直接跨系统复用。

## 3. 复现结果需要运行证据和分层诊断

无论使用哪套工具，记录至少应包含机器与平台、Python 可执行文件、环境工具版本、创建或同步命令、关键包版本、测试结果和未验证内容：

```bash
python - <<'PY'
import platform
import sys

print("python:", sys.version)
print("executable:", sys.executable)
print("platform:", platform.platform())
PY
```

GPU 项目还要记录框架构建和设备检测。`nvidia-smi`、宿主机 `nvcc`、`torch.version.cuda` 和驱动兼容上限属于不同层，不能压成一个含义模糊的“CUDA 版本”。

macOS arm64、Linux x86_64 与 Windows 可能根据同一锁文件选择不同 wheel；Mac 可能使用 CPU/MPS，Ubuntu 使用 CUDA。正确做法是共享源码、声明和锁定信息，在每个平台本地创建环境并运行对应验证，而不是复制 `.venv/`、Conda 环境目录或缓存。

复现失败时按层定位：

```text
仓库是否处于预期提交
→ Python 版本是否满足要求
→ 使用的工具是否与项目一致
→ 声明和锁文件是否同步
→ 包来源或 Channel 是否可访问
→ 当前平台是否存在兼容构建
→ 原生系统库是否齐全
→ GPU 驱动与框架构建是否匹配
→ 测试是否使用了刚创建的解释器
```

不同工具的最小证据可以分别收集：

```bash
# uv
uv --version
uv lock --check
uv sync --locked
uv run python -c 'import sys; print(sys.executable)'
uv run pytest

# venv / pip
python --version
python -c 'import sys; print(sys.executable)'
python -m pip --version
python -m pip install -r requirements.txt
python -m pytest

# Conda
conda --version
conda info --envs
conda list
python -c 'import sys; print(sys.executable)'
```

错误发生时保留完整命令、退出状态和关键日志，不要只记录“安装失败”。私有包源的环境报告也不应包含完整 `env`、认证 URL 或 Token。

## 4. 依赖变化与业务修改分开审查

依赖升级和工具迁移通常产生较大的锁文件 diff。先看声明变化，再判断锁文件是否只反映目标包、来源是否改变、平台兼容是否变化：

```bash
git diff -- pyproject.toml requirements.txt environment.yml
git diff --stat -- uv.lock conda-lock.yaml
git diff -- uv.lock
```

工具生成的文件也需要审查。diff 大到无法解释时，将依赖升级单独拆成任务和提交，比在普通 Bug 修复中顺手刷新全部锁定包更容易验证和回滚。

一条可复用的复现链是：

```text
识别项目权威依赖文件和工具
→ 确认 Python、平台与包来源
→ 在干净位置创建环境
→ 按声明或现有锁文件同步
→ 运行入口和测试
→ 记录解释器、工具版本、结果与限制
→ 在另一平台重新创建，而不是复制环境目录
```

让 AI 排查环境问题时，先让它列出仓库已有声明、锁文件、CI 命令和实际解释器。当前机器的 `pip freeze` 可以作为证据，但不应在没有确认项目权威来源时直接覆盖依赖文件。新增或升级前还应说明为什么现有依赖不能满足、准备修改哪些文件、是否改变索引或 Channel、怎样影响 Mac/Ubuntu/GPU/CI，以及运行哪些测试；不要自动全量升级、提交 `.venv` 或输出私有源凭据。
