# 01 镜像、容器、卷与网络

Docker 的价值不是“把命令塞进黑盒”，而是把应用运行环境写成可重复构建、启动和审查的描述。

先分清四个核心对象：

```text
Image
→ 镜像，只读模板

Container
→ 容器，镜像的运行实例

Volume
→ 卷，独立于容器生命周期的数据

Network
→ 网络，容器之间和外部通信的边界
```

---

## 1. 镜像不是完整虚拟机

查看镜像：

```bash
docker image ls
```

拉取：

```bash
docker pull python:3.12-slim
```

镜像通常包含：

- 用户空间文件；
- 运行时；
- 依赖；
- 应用代码；
- 默认启动命令；
- 元数据。

镜像不包含一套供容器独占的完整内核。原生 Linux Docker 中，容器共享 Linux 宿主机内核；Docker Desktop for Mac 中，Linux 容器运行在 Docker Desktop 管理的 Linux 虚拟机里，共享该虚拟机的 Linux 内核，而不是直接共享 macOS 的 XNU 内核。因此镜像和容器都不等于一台完整虚拟机。

标签也不是永久不变的内容保证。对复现要求高的项目，应同时保留 Dockerfile、明确标签、镜像摘要和 CI 构建记录，不要只依赖 `latest`。

---

## 2. 容器是一次运行实例

启动临时 Python 容器：

```bash
docker run --rm python:3.12-slim python --version
```

查看运行中的容器：

```bash
docker ps
```

包括已停止容器：

```bash
docker ps -a
```

一个镜像可以启动多个容器。容器停止不等于镜像消失，删除容器也不一定删除持久数据。

进入运行中的容器：

```bash
docker exec -it CONTAINER_NAME sh
```

不要默认每个镜像都有 Bash。

---

## 3. 容器可写层不适合保存重要数据

容器运行时会有自己的可写层，但删除容器后，其中未单独持久化的数据通常也会消失。

所以数据库、训练结果和重要上传文件应放在：

- Docker Volume；
- 明确的 Bind Mount；
- 外部对象存储或数据库。

不要把“容器现在还能看到文件”误解成“数据已经安全持久化”。

---

## 4. Volume 与 Bind Mount

### Volume

创建：

```bash
docker volume create demo-data
```

查看：

```bash
docker volume ls
docker volume inspect demo-data
```

适合：

- 数据库数据；
- 容器管理的持久状态；
- 不需要直接在宿主机编辑的内容。

### Bind Mount

把宿主机目录挂入容器：

```bash
docker run --rm \
  --mount type=bind,src="$PWD",dst=/app \
  -w /app \
  python:3.12-slim \
  python app.py
```

适合：

- 本地源码；
- 配置；
- 需要从宿主机查看的输出。

Bind Mount 会直接暴露宿主机路径。容器内进程如果有写权限，就可能修改或删除宿主机文件。

不要随手挂载：

- 整个 `$HOME`；
- `~/.ssh`；
- 云凭据目录；
- 浏览器数据；
- Docker Socket；
- 不相关项目。

---

## 5. 删除操作要先确认数据归属

删除停止容器：

```bash
docker rm CONTAINER_NAME
```

删除镜像：

```bash
docker image rm IMAGE_NAME
```

删除卷：

```bash
docker volume rm VOLUME_NAME
```

卷可能包含数据库或实验数据。删除前先检查：

```bash
docker volume inspect VOLUME_NAME
docker ps -a --filter volume=VOLUME_NAME
```

不建议新手把 `docker system prune` 当作普通清理命令。它的影响取决于参数和当前 Docker 状态。

---

## 6. 容器网络的基本模型

同一个自定义网络中的容器通常可以通过服务名或容器名通信。

创建网络：

```bash
docker network create demo-net
```

查看：

```bash
docker network ls
docker network inspect demo-net
```

容器内的：

```text
localhost
```

只代表该容器自己，不代表宿主机，也不代表旁边的数据库容器。

多服务项目应优先使用 Docker Compose，让服务名承担内部 DNS 名称。

---

## 7. 端口映射

```bash
docker run --rm \
  -p 127.0.0.1:8080:8000 \
  demo-web
```

含义：

```text
宿主机 127.0.0.1:8080
→ 容器 8000
```

只绑定 `127.0.0.1`，通常表示仅宿主机本地可以访问。

写成：

```text
8080:8000
```

可能绑定所有接口，使局域网甚至更大范围可达。开发服务是否需要对外开放，应明确决定，而不是省略地址后碰运气。

应用还必须在容器内监听正确地址。只监听容器内 `127.0.0.1`，即使映射端口也可能无法从宿主机访问。

## 8. Dockerfile 的最小心智模型

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN python -m pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]
```

构建：

```bash
docker build -t demo-app .
```

运行：

```bash
docker run --rm demo-app
```

注意：

- 构建上下文中的文件可能被发送给 Docker daemon；
- 应使用 `.dockerignore` 排除秘密和大型目录；
- 不要把 Token 写进 Dockerfile；
- 镜像层可能保留曾经复制进去的敏感文件；
- 构建成功不等于应用测试通过。

---

## 9. `.dockerignore` 很重要

示例：

```text
.git
.venv
__pycache__
.env
.env.*
node_modules
runs
checkpoints
*.log
```

它可以减少构建上下文体积，并降低敏感文件进入镜像的风险。

`.dockerignore`、`.gitignore` 和 `.rsyncignore` 分别影响不同工具，不能互相替代。

---

## 10. 容器不是任意不可信代码的绝对安全边界

原生 Linux Docker 中，容器共享 Linux 宿主机内核；Docker Desktop for Mac 中，Linux 容器共享的是其 Linux 虚拟机内核，不是 macOS 的 XNU 内核。无论哪种平台，容器都不是运行任意不可信代码的绝对安全边界。风险会因为以下行为显著扩大：

- 以特权模式运行；
- 挂载 Docker Socket；
- 挂载整个宿主机文件系统；
- 使用 Host Network；
- 赋予额外 Linux Capabilities；
- 运行来源不明的镜像；
- 把真实凭据注入容器。

不要把“它在 Docker 里”当作可以放心运行任何代码的理由。

---

## 11. 常见诊断命令

```bash
docker version
docker info
docker ps -a
docker image ls
docker volume ls
docker network ls
docker logs CONTAINER_NAME
docker inspect CONTAINER_NAME
```

排查顺序：

```text
Docker daemon
→ 镜像是否存在或构建成功
→ 容器进程是否退出
→ 日志
→ 端口和监听地址
→ 环境变量
→ Volume / Bind Mount
→ 网络和依赖服务
```
