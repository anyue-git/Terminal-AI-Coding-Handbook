# 01 镜像、容器、卷与网络

Docker 最容易被误解成“把命令放进一个黑盒里运行”。这种理解能让人暂时把程序启动起来，却解释不了为什么容器退出、端口打不开、源码没有更新，或者删除容器后数据消失。

这一章用一个很小的 Python Web 服务贯穿镜像、容器、Bind Mount、Volume 和端口映射。完成练习后，你应该能够回答：程序来自哪个镜像，当前运行的是哪个容器，哪些文件属于宿主机，哪些数据独立保存，以及浏览器为什么能访问容器里的服务。

> 运行本章前需要已经安装并启动 Docker Desktop。命令默认在 Mac 终端执行。练习只使用当前用户家目录中的 `~/docker-practice`，不会要求管理员权限。

## 1. 先确认 Docker 能正常工作

运行：

```bash
docker version
```

正常情况下，输出会同时包含 Client 和 Server。Client 是你输入命令时使用的 Docker 客户端；Server 是负责创建镜像、容器和网络的 Docker Engine。Docker Desktop 没有启动时，通常只能看到客户端信息，随后出现无法连接 daemon 的错误。

再运行一个最小容器：

```bash
docker run --rm hello-world
```

第一次运行时，本机可能没有 `hello-world` 镜像。Docker 会先从镜像仓库下载它，再创建容器并执行默认程序。看到欢迎文字后，容器已经完成任务并退出；`--rm` 会在退出后自动清理这个临时容器。

如果出现网络超时，问题可能发生在镜像下载阶段；如果出现无法连接 Docker daemon，则应先检查 Docker Desktop，而不是修改镜像名称。

## 2. 镜像和容器不是同一个东西

可以先把关系理解为：

```text
Dockerfile 或镜像仓库
→ Image：可重复使用的只读模板
→ Container：从镜像启动的一次运行实例
```

查看本机已有镜像：

```bash
docker image ls
```

输出可能包含：

```text
REPOSITORY    TAG       IMAGE ID       CREATED        SIZE
hello-world   latest    ...            ...            ...
```

`hello-world:latest` 表示仓库名和标签。标签方便人阅读，但标签可以被重新指向其他内容；对复现要求高的项目还应记录镜像摘要、Dockerfile 和构建过程。

一个镜像可以启动很多容器。下面两条命令都使用同一个 Python 镜像，却会创建两个彼此独立的临时容器：

```bash
docker run --rm python:3.12-slim python --version
docker run --rm python:3.12-slim python -c 'print(2 + 3)'
```

它们共享镜像内容，但每个容器都有自己的进程和临时可写层。容器退出不会自动删除镜像。

Docker 容器也不是一台完整虚拟机。原生 Linux 中的容器共享宿主机 Linux 内核；Docker Desktop for Mac 会在受管理的 Linux 虚拟机中运行 Linux 容器。容器看到的是 Linux 用户空间和文件系统，不会直接变成 macOS 进程。

## 3. 准备一个最小 Web 项目

创建练习目录：

```bash
mkdir -p ~/docker-practice/web-demo
cd ~/docker-practice/web-demo
pwd
```

创建 `app.py`：

```bash
cat > app.py <<'PY'
from http.server import BaseHTTPRequestHandler, HTTPServer


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        body = b"Hello from Docker\n"
        self.send_response(200)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()
PY
```

先在 Mac 本机检查语法：

```bash
python3 -m py_compile app.py
```

没有输出通常表示语法检查通过。这里让服务监听 `0.0.0.0:8000`，因为容器外部的端口映射需要访问容器的网络接口。如果程序只监听容器内的 `127.0.0.1`，宿主机可能无法通过映射端口访问它。

## 4. 用 Dockerfile 描述运行环境

在同一目录创建 `Dockerfile`：

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY app.py .
CMD ["python", "app.py"]
```

四行分别表示：

- 从 `python:3.12-slim` 镜像开始；
- 把容器内工作目录设为 `/app`；
- 将构建上下文中的 `app.py` 复制进镜像；
- 容器启动时默认运行 `python app.py`。

查看当前目录，确认构建需要的文件都在这里：

```bash
ls -la
```

应至少看到：

```text
Dockerfile
app.py
```

Docker 构建命令末尾的点号表示“当前目录是构建上下文”。Docker 会从这里读取 Dockerfile 和需要复制的文件，因此不要在包含大量数据、凭证或无关项目的父目录中随手构建。

## 5. 构建镜像并观察结果

运行：

```bash
docker build -t handbook-web:demo .
```

`-t handbook-web:demo` 为镜像设置名称和标签。构建成功后检查：

```bash
docker image ls handbook-web
```

可能看到：

```text
REPOSITORY     TAG    IMAGE ID       CREATED          SIZE
handbook-web   demo   ...            ...              ...
```

如果构建时报：

```text
failed to read dockerfile
```

先运行 `pwd` 和 `ls -la`，确认当前目录确实包含名为 `Dockerfile` 的文件。不要因为找不到文件就给 Docker 加管理员权限。

如果 `COPY app.py .` 报错，则检查文件名、大小写和构建上下文。Docker 只能复制构建上下文中的内容，不能用 `COPY` 随意读取当前目录以外的文件。

## 6. 启动容器并访问服务

启动容器：

```bash
docker run --name handbook-web-demo \
  -p 127.0.0.1:8080:8000 \
  handbook-web:demo
```

这条命令会占用当前终端并显示访问日志。另开一个终端窗口，运行：

```bash
curl http://127.0.0.1:8080
```

应该收到：

```text
Hello from Docker
```

端口映射可以读成：

```text
Mac 的 127.0.0.1:8080
→ 容器的 8000 端口
```

只绑定 `127.0.0.1`，通常表示服务只从本机访问。写成 `8080:8000` 时，Docker 可能绑定所有网络接口，使同一局域网中的设备也能连接。开发服务是否需要对外开放应明确决定，不能把省略地址当作无关紧要的简写。

回到运行容器的终端，按 `Ctrl + C` 停止服务。然后查看容器状态：

```bash
docker ps -a --filter name=handbook-web-demo
```

容器虽然已经停止，但仍然存在。镜像也仍然存在。这说明“停止容器”“删除容器”和“删除镜像”是三件不同的事。

## 7. 为什么修改源码后容器没有变化

在 Mac 上修改 `app.py`，把响应改成：

```python
body = b"Hello after editing\n"
```

重新启动刚才的容器并不会自动获得新代码，因为 `app.py` 已在构建时复制进镜像。要把变化做进镜像，需要重新构建：

```bash
docker build -t handbook-web:demo .
```

然后基于新镜像启动新容器。

开发时频繁重建并不总是方便，因此可以使用 Bind Mount，把宿主机当前目录直接挂入容器：

```bash
docker run --rm \
  -p 127.0.0.1:8081:8000 \
  --mount type=bind,src="$PWD",dst=/app,readonly \
  -w /app \
  python:3.12-slim \
  python app.py
```

这里没有使用刚才构建的镜像，而是直接用 Python 基础镜像运行宿主机文件。`readonly` 表示容器只能读取挂载目录，不能修改 Mac 上的源码。另开终端访问：

```bash
curl http://127.0.0.1:8081
```

Bind Mount 的特点是双方看到同一批文件。宿主机修改源码后，容器读取到的也是新内容；容器若获得写权限，也能修改或删除宿主机文件。因此不要为了方便把整个家目录、`~/.ssh`、云凭证目录或不相关项目挂入容器。

## 8. 容器可写层为什么不适合保存重要数据

启动一个临时容器并创建文件：

```bash
docker run --name writable-layer-demo \
  python:3.12-slim \
  sh -c 'echo "temporary data" > /result.txt && cat /result.txt'
```

容器退出后，文件仍在这个已停止容器的可写层中。可以验证：

```bash
docker start -a writable-layer-demo
```

不过这种数据与容器绑定。清理容器时，未单独持久化的文件也会消失。数据库、训练结果、上传文件和长期日志不应只留在容器可写层。

## 9. 用 Volume 保存独立数据

创建一个专门的练习卷：

```bash
docker volume create handbook-demo-data
```

查看：

```bash
docker volume inspect handbook-demo-data
```

向 Volume 写入文件：

```bash
docker run --rm \
  --mount type=volume,src=handbook-demo-data,dst=/data \
  python:3.12-slim \
  sh -c 'echo "persistent data" > /data/result.txt'
```

第一个容器已经因为 `--rm` 被自动删除。再启动另一个容器读取同一个 Volume：

```bash
docker run --rm \
  --mount type=volume,src=handbook-demo-data,dst=/data,readonly \
  python:3.12-slim \
  cat /data/result.txt
```

输出应为：

```text
persistent data
```

这说明 Volume 的生命周期独立于某一个容器。它适合数据库数据、容器管理的持久状态和不需要直接在宿主机编辑的内容。

Volume 独立保存并不等于自动备份。误删 Volume、磁盘损坏或程序写入错误数据仍可能造成损失。重要数据需要另外制定备份和恢复方案。

## 10. Volume 与 Bind Mount 应该怎么选

两者都能让数据出现在容器中，但用途不同。

**Bind Mount** 直接对应宿主机路径，适合源码、配置和需要从 Mac 查看或编辑的输出。它的风险也最直接：容器拥有写权限时，宿主机文件会被真实修改。

**Volume** 由 Docker 管理，适合数据库和应用状态。你通常不直接进入 Docker Desktop 的内部目录编辑它，而是通过容器、备份命令或应用本身读取。

可以按下面的思路选择：

```text
需要在 Mac 编辑源码
→ Bind Mount

数据应独立于单个容器保存
→ Volume

需要团队长期复现
→ Dockerfile、Compose 和明确的数据策略
```

## 11. 容器网络中的 localhost 指向谁

在 Mac 终端中，`localhost` 指向 Mac 本机。在容器中，`localhost` 只指向当前容器，不会自动指向 Mac，也不会指向另一个数据库容器。

创建自定义网络：

```bash
docker network create handbook-demo-net
```

启动一个临时服务：

```bash
docker run -d --rm \
  --name demo-server \
  --network handbook-demo-net \
  python:3.12-slim \
  python -m http.server 8000
```

再从同一网络中的另一个容器访问服务名：

```bash
docker run --rm \
  --network handbook-demo-net \
  python:3.12-slim \
  python -c 'from urllib.request import urlopen; print(urlopen("http://demo-server:8000").status)'
```

如果返回：

```text
200
```

说明两个容器能够通过容器名通信。多服务项目通常使用 Docker Compose，让服务名承担内部 DNS 名称，而不是手工记忆不断变化的容器 IP。

## 12. `.dockerignore` 防止无关文件进入构建上下文

在项目根目录创建 `.dockerignore`：

```text
.git
.venv
__pycache__
.env
.env.*
node_modules
runs
checkpoints
*.log
```

它能减少发送给 Docker 的构建上下文，也能降低日志、虚拟环境、数据集和凭证被复制进镜像的风险。

`.dockerignore`、`.gitignore` 和 `.rsyncignore` 影响不同工具，不能互相替代。文件被 Git 忽略，并不意味着 Docker 构建时一定看不到它。

不要把 API Key 写入 Dockerfile，再指望后续删除那一行就能消除风险。构建层和缓存可能保留曾经加入的内容。需要构建期秘密时，应使用 Docker 提供的 Secret 机制，并确认最终镜像中没有残留。

## 13. 清理前先分清对象

练习结束后可以先查看所有相关对象：

```bash
docker ps -a --filter name=handbook-web-demo
docker ps -a --filter name=writable-layer-demo
docker image ls handbook-web
docker volume ls --filter name=handbook-demo-data
docker network ls --filter name=handbook-demo-net
```

容器、镜像、Volume 和网络分别管理。删除某个停止容器不会自动删除镜像，也不会自动删除命名 Volume。反过来，删除 Volume 可能直接丢失其中的数据，因此不能把批量清理命令当成日常操作。

本章刻意不提供一条“把所有东西一次删干净”的命令。更好的做法是逐项确认对象名称和用途，再使用对应的 Docker 子命令处理。对真实项目，清理前还要检查数据库、训练结果、Compose 项目和其他容器是否引用同一 Volume 或网络。

## 14. 常见故障按什么顺序检查

容器启动失败时，先确认 Docker Engine：

```bash
docker version
docker info
```

再检查容器状态和日志：

```bash
docker ps -a
docker logs CONTAINER_NAME
docker inspect CONTAINER_NAME
```

可以按下面的顺序缩小问题：

```text
Docker Desktop 是否运行
→ 镜像是否存在或构建成功
→ 容器进程是否立即退出
→ 日志中的真实错误
→ 启动命令和环境变量
→ 端口映射与应用监听地址
→ Bind Mount / Volume 路径
→ 容器网络与依赖服务
```

几个常见现象：

- **端口已经占用**：换一个宿主机端口，或找到占用端口的现有进程；
- **容器启动后立刻退出**：查看 `docker logs`，前台主进程结束时容器也会结束；
- **文件不存在**：检查工作目录、`COPY` 路径和挂载目标；
- **修改源码没有生效**：确认使用的是旧镜像还是 Bind Mount；
- **宿主机访问不到服务**：检查端口映射和容器内监听地址；
- **容器之间连不上**：确认是否位于同一自定义网络，并使用服务名而不是 `localhost`。

## 15. Docker 不是任意代码的绝对安全边界

容器能够限制和组织运行环境，但不能让来源不明的代码自动变得可信。风险会因为特权模式、Docker Socket、宿主机敏感目录挂载、额外 Linux Capabilities、Host Network 和真实凭证注入而显著扩大。

运行陌生镜像前至少检查来源、Dockerfile、所需挂载、端口和环境变量。把源码放进只读挂载也只能降低文件被修改的风险，不能解决网络访问、资源占用、内核漏洞或凭证泄露等全部问题。
