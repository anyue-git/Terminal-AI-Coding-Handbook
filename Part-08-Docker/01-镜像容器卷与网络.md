# 01 镜像、容器、卷与网络

Docker 不是把命令放进黑盒。镜像提供可重复使用的文件系统与默认启动方式，容器是镜像的一次运行实例，Bind Mount 把宿主目录交给容器，Volume 独立保存数据，端口映射和容器网络则决定服务怎样互相访问。本章用一个最小 Python Web 服务贯穿这些对象，解释为什么容器退出、源码不更新、数据随容器消失或端口无法访问。

> 命令默认在已启动 Docker Desktop 的 Mac 终端执行。练习只使用 `~/docker-practice`，不需要管理员权限。

## 1. 确认客户端、Engine、镜像和容器属于不同层

```bash
docker version
docker run --rm hello-world
```

`docker version` 中 Client 是当前终端调用的 CLI，Server 是创建镜像、容器和网络的 Docker Engine。Docker Desktop 未启动时，通常能看到客户端版本，却无法连接 daemon。`hello-world` 第一次运行会先拉取镜像，再创建容器执行默认程序；程序结束后，`--rm` 删除这个临时容器，但镜像仍保留。镜像下载超时与 daemon 无法连接属于不同故障，应根据输出判断发生在哪一层。

镜像与容器可以理解为：

```text
Dockerfile 或镜像仓库
→ Image：只读模板
→ Container：一次运行实例和临时可写层
```

同一个 `python:3.12-slim` 可以启动多个彼此独立的容器：

```bash
docker run --rm python:3.12-slim python --version
docker run --rm python:3.12-slim python -c 'print(2 + 3)'
docker image ls
```

标签便于人识别，却可以被重新指向其他内容。复现要求高的项目还应记录 Dockerfile、构建过程和镜像摘要。Linux 容器也不是完整虚拟机：Ubuntu 上共享宿主 Linux 内核，Mac 的 Docker Desktop 则在受管理的 Linux VM 中运行 Engine 与容器。

## 2. 构建上下文决定哪些文件能够进入镜像

建立项目并创建服务：

```bash
mkdir -p ~/docker-practice/web-demo
cd ~/docker-practice/web-demo

cat > app.py <<'PY'
from http.server import BaseHTTPRequestHandler, HTTPServer


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        body = b"Hello from Docker\n"
        self.send_response(200)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()
PY

python3 -m py_compile app.py
```

服务监听容器内 `0.0.0.0:8000`，端口映射才能通过容器网络接口访问。创建 `Dockerfile`：

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY app.py .
CMD ["python", "app.py"]
```

构建命令末尾的点号表示当前目录是构建上下文：

```bash
pwd
ls -la
docker build -t handbook-web:demo .
docker image ls handbook-web
```

Docker 只能从构建上下文读取 `COPY` 所需文件。真实项目应使用 `.dockerignore`，避免把 Git 元数据、虚拟环境、缓存、凭据和运行产物发送给构建器：

```text
.git
.venv
__pycache__
.env
.env.*
node_modules
runs
checkpoints
*.log
```

`.dockerignore`、`.gitignore` 和 `.rsyncignore` 分别影响 Docker 构建、Git 跟踪与 rsync 传输，不能互相替代。文件被 Git 忽略，不代表 Docker 构建一定看不到它。API Key 也不能先写入 Dockerfile、再通过后续删除来“清除”；构建层与缓存可能保留历史内容，需要构建期秘密时应使用 Docker 支持的 Secret 机制，并检查最终镜像。

`failed to read dockerfile` 或 `COPY` 找不到文件时，检查目录、文件名、大小写与上下文，而不是添加 `sudo`。

## 3. 运行、访问、停止和删除是不同动作

启动命名容器：

```bash
docker run --name handbook-web-demo \
  -p 127.0.0.1:8080:8000 \
  handbook-web:demo
```

另开终端访问：

```bash
curl http://127.0.0.1:8080
```

映射表示 Mac 的 `127.0.0.1:8080` 进入容器 8000。显式绑定本机回环地址通常只允许本机访问；简写 `8080:8000` 可能绑定所有宿主接口，使局域网设备也能访问。

在前台容器终端按 `Ctrl + C` 后，容器停止但仍存在：

```bash
docker ps -a --filter name=handbook-web-demo
docker logs --tail=100 handbook-web-demo
docker inspect handbook-web-demo
docker rm handbook-web-demo
```

`docker logs` 读取容器进程输出，`docker inspect` 展示启动配置、挂载、网络和状态。停止容器、删除容器和删除镜像是不同动作；删除前通过名称、状态和引用关系确认对象，不使用来源不明的批量清理命令。

## 4. 构建时复制与开发时挂载是两种代码来源

修改 Mac 上的 `app.py` 后，旧容器不会自动获得新代码，因为文件已经在 build 阶段复制进镜像。发布新镜像需要重新构建并创建新容器。

开发时可以把宿主目录只读挂入基础镜像：

```bash
docker run --rm \
  -p 127.0.0.1:8081:8000 \
  --mount type=bind,src="$PWD",dst=/app,readonly \
  -w /app \
  python:3.12-slim \
  python app.py
```

Bind Mount 让宿主机与容器看到同一批文件；去掉 `readonly` 后，容器也可能修改或删除 Mac 文件。因此只挂载任务需要的目录，不把整个家目录、`~/.ssh`、云凭证或无关项目交给容器。开发挂载也不能代替正式镜像构建与测试。

## 5. 可写层、Bind Mount 与 Volume 的生命周期不同

容器可写层随容器存在。下面的文件留在已停止容器中，但删除容器后也会消失：

```bash
docker run --name writable-layer-demo \
  python:3.12-slim \
  sh -c 'echo "temporary data" > /result.txt && cat /result.txt'

docker start -a writable-layer-demo
```

数据库、上传文件、训练结果和长期日志不应只放在容器可写层。

Named Volume 独立于某个容器：

```bash
docker volume create handbook-demo-data
docker volume inspect handbook-demo-data

docker run --rm \
  --mount type=volume,src=handbook-demo-data,dst=/data \
  python:3.12-slim \
  sh -c 'echo "persistent data" > /data/result.txt'

docker run --rm \
  --mount type=volume,src=handbook-demo-data,dst=/data,readonly \
  python:3.12-slim \
  cat /data/result.txt
```

第一个临时容器已经删除，第二个容器仍能读取 `persistent data`，说明 Volume 生命周期独立于单个容器。Bind Mount 适合宿主机直接编辑的源码与配置；Volume 适合由容器管理的数据库、缓存和持久状态。Volume 独立保存不等于自动备份，误删、磁盘损坏和程序写错仍会造成损失。

## 6. 宿主端口和容器内部网络解决不同访问路径

容器内 `localhost` 只指当前容器。宿主机访问容器通常通过 `-p`；多个容器之间则可加入同一自定义网络，并使用容器名通信：

```bash
docker network create handbook-demo-net

docker run -d --rm \
  --name demo-server \
  --network handbook-demo-net \
  python:3.12-slim \
  python -m http.server 8000

docker run --rm \
  --network handbook-demo-net \
  python:3.12-slim \
  python -c 'from urllib.request import urlopen; print(urlopen("http://demo-server:8000").status)'
```

返回 `200` 说明两个容器能够通过名称通信。Compose 会自动创建项目网络，并让服务名承担内部 DNS；不应手工依赖会变化的容器 IP。程序若只监听容器内 `127.0.0.1`，即使设置宿主端口映射，也可能无法从容器外访问。

检查宿主映射、日志和网络状态：

```bash
docker ps
docker port CONTAINER
docker logs --tail=100 CONTAINER
docker inspect CONTAINER
```

端口占用时找到宿主监听者，再决定换端口或停止正确进程：

```bash
lsof -nP -iTCP:8080 -sTCP:LISTEN
```

## 7. 故障排查与清理都要先区分对象

```bash
docker ps -a
docker image ls
docker volume ls
docker network ls
docker system df
```

容器通常可从镜像重建，镜像可由 Dockerfile 或仓库重新获得，Volume 可能承载唯一数据，Bind Mount 则直接指向宿主文件。常见故障可以沿下面顺序缩小：

```text
Docker Engine 是否可用
→ 镜像是否存在或构建成功
→ 容器主进程是否立即退出
→ logs 与 inspect 中的真实错误
→ 启动命令、工作目录和环境变量
→ 端口映射与应用监听地址
→ Bind Mount / Volume 路径
→ 容器网络与依赖服务
```

- 端口已占用：找到宿主监听者，换端口或停止正确进程；
- 容器启动后立即退出：查看主进程和 `docker logs`；
- 文件不存在：检查工作目录、`COPY` 路径和挂载目标；
- 修改源码未生效：确认使用旧镜像还是 Bind Mount；
- 宿主访问不到服务：检查端口映射和容器内监听地址；
- 容器之间无法连接：确认同一网络，并使用服务名而不是 `localhost`。

练习结束时只删除自己明确创建的对象：

```bash
docker rm writable-layer-demo 2>/dev/null || true
docker stop demo-server 2>/dev/null || true
docker network rm handbook-demo-net
docker volume rm handbook-demo-data
```

删除 Volume 前再次确认不含需要保留的数据。`docker system prune`、删除全部 Volume 或强制清理不属于普通收尾。

容器也不是任意代码的绝对安全边界。特权模式、Docker Socket、宿主敏感目录挂载、额外 Linux Capabilities、Host Network 和真实凭据注入都会扩大影响。运行陌生镜像前仍要检查来源、Dockerfile、挂载、端口和环境变量；源码只读挂载只能降低文件被修改的机会，不能消除网络访问、资源占用、内核漏洞或凭据泄露风险。

## 8. Docker 核心对象的判断顺序

```text
确认 CLI 正在连接可用 Engine
→ 确认构建上下文与 .dockerignore
→ 从镜像创建容器并检查主进程、日志和端口
→ 判断代码来自镜像 COPY 还是 Bind Mount
→ 判断数据位于可写层、宿主目录还是 Volume
→ 判断访问发生在宿主映射还是容器网络
→ 停止、删除和清理分别处理
```
