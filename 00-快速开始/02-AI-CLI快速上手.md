# 02 AI CLI 快速上手

> 适用于 Claude Code、Codex CLI 和 Grok CLI。
>
> 目标：安全完成一次小修改，并知道怎样检查结果。

AI CLI 是运行在终端里的编程 Agent。它不只会回答问题，还可能读取文件、修改代码和执行命令。所以第一原则不是“让它尽量自动”，而是先确认它站在哪个目录、能碰哪些文件，以及改完后怎样证明结果没问题。

本页只讲最短流程。权限、Sandbox、多 Agent 协作和远程 GPU 的详细内容放在后面的正式章节。

---

## 1. 先进入正确的项目目录

把下面的 `PROJECT_PATH` 换成自己的项目路径：

```bash
cd PROJECT_PATH
```

确认当前机器、用户、目录和 Git 状态：

```bash
hostname
whoami
pwd
git status
git branch --show-current
```

这里最重要的是 `pwd` 和 `git status`。

- `pwd` 告诉你 Agent 会从哪个目录开始看文件；
- `git status` 告诉你项目里是否已经有未提交修改。

不要从家目录、下载目录或同时装着多个项目的父目录启动 Agent。否则它可能看见很多与当前任务无关的文件。AI 的阅读速度很快，但“看得多”不等于“看得准”。

如果 `git status` 已经显示修改，先弄清这些内容是谁改的、属于哪个任务。不要让 Agent 顺手整理、覆盖或提交它们。

---

## 2. 建立一个任务分支

工作区状态确认无误后，创建分支：

```bash
git switch -c task/fix-parser
```

分支名写任务内容，例如：

```text
fix/login-timeout
task/update-training-config
docs/improve-install-guide
```

不要只写 `ai-test`、`new-branch` 之类看不出用途的名字。过几个月再看 Git 历史时，你关心的是做了什么，不是哪位电子同事当时值班。

再次确认：

```bash
git branch --show-current
git status
```

---

## 3. 选择一个工具启动

在项目目录中运行其中一个：

```bash
claude
```

```bash
codex
```

```bash
grok
```

对应关系：

- `claude`：Claude Code；
- `codex`：Codex CLI；
- `grok`：Grok CLI，xAI 的终端编程工具。

第一次使用或升级工具后，可以先查看本机版本提供的选项：

```bash
claude --help
codex --help
grok --help
```

不同版本的权限名称和界面可能变化，以本机 `--help` 和官方文档为准。

这次只启动一个 Agent。不要让三个工具同时修改同一个工作区，否则它们可能非常勤快地互相覆盖。

---

## 4. 第一条 Prompt：只读调查

启动后先发：

```text
当前阶段只读，不要修改文件、安装依赖、访问外部服务或执行 Git 写操作。

请检查：
- 当前目录和 Git 状态；
- README 与项目规则；
- 与任务相关的代码；
- 测试位置和运行方式。

然后说明：
1. 项目入口；
2. 任务涉及哪些文件；
3. 哪些目录不应修改；
4. 当前有哪些未提交改动；
5. 哪些结论已经确认，哪些仍是推测。

每个重要结论给出文件路径。
```

这一步的目的是让 Agent 先理解项目，而不是刚进门就开始改代码。

如果它找错入口、误把生成目录当成源码，或者无法说明结论来自哪个文件，先纠正调查结果，不要进入修改阶段。

---

## 5. 第二条 Prompt：把任务范围说清楚

假设这次只允许修改两个文件，可以发：

```text
目标：修复解析器无法正确处理制表符的问题，并补充测试。

允许修改：
- src/parser.py
- tests/test_parser.py

禁止：
- 修改其他文件；
- 安装或升级依赖；
- 删除未跟踪文件；
- 访问项目目录之外的文件；
- 执行 git add、commit 或 push。

先给出最小计划，不要立即修改。
计划中写明：
1. 每个文件为什么要改；
2. 准备运行什么测试；
3. 哪些行为可能受影响；
4. 什么情况必须停止并询问。
```

把示例路径换成真实文件。

任务范围越清楚，最后的 diff 越容易检查。diff 是 Git 显示的“修改前后差异”，它比 Agent 的总结更接近实际发生的事情。

---

## 6. 确认计划后，只执行一个小步骤

计划合理后，再允许修改：

```text
现在只执行计划中的第一步。

只允许修改：
- src/parser.py
- tests/test_parser.py

完成后运行最相关的测试，然后停止并汇报：
- 修改了哪些文件；
- 执行了什么命令；
- 测试结果和退出状态；
- 哪些内容没有验证；
- 是否需要扩大修改范围。

不要提交或推送。
```

修改较复杂时，先补测试，再改实现。一次只完成一个可以验证的步骤，比一次改十几个文件更容易发现方向错误。

不要因为工具提供“自动批准”就直接全开。自动批准只是不再逐次询问，并不会让错误命令突然变得安全。

---

## 7. 不要只看 Agent 的完成总结

暂停或退出 Agent 后，在普通终端中运行：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

分别可以看见：

- 哪些文件发生变化；
- 文件是新增、修改还是删除；
- 每个文件改动多少；
- 具体改了什么。

重点检查：

- 是否修改了允许范围之外的文件；
- 是否出现意外删除；
- 是否修改依赖或锁文件；
- 是否生成日志、缓存或大型文件；
- 是否加入真实路径、Token、密码或私钥；
- 测试是否被削弱；
- 是否出现大范围无关格式化。

Agent 说“只改了两个文件”，只能算它的陈述；`git diff` 才是现场记录。

---

## 8. 运行项目真实测试

按项目实际情况运行测试，例如：

```bash
python -m pytest tests/test_parser.py
```

或者运行项目 README、`package.json`、`pyproject.toml` 等文件中规定的命令。

测试结果至少要记录：

```text
执行命令：...
结果：通过 / 失败
退出状态：...
未运行：...
环境限制：...
```

Mac 没有 CUDA 时，就不能把 GPU 测试写成“已经验证”；只能明确记录哪些内容需要到 Ubuntu 上继续检查。

---

## 9. 只暂存确认过的文件

确认 diff 和测试结果后，只暂存本次需要的文件：

```bash
git add src/parser.py tests/test_parser.py
```

检查暂存区：

```bash
git diff --cached --name-status
git diff --cached
```

确认无误后再提交：

```bash
git commit -m "修复解析器的制表符处理"
```

不推荐新手默认使用：

```bash
git add .
```

它可能把与任务无关的文件一起装进提交。提交前多看一次暂存区，通常比提交后再研究怎么撤销轻松。

是否 push 到远程仓库，仍然由人决定。

---

## 10. 权限设置先记住三件事

不同工具的权限选项不完全一样，但可以先记住：

1. **审批**：Agent 执行操作前是否需要询问；
2. **Sandbox**：即使批准了，工具在技术上能访问到哪里；
3. **任务范围**：你在 Prompt 中允许它做什么。

三者不能互相替代。Prompt 写了“不要访问网络”，不等于网络权限已经被系统关闭；Sandbox 限制了目录，也不等于每一次修改都合理。

新项目优先从只读或需要逐步审批的模式开始。不要一上来跳过全部确认，也不要默认允许：

- 管理员权限；
- 任意网络写入；
- Git push；
- 系统服务和防火墙修改；
- 私钥、云凭据和密码目录读取；
- Docker Socket 操作；
- 数据集、模型和 checkpoint 删除。

---

## 11. 在远程 Ubuntu 上启动时

SSH 登录后，先确认没有连错机器：

```bash
hostname
whoami
pwd
git status
```

再启动 AI CLI。

需要运行长时间训练时，在 tmux 中启动任务：

```bash
tmux new -s train
```

tmux 可以防止 SSH 断开直接带走训练进程，但挡不住关机、程序崩溃或磁盘写满。训练恢复仍然需要日志和 checkpoint。

Agent 可以帮助修改训练代码，但不要默认允许它修改 NVIDIA 驱动、CUDA、SSH、防火墙或删除实验数据。

---

## 12. 一份最短可复制模板

```text
目标：
[写清楚要解决的问题]

当前阶段：
[只读调查 / 计划 / 修改 / 测试 / 审查]

允许修改：
- [真实文件路径]

禁止：
- 修改其他文件；
- 安装依赖；
- 读取凭据；
- 删除数据或未跟踪文件；
- git add、commit、push。

验证：
[真实测试命令]

完成后汇报：
- 修改文件；
- 执行命令；
- 测试结果；
- 未验证内容；
- 风险。

需要扩大范围或使用更高权限时，停止并询问。
```

Prompt 不需要写得像合同，但目标、范围、验证和停止条件不能全靠默契。人和 Agent 之间的默契，目前还没有可靠到可以跳过说明书。
