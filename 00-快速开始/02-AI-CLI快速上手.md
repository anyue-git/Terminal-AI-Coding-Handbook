# 02 AI CLI 快速上手

> 适用于第一次在项目中使用 Claude Code、Codex CLI 或 Grok CLI 的读者。
>
> 本页只完成一件事：让一个 Agent 在明确范围内完成小修改，然后由你检查实际结果。

AI CLI 不只是聊天窗口。它可能读取项目文件、修改代码、运行测试和调用 Git，因此启动前必须先确认当前目录和工作区状态。本页聚焦终端中的 Claude Code、Codex CLI 和 Grok CLI；图形化客户端的按钮可能不同，但“确认目录、限定范围、查看 diff、运行测试”的方法仍然适用。

## 1. 进入真实项目前先检查工作区

把 `PROJECT_PATH` 换成自己的项目目录：

```bash
cd PROJECT_PATH
hostname
pwd
git status
git branch --show-current
```

一个状态正常的项目可能显示：

```text
On branch main
nothing to commit, working tree clean
```

也可能显示已有修改：

```text
modified: src/parser.py
untracked files: notes.txt
```

第二种情况不能直接忽略。先弄清这些修改是谁产生的、是否属于当前任务。创建新分支不会自动把未提交修改隔离出去，它们会继续留在工作区中。

不要从主目录、下载目录或同时包含多个仓库的父目录启动 Agent。启动目录通常决定它最先看到哪些文件，也会影响相对路径和项目规则的加载。

## 2. 为这次任务建立清楚的起点

确认现有修改已经处理后，创建一个写明任务目的的分支：

```bash
git switch -c fix/parser-tab-handling
```

再次检查：

```bash
git branch --show-current
git status
```

分支不是万能备份，但它能让本次修改与 `main` 保持可比较状态。分支名应描述任务，例如 `docs/improve-install-guide` 或 `fix/login-timeout`，而不是 `ai-test-2`、`final-new` 之类以后看不懂的名称。

## 3. 只启动一个 Agent

在项目根目录中选择一个工具：

```bash
claude
```

或：

```bash
codex
```

或：

```bash
grok
```

第一次使用或升级后，可以先在普通 Shell 中查看：

```bash
claude --help
codex --help
grok --help
```

这次练习只让一个 Agent 修改当前工作区。三个工具同时工作并不会自动形成可靠协作，反而可能读取到彼此尚未完成的文件变化。

## 4. 第一轮只让它调查项目

进入 AI CLI 后，先输入下面这段内容：

```text
当前阶段只读，不要修改文件、安装依赖、访问外部服务或执行 Git 写操作。

请检查当前目录、Git 状态、README、项目规则、依赖声明和测试配置，并回答：
1. 项目入口在哪里；
2. 与当前任务相关的实现和测试位于哪些文件；
3. 当前有哪些未提交修改；
4. 哪些目录不应修改；
5. 怎样运行最相关的测试；
6. 哪些结论已经由文件确认，哪些仍是推测。

重要结论附上文件路径。
```

调查阶段的目标不是让 Agent 写一篇项目介绍，而是确认它有没有找到正确入口、真实测试和当前工作区状态。如果它把构建产物当成源码，或无法给出路径证据，先纠正调查结果，不要马上授权修改。

## 5. 把任务写成可以验收的内容

假设项目中存在一个解析器问题，可以继续输入：

```text
任务目标：修复解析器处理制表符时产生错误结果的问题，并补充回归测试。

允许修改：
- src/parser.py
- tests/test_parser.py

禁止：
- 修改其他文件；
- 安装或升级依赖；
- 删除文件或未跟踪内容；
- 读取项目外目录和凭证；
- 执行 git add、commit 或 push。

验收方式：
- 新增一个能够复现问题的测试；
- 修改前该测试失败；
- 修复后目标测试和现有解析器测试通过。

先给出最小计划，不要立即修改。
```

把文件路径和测试要求换成当前项目的真实情况。任务描述至少要说清楚改什么、不改什么、怎样证明改好了。只写“帮我优化一下”会把范围判断全部交给 Agent，也会让最后的 diff 很难验收。

## 6. 一次只允许完成一个可验证步骤

计划合理后，可以让它先添加测试：

```text
现在只修改 tests/test_parser.py，增加一个能够复现制表符问题的最小测试。
不要修改生产代码。
完成后运行该测试，并报告实际命令、退出状态和失败原因，然后停止。
```

确认测试确实暴露问题后，再允许修改实现：

```text
现在允许修改 src/parser.py，只修复刚才测试覆盖的问题，不重构其他解析逻辑。
完成后重新运行目标测试和现有解析器测试，并报告实际结果。
不要提交或推送。
```

不必强求所有任务都严格测试先行，但每一轮最好只完成一个能检查的小步骤。这样方向错误时，可以在改动仍然很小时停下来。

## 7. 权限提示应该怎样判断

Agent 请求执行命令或修改文件时，先看四件事：

1. 命令在哪个目录执行；
2. 会读取或修改哪些对象；
3. 是否超出刚才允许的文件范围；
4. 失败后是否容易恢复。

看到测试命令并不等于可以无条件批准。例如测试脚本可能启动 Docker、访问网络、写数据库或下载大型模型。命令不熟悉时，让 Agent 先解释每个参数和预期影响，再决定是否执行。

审批、Sandbox 和 Prompt 范围是三层不同约束。Prompt 写了“不要访问网络”，不表示系统网络权限已经关闭；Sandbox 限制了目录，也不表示允许目录中的每项修改都合理。

## 8. Agent 说“完成”以后才开始验收

暂停或退出 AI CLI，回到普通 Shell 后运行：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

这四条命令分别回答：哪些文件发生变化、变化类型是什么、改动规模多大、具体修改了什么。重点检查是否出现范围外文件、意外删除、依赖或锁文件变化、调试输出、真实路径、Token、大文件以及无关格式化。

Agent 的总结是它对工作的描述，`git diff` 才是工作区中的实际记录。两者不一致时，以文件和测试结果为准。

## 9. 自己运行项目规定的测试

按照项目文档运行真实测试，例如：

```bash
python -m pytest tests/test_parser.py
```

结果可能类似：

```text
18 passed in 0.42s
```

记录测试时至少保留：

```text
执行命令：python -m pytest tests/test_parser.py
结果：18 passed
退出状态：0
未运行：完整项目测试
环境：当前 macOS Python 环境
```

Mac 上没有 CUDA 时，不能把 GPU 行为写成已经验证；只能明确说明需要到 Ubuntu 或实际 GPU 环境继续检查。

## 10. 提交仍然由人决定

确认 diff 和测试结果后，只暂存本次需要的文件：

```bash
git add src/parser.py tests/test_parser.py
git diff --cached --name-status
git diff --cached
```

暂存区内容正确后再提交：

```bash
git commit -m "修复解析器的制表符处理"
```

不要把 `git add .` 当成固定动作。它可能把日志、缓存、凭证配置和其他任务的修改一起放入提交。是否 push 到远程仓库，也应在确认分支和提交内容后单独决定。

## 11. 一份可直接改写的任务模板

```text
任务目标：
[写清楚要解决的问题]

当前阶段：
[只读调查 / 计划 / 修改 / 测试 / 审查]

允许修改：
- [真实文件路径]

禁止：
- 修改其他文件；
- 安装依赖；
- 读取凭证；
- 删除数据或未跟踪文件；
- 执行 git add、commit 或 push。

验收方式：
- [真实测试命令或可观察结果]

完成后报告：
- 修改文件；
- 执行命令；
- 测试结果和退出状态；
- 未验证内容；
- 风险和需要人工决定的事项。
```

这份模板不要求逐字复制。它的作用是把任务边界和验收方式从脑子里写出来，让你和 Agent 对“完成”使用同一套标准。
