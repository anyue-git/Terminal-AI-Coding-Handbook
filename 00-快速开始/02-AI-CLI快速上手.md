# 02 AI CLI 快速上手

> 适用于第一次在项目中使用 Claude Code、Codex CLI 或 Grok Build 的读者。  
> 本页只完成一件事：让一个 Agent 在明确范围内完成小修改，然后由你检查真实结果。

AI CLI 可以读取项目、修改代码、运行测试和调用 Git。不同工具的界面与权限模式并不相同，但第一次练习可以共用一条简单路径：建立项目基线，让一个 Agent 只读调查，限定一个小任务，分步实施，再回到 Shell 阅读 diff 和测试结果。

## 1. 建立项目现场，并且只启动一个 Agent

把 `PROJECT_PATH` 换成真实项目目录：

```bash
cd PROJECT_PATH
hostname
pwd
git branch --show-current
git status --short
```

`hostname` 和 `pwd` 确认命令发生在哪台机器、哪个目录；后两条显示当前分支和未提交修改。干净工作区可能没有 `git status --short` 输出。若看到 `M src/parser.py`、`?? notes.txt` 等内容，应先弄清变化来源；新建分支不会隔离同一工作区中的未提交修改。

不要从主目录、Downloads 或同时包含多个仓库的父目录启动 Agent。确认现场可用于本次任务后，建立描述目的的分支：

```bash
git switch -c fix/parser-tab-handling
git branch --show-current
git status --short
```

分支保留可比较的基线，但不能恢复数据库、远程操作或项目外文件。名称写清任务，例如 `docs/improve-install-guide` 或 `fix/login-timeout`，比 `ai-test-2` 更容易在以后理解。

在项目根目录选择一个已经安装并登录的工具：

```bash
claude
# 或
codex
# 或
grok
```

本次只使用一个 Agent。多个客户端同时修改同一工作区，不会自动形成协作，反而可能把彼此的半成品当成项目原状。

## 2. 用只读调查把任务落到真实文件

进入 AI CLI 后，第一轮不授权修改：

```text
当前阶段只读，不修改文件、安装依赖、访问外部服务或执行 Git 写操作。

请检查当前目录、Git 状态、README、项目规则、依赖声明和测试配置，并回答：
- 项目入口在哪里；
- 与当前任务相关的实现和测试位于哪些文件；
- 当前有哪些未提交修改；
- 哪些目录不应修改；
- 怎样运行最相关的测试；
- 哪些结论已经由文件确认，哪些仍是推测。

重要结论附上文件路径。
```

调查的目的不是生成项目介绍，而是找到真实入口、测试和工作区状态。如果 Agent 讨论不存在的框架、把构建产物当成源码，或无法给出路径证据，应该继续调查而不是进入修改。

假设项目中存在解析器处理制表符的问题，可以把任务限定为：

```text
目标：修复解析器处理制表符时的错误结果，并补充回归测试。

允许修改：
- src/parser.py
- tests/test_parser.py

禁止：
- 修改其他文件；
- 安装或升级依赖；
- 删除文件或未跟踪内容；
- 读取项目外目录和凭证；
- 执行 git add、commit 或 push。

验收：
- 新测试能复现目标问题；
- 修改前失败原因确实来自制表符处理；
- 修复后目标测试和现有解析器测试通过。

先给出最小计划，不立即修改。
```

真实任务需要替换路径、行为和测试命令。任务描述要说明改变什么、哪些内容不能改变、怎样证明完成；“帮我优化一下”无法支持最后的 diff 验收。Agent 若提出新依赖、全模块重写或无关清理，应先缩小方案。

## 3. 分两步实施，让每次变化都能检查

第一步只增加复现测试：

```text
只修改 tests/test_parser.py，增加一个能够复现制表符问题的最小测试。
不要修改生产代码。
运行该测试，报告完整命令、退出状态和失败原因，然后停止。
```

测试失败不自动等于复现成功。导入错误、依赖缺失、测试数据不存在或错误解释器都不是目标问题。失败信息确实指向解析结果后，才允许修改实现：

```text
现在只修改 src/parser.py，修复刚才测试覆盖的问题，不重构其他解析逻辑。
重新运行目标测试和现有解析器测试，并报告命令、测试数量、退出状态和未验证内容。
不要提交或推送。
```

并非所有任务都必须采用测试先行，但第一次练习把测试与实现分开，能够清楚观察“问题如何被证明”和“代码如何使它通过”。复杂任务的批次设计见[复杂任务拆分与独立复核](../Part-12-AI开发工作流/05-复杂任务拆分与独立复核.md)。

Agent 请求命令或文件修改时，检查运行目录、对象范围、恢复难度和是否符合当前阶段。测试脚本也可能启动 Docker、访问网络、写数据库或下载模型，不能仅凭名称批准。Prompt、审批与 Sandbox 是不同层：文字约束不等于系统权限已经关闭，Sandbox 允许写入也不等于每项修改都合理。

## 4. Agent 说完成后，回到 Shell 读取真实结果

暂停或退出 AI CLI，运行：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

这些命令展示变化文件、变化类型、规模和具体内容。检查是否出现范围外文件、意外删除、依赖或锁文件变化、调试输出、真实路径、Token、大文件和无关格式化。Agent 的总结是解释，Git diff 是工作区实际发生的变化；两者不一致时，以文件和可复现结果为准。

按照项目文档亲自运行测试，例如：

```bash
python -m pytest tests/test_parser.py
```

一份可复核记录应包含实际命令、通过/失败数量、退出状态、运行环境和未运行项目：

```text
命令：python -m pytest tests/test_parser.py
结果：18 passed
退出状态：0
未运行：完整项目测试
环境：当前 macOS Python 环境
```

Mac 没有真实 NVIDIA GPU 时，不能把 CUDA 行为写成已验证；只能记录仍需在 Ubuntu 或其他 GPU 环境完成。阅读代码认为“应该可用”属于分析，不是测试结果。

## 5. Git 写操作是人工确认后的下一层影响

确认 diff 和测试证据符合任务后，只暂存目标文件：

```bash
git add src/parser.py tests/test_parser.py
git diff --cached --name-status
git diff --cached
```

候选内容正确后提交：

```bash
git commit -m "修复解析器的制表符处理"
```

`git add .` 可能同时收进日志、缓存、凭证配置和其他任务的修改，不适合作为固定动作。push、PR 和合并会改变远程协作范围，应在确认分支、提交和远程目标后单独决定。

到这里，第一次 AI CLI 练习已经形成一条完整证据链：任务落到真实文件，测试证明问题，最小实现使测试通过，Git diff 展示实际变化，人决定是否提交。以后需要复制任务格式时，直接使用[通用 Prompt 模板库](../Part-12-AI开发工作流/02-通用Prompt模板库.md)，不必从本页重新抄写整套字段。
