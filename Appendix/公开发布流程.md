# 公开仓库发布流程

本项目采用“私有源仓库是唯一开发源头，公开仓库是经过筛选的发布副本”这一模式。正文、`LICENSE`、README、GitHub Actions 工作流、检查脚本和其他需要公开的配置都应先进入私有源仓库，再通过固定导出流程同步到公开仓库。公开仓库原则上不应长期保留私有源仓库中不存在的独立文件，否则下一次发布时容易出现许可证、工作流或说明文档被覆盖后需要手工补回的问题。

## 仓库关系

私有源仓库为：

```text
anyue-git/Terminal-AI-Coding-Handbook-Source
```

公开发布仓库为：

```text
anyue-git/Terminal-AI-Coding-Handbook
```

日常编辑、审查和版本开发只在私有源仓库进行。私有仓库的修改通过分支和 Pull Request 合并到 `main` 后，才能开始公开发布。公开仓库只接收已经完成审查的公开快照，不应在公开仓库先修改正文，再反向覆盖私有仓库。

## 导出机制

公开快照由以下两个文件控制：

```text
.publishignore
scripts/export_public.sh
```

`.publishignore` 使用 rsync 的排除规则，列出不得进入公开快照的本地凭据、缓存、私有草稿和内部维护材料。公开正文、`LICENSE`、`.github/workflows/`、`scripts/check_markdown.py` 等文件没有被排除，因此会随每次版本发布自动同步，不再需要在公开仓库中手工重建。

导出脚本不会直接从源目录覆盖公开仓库。它会先在系统临时目录中生成一份完整的公开快照，再用这份快照与公开仓库工作区比较。这样既能正确复制隐藏目录，也能把“以前公开、后来加入排除规则”的文件显示为删除项。目标仓库的 `.git` 在比较和同步阶段都会被排除。

## 发布前准备

开始公开发布前，应满足以下条件：

1. 私有源仓库已经切换到 `main`，并且工作区没有未提交修改；
2. 私有源仓库的 `origin` 指向 `anyue-git/Terminal-AI-Coding-Handbook-Source`；
3. 公开仓库已经克隆到本地，且 `origin` 指向 `anyue-git/Terminal-AI-Coding-Handbook`；
4. 公开仓库工作区没有未提交修改；
5. 公开仓库已经创建专用发布分支，不能直接在 `main` 或 `master` 上执行正式同步；
6. 本机能够使用 Git 和 rsync。macOS 自带的 rsync 即可满足当前脚本要求。

例如，可以先在公开仓库中创建发布分支：

```bash
git switch main
git pull --ff-only
git switch -c release/v3.0.0
```

分支名称可以根据实际版本调整，但不应直接把导出结果写入公开仓库 `main`。

## 先执行预演

在私有源仓库根目录执行：

```bash
bash scripts/export_public.sh \
  --dry-run \
  --target ../Terminal-AI-Coding-Handbook
```

`--dry-run` 会生成临时公开快照并展示目标仓库将要新增、修改和删除的文件，但不会写入目标仓库。执行结果会同时显示源提交、目标提交、目标分支、差异项数量和删除项数量。

预演阶段应重点检查：

- `LICENSE`、README、SUMMARY、工作流和检查脚本是否正常存在；
- 私有草稿、内部记录和本地凭据是否被排除；
- 删除列表中是否存在不应删除的公开文件；
- 目标仓库是否仍然存在仅在公开仓库维护的独立文件。如果存在，应先判断它是否应该回收到私有源仓库。

## 正式同步

预演没有删除项时，可以执行：

```bash
bash scripts/export_public.sh \
  --apply \
  --target ../Terminal-AI-Coding-Handbook
```

脚本仍会先重新展示完整差异，确认源仓库和目标仓库在预演后没有变化，然后才写入公开仓库工作区。

如果预览包含删除项，脚本默认停止。核对删除列表后，需要明确增加：

```bash
--confirm-delete
```

完整示例：

```bash
bash scripts/export_public.sh \
  --apply \
  --target ../Terminal-AI-Coding-Handbook \
  --confirm-delete
```

普通同步默认最多允许 25 个删除项。删除数量超过该阈值时，即使已经提供 `--confirm-delete`，脚本仍会停止。确认这确实是一次合理的大规模版本调整后，才可以额外提供：

```bash
--allow-large-delete
```

也可以通过 `--max-delete N` 调整普通删除阈值。删除确认参数只授权当前这一次命令，不会永久降低后续发布的安全边界。

## 同步后的复核与发布

脚本只修改公开仓库的本地工作区，不会自动提交、推送、合并或创建 Release。同步完成后，应进入公开仓库依次执行人工复核：

```bash
git status --short
git diff --stat
git diff
python3 scripts/check_markdown.py --strict-warnings
```

确认差异符合预期后，再提交到公开发布分支、推送并创建 Pull Request。等待 Markdown Check 成功并完成人工检查后，才能合并到公开仓库 `main`。版本标签和 GitHub Release 应在公开仓库最终状态确认后创建。

## 不会随文件同步的仓库设置

以下内容属于 GitHub 仓库级设置，不是仓库中的普通文件，因此不会由导出脚本同步：

- Public 或 Private 可见性；
- 默认分支和分支保护规则；
- GitHub Actions 权限；
- Secrets 和 Variables；
- Topics、仓库描述和 GitHub Pages 设置；
- Collaborators、Issues 和 Discussions 配置；
- 标签、Release 和历史 Pull Request。

这些设置应分别在两个仓库中维护。尤其不能把私有仓库 Secrets 复制到公开仓库，也不能把“文件同步成功”误认为仓库级配置已经一致。

## 维护原则

新增公开文件时，先把文件加入私有源仓库，再通过导出流程发布。新增私有材料时，应同时检查 `.publishignore` 是否覆盖其路径。修改排除规则后必须先运行 `--dry-run`，因为某个以前公开的文件一旦被排除，就会在目标仓库中表现为删除项。

公开仓库如果出现私有源仓库没有的必要配置，应优先把该配置回收到私有源仓库，而不是在每次发布后手工补写。只有 GitHub 仓库级设置和明确记录的特殊例外，才允许分别维护。
