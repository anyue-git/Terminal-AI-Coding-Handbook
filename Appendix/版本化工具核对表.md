# 版本化工具核对表

> 最近更新：2026-07-31

这张表用于维护变化较快的客户端、参数、模型、默认权限和兼容矩阵。正文负责稳定心智模型；容易变化的事实必须带核对日期，并在实际使用前同时检查官方文档、发布说明、本机版本、帮助输出、最终配置、账号能力、组织策略、操作系统和架构。

```text
官方文档与发布说明
+ 本机 --version / --help / 交互帮助
+ 当前配置、认证和账号策略
+ 操作系统、终端、架构与驱动
→ 才能判断当前机器上的真实能力
```

## 1. AI 编程客户端维护矩阵

| 工具 | 使用前命令 | 必须核对 | 维护边界 |
| --- | --- | --- | --- |
| Claude Code | `claude --version`、`claude --help`、`claude doctor` | 认证来源、模型后端、Permission Mode、用户与项目 Settings、`CLAUDE.md` 规则链、Hooks、MCP、子 Agent、会话恢复与分叉 | 客户端、模型供应商和认证分开；官方账号/API、云平台、企业 Gateway 与兼容供应商属于不同数据链；协议兼容不保证工具、缓存和行为一致；不把 bypass、Cookie、Session Token 或共享认证缓存写成普通路线 |
| Codex CLI | `codex --version`、`codex --help`、`codex login --help`、`codex exec --help`、`codex review --help` | ChatGPT 登录、Platform API Key、企业 Access Token；审批和 Sandbox；Permission Profiles；`AGENTS.md`；`CODEX_HOME`、Profile、Provider；非交互输出和会话 | 稳定 Sandbox/审批机制与实验权限机制不能混写；ChatGPT 计划用量与 Platform API 计费分开；跳过审批和 `danger-full-access` 不作为普通默认 |
| Grok Build | `grok version`、`grok --help`、`grok inspect`、`grok models`，进入 TUI 后查看 `/help` 和 `/` 菜单 | OAuth、Device Code、OIDC、External Auth 与 `XAI_API_KEY`；认证优先级；模型与 Provider；Ask/Auto/Always-approve、Plan、Rule、Sandbox；用户/项目/组织配置；TUI、Headless、ACP；Session、Memory、Goal、Workflow、Subagent、Worktree；Skill、Plugin、Hook、MCP、LSP 和兼容层 | 在线文档与随包指南可能短暂不同步；消费者订阅与 API 计费分开；会话恢复不是项目恢复；Worktree 只隔离 Git 目录；Persona 不隔离权限；Background Workflows 开关会改变 Goal Driver；`resume-codex` 等 Scanner 路线仍需按 staged 状态和实际 Skill 核对 |

三个客户端的非交互任务都应固定工作目录、分支、HEAD、模型、权限、工具集合、输出格式、外层超时、最大轮数或预算、退出状态和任务后的 Git diff。

| 对象 | 2026-07-31 核对结论 | 使用前再次确认 |
| --- | --- | --- |
| Slash Commands | 在线文档列出 `/share`、`/transcript`、`/queue`、`/tasks`；用户菜单还会加入 Skill Command | `/help`、输入 `/`、命令来源标签 |

| Goal | Background Workflows 开启时使用 Host-owned Engine，关闭时回退旧式工具 | `GROK_WORKFLOWS`、最终配置、Goal Feature |
| Workflow | 默认开启；Rhai 脚本；同进程可恢复，进程重启不恢复；Resume 非 exactly-once | 脚本、参数、Agent Budget、外部操作幂等性 |
| Agent Budget | 当前默认 128，显式范围 1–1024 | 当前上游帮助和 Workflow 定义 |
| Claude 导入 | `/import-claude` 为设置迁移；`grok import` 为 Claude 会话导入 | `grok import --help` 与测试会话 |
| Codex/Cursor Session | 兼容 Cell 仍标记 staged，需要匹配的 `resume-*` Skill | `/skills`、`grok inspect`、实际 Scanner 结果 |
| Auth | 模型级 Key > 活跃 Session Token > `XAI_API_KEY` | 登录状态、Base URL、用量和隔离 `GROK_HOME` |
| Project Config | 主要贡献 MCP、Plugin、Permission 与 MCP 输出限制 | `grok inspect` 中最终合并结果 |
| Privacy | `/privacy` 不自动关闭 Telemetry、Trace 或 External OTEL | 账号策略、配置、环境变量和外部服务 |

## 3. Provider、凭证与第三方管理工具

| 对象 | 使用前核对 | 不能仅凭什么判断 | 恢复要求 |
| --- | --- | --- | --- |
| 官方 API 或云平台 | Base URL、认证头、项目/组织、模型 ID、计费主体、区域和数据策略 | 客户端模型名称 | 保存官方端点、登录方式和恢复步骤 |
| 企业 LLM Gateway | 网关地址、上游 Provider、认证、审计、限速、模型映射、流式和工具调用兼容 | 普通文本成功 | 能切回官方路线，明确服务端责任边界 |
| CC Switch 桌面工具 | 仓库、安装来源、版本、修改文件、凭据、进程、监听地址、日志和备份 | “当前供应商”卡片 | 使用工具退出接管和恢复备份 |
| `ccswitch` 命令行项目 | 具体仓库、Keychain/凭据文件、环境变量覆盖、客户端重启要求 | 相近项目名称 | 确认活动凭据和官方登录可恢复 |
| Cockpit Tools | 本地端点、监听地址、上游账号、OAuth、日志、重试和退出恢复 | localhost Base URL | 停止服务，恢复原配置并重新认证 |

配置投影、凭据替换和本地路由接管是三种机制。界面显示的模型或账号不能单独证明请求最终到达哪个上游；切换后要检查活动配置、环境变量、凭据来源、进程和本地代理。

## 4. Docker、Python 与 GPU 软件栈

| 领域 | 使用前命令 | 变化较快的内容 | 稳定判断方式 |
| --- | --- | --- | --- |
| Docker Engine / Desktop | `docker version`、`docker info`、`docker context show` | Desktop、Linux Engine、Context、文件共享、权限和网络 | 先确认 CLI 连接的 daemon |
| Docker Compose | `docker compose version`、`docker compose config` | CLI、Specification、SDK 和平台功能 | 使用当前 Specification；顶层 `version` 不是新文件必需字段 |
| Python / pip | `python --version`、`python -c 'import sys; print(sys.executable)'`、`python -m pip --version` | Python、Wheel、原生扩展和安装源 | 解释器、pip 和项目环境属于同一套环境 |
| uv | `uv --version`、`uv sync --help` | `--locked`、`--frozen`、`--inexact`、Python 管理 | 明确精确同步是否移除额外包 |
| Conda | `conda --version`、`conda export --help` | 导出格式、Solver、Channel 和平台构建 | 高层环境与平台精确快照分开 |
| NVIDIA Driver | `nvidia-smi`、`ubuntu-drivers devices` | 推荐驱动、内核、Secure Boot/MOK | 宿主驱动先正常 |
| CUDA Toolkit / Runtime | `nvcc --version`、框架构建信息 | Toolkit、驱动上限、Wheel/镜像 Runtime | `nvidia-smi`、`nvcc`、`torch.version.cuda` 分层解释 |
| PyTorch / MPS | 查看 `torch.__version__`、`torch.version.cuda`、可用性 | Python、平台、CUDA 构建和算子 | 运行真实矩阵运算和项目短任务 |
| NVIDIA Container Toolkit | `nvidia-ctk --version`、`docker version` | 安装仓库、Runtime、CDI 和 Compose GPU | 不用 `--privileged`，不挂载 Socket、HOME 或凭据目录 |

## 5. OpenSSH、Tailscale 与自动检查

| 对象 | 使用前验证 | 维护提醒 |
| --- | --- | --- |
| OpenSSH Client | `ssh -V`、`ssh -G HOST_ALIAS` | 配置顺序以最终解析为准；不删除全部 `known_hosts`，不关闭主机密钥检查 |
| OpenSSH Server | `systemctl status ssh`、`sudo sshd -t`、必要时 `sudo sshd -T` | 保留旧会话和控制台；先检查、Reload、第二会话测试；公网 TCP 22 不作为默认 |
| Tailscale | `tailscale version`、`status`、`ping`、`netcheck` | Grants 和后台能力会变化；Tailscale 负责可达性，OpenSSH 负责登录 |
| GitHub Actions | Action 版本、Runner、权限、触发事件、凭据持久化、退出状态和 Artifact | 自动检查只证明脚本覆盖规则通过；Major Tag 仍需跟踪上游安全公告 |

## 6. 每次更新版本化章节的固定动作

```text
确认官方产品名和当前支持状态
→ 查看官方在线文档、发布说明和官方仓库
→ 比较在线文档与随包指南是否同步
→ 查看本机版本、帮助、交互菜单和最终配置
→ 区分稳定机制、当前默认、条件能力、扩展能力和 staged 能力
→ 核对账号、组织、平台、系统和架构差异
→ 更新正文与核对日期
→ 运行 Markdown、内部链接、敏感信息、外链和公开导出审计
→ 在真实环境抽样关键命令
→ 更新专项审查、内容审查和更新记录
```

核对表不能证明所有命令已经在每种系统、账号、终端、网络和组织策略下执行。它的作用是标记容易过期的边界，并告诉维护者发布前必须重新检查什么。
