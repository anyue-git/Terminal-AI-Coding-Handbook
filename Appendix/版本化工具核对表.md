# 版本化工具核对表

> 最近更新：2026-07-30

这张表用于维护变化较快的客户端、参数、模型、默认权限和兼容矩阵。正文应保留稳定的心智模型；容易变化的事实必须带核对日期，并在实际使用前同时检查官方文档、发布说明、本机版本、帮助输出、当前项目配置、账号能力、操作系统、CPU 架构和驱动条件。

```text
官方文档与发布说明
+ 本机 --version / --help
+ 当前配置和认证状态
+ 当前账号与组织策略
+ 操作系统、架构和驱动
→ 才能判断当前机器上的真实能力
```

## 1. AI 编程客户端维护矩阵

| 工具 | 使用前命令 | 必须核对 | 维护边界 |
| --- | --- | --- | --- |
| Claude Code | `claude --version`、`claude --help`、`claude doctor` | 当前认证来源、模型后端、Permission Mode、用户与项目 Settings、`CLAUDE.md` 规则链、Hooks、MCP、子 Agent、会话恢复与分叉 | 客户端、模型供应商和认证必须分开说明；官方账户/API、云平台、企业 Gateway 与兼容供应商属于不同数据链；协议兼容不保证工具调用、缓存和模型行为一致；不要把 bypass、Cookie、Session Token 或共享认证缓存写成日常路线 |
| Codex CLI | `codex --version`、`codex --help`、`codex login --help`、`codex exec --help`、`codex review --help` | ChatGPT 登录、Platform API Key 与企业 Access Token；审批策略与 Sandbox；是否启用 beta Permission Profiles；`AGENTS.md` 指令链；`CODEX_HOME`、Profile、Provider；非交互输出、工作目录和会话行为 | 稳定 Sandbox/审批机制与 beta 权限机制不能混成一套；弃用参数和实验功能按当前帮助确认；ChatGPT 计划用量与 Platform API 计费不是同一额度；跳过审批和 `danger-full-access` 不应成为普通默认 |
| Grok Build | `grok version` 或当前帮助支持的版本命令、`grok --help` | 浏览器认证、设备码与 `XAI_API_KEY`；认证优先级；Ask、Auto、Always-approve 与 Plan；Sandbox；用户与项目配置；Headless 输出与最大轮数；会话、Worktree 和扩展系统 | 产品名、默认模型、登录流程和配置结构变化较快；消费者订阅与 xAI API 用量分开；Always-approve 只减少确认；Worktree 只隔离 Git 目录；Plugins、Skills、Hooks、MCP、LSP 与 ACP 都扩大供应链和执行面 |

`grok inspect`、`grok models` 等入口目前出现在官方文档和 CLI 参考中，但维护者仍应先查看当前 `grok --help`，避免把任一子命令、别名或输出格式写成永久契约。三个客户端的非交互任务都应固定工作目录、权限边界、输出格式、外层超时、最大轮数或预算、退出状态和任务后的 Git diff。

## 2. Provider、凭证与第三方管理工具

| 对象 | 使用前核对 | 不能仅凭什么判断 | 恢复要求 |
| --- | --- | --- | --- |
| 官方 API 或云平台 | Base URL、认证头、项目/组织、模型 ID、计费主体、区域与数据策略 | 客户端界面中的模型名称 | 保存官方端点和登录方式，记录恢复步骤 |
| 企业 LLM Gateway | 网关地址、上游 Provider、认证方式、审计、限速、模型映射、流式和工具调用兼容 | 普通文本请求成功 | 能切回官方路线，并保留服务端故障排查责任边界 |
| CC Switch 桌面工具 | 仓库与作者、安装来源、版本、会改写的文件、是否接触凭据、是否启动本地服务、监听地址、日志、备份 | “当前供应商”卡片 | 优先使用工具自己的退出接管与恢复备份功能 |
| `ccswitch` 命令行项目 | 具体仓库、Keychain/凭证文件处理、环境变量覆盖、客户端是否需重启 | 与 CC Switch 相近的名称 | 确认活动凭证和官方登录仍可恢复 |
| Cockpit Tools | 本地 `/v1/responses`/模型端点、监听地址、上游账号路由、OAuth 存储、日志、失败重试与退出恢复 | 两个窗口或 localhost Base URL | 停止本地服务，恢复原始 Codex 配置并重新验证认证 |

配置投影、凭证替换和本地路由接管是三种不同机制。工具显示的模型或账号不能单独证明请求最终到达哪个上游；切换后要同时检查活动配置、环境变量、凭证来源、正在运行的进程和本地代理。Mac 与 Ubuntu 的配置不会自动同步，也不应通过复制整个认证目录来“保持一致”。

## 3. Docker、Python 与 GPU 软件栈

| 领域 | 使用前命令 | 变化较快的内容 | 稳定判断方式 |
| --- | --- | --- | --- |
| Docker Engine / Desktop | `docker version`、`docker info`、`docker context show` | Desktop 与 Linux Engine 架构、Context、文件共享、权限和网络实现 | 先确认 CLI 实际连接哪个 daemon，再判断容器、Volume 和端口状态 |
| Docker Compose | `docker compose version`、`docker compose config` | CLI 实现、Compose Specification、SDK 和平台功能 | 继续使用 `docker compose` 和当前 Specification；官方所称 Compose v5 主要引入官方 Go SDK，不代表用户需要迁移到新的文件格式或命令；顶层 `version` 已不是新文件的必需字段 |
| Python / pip | `python --version`、`python -c 'import sys; print(sys.executable)'`、`python -m pip --version` | Python 版本、wheel、原生扩展和安装源 | 解释器、pip 和项目环境必须属于同一套运行环境 |
| uv | `uv --version`、`uv --help`、`uv sync --help` | `--locked`、`--frozen`、`--inexact`、升级与 Python 管理行为 | 当前项目同步默认采用精确同步，可能移除锁文件之外的包；是否保留额外包应按当前帮助明确选择 |
| Conda | `conda --version`、`conda export --help` | 导出格式、Solver、Channel 和平台构建 | 高层 `environment.yml` 与平台精确快照分开，不能把一台机器的 explicit 环境当作跨平台通用文件 |
| NVIDIA Driver | `nvidia-smi`、`ubuntu-drivers devices` | 推荐驱动、内核、Secure Boot/MOK | 先让宿主驱动层正常，再进入 Python、容器和项目验证 |
| CUDA Toolkit / Runtime | `nvcc --version`、框架构建信息 | Toolkit、驱动兼容上限、wheel/镜像 Runtime | `nvidia-smi`、`nvcc` 与 `torch.version.cuda` 各自代表不同层，版本不同不自动表示错误 |
| PyTorch / MPS | 当前官方安装选择器；Python 中查看 `torch.__version__`、`torch.version.cuda`、`torch.cuda.is_available()` | Python、平台、CUDA 构建和算子支持 | 运行一次真实矩阵运算和项目短任务；Mac MPS 冒烟测试不能替代 Ubuntu CUDA 验证 |
| NVIDIA Container Toolkit | `nvidia-smi`、`nvidia-ctk --version`、`docker version` | 安装仓库、Runtime 配置、CDI 和 Compose GPU 声明 | 宿主驱动先正常；GPU 访问通常不需要 `--privileged`；不要挂载 Docker Socket、整个 HOME 或凭据目录 |

Docker 官方文档同时使用 Compose v2 和 v5 相关表述时，维护者应描述实际 CLI 与文件规范，不把代际名称写成永久唯一产品名。依赖升级、锁文件重算、驱动变更和 Docker daemon 修改都应独立成批，不与普通 Bug 修复混在一起。

## 4. OpenSSH、Tailscale 与自动检查

| 对象 | 使用前验证 | 维护提醒 |
| --- | --- | --- |
| OpenSSH Client | `ssh -V`、`ssh -G HOST_ALIAS` | 配置片段读取顺序以当前手册页和最终解析输出为准；不删除全部 `known_hosts`，不关闭主机密钥检查 |
| OpenSSH Server | `systemctl status ssh`、`sudo sshd -t`、必要时 `sudo sshd -T` | 修改服务端配置时保留旧会话和本机控制台；先语法检查、reload、第二会话测试；公网 TCP 22 不作为新手异网默认 |
| Tailscale | `tailscale version`、`tailscale status`、`tailscale ping HOSTNAME`、`tailscale netcheck` | Grants、策略语法和后台能力会变化；Tailscale 负责可达性，普通 OpenSSH 负责 Linux 登录；DERP 仍加密但性能可能较低，不为追求 direct 而公开 SSH 端口 |
| GitHub Actions | Action 版本、Runner OS、工作流权限、触发事件、凭据持久化、脚本退出状态、报告是否写回仓库 | 自动检查只证明脚本覆盖的规则通过；写权限工作流要审查触发来源和可修改文件；major tag 仍需跟踪上游发布和安全公告 |

## 5. 每次更新版本化章节的固定动作

```text
确认官方产品名和当前支持状态
→ 查看官方文档、发布说明和官方仓库
→ 查看本机 --version 与 --help
→ 区分稳定机制、当前默认、弃用入口和实验功能
→ 核对账号、组织、平台、系统、架构和驱动差异
→ 更新正文与最近核对日期
→ 运行严格 Markdown、内部链接和叙事审计
→ 在真实环境抽样执行关键命令
→ 更新内容审查记录与更新记录
```

核对表不能证明所有命令已经在每种操作系统、网络、显卡、账号和供应商条件下执行。它的作用是标记容易过期的边界，并告诉维护者在使用和发布前必须重新检查什么。
