# 版本化工具核对表

> 最近更新：2026-07-30

这张表记录变化较快的内容在使用和维护前应该核对什么。它不把某个时点的版本号、模型名或配置键写成永久结论。

实际操作前，优先组合检查：

```text
当前官方文档
+ 官方发布说明或仓库
+ 本机 --version
+ 本机 --help
+ 当前项目配置
+ 当前账号和平台能力
+ 当前操作系统、架构和驱动条件
```

正文应保留稳定心智模型；会频繁变化的参数、模型、默认权限和兼容矩阵则应带核对日期。

## 1. Claude Code

### 使用前验证

```bash
claude --version
claude --help
claude doctor
```

进入交互界面后，再使用当前版本提供的帮助、状态和诊断入口确认：

- 当前认证来源；
- 当前模型和供应商；
- Permission Mode；
- 项目和用户 Settings；
- CLAUDE.md 规则链；
- Hooks、MCP 和子 Agent；
- 会话恢复与分叉能力。

### 维护提醒

- Claude Code 是客户端，模型后端和认证方式应分开说明；
- 官方账户、API、云平台、企业 Gateway 与兼容供应商属于不同数据链；
- Anthropic 协议兼容不保证工具调用、缓存和模型行为完全一致；
- 安装渠道、最低 Node.js 要求和原生安装方式可能变化；
- 不把 bypass、Cookie、Session Token 或共享认证缓存写成日常路线；
- CC Switch 只管理配置，不替第三方供应商背书。

## 2. Codex CLI

### 使用前验证

```bash

codex review --help
```

还应核对：

- ChatGPT 登录、Platform API Key 与企业 Access Token 的区别；
- `sandbox_mode`；
- `approval_policy`；
- beta Permission Profiles 是否启用；
- `AGENTS.md` 指令链；
- `CODEX_HOME`、Profile 和 Provider；

- ChatGPT 计划用量与 Platform API 计费不是同一套额度；
- 不把跳过审批和 `danger-full-access` 写成普通默认。

## 3. Grok Build

> xAI 官方产品名为 Grok Build，终端命令为 `grok`。仓库目录保留 `Part-10B-Grok-CLI` 以避免破坏现有路径。

### 使用前验证

```bash
grok --version
grok --help
```

再按当前帮助和官方文档核对：

- 浏览器认证、设备码与 `XAI_API_KEY`；
- 认证优先级；
- Ask、Auto、Always-approve 与 Plan；
- Sandbox；
- 用户配置与项目 `.grok/config.toml`；
- Headless 输出格式与最大轮数；
- 会话恢复、分叉和 Worktree；
- Skills、Plugins、Agents、Hooks、MCP、LSP 与 ACP。

不要把 `grok inspect`、`grok models` 等命令当作永久存在的稳定入口；实际可用子命令以本机 `grok --help` 为准。

### 维护提醒

- 产品名、默认模型、登录流程和配置结构变化较快；
- 消费者订阅与 xAI API 用量不是同一套额度；
- Always-approve 减少确认，不代表没有 Sandbox 或系统风险；
- Worktree 只隔离 Git 工作目录；
- Plugin、Skill、Hook、MCP 和 ACP 都属于扩展与供应链攻击面；
- 项目配置未必覆盖所有用户级设置。

## 4. CC Switch、ccswitch 与 Cockpit Tools

### 使用前核对

```text
项目仓库和作者
安装来源
最近发布和提交
支持的客户端版本
会读取或改写的文件

是否记录请求和响应

```

### 维护提醒

- CC Switch 桌面工具与同名相近的 ccswitch CLI 不是同一个项目；
- 配置投影、凭据替换和本地路由接管是三种不同机制；
- 工具显示的“当前模型”不能单独证明请求实际到达哪个上游；
- Cockpit Tools 的本地端点、账号路由和日志能力需要按当前版本核对；
- Mac 和 Ubuntu 上的配置不会自动同步；
- 不指导提取、共享或转售网页登录会话和账号缓存。

## 5. Docker Engine、Desktop 与 Compose

### 使用前验证

```bash
docker version
docker info
docker context show
docker compose version
docker compose config
```

Ubuntu 还应检查：

```bash
systemctl status docker
```

### 维护提醒

- Docker Desktop 与 Ubuntu Docker Engine 的架构和文件共享方式不同；
- 当前 Compose CLI 仍使用 `docker compose` 和 Compose Specification；
- Docker 官方文档已同时涉及 Compose v2 与 v5，不能把“Compose v2”写成永久唯一代际名称；
- 顶层 `version` 字段不再是新 Compose 文件必需内容；
- `depends_on` 不自动表示依赖服务已经健康；
- Docker 组和 Docker Socket 都属于高权限能力；
- 发布端口的暴露范围不能只凭 UFW 状态判断；
- `docker compose down -v` 与 prune 操作可能删除持久数据。

## 6. Python、pip、venv、Conda 与 uv

### 使用前验证

```bash
python --version
python -c 'import sys; print(sys.executable)'
python -m pip --version
uv --version
uv --help
uv sync --help
conda --version
conda export --help
```

### 维护提醒

- `.venv` 与 Conda 环境目录不能在 Mac 和 Ubuntu 之间复制；
- `pip freeze` 是当前环境快照，不自动等于理想项目依赖；
- uv 可能下载和管理 Python，需确认项目实际解释器来源；
- 当前 uv 项目同步默认采用精确同步，可能移除锁文件之外的包；
- `--locked`、`--frozen`、`--inexact` 和升级参数的语义应按当前帮助核对；
- Conda explicit 导出通常具有平台依赖性；
- 不把依赖升级和普通功能修复放在同一批改动里。

## 7. PyTorch、NVIDIA Driver、CUDA 与 MPS

### 使用前验证

```bash
nvidia-smi
nvcc --version
python - <<'PY'
import torch
print("torch:", torch.__version__)
print("built_cuda:", torch.version.cuda)
print("cuda_available:", torch.cuda.is_available())
print("mps_available:", hasattr(torch.backends, "mps") and torch.backends.mps.is_available())
PY
```

### 维护提醒

- 不从旧文章复制固定 PyTorch、Python 和 CUDA 组合；
- PyTorch 安装命令以当前官方选择器为准；
- `nvidia-smi` 显示的 CUDA 能力不是本机 Toolkit 版本；
- 没有 `nvcc` 不自动表示预编译 PyTorch 无法使用 GPU；
- 系统 Toolkit 与 wheel Runtime 不同不自动表示错误；
- Secure Boot 和 MOK 可能影响驱动模块加载；
- Mac MPS 冒烟测试不能代替 Ubuntu CUDA 验证。

## 9. OpenSSH

### 使用前验证

Mac：

```bash
ssh -V
ssh -G HOST_ALIAS | sed -n '1,40p'
```

Ubuntu：

```bash
systemctl status ssh
sudo sshd -t
sudo sshd -T
```

### 维护提醒

- OpenSSH 配置片段的读取顺序应以当前手册页和最终解析输出为准；
- 修改服务端配置时保留旧会话和本机控制台；
- 不删除整个 `known_hosts`，不关闭主机密钥检查；
- Agent Forwarding 不作为普通个人开发默认；
- 不把公网 TCP 22 作为新手异网默认方案。

## 10. Tailscale

### 使用前验证

### 维护提醒

## 11. GitHub Actions 与仓库自动检查

### 使用前核对

```text
Action 版本标签
Runner 操作系统
工作流权限
是否持久化凭据
触发事件
脚本退出状态
报告是否会写回仓库
```

### 维护提醒

- 自动检查通过只证明脚本覆盖的规则通过；
- Markdown 检查不自动证明技术事实和外部链接有效；
- 使用写权限的工作流需要审查触发来源和可修改文件；
- Bot 提交与用户提交的作者显示可能不同；
- 依赖 Action 的 major tag 仍需要关注上游发布和安全公告。

## 12. 每次更新版本化章节的固定动作

```text
确认官方产品名和当前支持状态
→ 查看官方文档、发布说明和仓库
→ 查看本机 --version 与 --help
→ 区分稳定机制、当前默认和实验功能
→ 核对账号、平台、系统和架构差异
→ 更新正文与最近核对日期
→ 运行 Markdown 和内部链接检查
→ 抽样执行关键命令
→ 更新内容审查记录与更新记录
```

核对表不能证明所有命令已经在每种操作系统、网络、显卡、账号和供应商条件下真实执行。它的作用是标记容易过期的边界，并告诉维护者在使用前应检查什么。
