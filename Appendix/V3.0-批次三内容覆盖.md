## 2. Claude Code：客户端、权限、扩展、工作流与供应商分工

《安装、认证与第一次启动》只负责客户端安装来源、二进制路径、官方认证入口、第一次 Plan 会话、会话恢复和基础故障定位。原有原生安装、Homebrew、apt、npm、`type -a`、`claude doctor`、浏览器认证、API/企业路线、练习项目、Print 模式、会话命名与跨 Mac/Ubuntu 边界均保留；模型 Provider 和多实例原理移交 Part 10C。

《权限、审批、Sandbox 与安全边界》把 manual/default、acceptEdits、plan、auto、dontAsk 和 bypassPermissions 统一解释为默认审批策略，并与 Allow/Ask/Deny、Sandbox、附加目录、人工审批和 PreToolUse Hook 组成访问控制链。规则优先级、`.claude/settings*.json`、危险命令、网络路径、Hook 阻断示例和 Git 无法恢复的副作用均保留。

《会话、CLAUDE.md、Auto Memory、Hooks 与 MCP》由原来的大量扩展卡片重组为七层：会话与现实状态、人工维护规则、导入与路径规则、Auto Memory、Hooks、MCP、陌生项目清点。`/context`、`/memory`、`/permissions`、`/hooks`、`/mcp`、规则目录、前 200 行/25 KB Memory 限制、MCP Scope、凭据和提示注入边界均保留。

《大项目与多阶段任务工作流》删除与《通用 AI 编程闭环》重复的完整模板，只保留 Claude Code 特有的命名 Plan 会话、阶段停止点、`/compact`、worktree、子 Agent 和独立审查。登录空格案例、失败测试检查点、验证阶段、上下文交接、并行隔离、数据库/远程/GPU 闸门和最终验收均保留。

《Claude Code 接入 DeepSeek 与第三方供应商》集中讲后端路线、DeepSeek 当前官方变量映射、凭据输入、能力分级验证、兼容接口与官方支持边界、企业 Gateway、第三方切换工具和恢复官方路线。DeepSeek 变量、模型角色映射、Web Search/子 Agent/长上下文测试、401/403/404/工具调用故障和诊断元数据均保留；通用配置原理改由 Part 10C 主讲。

## 3. Codex CLI：认证、Sandbox、自动化与 Git 案例分工

《安装、认证与第一次启动》只讲独立安装器、npm/Homebrew 单一来源、ChatGPT 登录、Platform API Key、企业 Access Token、设备码、Mac/Ubuntu 分别认证、项目根启动、第一次只读调查、`AGENTS.md` 与会话恢复。ChatGPT 权益与 Platform API 计费不互换、`auth.json` 敏感边界和 IDE/CLI 共享状态均保留。

《权限、Sandbox 与配置》把 `read-only`、`workspace-write`、`danger-full-access` 与 `untrusted`、`on-request`、`never` 作为两条独立轴组织，并保留 Auto-review、beta Permission Profiles、与旧 `sandbox_mode` 互斥、文件/网络 TOML 示例、AGENTS 加载顺序、`codex sandbox` 测试和单变量配置实验。`--full-auto` 的弃用兼容定位和 `--yolo` 风险均保留。

《交互模式、codex exec 与自动化》围绕 TUI 与非交互任务选择、固定工作目录、执行工单、Sandbox/审批、会话与 `--ephemeral`、文本/JSONL/Schema、只读审计脚本、修改型自动化、证据、超时和 CI 密钥组织。`--add-dir`、`--skip-git-repo-check`、`--output-last-message`、`--json`、`--output-schema` 和完整 Shell 脚本均保留。

《Codex CLI 与 Git 协作案例》继续使用登录标识空格案例，保留基线项目、任务工单、只读计划、失败测试提交、最小实现、`codex review`、`/fork`、Worktree 对照、精确暂存、分支级 diff、人工 push 和证据型 PR。通用 Git 恢复原理只简要引用 Part 04，不再重复完整 Git 教程。

## 5. Part 10C：统一配置模型

《先分清配置、凭证、供应商与实例》建立全书统一术语：客户端、供应商、模型、配置、凭证、实例，以及模型切换、供应商切换、账号切换与独立实例的判定。Base URL、网络代理、LLM Gateway、默认配置、Profile、活动供应商和三种管理工具实现均连续解释。

《Codex 的 TOML、Profile 与凭证》保留 `CODEX_HOME`、TOML 基础、配置优先级、独立 Profile 文件、Responses Provider、外部 Token Helper、`wire_api` 兼容判断、Keyring/file/auto 存储与第二套 `CODEX_HOME` 实例。明确 Profile 不等于账号，localhost Base URL 仍需检查本地路由。

《Claude Code 的配置、凭证与网关》保留用户/项目/本地 JSON 作用域、`~/.claude.json`、Keychain/Linux 凭证文件、认证优先级、API Key/Auth Token/OAuth Token、`apiKeyHelper`、Gateway、兼容服务与 `CLAUDE_CONFIG_DIR` 隔离边界。配置、OAuth 与终端环境变量不再混成一个“供应商设置”。

《CC Switch、ccswitch 与 Cockpit Tools》明确三个同名/相近项目不是同一软件，并按配置投影、凭证替换和本地路由接管三种模式分析。各工具的可能改动、无密钥观察实验、真实路由验证、官方配置恢复、localhost 监听和 OAuth 使用边界均保留。
