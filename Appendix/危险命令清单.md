# 危险命令与高权限操作清单

> 最近核对：2026-07-30

这份清单不是说下面的命令永远不能使用，而是提醒你：同一条命令在不同机器、目录、用户和参数下，影响范围可能完全不同。高风险操作开始前，应当能够回答目标是什么、会影响哪些对象、能否预演、怎样确认成功，以及失败后怎样恢复。

## 1. 执行前先建立统一检查卡片

任何涉及删除、覆盖、管理员权限、远程机器、系统服务、网络、凭据或历史改写的命令，先确认：

```text
我在哪台机器？
我以哪个用户运行？
我在哪个目录？
完整命令展开后是什么？
目标路径、进程或服务实际是什么？
会匹配多少对象？
会覆盖、删除、上传或改写历史吗？
是否影响远程机器、其他用户或正在运行的任务？
有没有备份、Git 提交、checkpoint 或本机控制台？
能否先 dry run、预览或只读检查？
成功后怎样验证？
失败后怎样停止和恢复？
```

看不懂任意一项时先停下来。高风险命令需要的是上下文和恢复能力，而不是更快按下回车。让 AI 执行时，应先要求它输出主机、用户、目录、完整命令、影响、预演、验证和回滚卡片，不把“这是常见命令”当作充分解释。

## 2. 文件删除、覆盖与权限操作

| 操作 | 主要风险 | 最小防护 |
| --- | --- | --- |
| `rm -rf TARGET` | 递归删除、不进废纸篓、相对路径或变量指向错误位置 | 查看 `hostname`、`pwd`、`ls -ld TARGET`、`du -sh TARGET`；无法确认时先移动到隔离目录 |
| `rm -rf *`、`rm *.log` | Shell 在程序启动前展开通配符，可能匹配大量或错误文件 | 先运行 `printf '%s\n' *.log`；检查当前目录和隐藏文件 |
| `rm -rf "$TARGET_DIR"` | 变量为空、含换行、指向根目录或错误机器 | 先运行 `printf 'TARGET=<%s>\n' "$TARGET_DIR"` |
| `find ... -delete`、`find ... \| xargs rm` | 条件或目标写错会批量删除大量文件 | 先把删除动作改成 `-print`，确认匹配数量和目录 |
| `COMMAND > FILE` | 立即截断已有文件 | 先写 `FILE.new`，使用 `diff -u FILE FILE.new` 检查 |
| `cp`、`mv` | 可能覆盖同名目标或把目录层级理解错 | 查看 `ls -ld SOURCE DESTINATION`，重要文件先做时间戳备份 |
| `COMMAND >> ~/.zshrc` | 重复追加 PATH、环境变量和配置规则 | 先 `grep -n 'KEYWORD'`，编辑已有段落后重新加载并验证 |
| `chmod -R`、`chown -R` | 破坏可执行位、私钥权限、所有者和应用数据 | 先用 `ls -ld`、`namei -l` 定位真正缺少的权限，只改最小路径 |
| `dd`、`mkfs`、分区工具写入 | 直接覆盖磁盘、文件系统或双系统分区 | 按容量、序列号、挂载点和用途核对设备，保留离线备份与启动恢复介质 |

递归删除前的基本检查：

```bash
hostname
pwd
ls -ld TARGET
du -sh TARGET
```

文件名以 `-` 开头时，可以用 `--` 结束参数解析：

```bash
rm -- "-strange-name"
```

这只能防止文件名被当作选项，不能修复错误路径。重要配置需要备份时：

```bash
cp FILE "FILE.backup.$(date +%Y%m%d-%H%M%S)"
```

备份可能包含凭据，仍需限制权限并在确认恢复完成后安全清理。

`sudo` 不会让错误命令变正确，只会扩大影响范围。看到 `Permission denied` 时先运行：

```bash
whoami
pwd
ls -ld TARGET
namei -l TARGET 2>/dev/null || true
```

不要把 `sudo pip install`、`sudo brew install`、`chmod -R 777` 或递归修改整个主目录所有者当作通用修复。修改 `/etc`、SSH、防火墙、内核模块或 NVIDIA 驱动前，应准备配置备份、本机控制台和恢复步骤。

磁盘设备名不能靠 `/dev/sda`、`/dev/nvme0n1` 顺序猜测。双系统和多硬盘机器的枚举顺序可能变化，`dd`、`mkfs`、分区写入和错误 mount 不应交给 Agent 自动执行。

## 3. Git、rsync 与历史变化

Git 能恢复已经记录的源码，但不能自动恢复未跟踪文件、数据库、Volume、远程数据或已上传内容。以下操作必须先明确工作区、暂存区、提交和远程状态：

| 操作 | 可能影响 | 预演或更稳妥方式 |
| --- | --- | --- |
| `git restore .` | 丢弃未暂存的已跟踪修改 | 先查看 `git diff`，只恢复明确文件 |
| `git reset --hard TARGET` | 重置分支、暂存区和工作区 | 先查看 status/diff/log，必要时保存分支或补丁 |
| `git clean -fd` | 删除未跟踪文件和目录 | 先使用 `git clean -n`、`git clean -nd` |
| `git clean -fdx` | 还会删除 `.gitignore` 中的本地配置、缓存或环境 | 先使用 `git clean -ndx`，逐项检查 |
| `git rebase`、`commit --amend` | 改变提交哈希 | 只在理解共享状态和恢复方式时使用 |
| `git push --force` | 覆盖远程历史 | 普通协作不使用；需要时至少评估 `--force-with-lease` 和人工确认 |
| `git revert COMMIT_SHA` | 创建反向提交，不改写已有共享历史 | 已推送提交需要撤销时通常优先评估 |

执行危险 Git 操作前：

```bash
git status
git diff
git diff --cached
git log --oneline --decorate -10
```

`--force-with-lease` 比裸 `--force` 多一层远端引用检查，但仍然是历史改写。AI 不应在没有明确分支、远端状态和人工确认时执行强制推送。

rsync 的高风险点是方向、尾部斜杠、排除规则和删除：

```bash
rsync -av --delete SOURCE/ DESTINATION/
```

`--delete` 会删除目标端存在、但源端不存在的文件。源和目标写反，或源目录意外为空时，可能造成大量删除。必须先运行：

```bash
rsync -av --delete --dry-run SOURCE/ DESTINATION/
```

同时确认当前机器、源和目标方向、源路径尾部 `/` 的含义、排除文件是否生效、目标端是否有独立生成数据，以及 dry run 中所有删除项。普通源码同步默认不需要 `--delete`。

## 4. 安装、依赖、网络与系统服务

远程脚本直接执行：

```bash
curl URL | sh
curl URL | sudo sh
```

会把网络返回内容直接交给 Shell，第二条还同时授予管理员权限。至少确认 URL 来自当前官方文档、HTTPS 域名正确、是否发生重定向、脚本会修改哪些文件、是否安装后台服务和自动更新，以及管理员权限是否必要。能够先下载时：

```bash
curl -fsSL URL -o /tmp/installer.sh
less /tmp/installer.sh
```

大型官方脚本不一定容易完整审计，但先保存至少可以确认来源、头部说明和明显高风险动作。来源不明的命令不能因为群组中很多人使用就直接执行。

包管理器和环境工具的批量变化可能修改锁文件、间接依赖、原生扩展和平台兼容性：

```bash
brew upgrade
python -m pip install -U PACKAGE
uv lock --upgrade
uv sync
conda update --all
```

项目已有锁文件时，普通复现使用项目规定的 locked/frozen 参数；升级依赖应作为独立任务，不与普通 Bug 修复混在一起。uv 项目同步可能移除锁文件未声明的额外包，使用前查看：

```bash
uv lock --check
uv sync --help
git diff -- pyproject.toml uv.lock
```

SSH、防火墙和系统服务修改可能让远程连接立即失效。高风险行为包括修改 `sshd_config`、关闭认证方式、删除全部 `known_hosts`、关闭主机密钥检查、开放公网 TCP 22 和重置防火墙。远程修改 sshd 时固定采用：

```text
保留当前会话和本机控制台
→ 备份配置
→ sudo sshd -t
→ reload 服务
→ 第二个终端测试新连接
→ 成功后才关闭旧会话
```

个人异网访问优先使用 Tailscale 加普通 OpenSSH，而不是直接公开 TCP 22。

服务监听 `127.0.0.1` 时通常只有本机能直接访问；监听 `0.0.0.0` 或 `::` 可能把 Jupyter、TensorBoard、开发服务器、本地模型 API、Cockpit Tools 网关或调试端口暴露给局域网、Tailscale 网络或公网路径。检查监听：

```bash
ss -lntp 2>/dev/null || lsof -nP -iTCP -sTCP:LISTEN
```

远程访问优先让服务监听回环地址，再通过 SSH 本地端口转发。端口暂时没人知道不构成安全控制。

批量或强制终止进程同样需要核对对象：

```bash
kill -9 PID
pkill python
pkill -f PATTERN
killall PROCESS_NAME
```

先运行：

```bash
pgrep -af PATTERN
ps -p PID -o pid,user,etime,command
nvidia-smi
```

普通停止优先使用程序自身退出方式、`Ctrl + C` 或普通 `kill PID`。不要终止不属于自己的 GPU、数据库、远程服务或桌面图形进程。

## 5. Docker 高权限与数据删除

下列配置会显著扩大容器对宿主机的控制：

```text
--privileged
挂载 /var/run/docker.sock
挂载宿主机根目录或整个 HOME
Host Network
注入真实 SSH 或云凭据
以 root 写入共享项目目录
```

Docker Socket 通常意味着很高的宿主机控制能力。容器共享宿主机内核，即使没有 `--privileged`，Bind Mount、网络、设备和凭据挂载仍会扩大影响范围；不要把这些能力交给不可信容器、任意插件或未经审查的 AI 生成代码。

数据清理命令包括：

```bash
docker compose down -v
docker system prune
docker system prune -a --volumes
docker volume prune
docker image prune -a
```

`docker compose down -v` 会删除 Compose 声明的命名卷和附加匿名卷，数据库与其他持久数据可能随之消失。清理前检查：

```bash
docker ps -a
docker volume ls
docker image ls
docker system df
docker compose config
```

重要 Volume 必须先确认备份和恢复命令。不要把 prune 当作解决端口冲突、容器退出或镜像构建失败的第一步。

## 6. AI 自动批准、配置工具与凭据

任何具有以下含义的模式都不应作为日常默认：

```text
跳过审批
完全文件系统权限
关闭 Sandbox
自动同意全部工具调用
允许任意网络访问
在远程主机执行任意 sudo
```

自动批准减少的是确认步骤，不会自动限制当前用户可访问的文件、Docker Socket、SSH 密钥、云凭据、MCP、Hook、Plugin、数据集、模型目录或远程系统。自动化还应限制工作目录、最大轮数、外层超时、输出位置和失败条件；高权限模式只在隔离环境、明确任务和可恢复数据上短时使用。

CC Switch、ccswitch、Cockpit Tools 或其他管理工具可能改写 `config.toml`、`settings.json`、`auth.json` 或 Keychain，修改 Base URL，启动本地代理，轮换上游账号，并读取 Prompt、源码与请求日志。切换前确认备份和恢复入口；工具仍在监视配置时，不要同时手工覆盖 live 文件。恢复官方配置后核对：

```text
本地代理是否停止
Base URL 是否恢复
官方登录是否仍有效
Shell 中是否残留覆盖变量
客户端重启后实际 Provider 是否正确
```

不要分享、提交或交给不可信工具：

```text
API Key
Access Token
SSH 私钥
浏览器 Cookie
Session Token
Refresh Token
云平台凭据
AI CLI 认证缓存
.env 中的真实秘密
Tailscale 登录或设备授权链接
```

秘密一旦进入 Git 历史、聊天、截图或第三方日志，仅删除本地文件通常不够。应立即撤销或轮换凭据，并检查远程仓库、CI 日志和共享渠道中的传播范围。
