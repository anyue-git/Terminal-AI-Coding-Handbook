# 02 项目同步与目录规范

> 最近核对：2026-07-29

Mac 与 Ubuntu 协作时，最危险的并不是 SSH 断开，而是两台机器同时修改同一项目，并且双方都认为自己手里的版本最新。远程 GPU 工作流必须先确定一个主副本，再决定 Git、rsync、数据目录和实验目录各自承担什么职责。

本章沿用下面的默认分工：

```text
Mac
→ 源码主要编辑端
→ Git 提交与人工复核

Ubuntu
→ 源码运行副本
→ 数据、模型、GPU 训练与实验结果
```

这不是唯一方案。后面使用 VS Code Remote SSH 时，也可以让 Ubuntu 成为源码主副本；但同一阶段必须只有一个主要修改端。

## 1. 先建立清晰目录

在 Mac：

```text
~/Projects/my-project/
→ 源码

~/ML-Runs/my-project/
→ 拉回的日志、指标、图表和必要 checkpoint
```

在 Ubuntu：

```text
~/projects/my-project/
→ 源码和测试

~/datasets/
→ 数据集

~/models/
→ 模型权重和缓存

~/runs/my-project/
→ 每次实验的配置、日志、指标和 checkpoint
```

不要把所有内容放进项目目录：

```text
my-project/
├── data/           几十 GB
├── models/         大模型
├── runs/           大量 checkpoint
├── .venv/          平台相关环境
└── src/
```

这种布局会让 Git、rsync、VS Code、语言服务器和 AI CLI 扫描大量无关文件，也更容易误删或误提交。

## 2. Git 和 rsync 不是替代关系

Git 负责：

- 源码和文档；
- 小型配置模板；
- 可审查的版本历史；
- 分支、提交和多人协作；
- 从 Ubuntu 把临时修复安全带回 Mac。

rsync 负责：

- 在两台机器之间快速同步当前工作区；
- 传输未提交但需要试跑的代码；
- 传输数据、日志、图表和 checkpoint；
- 只复制发生变化的文件。

推荐理解：

```text
Git
→ 哪个版本是正式版本

rsync
→ 当前这批文件怎样高效到另一台机器
```

rsync 不会自动保存版本历史，也不会告诉你覆盖掉的内容属于谁。

## 3. 两种稳定开发模式

### 模式 A：Git 为正式同步路径

Mac：

```bash
cd ~/Projects/my-project
git status
git add 明确文件
git diff --cached
git commit -m "描述本次修改"
git push
```

Ubuntu：

```bash
ssh gpu-laptop
cd ~/projects/my-project
git status
git pull --ff-only
```

`--ff-only` 会在需要自动合并时拒绝操作，避免 Ubuntu 上的本地提交被悄悄合并。适合多人项目和准备长期保留的实验。

### 模式 B：Mac 单向 rsync 到 Ubuntu

Mac：

```bash
cd ~/Projects/my-project
rsync -av --dry-run \
  --exclude-from='.rsyncignore' \
  ./ gpu-laptop:~/projects/my-project/
```

确认文件列表后：

```bash
rsync -av \
  --exclude-from='.rsyncignore' \
  ./ gpu-laptop:~/projects/my-project/
```

适合个人局域网快速试验，尤其是代码还没准备提交时。

合理组合通常是：

```text
日常快速试跑
→ rsync

达到稳定检查点
→ Git 提交和推送
```

## 4. 源目录末尾的斜杠必须理解

```bash
rsync -av source/ host:target/
```

表示复制 `source` 目录里面的内容。

```bash
rsync -av source host:target/
```

通常会在目标中形成：

```text
target/source/
```

一个斜杠就可能让远端出现多套嵌套目录。正式同步前始终使用 `--dry-run`，并检查目标目录结构。

## 5. 创建 `.rsyncignore`

在 Mac 项目根目录创建：

```text
.rsyncignore
```

建议初始内容：

```text
.git/
.venv/
venv/
__pycache__/
*.pyc
.pytest_cache/
.mypy_cache/
.ruff_cache/
node_modules/
.env
.env.*
runs/
checkpoints/
data/
models/
*.log
.DS_Store
```

这里排除 `.git/` 的原因是 Ubuntu 通常拥有自己的 Git 元数据。把 Mac 的 `.git` 整体覆盖到 Ubuntu，可能破坏 Ubuntu 当前分支、索引和 Worktree 信息。

`.gitignore` 与 `.rsyncignore` 不同：

```text
.gitignore
→ Git 是否追踪

.rsyncignore
→ rsync 在这条命令中是否传输
```

rsync 只有在命令中显式使用 `--exclude-from` 才会读取它。

## 6. 不要在第一版脚本中加入 `--delete`

`--delete` 会删除目标端有、源端没有的文件。对严格镜像很有用，但在 GPU 节点上可能删除：

- Ubuntu 本地生成的配置；
- 临时诊断文件；
- 尚未回传的训练结果；
- checkpoint；
- Ubuntu 上临时修复的代码。

使用前至少预演：

```bash
rsync -av --dry-run --delete \
  --exclude-from='.rsyncignore' \
  ./ gpu-laptop:~/projects/my-project/
```

阅读所有 `deleting` 项。新手和日常训练脚本默认不使用 `--delete`。

## 7. 建立带预演模式的同步脚本

在项目根目录创建：

```text
scripts/sync-to-gpu.sh
```

内容：

```bash
#!/usr/bin/env bash
set -euo pipefail

PROJECT_ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
SOURCE_DIR="$PROJECT_ROOT/"
DESTINATION="gpu-laptop:~/projects/my-project/"
DRY_RUN=()

if [[ "${1:-}" == "--dry-run" ]]; then
  DRY_RUN=(--dry-run)
fi

printf 'source: %s\n' "$SOURCE_DIR"
printf 'destination: %s\n' "$DESTINATION"

rsync -av \
  "${DRY_RUN[@]}" \
  --exclude-from="$PROJECT_ROOT/.rsyncignore" \
  "$SOURCE_DIR" \
  "$DESTINATION"
```

赋予执行权限：

```bash
chmod +x scripts/sync-to-gpu.sh
```

先运行：

```bash
./scripts/sync-to-gpu.sh --dry-run
```

确认后：

```bash
./scripts/sync-to-gpu.sh
```

脚本只是固定参数，不会替你判断远端是否存在尚未回传的修改。每次重要同步前仍应查看两边 Git 状态。

## 8. 同步前进行“双端状态检查”

Mac：

```bash
cd ~/Projects/my-project
printf 'MAC\n'
hostname
pwd
git branch --show-current
git status --short
git rev-parse --short HEAD
```

Ubuntu：

```bash
ssh gpu-laptop '
  cd ~/projects/my-project &&
  printf "UBUNTU\n" &&
  hostname &&
  pwd &&
  git branch --show-current &&
  git status --short &&
  git rev-parse --short HEAD
'
```

如果 Ubuntu 有自己修改的源码，先停止覆盖操作。不要因为 Mac 是“主副本”就默认远端变化没有价值。

## 9. Ubuntu 临时修改代码后的安全回收

最稳妥方式是 Git：

```text
Ubuntu 创建分支
→ 提交最小修改
→ 推送
→ Mac fetch
→ 人工 merge 或 cherry-pick
```

Ubuntu：

```bash
cd ~/projects/my-project
git switch -c fix/ubuntu-runtime
git status
git diff
git add 明确文件
git diff --cached
git commit -m "fix: adjust Ubuntu runtime behavior"
git push -u origin fix/ubuntu-runtime
```

Mac：

```bash
cd ~/Projects/my-project
git fetch origin
git log --oneline --decorate origin/fix/ubuntu-runtime -5
git diff HEAD...origin/fix/ubuntu-runtime
```

然后由人决定合并。

修改还不适合提交时，可以在 Ubuntu 导出补丁：

```bash
git diff --binary HEAD > ~/ubuntu-runtime.patch
```

拉回 Mac：

```bash
scp gpu-laptop:~/ubuntu-runtime.patch ~/Downloads/
```

先查看：

```bash
less ~/Downloads/ubuntu-runtime.patch
```

再决定是否在单独分支应用：

```bash
git apply --check ~/Downloads/ubuntu-runtime.patch
git apply ~/Downloads/ubuntu-runtime.patch
```

未跟踪文件不会自动进入 `git diff HEAD`，需要另行审查。

## 10. 源码和实验结果保持不同方向

推荐：

```text
源码
Mac → Ubuntu

实验结果
Ubuntu → Mac
```

Mac 拉回完整结果前先预演：

```bash
mkdir -p ~/ML-Runs/my-project
rsync -av --dry-run \
  gpu-laptop:~/runs/my-project/ \
  ~/ML-Runs/my-project/
```

只拉回轻量结果：

```bash
rsync -av --dry-run \
  --include '*/' \
  --include 'config.yaml' \
  --include 'command.txt' \
  --include 'environment.txt' \
  --include 'metrics.json' \
  --include 'metrics.jsonl' \
  --include '*.png' \
  --include '*.csv' \
  --include '*.sha256' \
  --exclude '*' \
  gpu-laptop:~/runs/my-project/ \
  ~/ML-Runs/my-project/
```

复杂 include/exclude 规则从上往下匹配，必须先预演。

## 11. 数据和模型使用本地路径配置

Ubuntu：

```bash
export DATA_DIR="$HOME/datasets/my-dataset"
export MODEL_DIR="$HOME/models/my-model"
```

项目可以提交：

```text
config.example.yaml
.env.example
```

真实配置保存在未追踪文件中，例如：

```text
config.local.yaml
.env
```

并加入 `.gitignore`。不要把真实用户名、绝对私人路径、下载 Token 或数据访问凭据写进公开配置。

## 12. 不同步虚拟环境

以下目录必须排除：

```text
.venv/
venv/
__pycache__/
*.pyc
```

原因不是“文件太多”这么简单，而是 Mac 与 Ubuntu 的解释器、二进制格式、CPU 架构和 GPU 后端不同。两台机器应共享依赖声明和锁文件，并各自在本地建立环境。详见 [Mac 与 Ubuntu 分别创建环境](05-Mac与Ubuntu分别创建环境.md)。

## 13. 训练前固定检查

在 Ubuntu 项目目录运行：

```bash
hostname
pwd
git branch --show-current
git status --short
git rev-parse --short HEAD
python --version
python -c 'import sys; print(sys.executable)'
nvidia-smi
```

需要确认：

```text
机器正确
目录正确
分支和提交正确
未提交修改已知
Python 环境正确
GPU 可见
数据和输出路径正确
```

将这组检查加入训练启动脚本，比事后猜测“到底跑的是哪份代码”可靠得多。

## 14. 一次完整同步练习

### Mac：准备项目

```bash
mkdir -p ~/Projects/gpu-sync-demo/scripts
cd ~/Projects/gpu-sync-demo
printf 'print("hello gpu node")\n' > main.py
printf '.git/\n.venv/\n__pycache__/\n.env\nruns/\n' > .rsyncignore
git init
git add main.py .rsyncignore
git commit -m "chore: create GPU sync demo"
```

把上一节的脚本复制为：

```text
scripts/sync-to-gpu.sh
```

并把目标项目名改为 `gpu-sync-demo`。

### Mac：预演并同步

```bash
./scripts/sync-to-gpu.sh --dry-run
./scripts/sync-to-gpu.sh
```

### Mac：远程运行

```bash
ssh gpu-laptop '
  cd ~/projects/gpu-sync-demo &&
  hostname &&
  pwd &&
  python3 main.py
'
```

预期输出包含：

```text
hello gpu node
```

### Ubuntu：创建运行结果

```bash
ssh gpu-laptop '
  mkdir -p ~/runs/gpu-sync-demo/test-run &&
  printf "status=ok\n" > ~/runs/gpu-sync-demo/test-run/result.txt
'
```

### Mac：拉回结果

```bash
mkdir -p ~/ML-Runs/gpu-sync-demo
rsync -av --dry-run \
  gpu-laptop:~/runs/gpu-sync-demo/ \
  ~/ML-Runs/gpu-sync-demo/
rsync -av \
  gpu-laptop:~/runs/gpu-sync-demo/ \
  ~/ML-Runs/gpu-sync-demo/
cat ~/ML-Runs/gpu-sync-demo/test-run/result.txt
```

至此，你完成了：

```text
Mac 源码
→ 单向同步到 Ubuntu
→ Ubuntu 运行
→ 结果单向回传 Mac
```

下一步是在 Ubuntu 使用 tmux 维持长任务，并把每次实验放入独立运行目录。
