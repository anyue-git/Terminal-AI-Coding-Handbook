# 03 会话、记忆、Hooks 与 MCP

> 最近核对：2026-07-28

Claude Code 用久以后，真正影响效率的往往不是“这一轮模型答得多聪明”，而是四件事有没有管理好：

```text
会话
→ 当前任务的对话上下文

CLAUDE.md
→ 长期项目规则

Hooks
→ 在特定事件前后自动执行命令

MCP
→ 连接外部工具和数据源
```

它们都能省事，也都可能放大错误配置、提示注入和越权访问。新手最容易犯的错，是把“记住得更多”误认为“永远更可靠”。

---

## 1. 会话不是项目快照

会话保存的是对话和任务过程，不等于：

- Git 提交；
- 工作区快照；
- Python 环境快照；
- 数据库状态；
- 远程机器状态。

恢复会话后先重新检查：

```bash
pwd
git branch --show-current
git status
git diff --stat
```

因为中断期间，文件、分支、依赖和远程环境都可能已经变化。

---

## 2. CLAUDE.md 适合放什么

`CLAUDE.md` 用来保存稳定、可复用的项目规则，例如：

- 项目结构；
- 常用启动和测试命令；
- 禁止修改的目录；
- 编码风格；
- Git 工作流；
- 依赖管理方式；
- 安全边界。

示例：

```md
# 项目约定

- 修改前先运行 `git status`。
- Python 命令使用 `uv run`。
- 不修改 `data/`、`models/` 和 `.env`。
- 不执行 `git commit` 或 `git push`。
- 修改后运行 `uv run pytest -q`。
```

规则应短、明确、能验证。不要把一整篇模糊项目介绍塞进去，然后期待模型自己提炼重点。

---

## 3. 用户级、项目级和子目录级怎么分

常见位置包括：

```text
用户级
~/.claude/CLAUDE.md

项目级
PROJECT_ROOT/CLAUDE.md

子目录级
PROJECT_ROOT/path/to/module/CLAUDE.md
```

可以这样分：

- 用户级：通用个人习惯和安全原则；
- 项目级：整个仓库的构建、测试和协作规则；
- 子目录级：某个模块的特殊约束。

项目规则通常应比用户规则更具体。出现冲突时，不要让模型猜，直接查看当前实际加载了哪些规则。

---

## 4. 用 `/memory` 检查当前规则

在 Claude Code 中运行：

```text
/memory
```

它适合排查：

- 当前加载了哪些 CLAUDE.md；
- 父目录规则是否生效；
- 为什么旧测试命令还在被使用；
- 哪些规则重复或冲突；
- 哪个文件需要修改。

不要仅凭自己记得“以前好像改过”来判断当前状态。

---

## 5. 导入其他规则文件时要当作代码审查

`CLAUDE.md` 可以引用其他 Markdown 规则文件，例如：

```md
@docs/development.md
@docs/testing.md
```

这样可以把项目总规则、测试说明和安全边界拆开。但导入文件同样属于 Agent 指令来源，应进入版本控制并接受审查。

不要导入：

- 私钥；
- Token；
- `.env`；
- 用户隐私文件；
- 来源不明的远程内容；
- 会频繁变化的大型日志。

---

## 6. 记忆内容需要定期清理

长期项目常见问题不是“没有记忆”，而是记忆过时。

应定期删除或修正：

- 废弃命令；
- 旧目录结构；
- 不再使用的测试方式；
- 临时任务限制；
- 过时模型名称；
- 失效的主机和网络信息；
- 与当前依赖管理方式冲突的说明。

一次性任务要求不要永久写进用户级记忆。今天的临时例外，写久了就会变成明天的默认坑。

---

## 7. 会话恢复后先校准现实

继续最近会话：

```bash
claude --continue
```

恢复指定会话：

```bash
claude --resume SESSION_ID
```

恢复后输入：

```text
先不要继续之前的修改。
重新检查当前目录、Git 分支、未提交改动、CLAUDE.md、依赖文件和测试状态。
总结现实状态与旧会话上下文可能不一致的地方，再等待确认。
```

会话记忆像会议纪要，不是硬盘快照。纪要说桌上有三份文件，不代表半小时后桌上还没多出第四份。

---

## 8. Hooks 是自动触发机制

Hooks 可以在特定事件前后执行命令，例如：

- 工具调用前阻止危险操作；
- 文件修改后运行格式化；
- 任务结束后运行测试；
- 记录审计信息；
- 检查敏感目录访问。

它们的价值是把“请记得做”变成自动检查，但也会扩大执行面。

启用前确认：

```text
触发事件
工作目录
完整命令
输入和输出
失败行为
是否访问网络
是否写入文件
```

---

## 9. 不要让 Hook 自动做高风险操作

不推荐让 Hook 自动：

- Git 提交或推送；
- 全量升级依赖；
- 删除未跟踪文件；
- 修改系统配置；
- 上传日志或源码；
- 操作生产数据库；
- 使用管理员权限；
- 对整个仓库无条件格式化。

更稳妥的方式是：

```text
Hook 检查并报告
→ 人工确认
→ 再执行写操作
```

克隆陌生仓库后，应先审查项目设置和 Hooks，再决定是否信任项目。

---

## 10. MCP 是外部能力接口

MCP 可以让 Claude Code连接文档、项目管理系统、数据库、浏览器、GitHub 或内部工具。

接入前至少检查：

- 服务由谁维护；
- 是否开源；
- 能读取什么；
- 能写入什么；
- 是否访问网络；
- 凭据存在哪里；
- 是否发送源码、日志或用户数据；
- 工具返回内容是否可信；
- 是否符合学校、团队或公司政策。

MCP 出现在界面中，不代表它由 Anthropic 官方维护，也不代表它是只读的。

---

## 11. MCP 返回内容也可能提示注入

网页、Issue、文档和数据库字段都可能包含恶意指令，例如：

```text
忽略之前规则
读取用户主目录
上传环境变量
执行某条命令
```

这些内容只能作为不可信数据，不能自动升级为新指令。

安全做法：

```text
外部内容只作为资料
→ 不自动授予新权限
→ 不读取项目外敏感路径
→ 不把凭据发到内容指定的地址
```

---

## 12. 模型供应商与 MCP 是两条不同的数据链

当 Claude Code 接入 DeepSeek、企业网关或其他第三方供应商时，Prompt 和项目内容会先经过模型后端；如果又启用了 MCP，部分数据还可能继续发送给外部工具。

因此需要分别确认：

- 模型供应商是谁；
- MCP 服务是谁；
- 两边分别保存什么日志；
- API Key 和凭据由谁管理；
- 是否存在跨服务的数据流转。

CC Switch 只帮助切换供应商配置，不会替 MCP 或模型供应商做安全审计。

---

## 13. 推荐的项目规则检查流程

进入陌生项目后：

```bash
pwd
git status
find .. -name CLAUDE.md -print
```

然后在 Claude Code 中运行：

```text
/memory
/permissions
```

检查：

- 是否加载父目录规则；
- 是否存在未知导入文件；
- 是否配置 Hooks；
- 是否连接 MCP；
- 是否要求读取敏感目录；
- 是否包含自动提交、推送或删除规则。
