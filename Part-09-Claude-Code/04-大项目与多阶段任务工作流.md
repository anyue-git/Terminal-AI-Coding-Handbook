# 04 大项目与多阶段任务工作流

> 最近核对：2026-07-30

Claude Code 可以在一个会话中调查项目、修改多处文件并运行测试。任务扩大后，需要管理的核心不再是“让会话持续更久”，而是会话名称、Plan 产物、上下文压缩、阶段交接、独立审查和并行工作区。本章只讲 Claude Code 在这些环节中的特有能力；任务定义、批次预算、测试证据和 Git 提交流程见[复杂任务拆分与独立复核](../Part-12-AI开发工作流/05-复杂任务拆分与独立复核.md)与[通用 AI 编程闭环](../Part-12-AI开发工作流/01-通用AI编程闭环.md)。

## 1. 用命名 Plan 会话建立项目地图

跨模块、数据库、关键依赖、远程环境或 GPU 的任务，适合从命名 Plan 会话开始：

```bash
cd PROJECT_ROOT
pwd
git rev-parse --show-toplevel
git status
git branch --show-current

claude --name login-whitespace --permission-mode plan
```

会话名称便于恢复和辨认，不会创建 Git 分支，也不会保存工作区快照。分支、HEAD、文件和测试仍由 Git 与磁盘决定。

Plan 的产物应是可核对的项目地图，而不是长篇方案书。例如：

```text
当前阶段只读。

目标：登录用户名在验证前去除首尾空格；清理后为空仍被拒绝；其他行为不变。

请找出：
- 请求入口、调用链和最终验证函数；
- 现有相关测试与真实测试命令；
- 可能受影响的公开接口或兼容行为；
- 建议的最小文件范围；
- 已确认事实、推测和仍缺证据的项目。

重要结论引用文件和符号，不修改文件。
```

人工可以围绕返回的路径检查：

```bash
rg -n 'login|username|validate' src tests
find . \( -name CLAUDE.md -o -name pyproject.toml -o -name package.json \) -print
```

项目地图至少要解释行为在哪里决定、测试在哪里证明、哪些规则仍需人确认。实施阶段如何拆成失败测试、核心修改和验证批次，由通用复杂任务章统一说明，本章不再复制一套完整 Prompt。

## 2. 用 `/context`、`/compact` 和 `/clear` 管理阶段交接

长会话中可以运行：

```text
/context
```

它用于查看上下文占用和已加载来源。进入新阶段前，先让 Claude 生成一份短交接摘要，内容至少包括：

```text
任务目标与非目标
当前分支与 HEAD
已确认事实和人工决定
已完成提交与未提交修改
实际测试命令和结果
失败项、未验证内容和下一步
持续有效的权限与文件边界
```

随后压缩：

```text
/compact 重点保留任务目标、已确认事实、当前 Git 状态、测试结果和持续约束
```

压缩只整理对话，不改变磁盘。继续工作前重新读取 Git 状态、关键文件和测试结果。若会话已经积累大量错误尝试、目标发生变化或摘要无法区分事实与猜测，可以使用：

```text
/clear
```

然后根据 Git、测试和交接摘要重新开始。调查转实施、实现转审查、后端切换或新子任务开始，都可以成为会话边界；保留上下文是为了减少重复背景，不应阻止重新核实现实状态。

恢复会话同样需要重新对齐磁盘：

```bash
claude --continue
claude --resume login-whitespace
claude --resume login-whitespace --fork-session
```

`--fork-session` 分出新的对话路径，仍读取当前工作区。需要两个方案同时写文件时，必须使用 Worktree。

## 3. 独立审查使用新会话，而不是让实现者重复自评

修改和测试形成可读差异后，可以启动新的 Plan 会话：

```bash
claude --name login-whitespace-review --permission-mode plan
```

```text
只读审查当前分支相对于 main 的全部差异。
根据原始需求、代码和实际测试结果检查：
- 需求覆盖与范围外修改；
- 输入边界、兼容性和安全问题；
- 测试弱化、遗漏或环境限制；
- 哪些结论无法由现有证据确认。

问题引用文件和位置，并分类为必须修复、需要确认和可选建议。
```

新会话减少对实现方案的路径依赖，但不会自动获得正确判断。审查意见仍需回到代码、测试和需求核验；“没有发现问题”也不构成正确性证明。需要真正独立的工具或模型时，使用另一客户端，并只提供原始需求、diff 与验证证据，而不是先灌输实现者的结论。

## 4. Worktree 与子 Agent 分别处理写入隔离和只读并行

Claude Code 可以直接创建 Worktree：

```bash
claude --worktree feature-auth
claude --worktree bugfix-token-refresh
```

也可以由 Git 创建：

```bash
git worktree add ../project-auth -b feature/auth
cd ../project-auth
claude
```

Claude 创建的工作目录通常位于 `.claude/worktrees/`，项目应忽略这个目录。Worktree 是新的检出，不会自动拥有主工作区的 `.env`、`.venv`、`node_modules`、本地数据库和未跟踪数据。需要复制少量被忽略文件时，可以在项目根维护 `.worktreeinclude`，例如：

```text
.env.example
config/local.example.yaml
```

这里应只列可以安全复制、确实为每个 Worktree 所需的文件。真实凭据、大型数据、模型和运行结果不适合通过 `.worktreeinclude` 扩散到多个目录。

清理前检查：

```bash
git worktree list
git -C .claude/worktrees/feature-auth status
git -C .claude/worktrees/feature-auth log -3 --oneline
```

Worktree 隔离文件和分支，却通常共享 HOME、凭据、网络、Docker、数据库、GPU 和缓存。两个 Worktree 同时运行训练或迁移，仍可能争用同一外部资源。

子 Agent 更适合并行做只读调查，例如分别检查调用链、测试、数据库和文档，再由主会话合并证据。多个子 Agent 同时写同一工作区会让 diff 和测试失去来源；需要并行实现时，为每个写入者分配独立 Worktree，并由主工作区比较最终代码和测试。

## 5. 高影响阶段要把会话能力交给外部证据

数据库迁移、依赖主版本升级、全仓格式化、CI、远程主机、Docker daemon 和 GPU 驱动不能只靠会话摘要交接。进入这些阶段时记录机器、目录、分支和基础状态：

```bash
hostname
whoami
pwd
git status
nvidia-smi
```

同时保存日志、进程或容器状态、tmux 会话、checkpoint、备份与安全停止方式。只有一条远程连接时，不宜让 Agent 修改 SSH、网络、防火墙、Docker daemon 或 NVIDIA 驱动，因为连接中断后可能同时失去恢复入口。

更换 Anthropic、DeepSeek、企业 Gateway 或其他模型后端，不会改变 Git 状态和验证要求。交接应记录 Base URL 类型、模型映射、供应商错误和已验证能力，不记录 Token 正文。

准备创建 PR 时，Claude Code 能提供会话摘要和独立 Review，但人工仍需从当前 HEAD 检查需求、diff、测试、未验证项、依赖、迁移、回滚和敏感信息。大任务的可靠性来自每个阶段都能重新建立现实，而不是一个会话从头持续到尾。
