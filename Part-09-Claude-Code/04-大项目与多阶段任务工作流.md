# 04 大项目与多阶段任务工作流

> 最近核对：2026-07-28

Claude Code 可以一次完成小修改，但大项目不能把“理解需求、读代码、改实现、跑测试、修失败、更新文档、提交代码”全部塞进一句话。

复杂任务最稳妥的做法，是把它拆成多个能够单独检查的阶段：

```text
确认范围
→ 只读调查
→ 输出计划
→ 人工确认
→ 小步修改
→ 每阶段测试
→ 检查 diff
→ 独立复核
→ 人工提交
```

效率来自减少返工，而不是减少确认次数。

---

## 1. 什么情况应该按大任务处理

出现下面任意情况，就不适合让 Agent 一口气跑到底：

- 修改多个模块；
- 同时涉及前端、后端和数据库；
- 改动认证、权限、支付或数据迁移；
- 需要替换框架或升级关键依赖；
- 大范围重构；
- 测试耗时很长；
- 项目文档不完整；
- 需求存在明显歧义；
- 需要访问远程机器、外部服务或生产环境。

大任务最常见的失败不是“代码完全写不出来”，而是理解错方向、范围逐渐膨胀，最后产生一份没人敢认真看的巨大 diff。

---

## 2. 第一阶段只建立项目地图

第一轮不要修改文件：

```text
当前阶段只读，不要修改文件、安装依赖或执行 Git 写操作。

请读取 README、项目规则、依赖声明、测试配置和与任务相关的核心模块。
输出：
1. 项目入口；
2. 相关模块和调用关系；
3. 当前行为；
4. 测试方式；
5. 可能受影响的文件；
6. 已确认事实与推测；
7. 仍然缺失的信息。

重要结论给出文件路径。
```

如果项目地图不可靠，不要进入实施阶段。

---

## 3. 计划必须具体到文件和验证方法

要求计划说明：

- 每个阶段解决什么；
- 修改哪些文件；
- 为什么要改；
- 接口是否变化；
- 运行什么测试；
- 失败时在哪里停；
- 怎样回滚；
- 哪些内容明确不处理。

例如：

```text
阶段 1：补充现有行为测试
阶段 2：修改核心实现
阶段 3：处理异常路径
阶段 4：运行完整测试和静态检查
阶段 5：更新文档
```

“分析代码并优化系统”不算计划，只算愿望。

---

## 4. Bug 修复优先先建立失败测试

```text
先只添加一个能够稳定复现问题的最小回归测试。
不要修改生产代码。
运行该测试，并确认它因为预期原因失败。
如果失败原因与任务不一致，停止并说明。
```

测试在修改前失败，才能说明它确实覆盖了问题。否则很容易出现修完代码后才补一份“无论如何都会通过”的测试。

并不是所有任务都能严格测试先行，但每个阶段至少要有可观察的验证结果。

---

## 5. 每次只执行一个阶段

```text
现在只执行计划中的阶段 2。

允许修改：
- src/auth/service.py
- tests/test_auth.py

不要修改其他文件，不安装依赖，不执行 Git 写操作。
完成后运行指定测试，并停止汇报。
如果必须扩大范围，先说明原因、影响和替代方案，等待确认。
```

如果 Claude Code 觉得需要顺手改十几个文件，先让它解释。大项目经常不是被一个严重错误拖垮，而是被十几个“顺便”慢慢撑大。

---

## 6. 每个阶段都要有停止点

阶段结束后要求输出：

```text
本阶段完成后停止。
请汇报：
- 修改文件；
- 核心变化；
- 执行命令；
- 测试结果和退出状态；
- 未验证内容；
- 当前风险；
- 是否建议进入下一阶段。
```

不要让 Agent 在没有人工检查的情况下自动连续推进全部阶段。

---

## 7. 用 Git 保存清楚的检查点

开始前：

```bash
git status
git switch -c feature/login-validation
```

每个稳定阶段后由人检查：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

确认后只暂存相关文件：

```bash
git add tests/test_auth.py
git diff --cached
git commit -m "test: reproduce auth regression"
```

下一个阶段再创建下一次提交。小提交更容易回滚、定位问题和审查。

---

## 8. 长会话会出现上下文衰减

随着会话变长，Agent 可能：

- 忘记早期限制；
- 重复已经完成的工作；
- 混淆旧计划和新计划；
- 引用已经删除的代码；
- 错判当前 Git 状态。

定期生成任务摘要：

```text
不要修改文件。
请总结当前任务状态：
- 最终目标；
- 当前分支；
- 已完成阶段；
- 已修改文件；
- 已运行测试；
- 当前失败；
- 未解决风险；
- 下一步；
- 必须继续遵守的限制。
```

恢复会话后重新运行：

```bash
pwd
git status
git log -5 --oneline
```

不要只依赖对话记忆判断项目现实。

---

## 9. 什么时候应该新开会话

适合新开会话的情况：

- 从调查阶段进入实现阶段；
- 一个子任务已经完成；
- 当前会话包含大量失败尝试；
- 任务目标明显改变；
- 对话开始反复和混乱；
- 需要独立审查已有修改。

新会话应收到简洁的事实交接，而不是整段旧聊天记录。

```text
目标：修复登录输入验证。
分支：feature/login-validation。
已完成：回归测试和核心实现。
当前状态：相关测试通过，完整测试未运行。
允许范围：src/auth、tests/auth。
禁止：Git 写操作、依赖升级、数据库迁移。
下一步：审查 diff 并运行完整测试。
```

---

## 10. 用独立会话做复核

实现完成后，新开一个只读会话：

```text
不要修改文件。
请审查当前分支相对于 main 的差异。

重点检查：
- 逻辑错误；
- 边界条件；
- 安全问题；
- 测试缺口；
- 无关修改；
- 文档与实现不一致；
- 是否真正满足原始需求。

每条问题引用具体文件和位置，并区分：必须修复、需要确认、可选建议。
```

独立复核更容易发现实现会话已经习惯的错误，但仍不能替代人工阅读。

---

## 11. 测试失败时先分类，不要让它“修到绿”

不要直接说：

```text
修到所有测试通过为止。
```

这可能诱导 Agent 删除断言、跳过测试、扩大异常捕获或修改无关模块。

更好的要求是：

```text
先不要修改代码。
请区分失败属于：
1. 本次修改导致；
2. 原本就存在；
3. 环境或依赖问题；
4. 测试不稳定；
5. 需求与测试冲突。

每个判断提供证据，并给出下一条最小验证命令。
```

---

## 12. 大规模重构要把结构变化和行为变化分开

推荐顺序：

```text
先建立现有行为测试
→ 做机械结构调整
→ 验证行为不变
→ 再增加新功能
```

不要在同一个提交中同时：

- 重命名大量文件；
- 改业务逻辑；
- 更新依赖；
- 重写测试；
- 格式化整个仓库。

这种 diff 即使正确，也很难有效审查。

---

## 13. 数据库、远程环境和第三方后端要额外谨慎

数据库任务必须明确开发、测试和生产环境，说明迁移是否可逆、是否删除数据、如何备份和回滚。Claude Code 可以生成迁移文件，但不能因为脚本“看起来正确”就直接在生产执行。

远程机器上要确认：

```bash
hostname
whoami
pwd
git status
```

只有一个 SSH 会话时，不要让 Agent 自动修改 SSH、网络或防火墙。

使用 DeepSeek、企业网关或其他模型供应商时，长任务还要记录实际 Base URL、模型映射和供应商错误。换后端不会改变工作流原则，但可能改变工具调用、上下文和子 Agent 的表现。

---

## 14. 一份完整的启动模板

```text
任务目标：
[描述最终用户行为]

当前阶段：
只读分析和计划，不修改文件。

允许读取：
[目录或文件]

允许修改：
暂时无。

必须检查：
- README 与项目规则；
- 依赖声明；
- 测试配置；
- 相关实现和调用方；
- 当前 Git 状态。

输出：
1. 当前行为；
2. 相关模块；
3. 已确认事实和不确定点；
4. 分阶段计划；
5. 每阶段验证命令；
6. 预计修改文件；
7. 明确不修改的内容；
8. 停止条件。

限制：
- 不安装依赖；
- 不执行 Git 写操作；
- 不删除文件；
- 不访问生产环境；
- 不扩大范围；
- 信息不足时先提问。
```
