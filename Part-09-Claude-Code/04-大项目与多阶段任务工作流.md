# 04 大项目与多阶段任务工作流

> 最近核对：2026-07-29

Claude Code 可以在一次会话中完成小修改，但大型任务不适合把“理解需求、探索代码、修改实现、更新依赖、运行测试、处理失败、写文档和提交代码”全部塞进一句 Prompt。任务越大，范围误判、上下文衰减和巨大 diff 的代价越高。

更稳定的流程是把工作拆成可单独检查的阶段：

```text
确认目标和边界
→ 只读建立项目地图
→ 输出文件级计划
→ 人工批准一个阶段
→ 小步修改
→ 运行阶段验证
→ 检查 Git diff
→ 保存检查点
→ 新会话独立复核
→ 人工提交和推送
```

本章使用一个贯穿案例：给现有登录模块增加用户名首尾空格处理，并保证空字符串仍被拒绝。重点不是具体代码，而是怎样控制一项跨实现、测试和文档的任务。

## 1. 哪些任务应按“大任务”处理

出现下列任意情况，就不适合让 Agent 一口气运行到底：

- 修改多个模块或服务；
- 同时涉及前端、后端、数据库和基础设施；
- 改动认证、权限、支付、隐私或数据迁移；
- 更换框架或升级关键依赖；
- 大范围重命名和重构；
- 测试耗时很长或需要 GPU；
- 项目文档不足；
- 需求存在明显歧义；
- 需要访问远程机器、云资源或生产环境；
- 多个 Agent 或多人并行；
- diff 预计超过人工一次能完整审查的范围。

大型任务常见失败不是“代码完全写不出来”，而是起点理解错误，随后每一步都建立在错误假设上，最后生成一份看似完整但无法可靠审查的改动。

## 2. 先建立干净的 Git 起点

进入项目根目录：

```bash
cd PROJECT_ROOT
pwd
git rev-parse --show-toplevel
git status
git branch --show-current
```

如果工作区已有修改，先确认来源。不要让 Claude Code 在混有个人草稿、其他任务和未提交实验的工作区中开始大型改动。

创建任务分支：

```bash
git switch -c fix/login-whitespace
```

再次检查：

```bash
git status
git log -3 --oneline
```

Claude Code可以操作 Git，但本手册默认由人负责 `git add`、commit、push、merge、rebase 和 reset。这样每个检查点都经过人工 diff 审查。

## 3. 为会话命名并从 Plan 模式启动

```bash
claude --name login-whitespace --permission-mode plan
```

命名让长任务更容易恢复，也便于从其他 worktree 或目录中找到会话。Plan 模式先建立理解，不修改代码。

第一条 Prompt：

```text
当前阶段只读，不要修改文件、安装依赖、访问外部服务或执行 Git 写操作。

任务目标：
登录用户名在验证前应去除首尾空格；去除后为空的输入必须继续被拒绝；其他行为保持不变。

请建立项目地图并输出：
1. 登录请求从入口到验证的调用链；
2. 相关实现、测试、类型和文档文件；
3. 当前用户名处理行为；
4. 现有测试怎样运行；
5. 可以稳定复现问题的最小测试；
6. 可能的兼容性和安全风险；
7. 已确认事实与推测；
8. 仍缺失的信息。

重要结论引用具体文件和符号。
```

这一阶段的结果应是一张可验证的项目地图，而不是泛泛的“我会修改验证逻辑”。

## 4. 人工核对调查结果

检查 Claude 提到的文件：

```bash
rg -n 'login|username|validate' src tests
```

查看测试配置和项目规则：

```bash
find . \
  \( -name 'CLAUDE.md' -o -name 'pyproject.toml' -o -name 'package.json' \) \
  -print
```

核对：

- 入口文件是否真实；
- 调用关系是否遗漏中间层；
- 测试命令是否存在；
- 是否混淆显示名、账号名和邮箱；
- 是否存在 Unicode、大小写或数据库唯一性规则；
- 是否把“去除空格”错误理解成删除所有空白字符；
- 是否触及 API 契约和审计日志。

调查结果不可靠时，不要批准实施。继续要求它补证据或缩小问题。

## 5. 计划要具体到阶段、文件和停止条件

让 Claude 形成计划：

```text
根据已经确认的项目结构，提出分阶段计划。

每个阶段必须说明：
- 目标；
- 允许修改的文件；
- 不允许修改的内容；
- 运行命令；
- 预期结果；
- 失败时停止条件；
- 风险和回滚方式。

不要开始修改。
```

合格计划可能是：

```text
阶段 1：只增加回归测试，确认当前行为失败
阶段 2：最小修改用户名规范化实现
阶段 3：补充空白输入和已有行为测试
阶段 4：运行完整测试、静态检查和格式检查
阶段 5：更新必要文档
阶段 6：独立只读审查分支差异
```

“分析代码并优化登录”不是计划，因为没有文件、验证和边界。

## 6. 第一阶段只建立失败测试

切回 Manual 权限模式，或新开执行会话：

```bash
claude --resume login-whitespace
```

进入后确认权限模式，再输入：

```text
现在只执行阶段 1。

允许修改：
- tests/test_login.py

禁止修改：
- src/ 下全部生产代码；
- 依赖文件；
- 数据库迁移；
- Git 历史。

增加一个最小测试，证明用户名 "  alice  " 应按 "alice" 验证。
运行该测试，确认它因为当前实现未去除首尾空格而失败。
如果失败原因与预期不同，停止并说明，不要修改生产代码。
完成后停止汇报。
```

测试先失败，才能证明它覆盖了问题。Agent 不应为了让测试“按计划失败”而修改测试框架、跳过断言或注入假错误。

## 7. 阶段完成后只看证据

要求汇报：

```text
本阶段完成后停止。
请列出：
- 修改文件；
- 新增测试行为；
- 实际执行的完整命令；
- 退出状态；
- 关键失败信息；
- 是否符合预期失败原因；
- 当前未验证内容。
```

人工检查：

```bash
git status --short
git diff -- tests/test_login.py
```

重新运行测试：

```bash
PROJECT_TEST_COMMAND tests/test_login.py
```

不要只相信 Agent 的“测试如预期失败”。命令、退出状态和 diff 才是证据。

## 8. 人工创建第一个检查点

确认测试正确后：

```bash
git add tests/test_login.py
git diff --cached
git commit -m "test: reproduce username whitespace bug"
```

检查：

```bash
git status
git log -1 --stat
```

独立测试提交有两个价值：它证明 Bug 在实现修改前真实存在，也让后续实现改错时更容易恢复。

## 9. 第二阶段只做最小实现

输入：

```text
现在只执行阶段 2。

允许修改：
- src/auth/validation.py

不要修改测试、依赖、API Schema、数据库和其他模块。
实现用户名首尾空格规范化，使阶段 1 的回归测试通过，同时保留现有空字符串拒绝逻辑。

运行阶段 1 的测试和该模块现有测试。
如果必须扩大文件范围，先说明原因、影响和替代方案，等待确认。
完成后停止汇报，不执行 Git 写操作。
```

如果 Claude 提议“顺便重构整个认证模块”，应拒绝范围扩张。大型任务不是一次改得越多越好，而是每一步都能解释和验证。

## 10. 每阶段都运行窄测试和回归测试

先运行直接相关测试：

```bash
PROJECT_TEST_COMMAND tests/test_login.py
```

再运行认证模块测试：

```bash
PROJECT_TEST_COMMAND tests/auth/
```

人工查看：

```bash
git diff -- src/auth/validation.py
git diff --stat
```

重点检查：

- 是否只去除首尾空格；
- 是否改变大小写处理；
- 是否改变日志和错误信息；
- 是否在错误层重复规范化；
- 是否绕过已有验证；
- 是否引入无关格式化。

确认后再创建实现提交：

```bash
git add src/auth/validation.py
git diff --cached
git commit -m "fix: normalize username before validation"
```

## 11. 边界条件应成为单独阶段

下一阶段补充：

```text
普通用户名
前后空格
全为空格
空字符串
制表符或换行
已有非法字符
超长输入
Unicode 空白
```

这些场景不一定都应使用同一处理规则。先根据产品需求和现有行为决定，不要让模型自创规范。

Prompt：

```text
只执行阶段 3：补充边界测试。
不要修改生产代码。

先列出当前需求明确支持的边界与仍需要产品确认的边界。
只为已经确认的行为添加测试。
运行测试后停止。
```

将“需要产品决定”与“可以从代码推断”分开，避免模型把猜测固化成 API 行为。

## 12. 测试失败时先分类

不要输入：

```text
把所有测试修到通过为止。
```

这可能诱导 Agent 修改无关断言、增加跳过、扩大异常捕获或掩盖真实回归。

更好的要求：

```text
先不要修改文件。
请把失败分为：
1. 本次改动导致；
2. 修改前已经存在；
3. 环境或依赖问题；
4. 测试不稳定；
5. 需求与现有测试冲突。

每项提供文件、错误信息和下一条最小验证命令。
```

只有确认根因后，才批准对应修复。

## 13. 完整验证应独立于实现阶段

相关测试通过后，单独执行验证阶段：

```text
当前阶段只验证，不修改文件。

依次运行：
- 完整单元测试；
- 项目静态检查；
- 格式检查；
- 类型检查；
- 与登录相关的集成测试。

每条命令记录退出状态和通过/失败数量。
不能在当前环境执行的项目明确标记“未验证”，不要写成通过。
```

Mac 无法验证 Ubuntu CUDA，个人机器无法运行生产集成测试，这些都应如实记录。

## 14. 文档更新只覆盖真实变化

实现和测试稳定后，再检查是否需要更新：

- API 文档；
- 用户输入规则；
- 变更日志；
- 迁移说明；
- 示例；
- `CLAUDE.md` 中的测试命令。

不要为小修复生成大量空泛文档。只有外部行为、运行方式或维护规则变化时，才更新对应材料。

## 15. 长会话要主动管理上下文

使用：

```text
/context
```

查看上下文占用。会话过长时，可以要求：

```text
不要修改文件。
请生成当前任务交接摘要：
- 最终目标；
- 当前分支和 HEAD；
- 已完成阶段与提交；
- 当前工作区修改；
- 已运行测试；
- 失败和未验证内容；
- 下一阶段；
- 必须继续遵守的边界。
```

然后使用：

```text
/compact 重点保留任务目标、已确认事实、当前 Git 状态、测试结果和安全限制
```

或者在合适阶段使用 `/clear` 新开上下文，再通过 Git 和交接摘要恢复任务。

`/compact` 是摘要，不是精确数据库。压缩后仍要重新检查文件和 Git 状态。

## 16. 什么时候应该新开会话

适合新开会话：

- 从调查进入实施；
- 一个独立子任务已经完成；
- 当前会话积累大量错误尝试；
- 目标发生明显变化；
- 上下文开始重复和混乱；
- 需要独立审查；
- 需要换模型或供应商进行第二意见。

新会话收到的是简洁事实交接，而不是整段旧聊天：

```text
目标：规范化登录用户名首尾空格。
分支：fix/login-whitespace。
已完成：失败测试、最小实现、边界测试。
当前状态：相关测试通过，完整集成测试未运行。
允许范围：src/auth、tests/auth、相关文档。
禁止：依赖升级、数据库迁移、Git 写操作。
下一步：只读审查 main...HEAD 差异。
```

## 17. 使用独立会话做只读复核

新开 Plan 会话：

```bash
claude --name login-whitespace-review --permission-mode plan
```

Prompt：

```text
不要修改文件。
请审查当前分支相对于 main 的全部差异。

重点检查：
- 是否满足原始需求；
- 逻辑和边界错误；
- 安全与认证风险；
- 兼容性变化；
- 测试是否真正覆盖问题；
- 是否弱化了断言；
- 无关修改；
- 文档与实现不一致。

每条问题引用具体文件和位置，并分类为：
必须修复、需要确认、可选建议。
```

独立会话没有实现过程中的路径依赖，更容易发现“为了让当前方案成立而忽略的问题”。它仍不能替代人工代码审查。

## 18. 分叉会话比较两种方案

存在两个合理实现时，可以从调查会话分叉：

```bash
claude --resume login-whitespace --fork-session
```

分别要求：

```text
方案 A：在请求入口规范化
方案 B：在领域验证层规范化
```

两个会话都只输出计划，不同时修改同一工作区。人工比较：

- 责任归属；
- 重复调用；
- API 一致性；
- 测试成本；
- 兼容风险；
- 后续维护。

选择后只让一个会话实施。

## 19. 并行编辑必须使用独立 worktree

多个 Claude 会话不能同时修改同一个工作区。当前 Claude Code支持：

```bash
claude --worktree feature-auth
```

它会创建独立 worktree 和分支，默认位于：

```text
.claude/worktrees/feature-auth/
```

另一个任务：

```bash
claude --worktree bugfix-token-refresh
```

这样两个会话共享 Git 历史，但文件目录和分支彼此隔离。

第一次使用前，应在主仓库运行普通 `claude` 并确认 Workspace Trust。还应将：

```text
.claude/worktrees/
```

加入 `.gitignore`，避免主工作区出现未跟踪目录。

## 20. Worktree 不是完整环境复制

新的 worktree 是干净检出，通常不包含：

- `.env`；
- `.venv`；
- `node_modules`；
- 本地数据库；
- 未跟踪测试数据；
- 个人配置。

每个 worktree 需要单独创建依赖环境。不要把主项目的 `.venv` 直接复制到另一平台或路径后期待绝对路径仍正确。

Claude Code支持 `.worktreeinclude` 复制 Git 已忽略的文件，但不要用它无条件复制生产秘密。明确评估每个模式：

```text
.env.test
→ 可能合理

生产云凭据
→ 不应自动复制

大型数据集
→ 不应为每个 worktree 重复复制
```

## 21. 自动清理 worktree 前先看改动

退出 worktree 会话时，Claude Code会根据是否存在修改和提交决定自动清理或询问。

手工检查：

```bash
git worktree list
git -C .claude/worktrees/feature-auth status
git -C .claude/worktrees/feature-auth log -3 --oneline
```

移除 worktree 可能丢弃未提交文件和分支内容。不要在不检查状态时批量清理。

需要更强控制时，使用原生 Git：

```bash
git worktree add ../project-auth -b feature/auth
cd ../project-auth
claude
```

## 22. 子 Agent 适合调查，不自动等于独立编辑

大型项目中，可以让子 Agent 分别调查：

```text
认证调用链
现有测试覆盖
数据库影响
安全风险
文档和 API 变化
```

主会话只接收结论，减少大量文件读取占满上下文。

但多个子 Agent 如果共享同一工作区并同时编辑，仍可能冲突。需要并行写入时，应明确使用 worktree 隔离；自定义子 Agent 也可以设置 `isolation: worktree`。

每个 Agent 都应有：

- 独立职责；
- 最小工具；
- 明确目录；
- 输出格式；
- 停止条件；
- 最终集成负责人。

“让五个 Agent 一起看看”不是分工。

## 23. 多人和多 Agent 的集成顺序

推荐：

```text
主任务定义接口和文件边界
→ 每个子任务独立分支/worktree
→ 各自完成测试和 diff
→ 人工审查每个分支
→ 按依赖顺序合并
→ 运行集成测试
→ 独立整体复核
```

不要让多个 Agent 同时改同一核心文件后，再指望模型自动合并全部语义冲突。

集成负责人需要判断：

- 接口假设是否一致；
- 测试是否重叠或冲突；
- 依赖版本是否统一；
- 数据迁移顺序；
- 最终 Compose 和部署配置；
- 是否出现重复实现。

## 24. 重构要把机械变化与行为变化分开

推荐顺序：

```text
建立现有行为测试
→ 机械重命名和移动
→ 验证行为不变
→ 独立提交
→ 再修改业务行为
→ 新测试和文档
```

不要在同一个提交同时：

- 重命名大量文件；
- 改业务逻辑；
- 升级依赖；
- 重写测试；
- 格式化整个仓库；
- 调整 CI。

即使最终代码正确，这样的 diff 也很难有效审查和定位回归。

## 25. 数据库任务必须增加环境与回滚闸门

数据库变更先确认：

```text
开发 / 测试 / 预发布 / 生产
数据库地址
当前用户权限
备份状态
迁移是否可逆
预计锁表和运行时间
失败回滚方式
```

让 Claude 生成迁移文件不等于批准执行迁移。默认只在本地测试数据库验证，并明确禁止连接生产。

Prompt：

```text
只生成迁移方案和本地测试，不执行任何数据库迁移。
不得读取生产凭据。
请说明向前迁移、回滚、数据兼容、锁表风险和验证 SQL。
```

## 26. 远程和 GPU 任务需要记录机器身份

每次远程阶段先执行：

```bash
hostname
whoami
pwd
git status
nvidia-smi
```

长任务还要记录：

- tmux 会话名；
- 日志路径；
- PID 或容器名；
- GPU 设备；
- checkpoint 路径；
- 安全停止方式；
- Mac 与 Ubuntu 分别完成了哪些验证。

只有一个 SSH 会话时，不要让 Agent 修改 SSH、网络、防火墙、Docker daemon 或 NVIDIA 驱动。

## 27. 更换模型后端不会消除流程要求

使用 Anthropic、DeepSeek、企业 Gateway 或其他兼容后端时，都要保持：

```text
明确任务范围
阶段停止点
权限审查
Git diff
真实测试
独立复核
```

不同后端可能在工具调用、上下文、子 Agent、Web Search 和错误处理上表现不同。记录实际 Base URL、模型映射和供应商错误，但不要在日志中泄露 Token。

## 28. 一个完整的启动模板

```text
任务目标：
[描述最终用户行为，不只写技术手段]

当前阶段：
只读调查和计划，不修改文件。

允许读取：
[目录或文件]

禁止读取：
.env、凭据、项目外目录和生产数据。

允许修改：
暂时无。

必须检查：
- README、CLAUDE.md 和 .claude/rules；
- 依赖声明和锁文件；
- 测试配置；
- 相关实现、调用方和接口；
- 当前 Git 状态。

输出：
1. 当前行为；
2. 项目地图；
3. 已确认事实和不确定点；
4. 分阶段计划；
5. 每阶段文件、命令和停止条件；
6. 风险、验证和回滚。

禁止：
安装依赖、访问网络、删除文件、Git 写操作、数据库写入和远程环境修改。
```

## 29. 每阶段执行模板

```text
现在只执行计划中的阶段 [编号]。

允许修改：
- [文件列表]

禁止修改：
- [范围]

运行：
- [窄测试]
- [必要检查]

失败条件：
如果测试失败原因与预期不同，或必须扩大范围，立即停止并说明。

完成后停止并汇报：
- 修改文件；
- 核心变化；
- 完整命令；
- 退出状态；
- 测试结果；
- 未验证内容；
- 当前风险。

不要执行 git add、commit 或 push。
```

## 30. 最终验收清单

合并或创建 PR 前确认：

```text
需求已经由测试或可观察行为证明
相关测试和完整测试结果明确
未运行项目被标记为未验证
没有无关格式化和范围漂移
依赖与锁文件变化可解释
数据迁移和回滚清楚
敏感信息未进入 diff 或日志
独立复核问题已经处理
Git 提交按目的拆分
PR 描述包含验证、风险和未处理内容
```

大型任务的效率来自减少返工和提高可审查性，而不是让 Agent 更长时间无人监督地运行。
