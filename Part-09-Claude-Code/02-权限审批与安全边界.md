# 02 权限、审批、Sandbox 与安全边界

> 最近核对：2026-07-29

Claude Code 可能读取文件、修改代码、运行 Shell 命令、访问网络、调用 MCP、执行 Hooks 和启动子 Agent。安全使用它，不能只靠一句“请小心”。需要同时理解任务范围、权限模式、权限规则、Sandbox 和人工审批。

这五层分别回答：

```text
任务范围
→ 你希望它做什么

权限模式
→ 默认怎样处理工具调用

权限规则
→ 哪些操作允许、询问或拒绝

Sandbox
→ Bash 进程在操作系统层实际能访问什么

人工审批
→ 当前这一次操作是否值得执行
```

Prompt 和 `CLAUDE.md` 只影响模型的行为倾向，不是强制安全边界。真正的限制应由权限规则、Sandbox、Hook 和外部隔离共同完成。

## 1. 先检查当前权限状态

从项目根目录启动：

```bash
cd PROJECT_ROOT
pwd
git status
claude
```

进入 Claude Code 后运行：

```text
/permissions
```

重点检查：

- 当前权限模式；
- Allow、Ask 和 Deny 规则；
- 规则来自用户、项目、本地还是组织配置；
- 是否加入额外目录；
- 是否存在宽泛的 Bash 或 Web 规则；
- 是否启用了陌生 MCP、Hooks、Plugins 或子 Agent；
- 项目是否已经被信任。

不要因为上次会话处于 Plan 模式，就假设本次仍然只读。启动参数、设置文件、工作目录和项目规则都可能改变。

## 2. 当前主要权限模式

Claude Code 当前支持多种模式。CLI 中可以用：

```bash
claude --permission-mode MODE
```

### Manual / default

```bash
claude --permission-mode manual
```

`manual` 是 `default` 的界面别名。它采用标准行为，对新的工具使用和敏感操作按规则询问，适合日常开发和陌生项目。

### acceptEdits

```bash
claude --permission-mode acceptEdits
```

该模式自动接受项目工作目录或附加目录中的文件编辑，以及部分常见文件操作。Shell、网络、MCP 和其他能力仍受规则与审批影响。

适合：

- 任务范围已经清楚；
- 修改文件较多但命令较少；
- 当前分支干净；
- 仍希望对 Shell 和外部操作保留控制。

它不是“全自动模式”。

### plan

```bash
claude --permission-mode plan
```

Plan 模式主要用于阅读、探索和制定方案，不编辑源文件。当前版本中，某些只读命令或经过 Auto 分类器批准的命令可能运行，因此仍应检查命令内容。

适合：

- 第一次进入陌生仓库；
- 大型重构前调查；
- 安全、认证、数据库和基础设施任务；
- 需求还不明确；
- 希望先获得文件级计划。

### auto

```bash
claude --permission-mode auto
```

Auto 模式会通过后台安全检查判断工具调用是否与用户请求一致，并自动批准符合判断的操作。

它减少人工弹窗，但不代表操作没有风险。分类器可能无法理解项目外副作用、业务数据价值、远程环境和组织规则。个人电脑、含真实凭据的仓库和远程 GPU 主机上，不应仅因为模式名称含有“安全检查”就放弃审查。

### dontAsk

```bash
claude --permission-mode dontAsk
```

DontAsk 模式不会弹出普通审批请求。没有提前通过 `/permissions` 或 `permissions.allow` 允许的工具会被自动拒绝。

它适合：

- 非交互自动化；
- 明确的工具白名单；
- CI 中希望“未授权就失败”，而不是等待输入；
- 只允许少量可预测命令的任务。

该模式不是“什么都自动做”，而是“未预先允许就拒绝”。

### bypassPermissions

```bash
claude --permission-mode bypassPermissions
```

该模式跳过大多数权限提示，只保留显式 Ask 规则、部分组织 Connector、需要用户交互的 MCP，以及少数根目录和家目录删除熔断检查。

只应在真正隔离的临时容器、虚拟机或一次性环境中使用，并且隔离环境中不能挂载真实 HOME、SSH、云凭据、生产数据或 Docker Socket。

不要将它设为普通别名，也不要把：

```bash
claude --dangerously-skip-permissions
```

写进 Shell 启动文件、团队脚本或日常工作流。

## 3. 模式只决定默认处理方式

同一模式下，权限规则仍然会改变结果。例如在 Auto 或 bypassPermissions 模式中，显式 Ask 规则仍可能要求确认；显式 Deny 规则仍会拒绝。

因此应把模式理解为：

```text
默认审批策略
```

而不是：

```text
完整访问控制策略
```

对于重要项目，更推荐：

```text
Plan 调查
→ Manual 执行
→ 精确 Allow / Ask / Deny
→ Sandbox 限制 Bash
→ Git diff 人工复核
```

## 4. Allow、Ask、Deny 的优先顺序

权限规则按照固定顺序判断：

```text
Deny
→ Ask
→ Allow
```

先匹配到的类别决定结果。规则更具体也不能越过这个顺序。

例如：

```text
Deny: Bash(aws *)
Allow: Bash(aws s3 ls)
```

第二条不会成为例外，因为宽泛 Deny 已经先匹配。需要设计例外时，应重新缩小 Deny 范围，而不是依赖更具体 Allow 覆盖。

Allow 表示无需人工确认；Ask 表示每次匹配都要求确认；Deny 表示阻止操作。

## 5. 权限规则的基本格式

规则形式是：

```text
Tool
```

或：

```text
Tool(specifier)
```

裸工具名匹配所有用途：

```text
Bash
Read
Edit
WebFetch
```

更精确的示例：

```text
Bash(git status)
Bash(git diff *)
Bash(python3 -m unittest *)
Read(./docs/**)
WebFetch(domain:docs.python.org)
Agent(Explore)
```

规则语法会随版本完善。写入长期配置前，应查看当前权限文档和 `/permissions` 展示，不要从旧博客复制通配模式。

## 6. 一份适合练习项目的本地规则

项目设置位置包括：

```text
用户级
~/.claude/settings.json

项目共享
PROJECT_ROOT/.claude/settings.json

本机项目设置
PROJECT_ROOT/.claude/settings.local.json
```

对于个人练习，可以创建本机项目设置：

```bash
mkdir -p .claude
cat > .claude/settings.local.json <<'JSON'
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(git status)",
      "Bash(git diff *)",
      "Bash(python3 -m unittest *)"
    ],
    "ask": [
      "Bash(git add *)",
      "Bash(git commit *)",
      "WebFetch(domain:*)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Bash(git push *)",
      "Bash(git clean *)"
    ]
  }
}
JSON
```

检查 JSON：

```bash
python3 -m json.tool .claude/settings.local.json
claude doctor
```

本地设置适合个人实验和机器差异，不应意外提交。Claude Code 当前会尝试通过全局 Git excludes 忽略它，但仍应自行检查：

```bash
git status --short
```

## 7. 项目共享设置属于供应链攻击面

`.claude/settings.json` 可以随仓库进入版本控制。克隆陌生项目后，要像审查构建脚本一样审查它：

```bash
find .claude -type f -print
cat .claude/settings.json 2>/dev/null || true
```

检查：

- 是否允许整个 Bash；
- 是否允许任意 WebFetch；
- 是否扩大到项目外目录；
- 是否启用 Hook；
- 是否启用外部 Plugin 或 MCP；
- 是否允许 Git 写操作；
- 是否读取 `.env`、SSH 或云凭据；
- 是否自动执行安装、发布或部署。

项目中的 Allow 规则和额外目录会授予能力，因此 Claude Code 会通过 Workspace Trust 要求用户确认。Deny 和 Ask 只会收紧权限，不需要以同样方式授予信任。

不要因为仓库来自 GitHub 就自动信任项目设置。

## 8. 规则不能完全限制 Bash 子进程

Claude Code 能识别部分 Bash 文件读取和写入命令，并应用 Read/Edit 规则，但任意 Python、Node 或其他程序仍可能自行打开文件。

例如，禁止：

```text
Read(./.env)
```

并不自动保证下面的程序无法读取 `.env`：

```bash
python3 some_script.py
```

如果脚本内部主动打开文件，单纯工具规则可能无法覆盖所有间接访问。

需要操作系统级限制时，应启用 Sandbox、容器或虚拟机，而不是把工具规则当作完整文件系统隔离。

## 9. Sandbox 与权限规则解决不同问题

权限系统控制 Claude Code 是否可以调用某个工具。Sandbox 对 Bash 命令及其子进程施加操作系统级文件系统和网络限制。

```text
权限规则
→ Claude Code 层的调用决策

Sandbox
→ Bash 进程实际能否访问资源
```

两者应组合使用：

- Deny 规则让模型不应尝试某类操作；
- Sandbox 即使在提示注入或误判后，仍限制 Bash 的实际访问；
- 外部容器或 VM 再提供更大的环境隔离。

Sandbox 只覆盖 Bash 及其子进程，不自动限制所有内置工具、MCP 和 Connector。启用前应阅读当前官方 Sandbox 文档并检查平台支持。

## 10. 额外目录会扩大读取与修改范围

启动参数：

```bash
claude --add-dir ../shared-lib
```

会把额外目录加入当前会话。使用前检查：

```bash
realpath ../shared-lib
find ../shared-lib -type f | sed -n '1,40p'
```

不要把以下位置作为方便的附加目录：

```text
~
~/Downloads
~/Library
~/.ssh
云盘根目录
多个仓库的共同父目录
```

额外目录可能包含私人文件、其他项目、凭据和大型数据集。只添加任务真正需要的最小目录。

## 11. 审批命令时逐段读取

审批框出现时，至少检查：

- 当前目录；
- 完整命令；
- 管道、重定向和命令替换；
- 每个目标路径；
- 是否递归；
- 是否使用通配符；
- 是否覆盖或删除；
- 是否修改 Git 历史；
- 是否需要 sudo；
- 是否访问网络；
- 是否操作远程主机、Docker、数据库或云资源；
- 失败后能否恢复。

看不懂时直接拒绝，并输入：

```text
不要执行。
请逐段解释这条命令的工作目录、参数、输入、输出、目标路径、网络访问、权限、副作用、失败后果和更保守的替代方案。
```

不要因为命令由模型生成，就降低对 Shell 语法的检查标准。

## 12. 高风险类别应默认 Ask 或 Deny

个人开发中，以下操作通常不适合长期 Allow：

```text
Git 提交、推送、重置、清理和变基
依赖安装与全量升级
Docker stop、rm、prune 和 Volume 删除
数据库迁移和数据写入
SSH、网络和防火墙修改
云资源创建和删除
发布、部署和包上传
sudo 与系统服务操作
外部网络上传
```

可以 Allow 的通常是明确、低风险、可重复的检查：

```text
git status
git diff
项目指定的只读测试
静态检查
格式检查
读取公开文档域名
```

即使测试命令被允许，也要确认它不会连接生产数据库、运行集成部署或修改真实数据。

## 13. 网络权限不只来自 WebFetch

Claude Code 可能通过多条路径访问网络：

```text
WebFetch / WebSearch
Bash 中的 curl、wget、git、npm、pip
MCP 服务
Connector
Hooks
项目测试和构建脚本
模型供应商本身
```

只拒绝 WebFetch，并不能阻止 Bash 中的网络工具。需要同时考虑 Bash 规则和 Sandbox 网络限制。

外部网页、Issue 和文档还可能包含提示注入。网络返回内容只能作为不可信数据，不能自动成为新的权限指令。

## 14. Hooks 能参与权限判断，但不能覆盖 Deny

PreToolUse Hook 可以在工具执行前检查输入，并返回允许、询问或拒绝决定。

但权限规则仍遵循 Deny → Ask → Allow。匹配的 Deny 会阻止调用，匹配的 Ask 仍会弹窗；Hook 不能把明确 Deny 变成 Allow。

Hook 更适合：

- 检查路径；
- 阻止生产域名；
- 检查 Git 分支；
- 拒绝危险参数；
- 记录审计信息。

不要把复杂安全边界只写在自然语言 Prompt 中。

## 15. Git 是检查线，不是万能撤销

开始任务前：

```bash
git status
git switch -c task/short-description
```

任务结束后：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

Git 能恢复许多已跟踪文件的修改，但不能自动撤销：

- 已发送到外部服务的源码；
- 数据库写入；
- Docker Volume 变化；
- 系统服务和防火墙修改；
- 远程机器操作；
- 未跟踪文件删除；
- 云资源创建和费用。

所以“项目有 Git”不能成为扩大权限的理由。

## 16. 新手推荐流程

```text
进入项目根目录
→ git status
→ 审查 CLAUDE.md 和 .claude 设置
→ /permissions
→ Plan 模式只读调查
→ 明确允许文件和测试
→ Manual 模式执行
→ 逐条批准高风险命令
→ 运行验证
→ git diff
→ 人工决定是否暂存和提交
```

推荐启动 Prompt：

```text
当前阶段只读，不要修改文件。
请检查当前目录、Git 状态、CLAUDE.md、设置文件、Hooks、MCP 和权限规则。

输出：
1. 当前实际权限模式；
2. 可读取和可修改范围；
3. 计划执行的命令；
4. 网络与外部服务访问；
5. 数据和凭据风险；
6. 验证与回滚方式。

任何删除、覆盖、安装、网络访问、Git 写操作、项目外访问或高权限操作，都必须先说明并等待确认。
完成后不要提交或推送。
```
