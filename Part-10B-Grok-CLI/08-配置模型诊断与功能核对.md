# 08 配置、模型、诊断与功能核对

> 官方产品名：Grok Build  
> 最近核对：2026-07-31

Grok Build 的行为由 CLI 参数、环境变量、用户配置、项目配置、组织托管配置和内置默认共同决定。某项功能“出现在官方文档里”不等于当前账号、版本、平台和会话已经启用；判断真实能力需要同时查看版本、帮助、最终配置和运行结果。

## 1. 不存在适用于所有字段的一条优先级直线

上游随包配置指南对普通运行时覆盖给出一条简化顺序：

```text
CLI 参数
> 环境变量
> ~/.grok/config.toml
> Managed / Requirements 配置
> 内置默认
```

这条顺序适合解释许多个人设置和单次启动参数，但不能拿来推断企业策略一定能被 CLI 或环境变量绕过。官方 Enterprise 文档把配置文件层按“托管默认”和“策略钉死”区分：

```text
/etc/grok/managed_config.toml       系统托管默认
~/.grok/managed_config.toml         用户托管默认
~/.grok/config.toml                 用户偏好
~/.grok/requirements.toml           用户级策略钉死
/etc/grok/requirements.toml         系统级策略钉死
```

`requirements.toml` 中受支持的 Policy Pin 不能被用户配置、环境变量、远程设置或更低层放宽。部分字段还有自己的解析规则：MCP 与 Plugin 按当前目录、仓库根和用户配置选择同名定义；Permission Rule 跨来源合并并遵守 `deny > ask > allow`；Version Bound 只允许收紧；Ask User Question 超时、Hints、兼容 Cell 等又有各自明确的顺序。因此，“哪个值最终生效”必须按具体配置域判断，而不是套用同一个覆盖口诀。

排查时先记录：

```bash
hostname
grok version
grok --help
grok inspect
grok inspect --json > grok-inspect.json

env | grep -E '^(GROK|XAI)_' | sed 's/=.*$/=<redacted>/'
```

不要把完整环境变量、`auth.json` 或未经检查的 `grok-inspect.json` 直接发到 Issue 或聊天中。

## 2. 用户配置、项目配置和 Pager 配置分工不同

主要路径包括：

```text
~/.grok/config.toml       主配置
~/.grok/pager.toml        TUI 外观与滚动配置
~/.grok/auth.json         主账号凭据
~/.grok/sessions/         会话
~/.grok/memory/           Memory
~/.grok/logs/             内部日志

.grok/config.toml         项目 MCP、Plugin、Permission 等
.grok/sandbox.toml        项目 Sandbox Profile
.grok/skills/             项目 Skill
.grok/plugins/            项目 Plugin
.grok/agents/             项目 Agent Definition
.grok/hooks/              项目 Hook
.grok/lsp.json            项目 LSP
.grok/workflows/          项目 Workflow
```

`GROK_HOME` 可以改变默认的 `~/.grok` 根目录。用它做多实例隔离时，配置、认证、会话、Memory、扩展和日志会一起移动；它不是只切换一份 TOML。

项目 `.grok/config.toml` 当前主要支持 `[mcp_servers]`、`[plugins]`、`[permission]` 和 MCP 输出上限，其他多数主配置只从用户 `~/.grok/config.toml` 读取。项目同名 MCP 是整体替换用户定义，而不是逐字段叠加。

## 3. 认证、模型、Provider 和计费必须分开

认证入口包括：

```bash
grok login
grok login --oauth
grok login --device-auth
grok login --device-code
grok --oauth
grok logout
```

还可以使用企业 OIDC、External Auth Provider 或 `XAI_API_KEY`。当前官方资料给出的请求凭据优先级为：

```text
模型级 model.api_key
> 模型级 model.env_key 指向的环境变量
> 活跃 Session Token
> XAI_API_KEY
```

这里的前两项都是模型级凭据，但 `api_key` 比 `env_key` 解析出的值优先。活跃 Session Token 可能来自 External Auth Provider、企业 OIDC 或浏览器 OAuth。已经登录时，`XAI_API_KEY` 只是最后回退；要验证 API Key 路线，应先 `grok logout` 或使用隔离的 `GROK_HOME`，再重新启动并观察用量与日志。

浏览器订阅、团队账号和 xAI API Project 不是同一计费主体。模型显示名也不能证明请求经过哪个 Provider；需要同时核对模型 ID、Base URL、认证来源、额外 Header、账号和本地网关。

## 4. 自定义模型不只包含 Base URL

用户配置可以定义自定义或覆盖内置模型：

```toml
[model.my-model]
model = "model-id"
base_url = "https://api.example.com/v1"
name = "Display Name"
env_key = "PROVIDER_API_KEY"
context_window = 128000
max_completion_tokens = 8192
max_retries = 8
inference_idle_timeout_secs = 600

[models]
default = "my-model"
```

当前配置还可能支持：

```text
api_key
extra_headers / env_http_headers
query_params
temperature / top_p
stream_tool_calls
描述与显示信息
```

不要把真实 Key 写入可共享 TOML，优先使用环境变量或受控凭据系统。`context_window` 会影响自动 Compact 判断，填错可能造成过早压缩或请求失败。自定义端点能返回文本，不代表工具调用、结构化输出、流式事件、缓存和错误语义完全兼容。

## 5. Permission、Rule、Sandbox 和 Plan 是四层机制

权限链包括：

```text
Ask / Auto / Always-approve
Allow / Ask / Deny Rule
Sandbox Profile
Hook 与组织 Requirements
```

Plan Mode 还有独立的文件编辑门槛，只允许修改会话计划文件，直到用户批准。它与工具批准模式不是同一个开关。

`[ui] default_selected_permission` 只决定每次启动后第一次批准菜单默认高亮哪一行。当前官方默认值是 `always_allow_all_sessions`，这只是 UI 默认选择，但误按回车会产生很宽的授权。更保守的个人配置可以使用：

```toml
[ui]
default_selected_permission = "allow_once"
remember_tool_approvals = false
```

支持值当前包括：

```text
always_allow_all_sessions
allow_command_always
allow_once
reject
```

第一次选择后，后续弹窗可能沿用上次选择的 Sticky Cursor。`allow_command_always` 只针对具体命令、工具、域或编辑会话，不等于全局 Always-approve。

当前上游配置列出的内置 Sandbox Profile 包括：

```text
off
workspace
devbox
read-only
strict
```

例如：

```bash
grok --sandbox workspace
grok --sandbox read-only
grok --sandbox strict
```

也可以通过 `.grok/sandbox.toml` 定义自定义 Profile。具体平台能力仍以本机帮助和 Sandbox 文档为准。批准方式决定“是否允许调用”，Sandbox 决定“获准后能接触什么”，两者不能互相替代。

## 6. 工具级配置会改变超时、输出和网络边界

常见配置包括：

```toml
[toolset.bash]
timeout_secs = 120.0
output_byte_limit = 20000

[toolset.ask_user_question]
timeout_enabled = true
timeout_secs = 1800

[toolset.web_fetch]
allowed_domains = ["docs.x.ai", "github.com"]
allow_local = false
```

`allow_local` 默认关闭，用于防止 Web Fetch 访问本地和私有网络。即使开启，当前官方说明也只允许显式 Loopback；私网、Link-local 和云 Metadata 仍然阻断。不要为了访问本地开发服务而解除整个网络边界。

Bash Output Limit 会截断工具返回，但不一定阻止命令在本机产生更多日志或文件。Ask User Question 超时只影响等待回答，不代表任务整体超时。Headless 自动化还需要外层进程超时和退出码处理。

## 7. 功能开关决定命令是否出现以及使用哪种实现

主要功能开关包括：

```text
GROK_MEMORY / --experimental-memory / --no-memory
GROK_SUBAGENTS / --no-subagents
GROK_WORKFLOWS
GROK_WEB_FETCH
GROK_AGENT_DASHBOARD
[features] lsp_tools
[features] codebase_indexing
```

Memory 默认需要实验性入口或 `GROK_MEMORY=1`；Background Workflows 当前默认开启；Subagents 当前默认可用；Goal 是否出现还有独立 Feature Setting。`GROK_WORKFLOWS=0` 不只关闭 Workflow，还会让 `/goal` 回退到旧式 `update_goal` 驱动。

命令在文档中存在但菜单没有时，按以下顺序检查：

```text
版本与发布通道
操作系统与终端
账号或组织策略
功能开关
当前会话状态
依赖的 Backend
Skill / Plugin 是否存在且启用
在线文档与随包指南是否同步
```

不要为了让命令出现而一次打开所有实验功能。

## 8. TUI、通知与 Pager 有独立配置

Prompt 输入与滚动区导航是两套设置：

```toml
[ui]
simple_mode = true
vim_mode = false
screen_mode = "fullscreen"
compact_mode = false
```

`simple_mode = false` 启用 Prompt 的实验性 Vim 编辑；`vim_mode = true` 启用滚动区 Vim 键位。二者互不替代。

通知可以使用 OSC 9、OSC 99、OSC 777 或 BEL，并按终端自动选择：

```toml
[ui.notifications]
method = "auto"
condition = "unfocused"
idle_threshold_secs = 3
events = ["turn_complete", "approval_required"]
sleep_prevention = true
progress_bar = true
```

通知 Hook 还可以运行自定义命令，并接收 `GROK_EVENT`、`GROK_MESSAGE` 和 `GROK_SESSION_ID`。这会增加新的 Shell 与网络执行面，不能把通知脚本当作无风险 UI 设置。

`~/.grok/pager.toml` 管理 Alt Screen、动画、Prompt 外观、滚动、折叠和区块显示。外观异常不一定来自主 `config.toml`，排查时两份文件都要看。

## 9. Privacy、Telemetry、Trace 和 External OTEL 相互独立

`/privacy` 管理编码数据、保留和训练选择，不会自动改变：

```text
[features] telemetry
GROK_TELEMETRY_ENABLED
GROK_TELEMETRY_TRACE_UPLOAD
Mixpanel 开关
GROK_EXTERNAL_OTEL
外部 MCP、Plugin 与自定义 Provider 的数据处理
```

因此，“已经 Opt out”不能推出“客户端完全没有遥测或外部数据流”。团队账号还可能使用管理员策略或 Zero Data Retention。需要按账号、组织和每个外部服务分别核对。

调试日志入口包括：

```bash
GROK_LOG_FILE=/tmp/grok.log RUST_LOG=debug grok
RUST_LOG=debug grok -p "hello" 2> /tmp/grok-headless.log
```

`GROK_LOG_FILE` 被当作实际路径，使用相对值可能在当前项目创建日志文件。日志可能包含路径、模型、工具、MCP 和错误上下文，上传前必须脱敏。

## 10. 更新、版本固定与企业边界

更新入口包括：

```bash
grok update --check
grok update --stable
grok update --alpha
grok update --version VERSION
grok version
```

CI、Headless、ACP 和可复现实验更适合关闭自动更新：

```bash
grok --no-auto-update
```

```toml
[cli]
auto_update = false
```

企业还可以设置软 Floor/Ceiling 和强制 Minimum/Maximum Version。强制边界会在版本超范围时阻止正常启动，但保留 `grok update` 和版本查询用于恢复。多个配置层只允许把边界收紧，不能用用户配置放宽组织要求。

升级后重新检查：

```bash
grok version
grok --help
grok models
grok inspect
```

再抽样验证认证、会话恢复、权限弹窗、Sandbox、结构化输出、Skill、MCP、Worktree、Memory 和 Workflow。

## 11. 分层诊断顺序

出现问题时按来源逐层判断：

```text
1. type -a grok、PATH 与安装来源
2. grok version、grok --help 与发布通道
3. 认证文件、账号和 Credential Precedence
4. 模型 ID、Provider、Base URL 与用量
5. cwd、仓库根、分支、HEAD 与工作区
6. 用户、项目、组织和 Pager 配置
7. Permission、Rule、Plan 与 Sandbox
8. Skill、Plugin、Hook、MCP、LSP、Workflow
9. 网络、代理、外部服务和数据策略
10. 日志、退出码、测试与 Git diff
```

常用入口：

```bash
grok inspect
grok inspect --json
grok mcp doctor
```

```text
/doctor
/doctor fix
```

不要把删除整个 `~/.grok` 当作第一步。认证、会话、Memory、扩展、配置和日志都在其中，整目录删除会同时破坏多个诊断线索。更稳妥的方法是备份后一次只隔离一个来源，例如临时使用新的 `GROK_HOME`。

```text
安装、版本、PATH 与更新
浏览器、设备码、API Key、OIDC 与 External Auth
模型、Provider、推理强度、用量与自定义端点
TUI、输入、滚动、主题、通知与 Pager
会话、恢复、分叉、回退、分享、转录与导出
Context、Compact、History、Find 与 Copy
Memory、Remember、Flush、Dream 与清理范围
Ask、Auto、Always-approve、Rule、Plan 与 Sandbox
Headless、JSON/JSONL、轮数、超时和工具集合
Worktree、Git 分支和外部资源隔离
Goal、Deep Research、Workflow 与预算
Dashboard、队列、任务、子 Agent 与 Persona

```
