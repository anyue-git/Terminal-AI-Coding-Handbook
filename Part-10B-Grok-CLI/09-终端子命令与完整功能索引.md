# 09 终端子命令与完整功能索引

> 官方产品名：Grok Build  
> 最近核对：2026-07-31

前面章节主要解释 TUI、权限、会话、Memory、Workflow 和扩展系统。本章集中整理 Shell 中公开的 `grok` 子命令与常用 Flags，作为版本化索引。官方 CLI Reference 本身只列出“最常用入口”，分散在 Enterprise、Plugin 和其他功能页的公开 Flag 也会在本章补充；实际使用前仍要运行 `grok --help` 与 `grok SUBCOMMAND --help`。

## 1. 三种主要运行入口

### 交互式 TUI

```bash
cd ~/Projects/my-project
grok
```

没有子命令和 `-p` 时，Grok 启动交互式 TUI。

### Headless

```bash
grok -p "解释当前项目架构"
grok --single "解释当前项目架构"
```

`-p` 是 `--single` 的短入口，适合脚本、CI、Bot 和远程无交互任务。

### ACP

```bash
grok agent stdio
```

ACP 通过 stdin/stdout 使用 JSON-RPC，让编辑器或其他宿主驱动 Grok。三种入口共享部分配置、认证、规则和工具，但界面、批准流程、输出格式和日志通道不同。

## 2. 认证与账号

```bash
grok login
grok login --oauth
grok login --device-auth
grok login --device-code
grok --oauth
grok logout
```

| 命令 | 作用 |
| --- | --- |
| `grok login` | 使用默认浏览器 OAuth 登录并更新缓存 Session Token |
| `grok login --oauth` | 显式选择浏览器 OAuth；当前上游认证指南说明它与默认登录路线相同，因此该 Flag 通常可省略 |
| `grok login --device-auth`、`--device-code` | 使用设备码登录；当前上游把 `--device-code` 列为 `--device-auth` 的别名 |
| `grok --oauth` | 从欢迎页启动认证时显式选择 OAuth 的全局入口 |
| `grok logout` | 清除主账号缓存凭据 |

`grok login --oauth` 和 `grok --oauth` 都有官方依据，但作用位置不同：前者属于 `login` 子命令，后者属于启动欢迎页时的全局 Flag。升级后分别用 `grok login --help` 和 `grok --help` 核对，不要因为两者都含 `oauth` 就假设任意参数排列都长期兼容。

`grok logout` 不一定清除 MCP OAuth 凭据或撤销外部服务授权。账号和 API Key 的精确优先级见[配置、模型、诊断与功能核对](08-配置模型诊断与功能核对.md)。

## 3. 检查环境与模型

```bash
grok version
grok inspect
grok inspect --json
grok models
```

| 命令 | 作用 |
| --- | --- |
| `grok version` | 显示客户端版本 |
| `grok inspect` | 显示当前目录发现的规则、配置、Skill、Plugin、Hook 与 MCP |
| `grok inspect --json` | 输出结构化检查结果，适合前后比较 |
| `grok models` | 列出当前账号和配置可使用的模型 |

`inspect --json` 可能包含本地路径、服务地址和扩展元数据，不能默认当作可公开日志。

## 4. MCP 管理

```bash
grok mcp list
grok mcp add ...
grok mcp remove NAME
grok mcp doctor
```

| 子命令 | 作用 |
| --- | --- |
| `list` | 列出最终发现的 MCP Server |
| `add` | 添加 Server，参数随传输类型变化 |
| `remove` | 删除配置条目 |
| `doctor` | 检查启动、连接、认证或配置问题 |

添加和删除条目不一定同步撤销服务端 OAuth，也不保证清除 `~/.grok/mcp_credentials.json`。执行前查看：

```bash
grok mcp add --help
grok mcp remove --help
```

## 5. Plugin 与 Marketplace

```bash
grok plugin list
grok plugin install SOURCE
grok plugin uninstall NAME
grok plugin update
grok plugin enable NAME
grok plugin disable NAME
grok plugin details NAME
grok plugin validate PATH
```

Marketplace Source：

```bash
grok plugin marketplace list
grok plugin marketplace add SOURCE
grok plugin marketplace remove NAME
grok plugin marketplace update
```

官方 Plugin 文档还公开了单次加载本地目录的入口：

```bash
grok --plugin-dir /path/to/local-plugin
```

`--plugin-dir` 把指定目录加入当前运行的 Plugin 来源，适合本地开发和测试。它不等于从 Marketplace 安装，也不自动证明 Plugin 已受信任；目录中的 Skill、Agent、Hook、MCP 和 LSP 仍可能运行脚本、联网或接触凭据。自动化中应使用固定的绝对路径和已审查版本，不要指向会被其他进程随意改写的共享目录。

安装、启用、临时加载和信任是不同状态。`validate` 只能验证工具覆盖的结构规则，不能证明脚本、Hook、MCP、下载源和供应链安全。

## 6. 会话列表、搜索、删除与导出

```bash
grok sessions list
grok sessions search KEYWORD
grok sessions delete SESSION_ID

grok export SESSION_ID
grok export SESSION_ID OUTPUT.md
```

| 命令 | 作用 |
| --- | --- |
| `sessions list` | 列出磁盘会话 |
| `sessions search` | 按关键字搜索会话 |
| `sessions delete` | 删除指定会话 |
| `export` | 将指定会话转录导出为 Markdown |

这些 Shell 子命令面向持久化会话；TUI 的 `/sessions` 与 `/dashboard` 则面向当前 Pager 的活动会话。删除或导出磁盘会话都不会恢复或改变 Git、数据库、容器和外部服务。

## 7. Claude Code 会话导入

```bash
grok import
grok import TARGETS...
```

当前官方 CLI Reference 将它描述为从 Claude Code 导入会话。它不同于 TUI 中的设置迁移：

```text
/import-claude      导入 Claude 设置

grok import        导入 Claude Code 会话
```

也不同于 staged 的 `resume-claude`、`resume-codex` 和 `resume-cursor` Skill Scanner。正式执行前查看当前支持的 Target 形式：

```bash
grok import --help
```

## 8. Memory 清理

```bash
grok memory clear --workspace
grok memory clear --global
grok memory clear --all
```

| 选项 | 预期范围 |
| --- | --- |
| `--workspace` | 当前工作区相关 Memory |
| `--global` | 全局 Memory |
| `--all` | 所有受该命令管理的 Memory |

具体文件和确认行为可能变化，删除前运行 `grok memory clear --help`，并先用 `/memory` 检查内容。Memory 清理不删除普通磁盘会话。

## 9. Worktree 管理

创建 Worktree 会话使用全局 Flag：

```bash
grok --worktree
grok --worktree NAME
grok --worktree NAME --ref main
```

管理已创建的 Worktree：

```bash
grok worktree list
grok worktree show NAME
grok worktree rm NAME
grok worktree gc
```

移除前确认没有未提交修改、未推送提交和仍在运行的进程。Grok Worktree 与 Git 的真实状态应交叉检查：

```bash
grok worktree list
git worktree list
```

## 10. Dashboard 与 ACP

```bash
grok dashboard
grok agent stdio
```

`grok dashboard` 直接打开 Agent Dashboard。`grok agent stdio` 启动 ACP Server，通过 JSON-RPC 在 stdin/stdout 上工作。ACP 的 stdout 是协议通道，不能混入普通日志；日志应进入 stderr 或指定文件。

## 11. Terminal Wrap

```bash
grok wrap COMMAND ARG...
```

`grok wrap` 在本地 PTY 中运行命令，并转发 OSC 52 剪贴板写入，适合 SSH、tmux 或某些嵌套终端的剪贴板兼容：

```bash
grok wrap ssh user@server
```

它不是 Sandbox，也不会判断被包装命令是否安全；命令仍拥有当前用户和终端环境中的真实权限。

## 12. 更新与版本

```bash
grok update --check
grok update --stable
grok update --alpha
grok update --version VERSION
grok version
```

| 命令 | 作用 |
| --- | --- |
| `--check` | 只检查可用更新 |
| `--stable` | 安装或切换到稳定通道 |
| `--alpha` | 使用 Alpha 通道 |
| `--version` | 安装指定版本 |
| `version` | 显示当前版本 |

CI 和可复现实验应使用 `--no-auto-update` 或配置关闭自动更新。企业强制 Version Bound 可能阻止超范围客户端正常启动。

## 13. Shell 自动补全

```bash
grok completions zsh
grok completions bash
grok completions fish
```

具体支持的 Shell 以 `grok completions --help` 为准。先检查生成内容，不要把未知脚本直接追加到 `.zshrc`：

```bash
grok completions zsh > /tmp/_grok
sed -n '1,80p' /tmp/_grok
```

## 14. Managed Setup

```bash
grok setup
```

官方 CLI Reference 将它描述为获取并安装 Managed Configuration，主要面向团队或企业部署。它可能改变托管配置、Requirements、认证或版本策略，不应因为名字像“初始化”就在个人机器上盲目执行。

```bash
grok setup --help
grok inspect
```

使用前应确认管理服务、Deployment Key、组织策略和恢复方法。

## 15. 工作目录、会话和 Worktree Flags

```bash
grok --cwd PATH

grok --resume SESSION_ID
grok -r SESSION_ID
grok --resume
grok --continue
grok -c
grok --session-id UUID
grok -s UUID
grok --fork-session

grok --worktree NAME
grok -w NAME
grok --ref REF
```

| Flag | 作用 |
| --- | --- |
| `--cwd` | 指定启动工作目录 |
| `--resume [ID]` | 恢复指定会话；省略 ID 时恢复最近记录 |
| `--continue` | 继续当前目录最近会话 |
| `--session-id` | 为新会话指定 UUID |
| `--fork-session` | 恢复时创建新会话 ID |
| `--worktree` | 在新 Worktree 启动会话 |
| `--ref` | 指定 Worktree 基准 Ref |

`--continue` 依赖当前目录；自动化应优先记录并使用明确 Session ID。

## 16. 模型、规则与 System Prompt Flags

```bash
grok --model MODEL
grok -m MODEL
grok --effort LEVEL

grok --rules "追加规则"
grok --system-prompt-override "完整系统提示"
```

`--rules` 把额外规则追加到现有 System Prompt；`--system-prompt-override` 替换整个 System Prompt，可能绕过项目已有规则和安全说明。自动化中使用 Override 时，应把完整内容纳入审查和版本管理。

## 17. 权限、Sandbox 与工具集合 Flags

日常入口：

```bash
grok --always-approve
grok --yolo

grok --allow RULE
grok --deny RULE

grok --sandbox PROFILE

grok --tools TOOL_LIST
grok --disallowed-tools TOOL_LIST
```

| Flag | 作用 |
| --- | --- |
| `--always-approve`、`--yolo` | 跳过工具批准提示 |
| `--allow`、`--deny` | 添加 Permission Rule |
| `--sandbox` | 选择 Sandbox Profile |
| `--tools` | 限定内置工具集合 |
| `--disallowed-tools` | 从工具集合中排除条目 |

工具集合、Permission Rule 和 Sandbox 是不同层。允许某个工具不等于允许所有参数，允许一次 Bash 也不等于限制了它能访问的文件和网络。

官方 Enterprise 文档还公开了 Headless 权限模式：

```bash
grok -p "只读审查当前 diff" \
  --permission-mode dontAsk \
  --allow 'Bash(git *)' \
  --allow 'Read' \
  --allow 'Grep' \
  --sandbox strict
```

| 模式 | 行为 |
| --- | --- |
| `dontAsk` | 未被显式 Allow 的调用静默拒绝，适合 CI 和无人值守审计 |
| `acceptEdits` | 自动批准文件编辑，Shell 等其他工具继续按规则处理 |
| `bypassPermissions` | 企业文档中的绕过批准模式；普通使用优先采用公开的 `--always-approve` |

`dontAsk` 不会自动推断任务需要哪些工具，Allow 不足时任务会无法完成；`acceptEdits` 也不限制编辑文件范围。企业可以从 root-owned Requirements 中锁定 `disable_bypass_permissions_mode = true`，阻止 `--yolo`、`bypassPermissions` 和 TUI 切换重新开启绕过模式。

本索引只优先展示官方 Grok 原生命名；其他客户端风格的兼容别名即使在某些版本可用，也应通过当前 `grok --help` 单独确认。

## 18. Headless Flags 与输出格式

```bash
grok -p "TASK"
grok --single "TASK"

grok --output-format plain
grok --output-format json
grok --output-format streaming-json

grok --max-turns 12
grok --no-auto-update
```

| Flag | 作用 |
| --- | --- |
| `-p`、`--single` | 发送一次 Prompt 并进入 Headless |
| `--output-format plain` | 人类可读文本 |
| `--output-format json` | 结束时输出单个 JSON 对象 |
| `--output-format streaming-json` | 输出逐行 JSON 事件 |
| `--max-turns` | 限制 Agent 轮数 |
| `--no-auto-update` | 跳过后台更新检查 |

Headless Session 仍保存在 `~/.grok/sessions/`。JSONL 解析器应逐行读取、忽略未知字段并显式处理错误事件。结构化输出可能包含 Prompt、路径、代码和工具结果，不应未经检查上传公开 Artifact。

## 19. 单次关闭和启用功能

```bash
grok --no-plan
grok --no-subagents
grok --no-memory
grok --disable-web-search
grok --experimental-memory
```

| Flag | 只改变什么 |
| --- | --- |
| `--no-plan` | 关闭当前会话的 Plan 能力 |
| `--no-subagents` | 关闭当前会话的子 Agent |
| `--no-memory` | 关闭当前会话的 Memory 使用 |
| `--disable-web-search` | 关闭内置 Web Search |
| `--experimental-memory` | 启用跨会话 Memory |

`--disable-web-search` 不会阻止 Bash、包管理器、Git、MCP、Plugin、Hook 或自定义工具联网。网络限制仍需 Sandbox、代理、容器或系统策略。

## 20. 终端呈现相关 Flags

```bash
grok --no-alt-screen
grok --minimal
grok --fullscreen
```

`--no-alt-screen` 让 Fullscreen 界面运行在终端主 Scrollback 中；它在命令可用性上仍按 Fullscreen 处理。`--minimal` 和 `--fullscreen` 选择当前会话的呈现模式。终端呈现方式不会改变 Agent 的文件、Shell 和网络权限。

## 21. 自动化的推荐现场记录

任务开始前：

```bash
hostname
pwd
git branch --show-current
git rev-parse HEAD
git status --short

grok version
grok inspect
```

显式运行：

```bash
grok \
  --no-auto-update \
  --cwd "$PWD" \
  --max-turns 12 \
  --output-format streaming-json \
  -p "读取 task.md 并执行。超出范围时停止。"
```

任务结束后：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

完整性来自“版本、目录、权限、工具、输出、退出状态和 diff 都可追踪”，而不是来自某个单独 Flag。

## 22. 版本化索引

| 类别 | 主要入口 |
| --- | --- |
| TUI | `grok` |
| Headless | `grok -p`、`grok --single` |
| ACP | `grok agent stdio` |
| 登录 | `login`、`login --oauth`、`--oauth`、`logout` |
| 检查 | `inspect`、`models`、`version` |
| MCP | `mcp list/add/remove/doctor` |
| Plugin | `plugin list/install/uninstall/update/enable/disable/details/validate`、`--plugin-dir` |
| Marketplace | `plugin marketplace list/add/remove/update` |
| 会话 | `sessions list/search/delete` |
| 导出导入 | `export`、`import` |
| Memory | `memory clear` |
| Worktree | `worktree list/show/rm/gc` |
| 多 Agent | `dashboard` |
| Terminal | `wrap`、`completions` |
| 企业配置 | `setup`、`--permission-mode`、Requirements |
| 更新 | `update`、`version` |

这张表描述 2026-07-31 官方文档公开的常用用户入口，不包含内部开发二进制、隐藏调试命令和没有公开契约的实现细节。升级后以 `grok --help` 为最终核对入口。
