# 01 Grok CLI：安装、登录与基础使用

> 官方产品名：Grok Build
>
> 终端命令：`grok`
>
> 最近核对：2026-07-28

Grok Build 是 xAI 提供的终端编程 Agent，启动命令是：

```bash
grok
```

本章讲的是客户端本身，不把某个模型 ID 当成产品名称。模型、别名和可用能力可能随账户与版本变化。

---

## 1. Grok CLI 能做什么

它可以：

- 读取和搜索代码；
- 修改文件；
- 执行命令与测试；
- 使用 Web Search；
- 管理会话；
- 配合 Git Worktree；
- 使用 Skills、Plugins、Hooks 与 MCP；
- 以 Headless 方式运行；
- 通过 ACP 接入其他客户端。

它与 Claude Code、Codex CLI 属于同类工具，但权限系统、扩展机制和自动化入口不同。

---

## 2. 安装前先确认平台

主要环境包括 macOS、Linux、WSL 和官方当前支持的 Windows 路线。

先检查：

```bash
uname -m
git --version
echo "$SHELL"
```

安装命令可能变化，应从 xAI 官方 Grok Build 安装页复制当前命令，不要长期使用旧博客里的远程脚本。

安装后检查：

```bash
type -a grok
grok --version
grok --help
```

出现多个路径时，先处理 PATH，不要继续重复安装。

---

## 3. 登录与退出

首次运行：

```bash
grok
```

也可以查看：

```bash
grok login --help
```

在 SSH、容器或无浏览器环境中，使用当前版本支持的设备授权等正规流程。

不要共享：

- 设备授权代码；
- API Key；
- 认证缓存；
- 浏览器登录状态；
- 其他人的账号凭据。

退出登录：

```bash
grok logout
```

---

## 4. 从项目根目录启动

```bash
cd ~/Projects/my-project
pwd
git status
git branch --show-current
grok
```

不要从家目录、下载目录或多个仓库的父目录启动。启动位置会影响它读取哪些配置、规则与文件。

已有未提交修改时，先弄清这些内容是否属于当前任务。

---

## 5. 安装后先做状态检查

```bash
grok --version
grok --help
grok models
grok inspect
```

它们分别用于查看版本、当前命令、可用模型和当前目录加载的配置与扩展。

排查“为什么加载了某个规则、MCP 或权限”时，`grok inspect` 比凭记忆可靠。

---

## 6. 第一次任务只读

```text
当前阶段只读，不要修改文件、安装依赖或执行 Git 写操作。

请检查：
- 当前目录和 Git 状态；
- README 与项目规则；
- 依赖声明；
- 测试入口；
- 与任务相关的模块。

然后说明：
1. 项目入口；
2. 如何运行和测试；
3. 任务可能涉及哪些文件；
4. 哪些目录不应修改；
5. 当前未提交改动；
6. 已确认事实与仍然存在的推测。
```

项目理解不可靠时，不要直接切到修改。

---

## 7. TUI 和普通 Shell 不一样

运行 `grok` 后会进入文本用户界面。此时快捷键主要由 Grok TUI 处理，不一定继续遵循 zsh。

遇到按键行为不同，先判断焦点属于：

- zsh；
- Grok 输入框；
- 滚动区域；
- tmux；
- SSH 远程终端；
- 编辑器集成。

---

## 8. 常用界面命令

常见入口包括：

```text
/help
/new
/resume
/sessions
/model
/context
/compact
/rewind
/export
/plan
/plugins
/skills
/hooks
/mcps
```

它们用于查看帮助、管理会话、选择模型、查看上下文和管理扩展。具体名称以当前 `/help` 为准。

---

## 9. Ask、Auto、Always-approve 与 Plan

日常权限模式常见为：

```text
Ask
Auto
Always-approve
```

Plan 是任务阶段，不是同一维度的权限模式。

新手推荐：

```text
Plan + Ask
```

不要在主分支、有未提交修改、包含真实数据、远程 GPU 系统目录或可访问 Docker Socket 的环境中默认使用 Always-approve。

---

## 10. 复杂任务先进入 Plan

```text
/plan
```

然后要求：

```text
先分析，不要修改文件。
输出计划读取的模块、预计修改文件、每个文件的原因、测试命令、风险和明确不处理的内容。
```

确认后再切回合适权限模式，并一次只执行一个阶段。

---

## 11. 模型名称不要写死

查看当前可用模型：

```bash
grok models
```

在 TUI 中：

```text
/model
```

工具名称和模型名称是两回事。团队文档应给出验证方法，不要把某个模型 ID 当作永久默认值。

---

## 12. 会话恢复前重新检查项目

查看会话：

```bash
grok sessions list
```

恢复后先输入：

```text
先不要继续旧任务。
重新检查当前目录、Git 分支、未提交改动、项目规则、依赖文件和测试状态。
说明现实状态与旧会话上下文可能不一致的地方。
```

会话保存上下文，不保存项目快照。

---

## 13. Mac 与 Ubuntu 分别安装

可以共享 Git 仓库、项目规则、测试和依赖声明，但不要直接同步：

- Grok 可执行文件；
- 认证缓存；
- 整个用户配置目录；
- 平台相关二进制；
- 一台机器的虚拟环境。

远程 Ubuntu 上启动前先运行：

```bash
hostname
whoami
pwd
git status
```

---

## 14. 启动前与结束后

启动前：

```bash
hostname
pwd
git status
grok inspect
```

结束后：

```bash
git status --short
git diff --name-status
git diff --stat
git diff
```

不要让“任务完成”四个字替代真实测试和差异检查。
