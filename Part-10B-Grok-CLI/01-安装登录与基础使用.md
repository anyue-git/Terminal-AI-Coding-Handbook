# 01 Grok Build：安装、认证与第一次使用

> 官方产品名：Grok Build  
> 终端命令：`grok`  
> 最近核对：2026-07-29

Grok Build 是 xAI 提供并开源的终端编程 Agent。第一次使用需要分清四件事：当前执行的是哪一份客户端、请求由哪种认证和账户承担、当前能用哪些模型，以及进入项目后实际加载了哪些规则与扩展。本章只建立这条基础链；权限、Headless、Worktree 和扩展系统在后续章节展开。

## 1. 安装后先确认唯一的客户端与模型入口

在每台机器上分别检查系统、架构、Shell、Git 和已有命令：

```bash
hostname
uname -s
uname -m
git --version
printf '%s\n' "$SHELL"

type -a grok 2>/dev/null
command -v grok 2>/dev/null
grok version 2>/dev/null || true
```

xAI 当前官方安装命令是：

```bash
curl -fsSL https://x.ai/cli/install.sh | bash
```

执行前核对域名仍来自官方文档，并遵守组织的软件安装要求。安装完成后重新打开终端或按提示加载 PATH，然后确认实际二进制与帮助：

```bash
type -a grok
command -v grok
grok version
grok --help
```

部分版本也支持 `grok --version`，以当前帮助为准。`type -a` 若同时显示官方安装器版本、旧测试版、手工二进制或其他同名命令，继续安装只会增加歧义；应查看 PATH 和真实文件：

```bash
printf '%s\n' "$PATH" | tr ':' '\n'
ls -l "$(command -v grok)"
```

Mac 与 Ubuntu 需要分别安装，远程 Ubuntu 中运行的安装命令不会改变 Mac。当前账户实际可用的模型通过以下入口确认：

```bash
grok models
```

TUI 中也可以使用 `/model`。模型 ID 会随账户、配置和版本变化，不应把某个当前名称当作长期固定的产品名。

## 2. 认证方式决定账户、计费和凭据位置

第一次运行 `grok` 通常会打开浏览器完成账户认证，也可以显式登录或退出：

```bash
grok
grok login
grok logout
```

主认证状态可能保存在 `~/.grok/auth.json`。它属于敏感材料，不进入 Git、截图、共享目录或同步脚本。SSH、容器和无浏览器环境可以使用设备码：

```bash
grok login --device-auth
```

当前别名可能包括 `--device-code`，以 `grok login --help` 为准；设备码只在自己的可信浏览器中使用。

明确采用 xAI API 时，在受控环境中设置：

```bash
export XAI_API_KEY="YOUR_XAI_API_KEY"
```

浏览器登录使用消费者产品的账户与策略，`XAI_API_KEY` 使用 xAI API 项目、余额和 API 计费。SuperGrok 或 Grok App 订阅不会自动变成通用 API Key，API 余额也不等于订阅消息额度。有效浏览器登录状态还可能优先于 API Key 回退；测试 API 路线时应先明确 `grok logout`，再设置 Key 并重新启动，不能仅凭环境变量存在就判断请求按 API 账户计费。

MCP OAuth 凭据可能保存在 `~/.grok/mcp_credentials.json`，与主账户认证分离。`grok logout` 不一定撤销外部 MCP 授权；移除 MCP Server 时还要检查服务端授权和本地凭据。

## 3. 用 `inspect` 确认项目实际加载了什么

进入项目之前先查看当前客户端状态：

```bash
grok version
grok --help
grok models
grok inspect
grok inspect --json
```

`grok inspect` 汇总当前目录涉及的用户配置、项目配置、规则、Sandbox、MCP 与扩展，比单独阅读某一份 TOML 更接近真实运行环境。结构化输出适合前后比较，但可能包含路径、服务地址和扩展信息，公开前仍需检查。

Mac 与 Ubuntu可以共享 Git 仓库、`AGENTS.md`、测试、依赖声明和不含秘密的项目 `.grok` 配置；客户端二进制、`auth.json`、`mcp_credentials.json`、整个 `~/.grok`、平台二进制和 `.venv` 都应在各自机器维护。两端分别确认：

```bash
hostname
type -a grok
grok version
grok inspect
```

从明确的项目根目录启动：

```bash
cd ~/Projects/my-project
pwd
git rev-parse --show-toplevel
git status
grok
```

也可以显式指定目录：

```bash
grok --cwd ~/Projects/my-project
```

启动目录决定仓库识别、`.grok/config.toml`、`AGENTS.md`、Skills、Plugins、Agents、Hooks、Sandbox 和默认命令位置。不要从整个 HOME 启动后让 Agent 自行寻找项目。

进入 TUI 后查看 `/help`、`/context` 和 `/model`，再切换 `/plan`，确认当前批准方式符合预期。第一条请求可以只做项目地图：

```text
只读检查当前项目，说明入口、测试命令和最小修改范围，不修改文件。
```

完整练习统一使用[AI CLI 快速上手](../00-快速开始/02-AI-CLI快速上手.md)，本章不再创建另一套示例项目。

## 4. 会话、更新和故障都要回到当前状态判断

常用斜杠入口按用途分为：会话使用 `/new`、`/resume`、`/sessions`、`/compact`、`/rewind`、`/export`；模型与上下文使用 `/model`、`/context`；工作方式使用 `/plan`、`/auto`、`/always-approve`；扩展入口包括 `/plugins`、`/skills`、`/hooks`、`/mcps`。具体名称以 `/help` 为准，Ask、Auto、Always-approve 与 Plan 的关系由下一章主讲。

模型和推理强度可以从命令行指定：

```bash
grok models
grok --model MODEL_NAME
grok -m MODEL_NAME
grok --effort LEVEL
```

会话入口包括：

```bash
grok sessions list
grok sessions search KEYWORD
grok --continue
grok -c
grok --resume SESSION_ID
grok -r SESSION_ID
grok --resume SESSION_ID --fork-session
```

会话通常位于 `~/.grok/sessions/`，保存的是对话上下文，不是 Git、环境或文件系统快照。恢复会话后仍应重新检查目录、分支和工作区；导出的会话可能包含 Prompt、路径、代码和工具调用，公开前要逐项检查。

查看更新入口：

```bash
grok update --help
grok version
```

交互使用可以接受自动更新，CI、Headless 与 ACP 更适合固定版本或关闭自动更新：

```bash
grok --no-auto-update
```

配置字段可能类似：

```toml
[cli]
auto_update = false
```

实际字段以当前 Settings 文档为准。升级后重新验证参数、权限模式、扩展和结构化输出。

故障排查也按来源分层：命令不存在或版本不对时检查 `type -a`、`command -v` 与 PATH；API Key 已设置却仍走浏览器账户时检查 `auth.json` 和登录状态；项目行为异常时运行 `grok inspect --json`；模型不存在时重新执行 `grok models`。安装、认证、模型选择和项目配置是四个不同来源，判断哪一层与预期不一致后再修改，比删除整个 `~/.grok` 或反复重装更容易恢复。
