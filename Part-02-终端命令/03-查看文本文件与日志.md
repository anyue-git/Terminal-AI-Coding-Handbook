# 03 查看文本文件与日志

终端里“查看一个文件”并不总是使用同一条命令。几行配置可以一次显示，几万行日志更适合分页浏览，正在增长的训练日志需要持续追踪，图片、压缩包和模型权重则不应按文本输出。本章通过一份练习日志，理解 `file`、`ls`、`wc`、`cat`、`less`、`head`、`tail` 和 `tee` 各自适合什么场景。

建立练习目录并生成一份小日志：

```bash
mkdir -p ~/terminal-practice/log-reading
cd ~/terminal-practice/log-reading
printf '%s\n' \
  '2026-07-29 10:00:00 INFO server started' \
  '2026-07-29 10:00:02 INFO request path=/health status=200' \
  '2026-07-29 10:00:05 WARN cache response slow' \
  '2026-07-29 10:00:08 ERROR database connection failed' \
  '2026-07-29 10:00:10 INFO retry succeeded' \
  > app.log
```

## 1. 打开文件前判断类型和规模

看到文件名时，先别急着 `cat`。运行：

```bash
file app.log
ls -lh app.log
wc -l app.log
```

可能看到：

```text
app.log: ASCII text
-rw-r--r--  1 student staff   287B Jul 29 10:01 app.log
       5 app.log
```

`file` 判断内容类型，`ls -lh` 显示大小，`wc -l` 统计行数。这个简单检查可以避免把压缩包、图片、模型权重或数 GB 日志完整输出到终端。文件不存在时，用 `pwd` 和 `ls -la` 核对位置、拼写、大小写和空格；出现 `Permission denied` 时查看 `ls -l PATH_TO_FILE`，确认自己是否本来就应该读取，不要立刻加 `sudo`。

## 2. 根据阅读目的选择 `cat`、`less`、`head` 或 `tail`

练习日志只有五行，可以直接完整显示：

```bash
cat app.log
```

`cat` 适合 README、短配置和小日志；文件很长时，内容会快速滚过屏幕。多个文件可以按顺序输出，也可以合并到练习文件：

```bash
printf '%s\n' \
  '2026-07-29 10:01:00 INFO shutdown requested' \
  '2026-07-29 10:01:01 INFO server stopped' \
  > shutdown.log
cat app.log shutdown.log > combined.log
wc -l combined.log
```

`>` 会覆盖目标原内容。真实文件已经存在时，查看 `ls -l TARGET` 和 `cat TARGET`，必要时把新结果写到另一文件中比较。

长文件更适合分页器：

```bash
less combined.log
```

进入后，键盘输入由 `less` 处理：Space 下一页，`b` 上一页，`/ERROR` 搜索，`n` 和 `N` 切换匹配，`g` 与 `G` 跳到开头和结尾，`q` 退出。底部出现文件名、百分比或冒号时，终端通常没有卡住，只是进入了分页器。

只想抽样时使用：

```bash
head -n 3 app.log
tail -n 2 app.log
```

配置和 CSV 常从开头取样；训练或服务失败时，结尾更接近最新状态。可以用 `tail -n 100 training.log` 阅读最近一段，再根据内容决定是否搜索整个文件。

## 3. 持续追踪日志，并把运行输出保留下来

在一个终端运行：

```bash
tail -f app.log
```

它会停留在前台等待新内容。另开一个终端，进入同一目录并追加一行：

```bash
cd ~/terminal-practice/log-reading
printf '%s\n' '2026-07-29 10:02:00 INFO background task completed' >> app.log
```

第一个终端会立即显示新行，观察结束后按 `Ctrl + C` 停止追踪。这个按键只停止 `tail -f`，不会自动停止写日志的服务或训练程序。日志长时间没有变化，也不能单独证明程序已经退出；它可能仍在计算、被阻塞、写入另一文件或已经异常结束，需要结合进程和资源状态判断。

`tee` 可以让命令输出同时显示并保存：

```bash
python3 -c 'print("task started"); print("task completed")' \
  2>&1 | tee task.log
```

追加使用 `tee -a`，但多次运行会让日志混在一起。训练任务更适合每次建立独立运行目录和带时间戳的日志。脚本中还要注意管道退出状态：左侧程序失败而 `tee` 成功时，默认状态可能只反映最后一个命令。需要可靠判断时在脚本中启用：

```bash
set -o pipefail
```

## 4. 文本格式和二进制对象不能用同一种方式查看

JSON 可以判断类型并查看几行内容，确认后用 `jq` 格式化：

```bash
printf '%s\n' '{"name":"demo","enabled":true}' > config.json
jq . config.json
```

出现 `command not found: jq` 说明工具尚未安装，不代表 JSON 已损坏。CSV 通常从表头和少量样本开始：

```bash
printf '%s\n' 'name,score' 'Alice,90' 'Bob,85' > scores.csv
head -n 3 scores.csv
```

图片、压缩包、可执行文件和模型权重只检查元数据：

```bash
file PATH_TO_FILE
ls -lh PATH_TO_FILE
```

不要直接 `cat` 二进制文件。误操作导致终端显示乱码时，可以尝试运行 `reset` 恢复显示，但这不会改变文件本身。

`wc` 还能统计单词和字节：

```bash
wc -l app.log
wc -w app.log
wc -c app.log
wc -l < app.log
```

第四种写法只输出数字，不附带文件名。准备让 AI 分析日志时，可以借助这些数据估算规模：几十行适合人工阅读，几十万行则应缩小时间范围、错误级别和上下文。

## 5. 日志可能包含凭证、地址和业务数据

日志中可能出现用户名、本机绝对路径、服务器地址、请求头、Cookie、Token、数据库连接信息和真实数据。发送给外部 AI 或粘贴到 Issue 前，可以做一次明显关键词搜索：

```bash
rg -n 'API_KEY|TOKEN|PASSWORD|Authorization|Cookie' app.log
```

没有结果只表示这些明显词没有出现，不能证明文件没有敏感内容。还要人工检查 URL、邮箱、数据样本、内部错误和路径。更稳妥的做法是只提取与问题有关的小段，用占位符替换真实地址与身份信息。已经泄露的凭证不能靠文本脱敏补救，应立即撤销并轮换。

使用管道把日志交给本地 `rg`、`less` 或 `wc`，数据通常仍停留在本机；右侧若是联网客户端、上传工具或 AI CLI，数据流向就会改变。执行前应明确供应商、Base URL、网关和上传范围。

## 6. 从最新错误逐步定位，而不是上传整份日志

应用出错后，可以沿下面的路径检查：

```bash
cd PROJECT_PATH
pwd
ls -lh logs/
tail -n 100 logs/app.log
rg -n -C 3 'ERROR|Traceback|Exception' logs/app.log
less logs/app.log
```

这组命令依次确认项目与日志位置、文件大小、最新内容和错误上下文；只有需要时才浏览全文。相比把整份日志复制进聊天，它更容易抓住重点，也能控制敏感信息范围。日志只是运行现场的一部分，根因判断还要结合命令、退出状态、进程、配置和代码。
