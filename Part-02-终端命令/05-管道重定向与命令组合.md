# 05 管道、重定向与命令组合

Shell 的一个重要能力，是把多个小工具连接成一条处理链。一个命令负责产生数据，另一个命令负责筛选、统计或保存。理解这种连接方式后，很多看似复杂的操作不需要专门软件，只需要把已有命令按正确的数据流组合起来。

继续使用前两章的练习目录：

```bash
cd ~/terminal-practice/log-reading
pwd
ls -la
```

本章会继续处理 `app.log`，但先不修改真实项目文件。

## 1. 三条标准通道

大多数命令都可以使用三条标准通道：

```text
stdin   标准输入，编号 0
stdout  标准输出，编号 1
stderr  标准错误，编号 2
```

运行：

```bash
cat app.log
```

文件内容通常发送到 stdout，终端负责显示。运行一个不存在的文件：

```bash
cat missing.log
```

报错通常发送到 stderr。两者都显示在同一个终端里，但 Shell 可以分别重定向它们。

理解通道比死记符号更重要。管道和重定向做的事情，本质上只是改变输入与输出流向。

## 2. 管道把左侧输出交给右侧

查看日志中的错误并分页：

```bash
rg 'ERROR|WARN' app.log | less
```

`rg` 的 stdout 不再直接显示，而是成为 `less` 的 stdin。退出分页器按 `q`。

统计日志中包含 `INFO` 的行数：

```bash
rg 'INFO' app.log | wc -l
```

可能输出：

```text
4
```

这里 `rg` 负责筛选，`wc -l` 负责统计。每个工具只做一件事，组合后完成更具体的任务。

列出 Python 文件并统计数量：

```bash
find . -type f -name '*.py' -print | wc -l
```

管道默认只传递 stdout。左侧命令产生的错误通常仍会直接显示在终端，不会自动进入右侧工具。

## 3. `>` 会覆盖目标文件

把错误和警告提取到新文件：

```bash
rg 'ERROR|WARN' app.log > important.log
cat important.log
```

如果 `important.log` 已经存在，`>` 会覆盖原内容，而且通常不会询问。再次执行前先检查：

```bash
ls -l important.log
cat important.log
```

当目标是重要配置、源码或已有日志时，更稳妥的方式是先写到新文件，再比较：

```bash
rg 'ERROR|WARN' app.log > important.new.log
diff important.log important.new.log
```

确认内容后再决定是否替换。每次看到 `>`，都应该先问目标文件是否已经存在。

## 4. `>>` 在文件末尾追加

向练习文件追加一行：

```bash
printf '%s\n' 'manual note: reviewed at 10:30' >> important.log
```

查看结尾：

```bash
tail -n 3 important.log
```

`>>` 不会清空原内容，但反复执行会产生重复行。网上常见的安装说明会让用户把 PATH 或环境变量追加到 `.zshrc`；重复粘贴多次后，配置文件可能出现几份相同内容。

修改真实 Shell 配置前，先备份并检查已有行：

```bash
cp ~/.zshrc ~/.zshrc.backup
rg -n 'PATH|API_KEY|BASE_URL' ~/.zshrc
```

长期配置更适合用编辑器有意识地修改，而不是不断执行追加命令。

## 5. 分别保存正常输出和错误

运行一个同时产生正常输出与错误的 Python 命令：

```bash
python3 -c 'import sys; print("normal output"); print("error output", file=sys.stderr)'
```

只保存正常输出：

```bash
python3 -c 'import sys; print("normal output"); print("error output", file=sys.stderr)' \
  > stdout.log
```

终端仍会显示 `error output`，而 `stdout.log` 只包含正常输出。

只保存错误：

```bash
python3 -c 'import sys; print("normal output"); print("error output", file=sys.stderr)' \
  2> stderr.log
```

全部保存到同一文件：

```bash
python3 -c 'import sys; print("normal output"); print("error output", file=sys.stderr)' \
  > all.log 2>&1
```

`2>&1` 表示让 stderr 指向 stdout 当前所指向的位置。顺序很重要；先重定向 stdout，再合并 stderr，才能把两者都写入 `all.log`。

## 6. `tee` 让输出既显示又保存

运行：

```bash
rg 'ERROR|WARN' app.log | tee filtered.log
```

结果会显示在终端，同时保存到 `filtered.log`。追加使用：

```bash
printf '%s\n' 'extra line' | tee -a filtered.log
```

训练、测试和部署命令常见：

```bash
python3 -m unittest 2>&1 | tee test.log
```

这样既能实时观察，又能保留完整记录。但这里有一个容易忽略的问题：默认情况下，整条管道的退出状态通常来自最后一个命令。即使测试失败，只要 `tee` 成功写文件，Shell 可能把管道视为成功。

在需要可靠退出状态的脚本中启用：

```bash
set -o pipefail
```

然后再运行管道。交互式终端中也可以检查：

```bash
printf '%s\n' "$?"
```

## 7. `&&`、`||` 和 `;` 控制是否继续

前一条成功才执行下一条：

```bash
python3 -m unittest && git status
```

只有测试返回成功状态，才会继续显示 Git 状态。这个组合适合“前一步通过后才能继续”的流程。

前一条失败时执行补救或提示：

```bash
python3 missing.py || printf '%s\n' '程序运行失败，请检查路径。'
```

无论成功失败都继续：

```bash
date; pwd; ls
```

分号只是按顺序执行，不关心前一条是否成功。安装、部署、删除和数据迁移等有依赖关系的步骤，不应使用 `;` 无条件推进。

## 8. 退出状态决定了组合逻辑

运行成功命令并检查状态：

```bash
true
printf '%s\n' "$?"
```

输出通常是：

```text
0
```

运行失败命令：

```bash
false
printf '%s\n' "$?"
```

输出通常是非零值。一般约定 `0` 表示成功，非零表示失败或特殊状态，具体数字由程序定义。

`&&` 与 `||` 正是根据退出状态决定是否执行下一条。看到某个脚本“没有明显报错但后续没执行”时，可以先检查前一条命令的退出状态。

## 9. 命令替换把输出保存到变量

取得当前 Git 分支：

```bash
CURRENT_BRANCH=$(git branch --show-current 2>/dev/null)
printf 'branch=%s\n' "$CURRENT_BRANCH"
```

`$(...)` 会先执行内部命令，再把 stdout 作为变量值。变量使用时通常应放在双引号中，避免空格和通配符被再次解释。

命令替换适合读取分支名、日期和查询结果，但不能把未经检查的输出直接拼入删除、权限或远程操作。先打印变量：

```bash
printf 'TARGET=%s\n' "$TARGET"
```

确认它不为空、指向正确目录，再执行会修改系统的命令。

## 10. 引号决定谁负责解释字符

单引号通常保留原样：

```bash
printf '%s\n' '$HOME'
```

输出：

```text
$HOME
```

双引号允许变量展开：

```bash
printf '%s\n' "$HOME"
```

输出当前用户主目录。

处理路径变量时，使用：

```bash
ls -la "$PROJECT_PATH"
```

不加引号时，路径中的空格、通配符和换行可能被 Shell 拆成多个参数。许多“明明变量是对的，命令却找不到文件”的问题，都来自缺少引号。

## 11. 一条日志处理链怎样逐步构建

目标是把错误和警告提取出来，保留行号，分页查看，并把结果保存到文件。不要一开始就写很长的命令，可以逐步验证。

第一步，确认搜索结果：

```bash
rg -n 'ERROR|WARN' app.log
```

第二步，分页：

```bash
rg -n 'ERROR|WARN' app.log | less
```

第三步，保存并显示：

```bash
rg -n 'ERROR|WARN' app.log | tee review.log
```

第四步，确认输出文件：

```bash
wc -l review.log
cat review.log
```

这种“先验证左边，再逐步增加右边”的方式，比一次写出复杂管道更容易发现错误，也更适合让 AI 生成后进行人工审查。

## 12. 管道中的敏感数据

把日志通过管道传给本地工具，通常仍停留在当前机器；但如果右侧命令是联网客户端、上传程序或 AI CLI，数据可能被发送到外部服务。

发送前先确认：

```bash
rg -n 'TOKEN|PASSWORD|Authorization|Cookie|API_KEY' review.log
```

还要检查用户名、绝对路径、服务器地址、内部代码和业务数据。知道当前模型供应商、Base URL 和网关，是判断数据流向的一部分。

给 AI CLI 的要求可以写成：

```text
先只在本地读取和筛选日志，不要上传完整文件。
说明准备使用的命令及其输入输出范围。
只提取与错误相关的最小片段，并在发送前检查凭证、路径和内部地址。
```

## 13. 最值得记住的组合

```bash
COMMAND | less
COMMAND > new-file
COMMAND 2>&1 | tee output.log
COMMAND_A && COMMAND_B
COMMAND_A || printf '%s\n' 'failed'
```

使用它们时，不要只看符号本身，要沿着数据流问：输入从哪里来，正常输出去了哪里，错误去了哪里，前一步失败后是否还会继续。
