# 05 管道、重定向与命令组合

Shell 可以把多个小工具连接成一条处理链：一个命令产生数据，另一个负责筛选、统计、分页或保存。理解输入、正常输出、错误输出和退出状态的流向后，复杂命令不再只是需要背诵的符号；同时也能看出覆盖文件、掩盖失败和外发敏感数据等风险。

继续使用日志练习目录：

```bash
cd ~/terminal-practice/log-reading
pwd
ls -la
```

## 1. 先理解三条标准通道

大多数命令使用三条标准通道：

```text
stdin   标准输入，编号 0
stdout  标准输出，编号 1
stderr  标准错误，编号 2
```

运行 `cat app.log` 时，文件内容通常进入 stdout，由 Terminal 显示；运行 `cat missing.log` 时，报错通常进入 stderr。两者看起来都出现在同一个窗口，Shell 却可以分别转发和保存。管道与重定向做的事情，就是改变这些通道的去向。

## 2. 管道把左侧 stdout 交给右侧 stdin

筛选错误和警告并分页：

```bash
rg 'ERROR|WARN' app.log | less
```

`rg` 的 stdout 不再直接显示，而是成为 `less` 的 stdin；退出分页器按 `q`。统计 INFO 行数：

```bash
rg 'INFO' app.log | wc -l
```

这里 `rg` 负责筛选，`wc -l` 负责统计。也可以统计 Python 文件：

```bash
find . -type f -name '*.py' -print | wc -l
```

管道默认只传递 stdout，左侧 stderr 通常仍显示在终端。构建长管道时，先单独运行最左侧并检查输出，再逐步增加右侧工具；这样更容易发现搜索范围、格式和参数错误。

## 3. 重定向和 `tee` 决定输出写到哪里

`>` 会创建或覆盖目标文件：

```bash
rg 'ERROR|WARN' app.log > important.log
cat important.log
```

再次执行会覆盖原内容，而且通常不询问。目标重要或已经存在时，先查看它，或者写入新文件后比较：

```bash
rg 'ERROR|WARN' app.log > important.new.log
diff important.log important.new.log
```

`>>` 在末尾追加：

```bash
printf '%s\n' 'manual note: reviewed at 10:30' >> important.log
tail -n 3 important.log
```

追加不会清空旧内容，但反复执行会产生重复行。安装教程让用户不断把 PATH 或环境变量追加到 `.zshrc`，很容易留下多份初始化；长期配置更适合备份后用编辑器修改。

stdout 与 stderr 可以分别保存：

```bash
python3 -c 'import sys; print("normal output"); print("error output", file=sys.stderr)' \
  > stdout.log

python3 -c 'import sys; print("normal output"); print("error output", file=sys.stderr)' \
  2> stderr.log

python3 -c 'import sys; print("normal output"); print("error output", file=sys.stderr)' \
  > all.log 2>&1
```

`2>&1` 表示让 stderr 指向 stdout 当前所指向的位置，顺序会影响结果。

希望边看边保存时使用 `tee`：

```bash
python3 -m unittest 2>&1 | tee test.log
```

默认情况下，整条管道的退出状态通常来自最后一个命令；测试失败而 `tee` 写入成功时，Shell 可能把管道视为成功。需要可靠状态的脚本应启用：

```bash
set -o pipefail
```

## 4. 退出状态控制 `&&`、`||` 和后续步骤

程序通常用 `0` 表示成功，非零表示失败或特殊状态。可以观察：

```bash
true
printf '%s\n' "$?"
false
printf '%s\n' "$?"
```

`&&` 只在左侧成功时继续：

```bash
python3 -m unittest && git status
```

`||` 只在左侧失败时执行右侧：

```bash
python3 missing.py || printf '%s\n' '程序运行失败，请检查路径。'
```

`;` 无论前一步结果如何都会继续：

```bash
date; pwd; ls
```

安装、部署、删除和数据迁移等有依赖关系的步骤，不应使用分号无条件推进。多条命令写在同一行也没有自动回滚或事务保证。

## 5. 命令替换、变量和引号会再次参与解析

命令替换可以把 stdout 保存到变量：

```bash
CURRENT_BRANCH=$(git branch --show-current 2>/dev/null)
printf 'branch=<%s>\n' "$CURRENT_BRANCH"
```

`$(...)` 先执行内部命令，再把输出作为变量值。变量使用时通常放在双引号中，避免空格、通配符和换行被重新拆分。未经检查的命令输出不应直接拼进删除、权限、远程或同步操作；先打印变量并确认不为空、范围正确。

单引号通常保留原样，双引号允许变量展开：

```bash
printf '%s\n' '$HOME'
printf '%s\n' "$HOME"
ls -la "$PROJECT_PATH"
```

很多“变量看起来正确，命令却找不到文件”的问题来自省略引号。特殊字符到底由当前 Shell、内部命令还是后续程序解释，是分析组合命令的关键。

## 6. 一条处理链应当逐步构建和验证

目标是提取日志中的错误与警告，保留行号，同时显示并保存。先确认搜索结果：

```bash
rg -n 'ERROR|WARN' app.log
```

再分页或保存：

```bash
rg -n 'ERROR|WARN' app.log | less
rg -n 'ERROR|WARN' app.log | tee review.log
wc -l review.log
cat review.log
```

这种“先验证左边，再增加右边”的方式，比一次写出复杂管道更容易检查，也更适合审查 AI 生成的命令。若任何一步的输出格式与预期不同，应停在这一层修改，而不是继续叠加处理。

## 7. 管道也可能把数据送到外部服务

日志交给本地 `less`、`rg` 和 `wc` 时，数据通常仍在当前机器；右侧若是上传工具、网络请求或 AI CLI，内容可能被发送到外部服务。发送前至少搜索明显敏感信息：

```bash
rg -n 'TOKEN|PASSWORD|Authorization|Cookie|API_KEY' review.log
```

还要人工检查用户名、绝对路径、服务器地址、内部代码和业务数据，并确认当前模型供应商、Base URL 与网关。给 Agent 的约束可以写成：先只在本地筛选日志，说明命令和输入输出范围，只提取与错误有关的最小片段，在发送前检查凭证、路径和内部地址。

最常用的组合包括：

```bash
COMMAND | less
COMMAND > new-file
COMMAND 2>&1 | tee output.log
COMMAND_A && COMMAND_B
COMMAND_A || printf '%s\n' 'failed'
```

使用它们时沿着数据流检查：输入来自哪里，stdout 和 stderr 去了哪里，前一步失败后是否还会继续，目标文件是否会被覆盖。
