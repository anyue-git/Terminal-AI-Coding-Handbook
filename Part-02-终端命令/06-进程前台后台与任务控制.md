# 06 进程、前台、后台与任务控制

命令按回车后，Shell 通常会启动一个进程。短命令很快结束，开发服务器、训练脚本和 AI CLI 可能持续运行。前台、后台、暂停、脱离当前终端和被 tmux 保持会话是不同状态；分不清这些层次，就容易把“提示符回来了”误判成任务安全运行，或把“tmux 还在”误判成训练仍然健康。

本章使用一个最多运行五分钟、不会修改其他文件的 Python 程序观察完整生命周期：

```bash
mkdir -p ~/terminal-practice/process-control
cd ~/terminal-practice/process-control
cat > worker.py <<'PY'
import time

for index in range(1, 301):
    print(f"tick {index}", flush=True)
    time.sleep(1)
PY
```

需要停止时按 `Ctrl + C`。

## 1. 前台、暂停与当前 Shell 的任务控制

运行：

```bash
python3 worker.py
```

终端会持续显示 `tick 1`、`tick 2`，Shell 提示符暂时消失，因为键盘输入交给了前台 Python 进程。开发服务器、`ping`、`less`、AI CLI 和训练脚本都可能以这种方式运行。

`Ctrl + C` 通常发送中断信号。Python 可能显示 `KeyboardInterrupt` 后退出，这不是系统损坏；有些程序会捕获信号，完成保存或清理后再结束，AI CLI 第一次按下也可能只取消当前生成。

重新启动程序并按 `Ctrl + Z`，Shell 可能显示：

```text
[1]+  Stopped                 python3 worker.py
```

程序此时被暂停，但仍然存在。`jobs` 查看当前 Shell 管理的任务，`fg` 恢复到前台，`bg` 让暂停任务在后台继续；有多个任务时可以写 `fg %1` 或 `bg %1`。`%1` 是当前 Shell 的任务编号，不是操作系统 PID。恢复到前台后按 `Ctrl + C`，可以正常结束练习程序。

## 2. 后台启动后，用任务编号、PID 和日志观察真实状态

从一开始就在后台运行，并把输出写入日志：

```bash
python3 worker.py > worker.log 2>&1 &
```

Shell 会返回提示符，并显示类似 `[1] 48231`；前者是任务编号，后者是 PID。最近后台进程的 PID 可以通过 `$!` 取得：

```bash
printf '%s\n' "$!"
jobs -l
tail -n 5 worker.log
```

`tail -f worker.log` 会持续观察日志，按 `Ctrl + C` 只停止 `tail`，不会停止后台的 `worker.py`。需要重新接管任务可以运行 `fg %1`。

`&` 让 Shell 立即返回，却不保证关闭窗口或 SSH 断开后进程继续。它通常仍与当前终端会话有关，可能收到挂断信号；`python3 train.py &` 因此不能作为可靠远程训练方案。

`jobs` 只显示当前 Shell 启动并管理的任务，换一个终端窗口通常看不到。`ps` 和 `pgrep` 查看操作系统进程，可以跨 Shell 调查：

```bash
python3 worker.py > worker.log 2>&1 &
WORKER_PID=$!
printf 'pid=%s\n' "$WORKER_PID"
ps -p "$WORKER_PID" -o pid,ppid,user,stat,etime,command
pgrep -fl 'python3 worker.py'
```

名称匹配只能生成候选。同一机器可能运行多个 Python 项目，处理进程前要核对 PID、用户、完整命令和运行时间；共享服务器上不能因为名称含 `python` 就批量终止。当前 Shell 自己的 PID 是 `$$`。

```text
jobs / fg / bg
→ 当前 Shell 的任务控制

ps / pgrep / kill
→ 操作系统进程

tmux
→ 可重新连接的终端会话
```

## 3. 结束进程从精确、可清理的信号开始

确认 PID 后运行：

```bash
kill "$WORKER_PID"
ps -p "$WORKER_PID"
```

`kill` 默认通常发送 TERM 信号，给程序清理资源的机会。检查只剩表头或进程不存在，说明任务已经结束。这个命令的作用是发送信号，并不天然等于强制终止。

只有普通结束无效、PID 已反复核对并理解数据风险时，才考虑强制信号。强制结束可能造成文件只写一部分、数据库状态不一致、checkpoint 未保存和临时资源残留，因此不适合作为日常模板。

`pkill` 按名称或模式匹配，范围更大。一个可审查的顺序是：

```bash
pgrep -fl 'worker.py'
ps -p SPECIFIC_PID -o pid,user,etime,command
kill SPECIFIC_PID
```

先列候选，再精确处理一个 PID。AI CLI 不应自动批量终止进程，也不应在共享 GPU 服务器上根据名称猜测哪些任务“已经没用”。

## 4. `nohup`、tmux 和 checkpoint 解决不同层次

简单、完全非交互的命令可以使用：

```bash
nohup python3 worker.py > worker-nohup.log 2>&1 &
printf '%s\n' "$!"
```

`nohup` 让程序忽略常见挂断信号，却没有可重新进入的终端界面。需要交互、调试或持续观察时，tmux 更直观：

```bash
tmux new -s train
```

会话中启动任务后，按 `Ctrl + b`，松开再按小写 `d` 脱离；恢复使用：

```bash
tmux attach -t train
tmux ls
```

`nohup` 和 tmux 都无法抵抗关机、进程崩溃、磁盘写满或 GPU OOM。远程长任务还要有正式日志、定期 checkpoint、数据一致性和可重复启动参数。systemd 适合长期服务，容器后台模式适合受容器生命周期管理的任务，Slurm 等调度器适合多人 GPU 集群；它们不能用同一个“放后台”概念替代。

## 5. Agent 启动长任务时必须交付可观察现场

给 AI CLI 的任务约束可以写成：

```text
不要把长期任务静默放到后台。
启动前说明工作目录、完整命令、日志路径、预计资源和安全停止方式。
启动后报告 PID 或 tmux 会话名，并验证进程和日志确实存在。
未经确认不要使用批量终止、强制终止或结束其他 GPU 进程。
```

“启动成功”只表示某条命令被执行。人工仍要检查进程是否存在、日志是否增长、GPU 是否被正确使用、输出与 checkpoint 写到哪里，以及 SSH 断开后怎样恢复。

完成一轮后台任务练习：

```bash
cd ~/terminal-practice/process-control
python3 worker.py > final-run.log 2>&1 &
PID=$!
printf 'pid=%s\n' "$PID"
ps -p "$PID" -o pid,user,etime,command
tail -n 3 final-run.log
kill "$PID"
ps -p "$PID"
```

这组命令依次完成后台启动、记录 PID、观察进程、查看日志、请求正常结束和验证结果。真实训练沿用同一思路，再加入 tmux、GPU 状态、磁盘空间和 checkpoint。
