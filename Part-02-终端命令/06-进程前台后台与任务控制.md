# 06 进程、前台、后台与任务控制

命令按回车后，Shell 通常会启动一个进程。短命令很快结束，开发服务器、训练脚本和 AI CLI 则可能持续运行。新手最容易混淆的是：程序在前台、程序进入后台、程序被暂停，以及程序已经脱离当前终端。这四种状态不是同一回事。

本章使用一个安全的 Python 示例观察进程状态。先建立练习目录：

```bash
mkdir -p ~/terminal-practice/process-control
cd ~/terminal-practice/process-control
```

创建一个每秒打印一次的程序：

```bash
cat > worker.py <<'PY'
import time

for index in range(1, 301):
    print(f"tick {index}", flush=True)
    time.sleep(1)
PY
```

它最多运行五分钟，不修改其他文件。需要停止时按 `Ctrl + C`。

## 1. 前台进程会占用当前终端

运行：

```bash
python3 worker.py
```

终端会持续显示：

```text
tick 1
tick 2
tick 3
```

此时键盘输入先交给 Python 程序，Shell 提示符暂时不会出现。这就是前台进程。开发服务器、`ping`、`less`、Claude Code、Codex CLI 和训练脚本都可能以这种方式运行。

按 `Ctrl + C` 后，程序通常收到中断信号并退出。你可能看到：

```text
^CTraceback (most recent call last):
...
KeyboardInterrupt
```

这表示程序响应了中断，并不等于系统损坏。部分程序会捕获信号，先保存状态或清理资源后再退出；AI CLI 中第一次 `Ctrl + C` 也可能只停止当前生成，而不是退出整个客户端。

## 2. `Ctrl + Z` 是暂停，不是结束

重新启动：

```bash
python3 worker.py
```

运行几秒后按 `Ctrl + Z`。Shell 可能显示：

```text
[1]+  Stopped                 python3 worker.py
```

程序此时没有继续打印，但仍然存在。查看当前 Shell 管理的任务：

```bash
jobs
```

可能看到：

```text
[1]+  stopped  python3 worker.py
```

恢复到前台：

```bash
fg
```

程序会继续输出。再按 `Ctrl + C` 正常结束。

如果希望暂停的任务在后台继续：

```bash
bg
```

指定任务编号时可以写：

```bash
fg %1
bg %1
```

任务编号只在当前 Shell 的 job control 中有意义，不等于操作系统 PID。

## 3. 使用 `&` 从一开始就在后台运行

运行：

```bash
python3 worker.py > worker.log 2>&1 &
```

Shell 会立即返回提示符，并显示类似：

```text
[1] 48231
```

`[1]` 是任务编号，`48231` 是进程 ID，也就是 PID。查看最近启动的后台进程 PID：

```bash
printf '%s\n' "$!"
```

观察日志：

```bash
tail -n 5 worker.log
```

或者持续追踪：

```bash
tail -f worker.log
```

停止 `tail -f` 按 `Ctrl + C`，这只会停止日志查看，不会停止后台的 `worker.py`。

查看 Shell 任务：

```bash
jobs -l
```

把后台任务带回前台：

```bash
fg %1
```

再按 `Ctrl + C` 结束。

## 4. 后台运行不等于能抵抗终端关闭

命令末尾加 `&` 只是让 Shell 立即返回提示符。进程通常仍然属于当前终端会话。关闭窗口、退出 Shell 或断开 SSH 后，它可能收到挂断信号并终止。

因此：

```bash
python3 train.py &
```

不能保证网络断开后训练继续。远程长任务更适合使用 tmux、systemd、容器后台模式或集群作业调度器。个人 Ubuntu 游戏本上，tmux 通常是最容易观察和重新进入的选择。

## 5. 查找一个正在运行的进程

再次在后台启动练习程序：

```bash
python3 worker.py > worker.log 2>&1 &
WORKER_PID=$!
printf 'pid=%s\n' "$WORKER_PID"
```

使用 PID 查看：

```bash
ps -p "$WORKER_PID" -o pid,ppid,user,stat,etime,command
```

可能看到：

```text
  PID  PPID USER   STAT ELAPSED COMMAND
48231 47000 student S      00:08 python3 worker.py
```

按名称查找：

```bash
pgrep -fl 'python3 worker.py'
```

名称匹配只能作为线索。同一台机器可能运行多个 Python 项目，结束进程前必须核对 PID、用户、完整命令和运行目录。共享服务器上尤其不能只看到“python”就批量终止。

查看当前 Shell 自己的 PID：

```bash
printf '%s\n' "$$"
```

`ps aux` 会显示系统上大量进程，适合调查，但不适合在没有筛选的情况下直接决定终止目标。

## 6. `kill` 默认是请求正常结束

确认刚才保存的 PID 后，运行：

```bash
kill "$WORKER_PID"
```

`kill` 默认通常发送 TERM 信号，给程序机会清理资源。等待片刻并检查：

```bash
ps -p "$WORKER_PID"
```

如果只显示表头或提示不存在，说明进程已经结束。

`kill` 的名字容易让人以为它一定是强制终止，实际上它是“向进程发送信号”的工具。默认 TERM 比强制信号更适合作为第一步。

只有普通结束无效、PID 已经反复核对，并且理解数据风险时，才会考虑强制终止。强制结束可能导致文件只写了一部分、数据库状态不一致、checkpoint 没有保存和临时资源残留。本书不把强制终止作为日常模板。

## 7. 为什么 `pkill` 风险更大

`pkill` 会按名称或模式匹配进程。如果一台机器上同时运行多个 Python 任务，粗略匹配可能影响无关项目甚至其他用户。

更稳妥的顺序是：

```bash
pgrep -fl 'worker.py'
ps -p SPECIFIC_PID -o pid,user,etime,command
kill SPECIFIC_PID
```

先列出候选，再精确处理一个 PID。AI CLI 不应自动执行批量进程终止，也不应在共享 GPU 服务器上根据模型猜测哪些任务“应该没用了”。

## 8. `nohup` 能做什么

`nohup` 可以让程序忽略常见的挂断信号：

```bash
nohup python3 worker.py > worker-nohup.log 2>&1 &
printf '%s\n' "$!"
```

随后可以查看：

```bash
tail -f worker-nohup.log
```

它适合简单非交互任务，但没有一个可以重新进入的终端界面。程序需要输入、调试或频繁观察时，tmux 更直观。

`nohup` 也不能防止电脑关机、进程崩溃、磁盘写满或 GPU OOM。真正的训练恢复依赖日志、定期 checkpoint 和可重复的启动参数。

## 9. tmux 解决的是会话断开问题

在 Ubuntu 上创建会话：

```bash
tmux new -s train
```

进入后启动训练。需要暂时离开时，按 tmux 前缀 `Ctrl + b`，松开后按小写 `d`。这会 detach 会话，而不是停止任务。

重新进入：

```bash
tmux attach -t train
```

列出会话：

```bash
tmux ls
```

如果 SSH 断开，tmux 和其中进程仍在 Ubuntu 上。但系统关机、断电或程序自身崩溃时，tmux 无法提供恢复能力。

## 10. 当前 Shell 的任务与系统进程要分开理解

`jobs` 只显示当前 Shell 启动并管理的任务。换一个终端窗口运行 `jobs`，通常看不到第一个窗口的后台任务。`ps` 和 `pgrep` 查看的是操作系统进程，因此能跨 Shell 观察。

可以这样区分：

```text
jobs / fg / bg
→ 当前 Shell 的任务控制

ps / pgrep / kill
→ 操作系统进程

tmux
→ 可重新连接的终端会话
```

知道自己正在处理哪一层，才能避免“任务明明还在，但 jobs 看不到”或“关闭 tail 后以为训练也停了”的误判。

## 11. AI CLI 启动长任务时应要求它报告什么

可以使用下面的约束：

```text
不要把长期任务静默放到后台。
启动前说明工作目录、完整命令、日志路径、预计资源和安全停止方式。
启动后报告 PID 或 tmux 会话名，并验证进程和日志确实存在。
未经确认不要使用批量终止、强制终止或结束其他 GPU 进程。
```

Agent 启动成功不等于任务健康。人工仍要检查日志是否增长、进程是否存在、GPU 是否被正确使用，以及输出和 checkpoint 写到哪里。

## 12. 一次完整练习

在练习目录中按顺序完成：

```bash
cd ~/terminal-practice/process-control
python3 worker.py > final-run.log 2>&1 &
PID=$!
printf 'pid=%s\n' "$PID"
ps -p "$PID" -o pid,user,etime,command
tail -n 3 final-run.log
kill "$PID"
ps -p "$PID"
```

这套练习经历了启动后台任务、记录 PID、观察进程、查看日志、请求正常结束和验证结果。真实训练任务的基本管理也遵循同样思路，只是还要加入 tmux、GPU 状态、磁盘空间和 checkpoint。
