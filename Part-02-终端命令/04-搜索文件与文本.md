# 04 搜索文件与文本

终端中的“搜索”有两个不同问题：文件在哪里，以及某段文字出现在哪些文件中。前者通常使用 `find`，后者可以使用 `grep` 或 `rg`。把这两类问题混在一起，常见结果是命令很长，却仍然找不到真正需要的内容。

继续使用上一章的练习目录，并补充几个文件：

```bash
cd ~/terminal-practice/log-reading
mkdir -p src tests archive
printf '%s\n' \
  'def connect_database():' \
  '    return "connected"' \
  > src/database.py
printf '%s\n' \
  'def test_connect_database():' \
  '    assert True' \
  > tests/test_database.py
cp app.log archive/app-2026-07-29.log
```

查看当前结构：

```bash
find . -print
```

这个目录现在同时包含源码、测试和日志，适合练习“按文件属性找目标”和“按内容定位实现”。

## 1. 使用 `find` 按名称和类型找文件

查找所有 Python 文件：

```bash
find . -type f -name '*.py'
```

可能看到：

```text
./src/database.py
./tests/test_database.py
```

`.` 表示从当前目录开始，`-type f` 只保留普通文件，`-name '*.py'` 按名称匹配。星号放在单引号中，是为了让 `find` 接收这个模式，而不是先被当前 Shell 展开。

只找目录：

```bash
find . -type d -name 'archive'
```

忽略大小写查找 README 一类文件：

```bash
find . -type f -iname '*readme*'
```

需要先快速观察时，可以从更小的目录开始搜索：

```bash
find . -type f -print
```

macOS 自带的是 BSD 工具，Ubuntu 常见的是 GNU 工具，部分扩展参数并不完全相同。教程中的命令报“unknown primary”或“不支持的选项”时，应先查看本机帮助：

```bash
man find
```

不要因为一个参数不兼容，就把整套命令反复交给 AI 猜测修改。

## 2. 搜索结果先作为清单，不要直接接修改操作

找出所有日志：

```bash
find . -type f -name '*.log' -print
```

可能得到：

```text
./app.log
./shutdown.log
./combined.log
./task.log
./archive/app-2026-07-29.log
```

这份结果只是候选清单。真正处理前还要确认数量、大小和目录：

```bash
find . -type f -name '*.log' -print | wc -l
find . -type f -name '*.log' -exec ls -lh {} \;
```

不要把尚未检查的 `find` 结果直接连接到删除、移动、上传或权限修改。搜索范围一旦写错，自动操作会把错误迅速放大。尤其不要把项目根目录、主目录或远程服务器上的搜索结果当作天然安全的目标列表。

## 3. `grep` 适合搜索明确文件

在应用日志中搜索错误：

```bash
grep 'ERROR' app.log
```

显示行号：

```bash
grep -n 'ERROR' app.log
```

输出类似：

```text
4:2026-07-29 10:00:08 ERROR database connection failed
```

忽略大小写：

```bash
grep -ni 'error' app.log
```

错误行本身经常不够。显示前后两行：

```bash
grep -n -C 2 'ERROR' app.log
```

`-C 2` 会同时显示匹配行附近的上下文。排查日志时，通常比只截取一行更容易判断错误前后发生了什么。

递归搜索整个练习目录：

```bash
grep -Rni 'database' .
```

它会搜索源码、测试和日志。目录中存在虚拟环境、依赖或大型生成文件时，普通递归搜索可能很慢，因此代码项目通常更适合使用 `rg`。

## 4. `rg` 更适合代码仓库

ripgrep 的命令是 `rg`。搜索当前目录中的文字：

```bash
rg -n 'database'
```

可能看到：

```text
src/database.py:1:def connect_database():
tests/test_database.py:1:def test_connect_database():
app.log:4:2026-07-29 10:00:08 ERROR database connection failed
```

结果同时给出文件路径、行号和内容。指定目录可以缩小范围：

```bash
rg -n 'database' src/ tests/
```

只搜索 Python 文件：

```bash
rg -n -t py 'database'
```

列出 `rg` 默认会搜索的文件：

```bash
rg --files
```

`rg` 通常尊重 `.gitignore`，会跳过依赖、缓存和构建目录，因此在代码仓库中速度很快。但这也意味着“没有结果”不一定表示所有磁盘文件中都不存在。需要检查隐藏文件时，可以明确使用：

```bash
rg --hidden -n 'TOKEN'
```

隐藏文件可能包含凭证、认证缓存和本地配置。搜索结果不要直接粘贴到聊天、Issue 或公开日志中。

## 5. 普通字符串与正则表达式

`grep` 和 `rg` 默认会把部分符号作为正则表达式解释。例如点号 `.` 表示任意字符，而不是普通的句点。搜索字面内容 `torch.cuda` 时，可以转义点号：

```bash
rg -n 'torch\.cuda'
```

只想按普通文本匹配时，ripgrep 可以使用固定字符串模式：

```bash
rg -n -F 'torch.cuda'
```

日志中搜索多个关键词可以写成：

```bash
rg -n 'ERROR|WARN|Traceback|Exception' app.log
```

复杂正则表达式容易出现“看起来合理但匹配范围错误”的问题。用于删除、替换或权限修改前，应先在少量文件中只读验证结果。

## 6. 文件名含空格时为什么会出问题

建立一个带空格的文件：

```bash
printf '%s\n' 'TODO: review this note' > 'review notes.txt'
```

下面这种循环并不可靠：

```bash
for file in $(find . -name '*.txt'); do
  printf '%s\n' "$file"
done
```

命令替换的结果会按空白再次拆分，所以 `review notes.txt` 可能被当成两个路径。只想搜索文本时，直接使用：

```bash
rg -n 'TODO' --glob '*.txt'
```

确实需要把 `find` 结果传给其他程序时，可以使用空字符分隔：

```bash
find . -type f -name '*.txt' -print0 \
  | xargs -0 grep -n 'TODO'
```

这比依赖换行或空格分隔更能正确处理特殊文件名。

## 7. 从错误日志定位代码的完整过程

假设日志中出现：

```text
ERROR database connection failed
```

可以先查看上下文：

```bash
rg -n -C 2 'database connection failed' app.log
```

再查项目里哪些代码与数据库连接有关：

```bash
rg -n 'connect_database|database connection' src/ tests/
```

查看匹配文件：

```bash
sed -n '1,120p' src/database.py
sed -n '1,120p' tests/test_database.py
```

这条路径完成了从运行时现象到源码和测试的定位。搜索结果只是调查线索，不能单凭关键词相同就断定某个函数一定是根因。接下来还要阅读调用关系、配置来源和测试。

## 8. 提交前搜索明显的敏感信息

在 Git 项目中，可以做一轮基础检查：

```bash
rg -n --hidden \
  'API_KEY|SECRET|TOKEN|PASSWORD|Authorization|Cookie'
```

这只能发现带有明显关键词的文本，不能代替专业 Secret Scanner、Git 历史检查和人工审查。随机字符串、私钥、云配置和认证 JSON 可能完全不包含这些词。

发现真实凭据时，应立即停止提交和分享。若凭据已经上传到远程仓库或发到群组，只从文件中删掉不够，还必须到服务端撤销并轮换。

## 9. 让 AI CLI 执行只读搜索

可以明确要求：

```text
当前阶段只读，不要修改文件。
请从日志中的错误信息出发，使用 rg、find 或项目索引定位相关源码和测试。
每个结论给出文件路径和行号，并区分已经确认的事实与推测。
不要读取 .env、认证缓存、SSH 私钥、云凭据或项目外目录。
```

这种任务适合交给 Agent，因为它能快速跨文件整理线索。但必须保留路径和证据，否则一段听起来完整的解释可能只是模型根据错误文字做出的猜测。

## 10. 工具选择可以这样判断

当问题是“某种文件放在哪里”时，使用 `find`；当问题是“一个明确文件中有没有某段文字”时，使用 `grep`；当问题是“代码仓库中这个函数、配置或错误在哪里出现”时，优先使用 `rg`。

常用组合：

```bash
find . -type f -name '*.py'
grep -n -C 2 'ERROR' app.log
rg -n -t py 'connect_database'
rg --files
```
